#  9장 S3 와 유사한 객체 저장소

## 저장소는 세 종류
| | 블록 저장소 | 파일 저장소 | 객체 저장소 |
| --- | --- | --- | --- |
| 아는 것 | 번호 붙은 칸 | 폴더, 파일 경로 | 버킷 + 키 |
| 접근 | 서버에 디스크로 연결 | 네트워크 파일 공유 | HTTP (PUT/GET) |
| 일부 수정 | 됨 | 됨 | 안 됨 |
| 비용 / 성능 | 비쌈 / 빠름 | 중간 | 쌈 / 느림 |
| 잘 맞는 것 | DB, 가상 머신 | 팀 공유 파일 | 사진, 영상, 백업 |


## 무엇을 얼마나 저장해야 하는가
- 버킷 만들기, 객체 올리기 내려받기, 버전 관리, 버킷 안 목록 보기
- KB부터 GB 까지 섞여있음
- 1년에 100PB 증가, 내구성 99.9999%, 가용성 99.99%, 비용 최소

## 객체 저장소에는 어떤 성질이 있는가?
- 한 번 저장하면 고치지 않음
- 키: URI, 값: 데이터
- 작은 객체와 큰 객체를 지원한다

## 메타 데이터와 데이터
유닉스의 파일 시스템과 같은 구조임
- 메타데이터 저장소: 버킷과 키를 객체 ID 로 저장함
- 데이터 저장소: ID 로 실제 데이터를 저장함

## 어떻게 올리고 내려받는가
- API 서비스: IAM, 메타, 데이터 저장소를 차례로 부름
- IAM: 권한이 있는지 확인함
- 데이터 저장소: 데이터를 객체 ID로 저장함
- 메타데이터 저장소: 객체의 ID 를 저장함
- 올리기: 권한을 확인함 -> 데이터 저장소에 바이트를 저장하고 ID를 받음 -> 메타데이터에 기록
- 내려받기: 권한을 확인함 -> 메타데이터에서 객체 ID 찾기 -> 데이터 저장소에서 바이트 찾아오기

## 데이터 저장소 안은 어떻게 생겼는가?
- 데이터 라우팅 서비스: 데이터를 각 노드로 보냄
- 배치 서비스: 노드의 위치를 가상 클러스터 지도로 관리함
- 데이터 노드: 실제 디스크가 달린 저장 서버


저장할 때: 라우팅이 UUID를 만들고, 배치 서비스에 주 노드를 물어봄 -> 주 노드에 데이터를 저장하고 부노드에 복제함 -> UUID 를 반환함

언제 완료라고 대답할까?
- 다 복제될 때까지 기다림: 안전하지만 느림
- 주 노드만 저장하고 답함: 빠르지만 고장 가능성이 있음

## 작은 파일이 많으면?
작은 객체를 파일 하나씩 저장하면 inode 가 낭비됨

해결: 작은 객체들을 큰 파일 하나에 이어 붙임. 몇 기가가 차게 되면 읽기 전용으로 변경하고 새 파일을 연다.

## 디스크가 고장 나면 어떡해?
복제본은 다른 장애 도메인에 두는 것을 원칙으로 함

소거 코드 8 + 4
- 데이터를 8조각으로 나누고 4조각을 복구용으로 둠
- 12조각 중 4개까지는 잃어도 다시 복구할 수 있음


3벌로 복제와의 비교
| | 3벌 복제 | 소거 코드 8+4 |
| --- | --- | --- |
| 추가 공간 | 200% | 50% |
| 내구성 | 9가 6개 | 9가 11개 |
| 속도 | 빠름 | 계산이 필요해서 느림 |

## 메타 데이터는 어떻게 저장하고 나눠?

객체를 저장할 때 버킷이름, 객체 이름, 객체 아이디가 저장되고 이는 주소록 처럼 사용됨 (줄이 6.8억개!!)

6.8억개의 줄을 하나의 디비에 저장하면 사진 올리기 내려받기 요청이 한 디비에 몰리기 때문에 디비를 나누어서 저장해야 함 (샤딩)

**규칙1. 버킷 이름으로 나누기**

- hyeona-photos 는 전부 DB0, bohum-photos 는 전부 DB1
- 디비 한 대에 또 요청이 몰리는 문제가 발생할 수 있음

**규칙2. 객체 ID로 나누기**

- a1b2는 DB0, c3d4는 DB1
- 세 대에 모두 물어봐야 하는 상황 발생

**규칙3. 버킷 이름 + 객체 이름으로 계산해서 나누기** (이 책에서 선택한 방법임)

- 해시 (이름을 숫자로 바꾸는 계산)를 하고 DB 개수로 나눈 나머지를 씀
- hash("hyeona-photos/2026/11/cat.jpg") = 7  →  7 % 3 = 1  →  DB1
- hash("hyeona-photos/2026/11/dog.jpg") = 9  →  9 % 3 = 0  →  DB0
- hash("hyeona-photos/backup/notes.zip") = 5 →  5 % 3 = 2  →  DB2


근데 규칙 3번을 쓰면 hyeona-photos 의 사진이 디비에 흩어져 있다. 그러면 목록을 보기가 힘듦 -> 3대에 모두 물어보고 합치는 과정을 거쳐야 함

해결:비졍규화 -> 목록 보기용 전용 표를 하나 두고 이 표에는 버킷 이름으로 나눈다.

## 같은 이름으로 다시 올리면?
버전 관리를 켜면 새 줄을 추가하게 됨.
삭제도 실제로 지우지 않기때문에 이전 버전으로 되돌릴 수 있다.

## 큰 파일을 올리다가 끊기면?
멀티 파트 업로드: 시작 -> uploadID 받음 -> 여러 조각으로 나눠서 올리고 ETag 받음 -> 완료 요청 -> 저장소에서 전체로 합침

끊기면 끊긴 조각만 다시 올리면 됨

## 지운 데이터는?
삭제 표시만 된 객체, 완료가 되지 않은 고아 데이터, 체크섬이 틀린 데이터 등을 압축해서 삭제함
