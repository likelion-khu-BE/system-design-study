# 9장 S3와 유사한 객체 저장소 학습노트 - 장찬욱

## 저장소는 왜 세 종류로 나뉘나

객체 저장소는 파일을 "변경할 수 없는 바이트 덩어리(데이터)"와 "이름·위치 정보(메타데이터)"로 나눠서, 둘을 각자에게 맞는 방식으로 확장하는 시스템이다. 이 장 전체가 이 분리 하나에서 출발하는 것 같다.

들어가기 전에, 저장소는 왜 블록, 파일, 객체 이렇게 나뉘까? 찾아보니 사용자가 무엇을 주소로 쓰느냐, 그리고 데이터를 얼마나 자유롭게 고칠 수 있게 해주느냐로 나뉜다고 한다. 많이 허용할수록 키우기 어려워진다.

저장소 유형별 비교(by AI)

| 구분 | 주소 단위 | 수정 | 장점 | 단점 | 대표 예 |
| --- | --- | --- | --- | --- | --- |
| 블록 | 번호 붙은 칸 (블록 번호) | 아무 칸이나 덮어쓰기 | 빠름. DB가 씀 | 칸의 의미는 쓰는 쪽이 관리. 보통 컴퓨터 한 대만 붙임 | 디스크, EBS |
| 파일 | 폴더 경로 `/a/b/c.txt` | 파일 중간도 수정 | 사람이 쓰기 편하고 여럿이 공유 | 동시 수정을 맞출 게 많고, 폴더 트리를 하나로 유지해야 해서 수십억 개가 되면 감당 불가 | NFS, EFS |
| 객체 | 평평한 키 `bucket/key` | 불가 (통째로 교체) | 맞출 게 없어서 서버를 계속 늘려도 됨 | 1GB 파일의 글자 하나만 바꿔도 1GB를 다시 올려야 함 | S3 |

결국 "자유롭게 고치기"와 "끝없이 키우기"를 둘 다 가질 수는 없는 것이다. 자주 고치면 블록, 여럿이 파일처럼 쓰면 파일, 엄청 많이 저장하고 거의 안 고치면 객체. 그리고 셋이 경쟁 관계인 줄 알았는데 실제로는 층층이 쌓여 있었다. 객체 저장소의 데이터 노드도 결국 로컬 파일 시스템 위에 큰 파일을 쓰고, 그 파일 시스템은 블록 장치 위에 있다.

객체 저장소 용어

- 버킷: 객체를 담는 논리적 통. 이름이 전 세계에서 유일하다.
- 객체: 페이로드(바이트) + 메타데이터(이름, 크기, 버전 등).
- URI `s3://bucket/path/to/obj`에서 `/`는 키 문자열의 일부일 뿐, 진짜 디렉터리가 아니다.

## 1단계 문제 이해 및 설계 범위 확정 (타겟 설정)

S3 같은 서비스를 만든다. 버킷을 만들고, 객체를 올리고 내려받고, 버전을 보관하고, 버킷 안의 목록을 볼 수 있어야 한다. 이 외에도 저장 규모, 내구성, 비용 같은 걸 알아야 설계를 시작할 수 있다.

Q&A

어떤 기능을 지원해야?

버킷 생성, 객체 업로드/다운로드, 버저닝, 버킷 내 객체 목록 출력.

객체 크기는?

KB 단위부터 GB 단위까지. 큰 객체와 작은 객체 모두 효율적으로 저장해야. <- 작은 객체를 하나씩 파일로 저장하면 공간 낭비가 생기므로 추가 설계 필요

매년 저장할 데이터 양은?

100PB.

데이터 내구성과 서비스 가용성은?

내구성 99.9999%(6 nines), 가용성 99.99%. <- 디스크는 언젠가 고장 나므로 복제 등 추가 설계 필요

내구성은 "데이터를 안 잃는 것", 가용성은 "서비스가 안 멈추는 것"이다. 비슷해 보이지만 다른 개념이니 헷갈리지 말자.

저장 비용 효율도 중요한가?

YES. 신뢰성과 성능은 유지하면서 저장 비용을 낮춰야. <- 내구성을 올리려면 사본을 늘려야 할 텐데, 비용과 부딪히는 지점이 나올 것 같다.

개략적 규모 추정

- 객체 크기 분포: 소형 20%(중앙값 0.5MB), 중형 60%(32MB), 대형 20%(200MB)
- 평균 크기 ≈ 0.2×0.5 + 0.6×32 + 0.2×200 ≈ 59.3MB
- 디스크 사용률 40%로 잡으면 100PB × 0.4 ÷ 59.3MB ≈ 약 6.8억 개
- 객체당 메타데이터 1KB면 전체 메타데이터 ≈ 0.68TB

내용은 100PB, 정보는 0.7TB. 10만 배 차이가 난다. 같은 방식으로 저장할 이유는 없어 보인다.

그런데 크기가 다르면 왜 저장 방식을 다르게 해야 할까? 크기에 따라 비싼 일이 다르기 때문이다. 0.7TB는 서버 몇 대에 다 들어가니까 이름 검색, 인덱스, 트랜잭션, 강한 일관성 같은 비싼 DB 기능을 써도 감당이 된다. 목록 조회나 버전 관리를 하려면 실제로 필요하기도 하다. 반면 100PB는 서버가 수천 대 필요한데, 여기에 "모든 쓰기를 서로 맞춘다" 같은 기능을 넣으면 감당이 안 될 것이다. 다행히 필요하지도 않다. 한 번 쓰면 안 바뀌고 번호로 통째로 읽기만 하니까.

다만 책의 분포는 용량 추정용이라 실제와는 다를 수 있다. 실제 워크로드에서는 KB 단위 작은 객체가 개수로는 대다수인 경우가 많아서, 용량보다 메타데이터 QPS가 병목이 될 수 있다고 한다.

## 2단계 개략적 설계안 제시 (뼈대 세우기)

핵심은 데이터와 메타데이터를 나누는 것이다.

- 메타데이터 저장소: "이 버킷의 이 이름 = 번호(UUID) abc123"을 기억. 작고 자주 바뀜.
- 데이터 저장소: "번호 abc123 = 실제 내용"을 기억. 거대하고 한 번 쓰면 안 바뀜.

데이터 저장소는 파일 이름을 모르고 번호만 안다. 그래서 단순한 "UUID → 바이트" 키-값 저장소가 될 수 있다.

번호를 받아서 메타데이터로 쓰는 게 마치 fd 같다고 생각했는데, 더 정확히는 inode 번호에 가깝다. fd는 프로세스가 파일을 열 때 잠깐 받는 핸들이라 닫으면 사라진다. 유닉스 디렉터리는 "이름 → inode 번호"를 기록하고 inode가 실제 데이터 위치를 가리킨다. "이름 → UUID → 내용"은 이 구조를 분산 시스템으로 옮긴 것이다. 책도 유닉스 파일 시스템 비유로 설계를 시작한다.

구성 요소: 로드밸런서 → API 서비스(무상태) → IAM(인증/인가), 메타데이터 저장소, 데이터 저장소.

업로드 흐름

1. `PUT /bucket`: IAM이 권한 확인 후 메타데이터 저장소에 버킷 행 생성.
2. `PUT /bucket/obj`: API 서비스가 페이로드를 데이터 저장소로 보내고 UUID를 받음.
3. 메타데이터 저장소에 `(bucket_id, object_name, object_id)` 기록.

다운로드 흐름

1. 메타데이터 저장소에서 이름으로 UUID 조회.
2. 데이터 저장소에서 UUID로 바이트를 가져옴.

그런데 왜 내용을 먼저 저장할까? UUID부터 받고 저장하면 안 되나?

순서 자체(내용 → UUID → 정보)는 책에 나오지만 이유는 안 나온다. UUID(v4)는 랜덤이라 아무 서버나 혼자 만들 수 있어서, API 서비스가 먼저 만들어도 된다고 한다. 그럼 진짜 문제는 UUID를 누가 만드느냐가 아니라 서로 다른 두 시스템에 쓰기를 두 번 한다는 것이다. 이건 UUID를 먼저 만들어도 그대로 남는다.

| 순서 | 중간에 실패하면 | 사용자가 보는 것 |
| --- | --- | --- |
| 데이터 → 메타데이터 | 아무도 안 가리키는 데이터(고아) | 업로드 실패로 보일 뿐. 고아는 나중에 GC가 청소 |
| 메타데이터 → 데이터 | 없는 데이터를 가리키는 이름 | 목록엔 있는데 받으면 오류 |

결국 메타데이터 쓰기가 커밋 지점이다. 이름이 적히는 순간 객체가 보이기 시작하므로, 그 전에 내용이 완전히 준비돼 있어야 한다. 메타데이터를 먼저 쓰고 싶다면 `상태 = 업로드 중`을 먼저 적고 데이터 저장 후 `완료`로 바꾸면 된다. 그래도 결국 "완료로 바꾸는 쓰기"가 커밋 지점이 된다.

여기서 하나의 원칙을 만났다. 커밋 지점은 마지막에 둔다.

선택의 기로 (2단계)

- **한 저장소에 다 넣기 VS 데이터/메타데이터 분리** → 분리. 크기가 10만 배 차이 나고, 메타데이터는 검색·트랜잭션이 필요한 반면 데이터는 번호로 통째 읽기만 하면 된다. 하나로 합치면 어느 쪽에도 맞지 않는다.
- **데이터 먼저 VS 메타데이터 먼저** → 데이터 먼저. 중간에 실패해도 고아 데이터만 남고 사용자에게는 오류가 안 보인다. 고아는 GC가 치운다. 반대로 하면 목록엔 있는데 받을 수 없는 객체가 생긴다.

## 3단계 상세 설계 (살 붙이기)

데이터 저장소

데이터 저장소는 세 가지로 이뤄진다.

- 데이터 라우팅 서비스(무상태): 요청을 받아 어느 노드로 보낼지 배치 서비스에 묻고 읽기/쓰기 수행.
- 배치 서비스: 가상 클러스터 지도(데이터센터 → 호스트 → 파티션)를 관리. 복제본을 서로 다른 장애 도메인에 배치하고, 하트비트로 노드 생존 판단. 자신이 단일 장애점이 되면 안 되므로 5\~7대를 Paxos/Raft로 묶는다.
- 데이터 노드: 실제 저장. 데몬이 디스크 수, 사용량을 하트비트로 보고.

라우팅은 어떻게 이뤄질까?

책은 "라우팅 서비스가 배치 서비스에 묻는다"까지만 말한다. 그런데 메타데이터에는 UUID만 있으니 위치는 UUID로부터 계산할 수 있어야 할 것이다. 찾아보니 실제 시스템은 두 단계로 찾는다고 한다.

1. UUID → 파티션: `hash(UUID) % N`. 결과는 항상 0\~N−1이라 그대로 파티션 번호가 된다. 값이 되돌아와 서로 다른 UUID가 같은 파티션에 떨어지는 건 의도한 동작이다. 파티션은 객체 여러 개를 담는 묶음이기 때문(객체 7억 개, N=4096이면 파티션당 약 17만 개).
2. 파티션 → 서버 목록: 배치 서비스의 표에서 찾는다.

`%` 연산상 값이 되돌아오는 건 괜찮았다. 진짜 문제는 N이 바뀔 때다. N을 4096에서 4097로 바꾸면 거의 모든 객체의 파티션이 바뀌어버린다. 그래서 N은 처음에 넉넉히 정하고 안 바꾼다. 바뀌는 건 서버 쪽이고, 그 변화는 표가 흡수한다.

그럼 그 표는 뭘 가지고 있고, 서버가 추가되거나 죽으면 뭘 어떻게 고칠까?

파티션마다 맡은 서버 목록(첫 번째가 주 서버)과 표 전체의 버전 번호를 가진다.

```
버전 41
파티션 0    → [A, B, C]
파티션 1    → [B, D, E]
파티션 2    → [C, A, F]
```

- 서버 G 추가: 일이 많은 서버의 파티션 몇 개를 G로 넘기기로 정하고, 데이터를 복사한 뒤 표를 고침(`[B, D, E]` → `[B, D, G]`), 버전 42로.
- 서버 A 사망: 하트비트가 일정 시간 안 오면 죽었다고 판정. A가 부 서버인 줄은 새 서버로 바꾸고 살아있는 복사본에서 복사, 주 서버인 줄은 부 서버를 주로 승격(`[A, B, C]` → `[B, C, G]`). 버전을 올린다.

객체의 파티션 번호는 절대 안 바뀌고 "파티션 → 서버" 줄만 바뀐다. 수억 개 객체 위치를 다시 계산할 필요가 없는 것이다.

객체 위치 조회

UUID로 "어느 파일의 몇 번째 바이트인지" 찾기 위해 각 데이터 노드에 표를 둔다.

```
object_mapping(object_id, file_name, start_offset, object_size)
```

저장 엔진으로 RocksDB(LSM, 쓰기 최적화)와 B+트리 관계형 DB(읽기 최적화)를 비교하는데, 한 번 쓰고 여러 번 읽는 워크로드라 책은 노드 로컬 관계형 DB(SQLite류)를 고른다. 매핑은 노드마다 독립적이라 공유할 필요도 없다.&#32;

선택의 기로 (데이터 저장소)

- **파티션 수 가변 VS 고정 + 파티션→서버 표** → 고정 + 표. N이 바뀌면 거의 모든 객체가 옮겨지지만, 표를 두면 서버가 늘거나 죽어도 줄 몇 개만 고치면 된다.

## 데이터 내구성

복제 3개

디스크 연간 고장률을 약 0.81%로 잡으면 세 개가 독립적으로 모두 고장 날 확률은 0.0081³ ≈ 5.3×10⁻⁷. 내구성 ≈ 99.99995%로 나온다. 단 "독립적"일 때만 맞다. 같은 랙에 있으면 랙 전원 하나에 세 개가 동시에 날아가므로 복제본을 서로 다른 장애 도메인(랙, AZ)에 둔다. 더 파보면, 실제 내구성은 "복구가 끝나기 전에 나머지가 고장 날 확률"이라 복구 시간(MTTR)과 같은 시기 생산 디스크의 상관 고장까지 봐야 한다.

소거 코드(Erasure Coding)

소거 코드는 흥미로웠다. 8+4 구성은 데이터를 8조각으로 나누고 복구용 4조각을 더 만들어 12조각을 서버 12대에 나눠 저장하는 것이다. 8MB 객체면 1MB씩 8조각(D1\~D8) + 계산한 1MB짜리 4조각(P1\~P4). 12대 중 아무 8대만 살아있으면 원래 8MB를 되찾는다.

3중 복제 vs 소거 코드(by AI)

|  | 3중 복제 | EC 8+4 |
| --- | --- | --- |
| 8MB 저장 공간 | 24MB (3배) | 12MB (1.5배) |
| 견디는 고장 | 2대 | 4대 |
| 내구성 | 약 6 nines | 약 11 nines |
| 읽을 때 | 서버 1대 | 서버 8대에서 모음 |
| 비용 | 저장 공간 | CPU, 지연, 복구 트래픽 |

그럼 실제로 쓰는 복원 알고리즘은 뭘까? 리드-솔로몬(Reed-Solomon)이라고 한다. 원리는 "점 2개면 직선이 하나로 정해진다"는 것이다.

가장 단순한 버전은 XOR(RAID 5)이다. P = A ⊕ B를 저장해두면 A를 잃었을 때 B ⊕ P = A. XOR은 무슨 특성이 있길래 이게 될까? 자기 자신이 역원인 덧셈이라서다(a ⊕ a = 0, a ⊕ 0 = a). 빼기가 곧 더하기라 어느 걸 잃어도 나머지를 XOR하면 복원된다. 다만 1개까지만.

리드-솔로몬은 이걸 다항식으로 늘린 것이다. 데이터 a=3, b=2로 직선 f(x) = 3 + 2x를 만들고 f(1)=5, f(2)=7, f(3)=9, f(4)=11을 저장한다. f(2)=7, f(4)=11만 남아도 a + 2b = 7, a + 4b = 11을 풀면(빼면 2b = 4, b = 2, a = 3) 원래 데이터가 나온다. 결국 연립방정식이다.

여기서 변수값과 함수값은 데이터에서 뭐에 해당하지?

| 수식 | 데이터에서 | 예시 |
| --- | --- | --- |
| a, b (계수) | 원래 데이터 | 3, 2 |
| x (변수) | 조각 번호 (몇 번 서버인지) | 1\~4 |
| f(x) (함수값) | 그 서버에 실제 저장된 내용 | 5, 7, 9, 11 |

x는 미리 아는 정보이고, 잃어버릴 수 있는 건 f(x)다. 즉 저장할 데이터를 계수로 하는 다항식을 세우고 서버 번호를 넣어 결과값을 뽑아 각 서버에 저장한다. 다항식은 계산에만 쓰고 버린다. 결과값을 저장하는 것이다. 디스크에 3과 2는 없지만 5, 7, 9, 11 중 아무 2개만 있으면 정확히 계산해낼 수 있다.

- 8+4면 데이터 8개 → 7차 다항식, 점 12개 저장, 임의의 점 8개로 복원.
- 다항식은 하나가 아니라 바이트 위치마다 하나씩. 각 조각의 0번째 바이트 8개로 다항식 하나, 1번째 바이트 8개로 또 하나... 1MB면 약 100만 개.
- 실제로는 서버 1\~8에 원본 조각을 그대로 두고 9\~12에만 계산값을 둔다고 한다. 평소에는 원본을 바로 읽고, 계산은 조각을 잃었을 때만. 이 모든 건 S3 서버 내부 이야기고, 다운로드하면 사용자는 원본 파일을 그대로 받는다.

그런데 유한체에서 계산한다는 건 왜 필요할까?

1. 실제 데이터는 1바이트(0\~255)다. a=200, b=100이면 f(4) = 600으로 1바이트에 안 들어간다. 복구용 조각이 데이터보다 커지면 공간 절약이라는 목적이 무너진다.
2. 그럼 256을 넘으면 돌려 감으면(mod 256)? 600 → 88로 들어가긴 하는데, 2b = 4를 풀면 b = 2도, b = 130도 답이 된다. 130 = 2 + 128이고 2 × 128 = 256이라, b에 128을 더하면 2b에 256이 더해져 제자리로 돌아온다. 2를 곱하면 256개 값이 128개 결과로 둘씩 겹치는 것. 답이 두 개면 복원 불가다.
3. 크기가 소수인 시계(mod 7)는 괜찮다. 3 × b에 b = 0\~6을 넣으면 0, 3, 6, 2, 5, 1, 4로 겹치지 않고, 3b = 5의 답은 b = 4 하나다.
4. 256은 소수가 아니니 곱셈 규칙 자체를 다르게 정의한다. 덧셈은 XOR, 곱셈은 특수한 규칙으로. 이게 GF(2⁸)이라고 한다. 곱셈 규칙은 나중에 따로 파봐야겠다.

정리하면 유한체는 "1바이트 안에서 돌면서도 나눗셈이 망가지지 않는 시계" 같은 것이다. 각 조건이 왜 필요한지 정리해보면,

| 조건 | 목적 |
| --- | --- |
| 더하기·곱하기 | 저장할 값을 계산 (인코딩) |
| 빼기·나누기, 답이 하나 | 원래 데이터로 정확히 복원 (디코딩) |
| 결과가 256개 안 | 조각 크기를 1바이트로 유지해 공간 절약 |

체크섬

디스크는 고장이 안 나도 내용이 슬쩍 바뀔 수 있다고 한다(bit rot). 그래서 객체마다, 파일마다 체크섬(MD5 등)을 붙이고, 읽을 때 다시 계산해서 다르면 다른 복제본에서 가져온다. 4장 메시지의 crc 필드와 같은 역할이다.

선택의 기로 (내구성)

- **3중 복제 VS 소거 코드** → 상황에 따라 다르다. 자주 읽고 지연이 중요한 데이터는 서버 1대에서 바로 읽는 복제가 낫고, 많이 쌓아두고 덜 읽는 데이터는 공간을 절반으로 줄이는 소거 코드가 낫다. 이번 요구사항에 "저장 비용 효율"이 있으니 소거 코드를 놓치기 어렵다.
- **같은 랙에 모아두기 VS 장애 도메인 나눠 두기** → 나눠 두기. 모아두면 가까워서 빠르지만, 랙 하나 죽으면 사본이 같이 죽어서 내구성 계산이 무너진다.

## 메타데이터 데이터 모델과 샤딩

```
bucket(bucket_name, bucket_id, owner_id, enable_versioning)
object(bucket_name, object_name, object_version, object_id)
```

지원해야 할 질의는 세 가지다. 이름으로 object\_id 조회, 이름으로 삽입·삭제, 접두어로 버킷 내 목록 조회.

샤딩 키 선택

버킷 표는 작아서 서버 한 대 + 읽기 복제본이면 충분하다. 문제는 객체 표다.

| 샤딩 키 | 문제 |
| --- | --- |
| bucket\_id | 객체가 수십억 개인 핫 버킷이 샤드 하나에 몰림 |
| object\_id | 사람들은 이름으로 찾는데 이름으로는 위치를 모름 |
| hash(bucket\_name, object\_name) | 이름으로 샤드 하나에서 바로 찾음. 채택 |

목록 조회가 조금 번거로워진다. 같은 버킷의 객체가 모든 샤드에 흩어져서 모든 샤드에 물어보고 합쳐야 한다. 페이지네이션은 샤드마다 오프셋을 따로 들고 다녀야 해서 더 까다롭다. 책의 해결은 목록 조회 전용 표를 bucket\_id로 샤딩해 비정규화하는 것.

한 버킷도 여러 서버에 나눠 저장할 수 있지 않을까? 가상/물리 메모리 MMU처럼. S3도 그렇게 한다고 한다. 버킷을 파일 이름 범위로 쪼개고(`a~f` → 서버 1, `g~m` → 서버 2), "어느 범위가 어느 서버"라는 표를 페이지 테이블처럼 두고, 범위가 뜨거워지면 쪼개고 표만 고친다. 그럼 사실상 "버킷 + 파일 이름" 기준이라 책의 해시 방식과 출발점이 같고, 차이는 섞느냐 순서를 유지하느냐 일 것이다.

|  | 해시로 나누기 (책) | 범위로 나누기 |
| --- | --- | --- |
| 이름으로 찾기 | 빠름 | 빠름 |
| 목록 보기 | 모든 서버에 물어야 함 | 해당 범위 서버만 |
| 관리 | 단순 | 쪼개기·표 관리 필요 |

선택의 기로 (메타데이터)

- **bucket\_id VS object\_id VS hash(bucket\_name, object\_name)** → hash. 요청은 항상 이름으로 들어오니 이름으로 샤드를 바로 찾을 수 있어야 하고, 핫 버킷도 피해야 한다.
- **목록 조회 성능 VS 조회·삽입 성능** → 조회·삽입 우선. 목록 조회는 덜 자주 일어나니 모든 샤드에 물어보는 비용을 감수하거나 전용 표로 보완한다.
- **해시로 나누기 VS 범위로 나누기** → 책은 해시. 단순하고 고르게 퍼지기 때문이다. 목록 조회가 중요한 서비스라면 관리가 복잡해도 범위 방식을 고려할 만할 것 같다.

## 버저닝

- `object_version` 컬럼에 시간순 정렬되는 TIMEUUID를 저장한다.
- 같은 이름으로 다시 올리면 덮어쓰지 않고 새 행을 추가. 가장 큰 TIMEUUID가 최신 버전.
- 삭제도 지우지 않고 삭제 마커라는 새 버전을 추가. 최신 버전이 삭제 마커면 GET은 404.

결국 객체 불변이라는 원칙을 메타데이터까지 가져간 것 같다. 메타데이터도 덮어쓰지 않고 추가만 한다.

선택의 기로 (버저닝)

- **기존 행 덮어쓰기 VS 새 행 추가** → 새 행 추가. 예전 버전을 남겨야 하는 게 요구사항이고, 삭제도 마커로 처리하면 되돌릴 수 있다. 대신 행이 계속 늘어난다.

## 멀티파트 업로드

큰 파일을 한 번에 올리다가 끊기면 처음부터 다시 해야 한다. 그래서 조각으로 나눠 올린다.

1. 시작 요청 → 서버가 `uploadID` 발급.
2. 조각마다 `(uploadID, partNumber)`를 붙여 업로드 → 조각별 ETag(MD5) 반환.
3. 완료 요청에 partNumber와 ETag 목록을 보내면 서버가 검증 후 조립.
4. 원래 조각들은 GC 대상.

패킷 스위칭의 스토어 앤 포워드 같다고 느꼈는데, 조각을 다 받아 보관했다가 완료 신호가 오면 합친다는 점이 닮았다. 목적(쪼개서 따로 보내고, 잃은 것만 다시 보내고, 도착지에서 번호대로 조립)을 보면 패킷 스위칭과 TCP 재전송에 더 가깝다. partNumber = 시퀀스 번호, ETag = 체크섬, 실패한 조각만 재업로드 = 재전송. 다른 점은 TCP는 순서대로 받아야 하지만 멀티파트는 순서 상관없이 동시에 올려도 된다는 것. 마지막에 번호 목록으로 순서를 정한다.

선택의 기로 (멀티파트)

- **한 번에 올리기 VS 조각으로 올리기** → 큰 객체는 조각. 실패한 조각만 다시 올리고 동시에 올릴 수 있다. 대신 버려진 조각이 생길 수 있어서 GC가 챙겨야 한다.

## 정리

1. 내용과 정보는 크기가 너무 달라서 따로 저장한다.
2. 내용은 번호로만 찾고, 작은 건 이어 붙이고, 복사하거나 조각내서 안 잃게 한다.
3. 정보는 이름 기준으로 나눠 저장하고 목록 보기는 따로 챙긴다.
4. 수정은 없다. 버전도 삭제도 새로 추가한다.
5. 두 시스템에 걸친 변경은 항상 "커밋 지점을 마지막에". 업로드의 메타데이터 쓰기, 위치 표 갱신이 둘 다 그렇다.
