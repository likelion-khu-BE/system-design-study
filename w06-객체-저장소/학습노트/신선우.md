- **블록 저장소**: 원시 블록을 서버에 볼륨으로 제공. HDD나 SSD
- **파일 저장소**: 블록 저장소 위에 디렉터리 계층을 올림
- **객체 저장소**: 성능보다 규모, 비용 우선, Restful API로 접근
- **버킷**: 객체를 보관하는 논리적 컨테이너
- **객체**: 버킷에 저장하는 개별 데이터
- **버전**: 한 객체의 여러 버전을 같은 버킷 안에 둘 수 있도록 하는 기능
- **SLA**: 서비스 수준 협약. 가용성이나 내구성, 복원에 관한 약속이 들어있음
## 버킷 만들기
 
- 버킷 생성
- 객체 업로드, 다운로드
- 객체 버전
- 버킷 내 객체 목록 출력 기능
- 연간 100PB 데이터
- **내구성**: six nines(99.9999%)
- **가용성**: four nines(99.99%)
- **효율성**: 안전성과 성능은 유지하면서 비용 최소화
## 객체 저장소의 흥미로운 특성
 
- **객체 불변성(immutability)**: 저장된 객체는 변경이 불가능하다. 삭제 후 새 버전으로 대체하던가 해야함
- **key-value 저장소**: 객체 URI가 key, 객체 데이터가 value
- **쓰기 1번, 읽기 매우 많음**: 95%가 읽기요청임
- **소형 및 대형 객체 동시 지원**: 다양한 크기의 객체 저장 지원
- 설계 철학이 UNIX 파일 시스템과 유사함
## 객체 업로드 흐름
 
1. 클라이언트가 PUT 요청 날려서 버킷 생성 요청
2. API 서비스가 IAM에 쓰기 권한 확인
3. 메타데이터 저장소에 버킷 정보를 기록하고 성공 응답 보냄
4. 클라이언트가 PUT 요청 날려서 객체 업로드
5. API 서비스가 IAM에서 쓰기 권한 확인하고 객체 데이터를 데이터 저장소에 보냄. UUID 반환
6. 메타데이터 저장소에 `object_id`, `bucket_id`, `object_name` 같은 정보를 저장
## 객체 다운로드 흐름
 
1. `GET /버킷이름/오브젝트이름`
2. IAM에서 읽기 권한 확인
3. 메타데이터 저장소에서 객체의 UUID 조회
4. 데이터 저장소에서 UUID로 데이터 가져오기
5. 클라이언트에 반환
## 데이터 저장소
 
- **데이터 라우팅 서비스**: 데이터 노드 클러스터에 접근하기 위한 RESTful 또는 gRPC 제공. stateless임
- **배치 서비스(placement service)**: 어느 데이터 노드에 저장할지 결정. 가상 클러스터 지도로 클러스터의 물리적 형상 관리. 모든 데이터 노드와 heartbeat 주고 받으며 상태 감시. 5대 또는 7대 노드로 클러스터 구성하고 Paxos나 Raft 합의 프로토콜 사용
- **데이터 노드**: 실제 객체 데이터 저장, 여러 노드에 복제해 안정성과 내구성 보장
### 데이터 저장 흐름
 
1. API 서비스가 객체 데이터를 데이터 저장소로 보냄
2. 데이터 라우팅 서비스가 객체에 UUID 할당하고 배치 서비스에 저장할 노드 물어봄. 배치 서비스는 가상 클러스터 지도 보고 주 데이터 노드 알려줌
3. 라우팅 서비스가 UUID 와 데이터를 주 노드로 직접 보냄
4. 주 노드는 데이터를 자기 노드에 저장하고 부 노드 2개에 복제
5. 객체 UUID가 API 서비스로 반환됨
#### trade-off(쓰고 나니 당연한 말..)
 
1. 주 노드가 사본 3개 모두 저장하고 응답: 강한 일관성, 높은 지연
2. 주 노드와 부 노드 1개에 저장하고 응답: 중간
3. 주 노드에만 저장: 약한 일관성, 낮은 지연
#### 작은 객체를 각각 저장하면 문제
 
1. **블록 낭비**: 블록 크기보다 작은 파일도 블록 하나를 통째로 차지함
2. **아이노드 고갈**: 작은 파일이 수백만 개면 아이노드가 먼저 바닥남
**해결책**: 작은 객체 여러개를 큰 파일 하나에 모아서 저장. Write-ahead log와 비슷한 방식
 
1. 새 객체는 현재 읽기-쓰기 파일에 추가
2. 파일이 일정 용량에 도달하면 읽기 전용으로 바꾸고 새 읽기-쓰기 파일 열기
3. 같은 읽기-쓰기 파일에 대한 쓰기는 직렬화 해야함
#### 객체 소재 찾는 법
 
- 파일 기반 키 값 저장소 이용
- 관계형 DB 이용

### 큰 파일 업로드

## 일단 S3 스토리지 클래스
 
| 클래스 | 가용성 | AZ 수 | 최소 보관 기간 | 최소 과금 크기 | 접근 방식 | 용도 |
| --- | --- | --- | --- | --- | --- | --- |
| **Standard** | 99.99% | 3+ | 없음 | 없음 | ms, 조회 비용 없음 | 자주 접근하는 데이터 |
| **Express One Zone** | 99.95% | 1 | 없음 | 없음 | 한 자릿수 ms | 지연에 민감한 앱 |
| **Intelligent-Tiering** | 99.9% | 3+ | 없음 | 없음 | ms, 조회 비용 없음, 객체당 모니터링 비용 | 접근 패턴을 모를 때 |
| **Standard-IA** | 99.9% | 3+ | 30일 | 128KB | ms, GB당 조회 비용 | 한 달에 한 번 정도 (백업) |
| **One Zone-IA** | 99.5% | 1 | 30일 | 128KB | ms, GB당 조회 비용 | 다시 만들 수 있는 데이터 |
| **Glacier Instant Retrieval** | 99.9% | 3+ | 90일 | 128KB | ms, GB당 조회 비용 | 분기에 한 번 정도 |
| **Glacier Flexible Retrieval** | 99.99% (복원 후) | 3+ | 90일 | - | 먼저 복원 필요, 수 분~수 시간 | 1년에 한 번 정도 |
| **Glacier Deep Archive** | 99.99% (복원 후) | 3+ | 180일 | - | 먼저 복원 필요, 수 시간 | 1년에 한 번 미만 |
 
- 자주 읽음 → Standard
- 극저지연 → Express One Zone
- 접근 패턴을 모름 → Intelligent-Tiering
- 월 1회 → Standard-IA / One Zone-IA
- 분기 1회 → Glacier Instant
- 연 1회 이하 → Glacier Flexible / Deep Archive
자신의 사용량을 고려해서 비용을 아껴보자
 
## S3에는 Transfer Acceleration(전송 가속)이라는 기법이 있다
 
전 세계 사용자와 범용 버킷 사이의 전송 속도를 높이도록 설계된 기능
 
쉽게 말해, 느린 공용 인터넷 구간은 짧게 하고 나머지는 AWS의 최적화된 네트워크 경로로 S3까지 전달된다
 
## 내가 신기했던 것
 
### S3로 정적 파일 배포하기
 
- **정적 파일**: HTML, CSS, JS, 이미지, 폰트처럼 서버가 따로 계산하지 않고 그대로 내려주는 파일
- S3는 파일을 저장하고 HTTP로 내려줄 수 있어서, **웹 서버(EC2, Nginx) 없이** 프론트엔드를 배포할 수 있습니다.
- 장점: 서버 관리가 필요 없고, 비용이 저렴하고, 트래픽이 늘어도 자동으로 감당하며, 11 nines 내구성을 그대로 누립니다.
- 한계: 서버 사이드 로직은 실행할 수 없습니다(SSR, API 불가). API는 Spring Boot 같은 별도 백엔드가 맡습니다.
