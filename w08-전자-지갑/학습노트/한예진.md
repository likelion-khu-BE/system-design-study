# W8 전자 지갑

# 1. 문제 이해 및 설계 범위 확정

### 1-1. 조정(reconciliation)만으로는 왜 불일치 "원인"을 알 수 없나?

**조정 = 결과(잔액)끼리 비교하는 작업**

- 내부 기록의 잔액과 은행 명세서를 비교 → "다르다"는 사실만 알 수 있음
- 지금까지의 설계는 DB에 **현재 잔액만 저장**(UPDATE로 덮어씀) → 어떤 과정을 거쳐 그 값이 됐는지 남아 있지 않음 (책 p.425)

**예시**

- 내부 기록 A = $3, 은행 명세서 A = $4 → $1 차이 발견
- 원인 후보: 이체 누락? 중복 차감? 코드 버그? 잘못된 입력? 순서 꼬임?
- 결과값만으로는 이 중 무엇인지 **구분 불가**
- 비유: 통장 잔고만 찍혀 있고 **거래 내역이 없는 통장**

**그래서 재현성(reproducibility)이 필요**

| 구분 | 조정 | 재현성 (이벤트 소싱) |
| --- | --- | --- |
| 보는 것 | 현재 결과(잔액) | 결과까지 오는 모든 과정(이벤트 이력) |
| 알 수 있는 것 | 불일치가 **있다** | **언제, 어떤 이벤트에서** 어긋났는지 |
| 과거 잔액 | 알 수 없음 | 이벤트를 그 시점까지 재생하면 복원 가능 |

→ 조정은 "이상 탐지기", 재현성은 "블랙박스". 실무에서는 둘 다 씀 (조정으로 발견 → 이벤트 재생으로 원인 추적)

# 2. 개략적 설계안

### 2-1. (API 설계) float/double을 "지원한다"는 게 어떤 의미인가?

**"지원한다" = 언어와 DB가 기본 타입으로 갖고 있어서 별도 처리 없이 바로 쓸 수 있다는 뜻**

- Java `double`, Python `float`, MySQL `FLOAT/DOUBLE` 등 기본 제공
- JavaScript는 숫자 타입이 사실상 double 하나뿐, 대부분의 JSON 파서도 숫자를 double로 읽음
- 그래서 변환 코드 없이 바로 계산·저장 가능 → **편해서** 쓰는 것이지 **정확해서** 쓰는 게 아님

**문제점: 2진 부동소수점이라 10진 소수를 정확히 표현 못 함**

- `0.1 + 0.2 = 0.30000000000000004`
- 11장(p.377)에서 amount를 string으로 둔 이유: 직렬화/역직렬화 과정에서 정밀도 손실, 시스템마다 숫자를 다르게 해석할 수 있음

**금액을 다루는 방법 비교**

| 방법 | 설명 | 특징 |
| --- | --- | --- |
| float / double | 언어 기본 타입 그대로 | 간편하지만 오차 발생 가능 |
| string 전송 + 고정소수점 연산 | API는 `"10.25"`, 내부는 `BigDecimal` / DB `DECIMAL` | 정확함. 이 책의 방식 |
| 최소 단위 정수 | $10.25 → `1025`(센트)로 저장 | 정확하고 빠름. Stripe 등이 사용 |

→ 책의 의미: "오차가 생길 수 있다는 걸 알고, 그게 문제 안 되는 곳(통계, 표시용 등)이라면 double도 선택지가 될 수 있다"

### 2-2. (인메모리 샤딩) "해시 값 % n = 파티션 번호" 예시

책 코드 그대로 사용 (Java의 `"A".hashCode()`는 실제로 `65`)

| 계정 ID | hashCode() | n = 3일 때 (% 3) | 저장 위치 |
| --- | --- | --- | --- |
| "A" | 65 | 65 % 3 = **2** | 레디스 노드 2 |
| "B" | 66 | 66 % 3 = **0** | 레디스 노드 0 |
| "C" | 67 | 67 % 3 = **1** | 레디스 노드 1 |
- A → C로 $1 이체: 지갑 서비스가 계산 → A는 노드 2에 `$1`, C는 노드 1에 `+$1`
- 같은 키는 항상 같은 나머지 → **항상 같은 노드**로 감 (조회할 때도 같은 계산)
- 해시가 고르게 퍼지면 데이터도 노드에 고르게 분산

**주의: n이 바뀌면 대부분 키가 이동**

| 계정 | n = 3 | n = 4 |
| --- | --- | --- |
| A (65) | 2 | 1 |
| B (66) | 0 | 2 |
| C (67) | 1 | 3 |

→ 노드 하나 추가했는데 전부 이동. 그래서 실무에서는 **안정 해시(consistent hashing, 1권 5장)** 나 고정 슬롯 방식(레디스 클러스터 16384 슬롯)을 많이 씀

### 2-3. (인메모리 샤딩) 무상태 서비스가 수평 확장이 쉬운 이유

- 지갑 서비스는 **잔액을 자기가 들고 있지 않음** → 잔액은 레디스, 파티션 정보는 주키퍼에 있음
- 지갑 서비스는 "요청 받기 → 검증 → 주키퍼에 위치 묻기 → 레디스 갱신"만 수행
- 따라서 **어떤 인스턴스가 요청을 받아도 결과가 같음**

| 구분 | 무상태 (지갑 서비스) | 상태 저장 (레디스) |
| --- | --- | --- |
| 서버 추가 시 | 띄우고 로드 밸런서에 등록하면 끝 | 데이터 재분배(리샤딩) 필요 |
| 서버 장애 시 | 다른 인스턴스가 바로 처리 | 그 노드의 데이터 복구 필요 |
| 요청 라우팅 | 아무 서버나 OK | 키가 있는 노드로 가야 함 |

→ 확장의 어려움을 상태 저장 계층(레디스, DB)으로 몰아 놓은 구조

### 2-4. (TC/C) "애플리케이션 계층에서 세부 사항을 관리하고 분산 트랜잭션 복잡성을 처리한다"는 게 정확히 무엇인가?

**2PC는 DB가 해줌, TC/C는 개발자가 코드로 직접 함**

| 할 일 | 2PC | TC/C |
| --- | --- | --- |
| 준비/커밋/롤백 | DB가 XA 프로토콜로 처리 | 개발자가 Try/Confirm/Cancel **비즈니스 연산을 직접 정의** |
| 되돌리기 | DB 롤백 | **보상 트랜잭션 직접 작성** (A-$1의 취소 = A+$1) |
| 진행 상황 기록 | DB 내부 로그 | **단계별 상태 테이블**에 직접 저장 |
| 장애 후 복구 | DB가 처리 | 상태 테이블을 읽고 이어서 Confirm/Cancel 재실행 |
| 순서 꼬임 | 해당 없음 | 취소가 먼저 오면 플래그 저장 → 나중 Try는 거절 |
| 중간 상태 | 락 때문에 외부에 안 보임 | 불균형 상태(돈이 잠깐 사라짐)를 감안해 **연산 순서 설계** (출금 먼저) |

**개발자가 짜는 코드 흐름 (의사 코드)**

```
// 1. 상태 테이블에 트랜잭션 기록 (txId, Try=not sent yet)
// 2. Try: A DB에 "A -$1", C DB에 NOP   (각각 별도 로컬 트랜잭션, 바로 커밋)
// 3. 응답 모으기 → 상태 테이블 갱신
// 4. 모두 성공 → Confirm: A는 NOP, C에 "C +$1"
//    하나라도 실패 → Cancel: A에 "A +$1", C는 NOP
// 5. Confirm/Cancel은 성공할 때까지 재시도 (멱등하게 구현해야 함)
```

→ "DB는 그냥 로컬 트랜잭션만 해줌, **분산 트랜잭션이라는 큰 흐름은 앱 코드가 책임**"이라는 뜻. 그래서 어떤 DB든 쓸 수 있지만 코드가 복잡해짐 (참고: Seata 같은 프레임워크가 TCC 모드를 제공해 일부 부담을 덜어줌)

### 2-5. (TC/C vs 사가) 지연 시간에 민감하고 서비스가 많으면 왜 TC/C가 나은가?

**핵심: 사가는 순서대로(직렬), TC/C는 동시에(병렬)**

예: 서비스 5개, 각 연산 100ms

| 구분 | 사가 | TC/C |
| --- | --- | --- |
| 실행 방식 | 1 → 2 → 3 → 4 → 5 차례로 | Try 5개 동시 → Confirm 5개 동시 |
| 정상 처리 시간 | 100 × 5 = **약 500ms** | Try 100 + Confirm 100 = **약 200ms** |
| 4번째에서 실패 시 | 3 → 2 → 1 보상도 차례로 | Cancel 5개 동시 |
| 서비스가 늘어나면 | 지연이 **선형으로 증가** | 지연이 거의 **그대로** (가장 느린 것 기준) |
- 서비스 2~3개면 차이가 작아서 아무거나 써도 됨 (책 p.420)
- 대신 TC/C는 서비스마다 Try/Confirm/Cancel 3개 인터페이스를 구현해야 하므로 개발 부담↑

### 2-6. (이벤트) 명령에 무작위성이나 I/O가 포함되는 예시

명령을 **처리(검증)하는 과정**에서 외부 상황에 따라 결과가 달라질 수 있는 경우

| 예시 | 종류 | 결과가 달라지는 이유 |
| --- | --- | --- |
| 이체 시 사기 탐지 서비스 호출 | 외부 I/O | 호출할 때마다 위험 점수가 다를 수 있음 → 승인/거절 |
| 해외 송금 시 환율 API 조회 | 외부 I/O | 처리 시점의 환율이 다름 |
| 현재 시각 읽기 (일일 한도, 시간대별 수수료) | 시간 | 언제 처리하느냐에 따라 한도 초과 여부가 다름 |
| 거래 ID를 UUID로 생성 | 난수 | 매번 다른 값 |
| 일부 거래만 무작위로 추가 인증 | 난수 | 같은 명령도 인증 대상 여부가 다름 |

→ 그래서 **같은 명령을 다시 처리하면 다른 이벤트가 나올 수 있음** → 이벤트에는 그 결과가 **확정된 값으로** 기록됨 (예: "A→C $1 완료, 환율 1,300원, txId=xxx") → 재생할 때 명령이 아니라 **이벤트를 재생**하는 이유 (책 p.432: 명령의 신뢰성만으로는 재현성 보장 불가)

#### 2-7. (이벤트) 이벤트 소싱 명령과 이벤트 관계 헷갈림

이벤트 생성이 명령인 것? 이벤트 생성은 결정론적 과정이 아니고 무작위적 요소가 포함될 수 있는데, 이벤트는 결정론적(불변, 과거의 사실)이다.

- 명령 - 무작위성이나 I/O 포함될 수 있다.
- 이벤트 - 결정론적, 과거에 실제로 있었던 일.

이게 맞음?

**결론: 거의 맞음. "이벤트 생성 = 명령"만 보정**

- 명령: 무작위성·I/O 포함 가능 ✅
- 이벤트 생성: 무작위적 요소 포함 가능 ✅
- 이벤트: 결정론적, 과거에 실제로 있었던 사실 ✅
- 이벤트 생성 = 명령? ❌ → **명령은 입력(요청)이고, 이벤트 생성은 그 명령을 "처리하는 과정"**
    - 명령에 무작위성이 "포함된다"는 말도 정확히는 **명령을 처리해 이벤트를 만드는 과정**에서 무작위성·I/O가 끼어든다는 뜻

**세 가지를 구분하면 정리됨**

```
명령 (입력, 의도)
  │  상태 기계 ① : 유효성 검사 + 이벤트 생성  ← 여기서 무작위성/I/O 개입 가능 (비결정적)
  ▼
이벤트 (출력, 확정된 사실, 불변)
  │  상태 기계 ② : 이벤트 적용               ← 항상 같은 결과 (결정적)
  ▼
상태 (잔액)
```

| 구분 | 명령 | 이벤트 |
| --- | --- | --- |
| 의미 | "A에서 C로 $1 보내줘" (요청) | "A에서 C로 $1 **보냈음**" (사실) |
| 시제 | 현재/미래 | 과거 |
| 유효성 | 거절될 수 있음 | 이미 검증 통과 |
| 결정론적? | 처리 결과가 매번 다를 수 있음 | 적용하면 항상 같은 상태 |
| 재생에 사용? | X | O |
- "이벤트가 결정론적"의 정확한 뜻: 이벤트는 이미 값이 확정되어 있어서, **적용하면 항상 같은 상태가 나온다**
- "이벤트 생성 과정은 비결정적"과 모순 아님 → 만드는 과정은 흔들릴 수 있지만, **한 번 만들어진 이벤트는 바뀌지 않음**

### 2-8. (이벤트) 이벤트 소싱 외에 다른 방법은? 이벤트 소싱이 가장 적합한가?

요구사항: **재현성(감사 가능)** + 정확성

| 방법 | 설명 | 한계 |
| --- | --- | --- |
| 잔액 UPDATE + 이력(감사 로그) 테이블 | 잔액은 덮어쓰고 변경 이력을 따로 저장 | 원본은 잔액이고 로그는 부가 기록 → 둘이 어긋날 수 있음 |
| 템포럴 테이블 (SQL:2011, 시스템 버전 테이블) | DB가 행의 과거 버전을 자동 보관 | 특정 시점 값은 알지만 **왜** 바뀌었는지(비즈니스 의도)는 모름 |
| CDC (Debezium 등) | DB 변경 로그를 캡처해 스트림으로 | 행 단위 변경일 뿐, 비즈니스 이벤트가 아님 |
| 복식부기 원장 (append-only ledger) | 11장 원장처럼 모든 거래를 불변 분개로 쌓고, 잔액 = 분개 합계 | 사실상 이벤트 소싱과 같은 사상. 실무 결제/지갑에서 매우 많이 씀 |
| 불변 원장 DB (immudb 등) | 변조 불가 검증까지 제공 | 성능·운영 경험 부족 |

**이벤트 소싱이 적합한 이유**

- **이벤트가 원본(source of truth)**, 잔액은 이벤트로부터 계산된 결과 → 둘이 어긋날 수 없음
- 감사관의 3가지 질문(특정 시점 잔액, 잔액 정확성, 코드 변경 후 검증)에 모두 답 가능
- 추가만 하는(append-only) 구조라 3단계의 파일 기반 고성능 설계와 잘 맞음

**단점도 있음**: 구조 복잡, 이벤트 스키마 변경 어려움, 읽기 모델은 최종적 일관성(CQRS)

→ 핵심은 "이벤트 소싱이라는 이름"보다 **불변 이력을 원본으로 삼는 것**. 복식부기 원장도 같은 원리라 금융 시스템에서는 이 계열이 사실상 표준

# 3. 상세 설계

### 3-1. (합의) 래프트에서 데이터가 손실될 수 있나? 다른 방법은?

**래프트의 보장: 커밋된(과반수에 복제된) 데이터는 손실되지 않음**

- 리더는 과반수 노드에 복제된 뒤에야 "커밋 완료"로 처리하고 클라이언트에 성공 응답
- 새 리더 선출 시 **로그가 가장 최신인 노드만** 표를 받을 수 있음 → 커밋된 데이터를 가진 노드가 반드시 리더가 됨

**그래도 손실(처럼 보이는) 경우**

| 상황 | 결과 | 대응 |
| --- | --- | --- |
| 과반수 복제 **전에** 리더 장애 | 그 데이터는 사라질 수 있음. 하지만 클라이언트는 성공 응답을 못 받음 | 타임아웃 → 새 리더에 재전송 (책 p.435). 중복 방지를 위해 **멱등성(transaction_id)** 필요 |
| 과반수 노드가 동시에 디스크까지 날아감 | 실제 손실 | 노드를 다른 랙/가용 영역에 분산 |
| 디스크에 fsync 전 응답하도록 구현 | 정전 시 손실 가능 | 구현 시 영속화 후 응답 |

**복제가 잘못됨 = 데이터 손실?**

- 팔로어 로그가 리더와 다르면 리더가 팔로어 로그를 **덮어써서 맞춤**
- 이때 지워지는 건 **커밋 안 된 데이터뿐** → 성공 응답한 데이터는 손실 X

**래프트 외 다른 방법**

| 방법 | 특징 | 사용 예 |
| --- | --- | --- |
| 래프트 (Raft) | 이해하기 쉽게 설계된 합의 알고리즘 | etcd, CockroachDB, TiKV, Consul, Kafka KRaft |
| 팩소스 / 멀티 팩소스 (Paxos) | 원조 합의 알고리즘, 이론적으로 강력하지만 이해·구현 어려움 | Google Chubby, Spanner |
| ZAB | 주키퍼 전용 원자적 브로드캐스트 | ZooKeeper |
| 주-부 복제 (비동기 / 반동기) | 합의 없이 리더가 복제본으로 전송 | MySQL, PostgreSQL 복제 (비동기면 장애 시 손실 가능) |
| 카프카 ISR 복제 | 동기화된 복제본 집합에 모두 복제되면 커밋 | Kafka 파티션 (4장) |

→ 돈처럼 **손실이 절대 안 되는 데이터**는 합의 기반 복제를 많이 씀

### 3-2. (풀 vs 푸시) 풀 모델이 왜 실시간이 아닌가?

**클라이언트가 "언제 바뀌었는지" 모르고, 정해진 주기에만 물어보기 때문**

- 명령 처리 흐름: 명령 → 이벤트 → (CQRS로) 읽기 경로에 반영 → 이 과정이 **비동기**
- 클라이언트는 이체 요청 후 결과를 알려면 주기적으로 읽기 전용 상태 기계에 질의(폴링)해야 함

**예시 (폴링 주기 1초)**

- 0.0초 폴링 → 아직 반영 전
- 0.1초에 이체 완료
- 1.0초 다음 폴링 → 그제야 확인 → **0.9초 지연**

| 구분 | 풀 (폴링) | 푸시 |
| --- | --- | --- |
| 방식 | 클라이언트가 주기적으로 질의 | 상태가 바뀌면 읽기 경로가 바로 알려줌 |
| 지연 | 최대 폴링 주기만큼 | 거의 즉시 |
| 주기를 줄이면 | 지연↓, 하지만 서버 과부하 | 해당 없음 |

→ 비유: 택배 조회 페이지를 계속 새로고침(풀) vs 도착하면 알림(푸시)

### 3-3. (분산 트랜잭션) "모든 이벤트 소싱 노드 그룹이 동기적 실행 모델을 채택한다"는 의미

**문제: 이벤트 소싱은 원래 비동기**

- 명령을 넣으면 "접수됨"만 알 수 있고, 실제로 성공했는지는 나중에 처리됨
- 그런데 사가/TC/C 조정자는 **"A-$1 성공했어?"를 알아야 다음 단계(C+$1)로 갈 수 있음**

**해결: 각 파티션(노드 그룹)을 "호출하면 결과를 돌려주는" 동기 방식처럼 보이게 만듦**

- 역방향 프락시가 명령을 받아 노드 그룹으로 전달
- 처리 완료 후 읽기 경로가 결과를 프락시로 **푸시**
- 프락시가 그 결과를 응답으로 돌려줌
- → 조정자 입장에서는 **일반 DB에 요청하고 응답받는 것과 똑같음**

| 구분 | 비동기 (원래) | 동기 실행 모델 |
| --- | --- | --- |
| 요청 후 받는 것 | "접수됨" | "성공 / 실패" 결과 |
| 결과 확인 | 따로 폴링 | 응답으로 바로 |
| 사가/TC/C 재사용 | 어려움 | **그대로 재사용 가능** |

→ 그래서 2단계에서 만든 사가/TC/C를 **각 파티션을 하나의 DB처럼 취급**해서 그대로 쓸 수 있게 된 것

### 3-4. (마무리) "TC/C, 사가로 여러 노드에 명령 실행을 조율"이 구체적으로 무엇인가?

**바로 최종 설계(그림 12.28, 12.29)의 이체 과정**

- 계정 A → 파티션 1, 계정 C → 파티션 2 (해시 % 2)
- 각 파티션 = 래프트 노드 그룹 + 이벤트 소싱 + CQRS + 역방향 프락시
- A → C로 $1 이체 = **서로 다른 노드 그룹에 걸친 분산 트랜잭션**

**사가 기준 흐름 (책 1~15 단계 압축)**

| 순서 | 동작 |
| --- | --- |
| ① ② | 사용자 → 사가 조정자에 이체 요청, 조정자가 단계별 상태 테이블에 기록 |
| ③ ~ ⑦ | 파티션 1에 `A -$1` 명령 → 래프트 복제 → 이벤트 적용 → 결과를 조정자에 푸시 |
| ⑧ | 상태 테이블에 "파티션 1 성공" 기록 |
| ⑨ ~ ⑬ | 파티션 2에 `C +$1` 명령 → 같은 과정 → 결과 푸시 |
| ⑭ ⑮ | 상태 테이블에 "파티션 2 성공" 기록 → 사용자에게 완료 응답 |

**책에서 생략한 실패 경로**

- ⑨에서 `C +$1` 실패 → 조정자가 파티션 1에 보상 명령 `A +$1` 전송 → 롤백

**TC/C로 하면**

- Try: 파티션 1에 `A -$1`, 파티션 2에 NOP를 **동시에** 전송
- 모두 성공 → Confirm: 파티션 2에 `C +$1` / 실패 → Cancel: 파티션 1에 `A +$1`

→ "조율" = 조정자가 **어느 파티션에 어떤 명령을 어떤 순서로 보내고, 실패하면 무엇으로 되돌릴지** 상태 테이블을 보며 지휘하는 것

# 4. 개념 정리

### 4-1. 명령-질의 책임 분리 (CQRS, Command-Query Responsibility Segregation)

**한 줄 정의: 쓰기(상태 변경)와 읽기(조회)를 서로 다른 모델·경로로 나누는 것**

- 명령(Command): 상태를 바꾸는 요청 (이체)
- 질의(Query): 상태를 읽기만 하는 요청 (잔액 조회)

**이 장에서 왜 필요했나?**

- 이벤트 소싱으로 이체(쓰기)는 잘 처리하게 됐음
- 그런데 원본은 **이벤트 목록**이라 "지금 A의 잔액은?"에 바로 답하기 불편 (매번 재생해야 함)
- → 이벤트를 받아 **조회용 데이터(뷰)를 따로 만들어 두자**

**구조 (그림 12.19)**

```
[쓰기 경로] 명령 → 상태 기계(검증) → 이벤트 → 상태 기계(적용) → 상태
                                       │
                                  이벤트 발행
                                       ▼
[읽기 경로] 읽기 전용 상태 기계들 → 잔액 뷰 / 거래 내역 뷰 / 감사용 뷰 → 질의 서비스 ← 클라이언트
```

- 쓰기 담당 상태 기계는 **1개**, 읽기 전용 상태 기계는 **여러 개** 가능
- 읽기 쪽은 목적별로 다른 형태의 뷰를 만들 수 있음 (잔액 조회용, 특정 기간 감사용 등)

**비유**

- 은행 본점의 **원본 장부(이벤트)** 를 관리하는 직원은 1명 → 기록만 함
- 장부 사본을 받아 **잔액표, 월별 내역서, 감사 보고서**를 만드는 직원은 여러 명 → 고객 질문엔 이쪽이 답함

**전통적 방식(CRUD)과 비교**

| 구분 | 전통적 CRUD | CQRS |
| --- | --- | --- |
| 모델 | 읽기·쓰기 같은 테이블/모델 | 쓰기 모델과 읽기 모델 분리 |
| 확장 | 함께 확장 | 읽기·쓰기 따로 확장 가능 |
| 조회 형태 | 저장 구조 그대로 | 조회 목적에 맞게 자유롭게 구성 |
| 일관성 | 즉시 일관성 | 읽기 쪽이 약간 늦을 수 있음 (최종적 일관성) |
| 복잡도 | 단순 | 복잡 |

**주의할 점**

- 읽기 경로는 쓰기보다 **조금 늦게** 반영됨 → 그래서 3-2의 풀/푸시 문제가 생긴 것
- CQRS가 꼭 이벤트 소싱과 함께 쓰여야 하는 건 아니지만, 이벤트 소싱과 **궁합이 아주 좋아** 자주 같이 씀
- 마틴 파울러(참고 문헌 [11])도 복잡도가 크게 늘어나므로 **필요한 부분에만 적용**하라고 권함
