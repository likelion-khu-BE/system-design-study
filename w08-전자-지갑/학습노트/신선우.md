# 전자 지갑

> 전자 지갑이 뭐지? 했지만 **네이버페이머니처럼 미리 충전한 돈이 저장되어있는 곳**이었음
>
> 우리는 이 **전자 지갑 간의 이체**하는 방법을 알아본 것임

---

## 1. 인메모리 샤딩

일단 인메모리 샤딩: **레디스(인메모리) + 분산(샤딩)**

그런데 레디스를 나눠놓으면 노드가 하나라도 죽으면 이체 실패, **원자성 만족 못함**

---

## 2. 분산 트랜잭션

다음 분산 트랜잭션: **2PC, TC/C, Saga**

### 2 Phase Commit

2 Phase Commit: 저수준 방식

1. 코디네이터가 각 DB에 작업을 실행하고 커밋 가능? 물어봄 이때 **락도 같이 건다**
2. 모두 오케이 하면 커밋, 하나라도 실패하면 전부 롤백

> 2PC는 락을 걸어놓고 계속 응답을 기다리기 때문에 **성능이 낮음**, 코디네이터가 **단일장애점**

### Saga

Saga: choreography, orchestration

모든 연산을 정해진 순서대로 하나씩 독립된 로컬 트랜잭션으로 진행. 실패하면 롤백 아니고 **역순으로 보상 트랜잭션**

- **choreography**: 오케스트레이터 없이 서비스들 끼리 이벤트 구독으로 다음 단계 진행, 서비스 많아지면 흐름 파악 어려움
- **오케스트레이션**: 오케스트레이터가 중간에서 서비스들의 순서 지시함. 복잡한 흐름일 때 좋음

### TC/C

2PC랑 Saga는 호텔 예약에서 공부를 했으니 TC/C를 알아보자

`A → B 1달러 이체한다`

- **Try**: A 1달러 감소, B NOP(항상 성공 응답) 보내기
- **Confirm**: Try가 모두 성공하면 B에 1달러 증가
- **Cancel**: 하나라도 실패하면 보상 트랜잭션: A에 1달러 다시 증가

#### Q&A

**Q.** 자 그러면 TC/C 하다가 죽으면? A 1달러 감소 됐는데 B가 못받나?
→ **단계별 상태 테이블**(분산 트랜잭션 id, 단계별 상태 저장)

**Q.** Try → Confirm 사이에 1달러 불일치 하잖아?
→ 이 틈은 분산 트랜잭션이기 때문에 어쩔 수 없어, 상태 테이블에 잘 적어서 **반드시 끝나도록 보장**

**Q.** 네트워크 지연으로 Cancel이 Try보다 먼저오면?
→ 시도 못받았어요 플래그를 참으로 하고 시도 명령이 도착했을 때 먼저 도착한 취소명령이 있었는지 확인

#### 비교

- 2PC 방식과의 차이는 **롤백**과 **보상 트랜잭션** 방식이라는 점
- TC/C는 **application에서 구현한 2PC** 느낌
- 그래서 Saga와의 차이점은 **병렬(TC/C), 순차(Saga)**
  - TC/C는 try에서 모두 가능한지 확인하고 실패하면 cancel 날려서 다 취소하는거고
  - Saga쓰면 1단계, 2단계 가다가 3단계에서 실패하면 2,1 단계 차례로 보상 트랜잭션 해주는 것임
- 그래서 선택 기준은 **latency**

## 3. 이벤트 소싱

| 개념 | 설명 |
| --- | --- |
| 명령 | 외부에서 전달된 의도가 명확한 요청 |
| 이벤트 | 명령 이행 결과, 반드시 검증 통과 필요 |
| 상태 | 이벤트 적용 결과 |
| 상태 머신 | 명령 유효성 검사 후 이벤트 생성, 이벤트 적용 후 상태 갱신을 하는 이 로직. 무작위성 없고 deterministic함 |

**재현성**: 이벤트 리스트는 immutable하고 이벤트 이력의 재생 결과는 언제나 동일하다

**CQRS**(Command Query Responsibility Separation): 명령-쿼리 책임 분리

- 상태 기록 담당 상태 머신 1개, 읽기 전용 상태머신은 여러개 있을 수 있다

### 고성능 이벤트 소싱

- 카프카 대신 **로컬에 명령과 이벤트 저장**하기
- **RocksDB**: 로컬 파일 기반 키-값 저장소
- **스냅샷**: 상태를 통째로 저장, 현재 상황을 찰칵 사진 찍는 느낌, 다음에 거기부터 시작

### 신뢰성

노드가 죽으면 데이터도 날아감 → 복제본 만들어야함

이벤트 목록을 확실히 복제해야함 → **Raft 알고리즘** 사용

- 리더가 외부에서 명령을 받아 이벤트를 만들고 팔로워들은 복제함
- **과반수가 살아있으면 동작** 3/5, 2/3 이런식으로 홀수로 해서 5대면 2대 장애까지 버티는 것임

### 분산 이벤트 소싱: 100만 TPS 버티기

- **풀 모델**: 클라이언트가 주기적으로 상태를 물어보는데 역방향 프록시를 앞에 둬서 거기에 명령을 넣고 응답을 받음, 실시간성 떨어짐
- **푸시 모델**: 읽기 전용 상태기계가 이벤트를 수신하자마자 실행 상태를 역방향 프록시에 푸시
