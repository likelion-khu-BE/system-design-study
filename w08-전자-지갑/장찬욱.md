# 12장 전자 지갑 학습노트 - 장찬욱

> 전자 지갑은 **두 군데에 흩어진 숫자를 동시에 바꾸는 문제**다. A에서 1달러를 빼고 C에 1달러를 더하는 게 전부인데, A와 C가 다른 서버에 있으면 이 두 줄이 하나의 거래처럼 움직이게 만드는 게 어려워진다.



## 1단계 문제 이해 및 설계 범위 확정

Q&A

어떤 기능을 지원해야?

두 지갑 간 잔액 이체만. 충전, 출금은 범위 밖.

처리량은?

1,000,000 TPS. <- 지금까지 본 장들 중 가장 큰 쓰기 숫자다. 게다가 돈이라 하나도 틀리면 안 된다.

신뢰성은?

99.99%.

트랜잭션 보장이 필요한가?

YES. <- 1M TPS를 처리하려면 쪼개야 하는데, 쪼개면 트랜잭션이 깨진다.

재현성이 필요한가?

YES. 처음부터 데이터를 다시 재생해서 과거 잔액을 재구성할 수 있어야. 

환전은?

없다고 가정.

개략적 규모 추정

- 이체 1건 = A 차감 + C 입금 = 연산 2개. 그래서 실제로는 2,000,000 TPS를 버텨야 한다.
- 관계형 DB 노드 하나가 처리할 수 있는 TPS에 따라 필요한 노드 수가 확 바뀐다.

| 노드당 TPS | 필요 노드 수 |
| ------- | ------- |
| 100     | 20,000  |
| 1,000   | 2,000   |
| 10,000  | 200     |

노드 수가 수천 개라는 건 계좌가 무조건 여러 노드에 흩어진다는 뜻이다. A와 C가 같은 노드에 있을 확률은 거의 없다. 그러니까 "이체 1건이 노드 2개에 걸친다"가 예외가 아니라 기본 상황이다.

## 2단계 개략적 설계안 제시

### API

```
POST /v1/wallet/balance_transfer
from_account, to_account, amount, currency, transaction_id
```

- `transaction_id`는 멱등키. 7주차 결제의 UUID, 5주차 reservation_id와 같은 역할이다.
- `amount`가 숫자가 아니라 **문자열**이다.

그런데 왜 금액을 문자열로 보낼까?

부동소수점 때문이다. `0.1 + 0.2 != 0.3` 문제. JSON의 number는 대부분의 언어에서 double로 파싱되는데, 거쳐가는 시스템이 많을수록 어딘가에서 정밀도가 깨질 수 있다. 그래서 직렬화·전송할 때는 문자열로 두고, 계산하거나 저장할 때만 정확한 십진수 타입(자바면 `BigDecimal`, DB면 `DECIMAL`)으로 바꾼다. 

### 첫 번째 안: 인메모리 샤딩 (Redis)

가장 단순한 방법. 계좌 → 잔액을 Redis에 넣고, 계좌 해시로 여러 Redis 노드에 나눈다.

- 파티션 수와 각 노드 주소는 ZooKeeper에 둔다.
- 지갑 서비스는 무상태. 이체 요청을 받으면 잔액을 확인하고 두 Redis 노드의 값을 각각 고친다.

문제는 두 가지다.

1. Redis는 메모리라 내구성이 약하다.
2. **원자성이 없다.** A 노드에서 1달러 빼는 데 성공하고, C 노드에 더하기 전에 지갑 서비스가 죽으면 1달러가 사라진다.

### 두 번째 안: 분산 트랜잭션

DB 노드 여러 개에 걸친 연산을 하나의 트랜잭션처럼 묶는 방법이 필요하다. 책은 세 가지를 소개한다.

#### 2PC (2단계 커밋)

1. 준비(prepare): 조정자가 A, C 노드에 "이거 커밋할 수 있어?"라고 묻는다. 각 노드는 변경을 해두고 **락을 건 채로** "준비됨"이라고 답한다.
2. 커밋(commit): 전부 준비됨이면 커밋, 하나라도 아니면 전부 롤백.

문제

- 준비 단계에서 잡은 락을 조정자의 결정이 올 때까지 계속 잡고 있다. 느리다.
- 조정자가 단일 장애점이다.
- DB 레벨 프로토콜이라 모든 DB가 XA 같은 걸 지원해야 한다.

#### TC/C (Try-Confirm/Cancel)

2PC처럼 두 단계지만 결정적으로 다른 점은 **각 단계가 독립된 로컬 트랜잭션으로 바로 커밋된다**는 것이다. 락을 들고 기다리지 않는다. 대신 잘못되면 되돌리는 보상 트랜잭션을 실행한다.

A → C 1달러 이체

| 단계                 | A 계좌         | C 계좌           |
| ------------------ | ------------ | -------------- |
| Try                | 잔액 -1 (커밋)   | 아무것도 안 함 (NOP) |
| Confirm (Try 성공 시) | NOP          | 잔액 +1          |
| Cancel (Try 실패 시)  | 잔액 +1 (되돌리기) | NOP            |

- A -1 먼저, C +1 나중 → 올바름
- C +1 먼저, A -1 나중 → C가 돈을 써버리면 없던 돈이 생겨버린다.
- 동시에 → 둘 중 하나만 실패하면 어떻게 처리할 건가?

-> **돈은 "빼는 쪽"을 먼저, "주는 쪽"을 나중에.** 되돌릴 수 있는 쪽을 먼저 실행한다. 

**불균형 상태**

Try가 끝나고 Confirm 전 순간에는 A에서 1달러가 빠졌는데 C에는 아직 없다. 전체 잔액 합이 1달러 줄어든 상태다. 복식부기 관점에서 보면 장부가 안 맞는 순간이 존재하는 것이다.

2PC는 커밋 전까지 아무것도 반영이 안 되니 이런 순간이 없다. TC/C는 이 순간을 허용한다. 대신 조정자가 "지금 1달러가 이동 중"이라는 사실을 기록하고 있으니, 이 불균형은 추적 가능하고 결국 해소된다. 그래서 트랜잭션 보장이 깨진 게 아니다.

**단계 상태 테이블**

조정자가 Try 끝내고 Confirm 보내기 전에 죽으면? 재시작한 조정자가 어디까지 했는지 알아야 이어서 할 수 있다. 그래서 진행 상황을 DB에 적는다. 책은 이 테이블을 돈이 빠져나가는 계좌(A)가 있는 DB에 둔다.

- 분산 트랜잭션 ID와 내용
- 각 DB에 대한 Try 단계 상태 (안 보냄 / 보냄 / 응답 받음)
- 2단계 이름 (Confirm 또는 Cancel)
- 2단계 상태
- 순서가 바뀌었음을 나타내는 플래그 (아래)

그런데 Confirm이나 Cancel 자체가 실패하면?

찾아보니 TC/C의 전제는 "Confirm과 Cancel은 성공할 때까지 재시도한다"라고 한다. 되돌릴 방법이 없으니 될 때까지 다시 보내는 수밖에 없다. 그래서 Confirm/Cancel은 **멱등해야** 한다. 같은 Cancel이 두 번 와도 A에 2달러가 돌아가면 안 되니까. 결국 여기서도 멱등키가 나온다. 5, 7주차에 이어 세 번째다.

**순서가 뒤바뀐 실행**

A에 Try가 가기 전에 Cancel이 먼저 도착하는 경우가 있다. Try 요청이 네트워크에서 늦어진 것이다.

- Cancel이 먼저 오면: 되돌릴 게 없으니 아무것도 안 하되, "Cancel이 먼저 왔음" 플래그를 DB에 남긴다.
- Try가 나중에 오면: 플래그를 확인하고 바로 실패를 반환한다.

플래그로 순서가 뒤바뀌었음을 아는 것이다.

#### Saga

모든 연산을 한 줄로 순서대로 실행한다. 각 연산은 독립된 로컬 트랜잭션이고, 중간에 실패하면 지금까지 한 것들을 **역순으로** 보상 트랜잭션으로 되돌린다. 연산이 n개면 보상까지 2n개를 준비해야 한다.

조율 방식은 두 가지

- 안무(choreography): 중앙 조정자 없이 각 서비스가 서로의 이벤트를 구독해서 다음 할 일을 결정. 서비스가 많아지면 흐름을 파악하기 어렵다.
- 오케스트레이션(orchestration): 조정자 하나가 순서대로 지시. 전자 지갑은 이걸 쓴다.

#### 비교

2PC vs TC/C

|      | 1단계                   | 2단계 성공            | 2단계 실패            |
| ---- | --------------------- | ----------------- | ----------------- |
| 2PC  | 로컬 트랜잭션 아직 미완료 (락 보유) | 전부 커밋             | 전부 취소             |
| TC/C | 로컬 트랜잭션 전부 완료 (커밋됨)   | 필요하면 새 로컬 트랜잭션 실행 | 이미 커밋된 것의 효과를 되돌림 |

2PC는 DB 레벨, TC/C는 애플리케이션(비즈니스 로직) 레벨이다. TC/C는 DB가 XA를 지원하지 않아도 되지만 Try/Confirm/Cancel 로직을 전부 직접 짜야 한다.

TC/C vs Saga

|                | TC/C        | Saga            |
| -------------- | ----------- | --------------- |
| 보상 동작          | Cancel 단계에서 | 롤백 단계에서         |
| 중앙 조정          | 있음          | 있음 (오케스트레이션 모드) |
| 실행 순서          | 아무 순서       | 선형              |
| 병렬 실행          | 가능          | 불가              |
| 중간의 불일치 상태가 보임 | 예           | 예               |
| 로직 위치          | 애플리케이션      | 애플리케이션          |

책의 결론: 지연시간이 중요하지 않거나 관련 서비스가 적으면 아무거나. 지연시간이 중요하고 서비스가 많으면 병렬로 Try를 보낼 수 있는 TC/C.

선택의 기로 (분산 트랜잭션)

- **2PC VS TC/C·Saga** → TC/C·Saga. 2PC는 락을 들고 기다리는 동안 처리량이 떨어지고 조정자가 죽으면 다 멈춘다. 1M TPS에서는 감당 못 한다. 대신 중간 불일치 상태를 허용하고 보상 로직을 직접 짜야 한다.
- **Try에서 양쪽 동시 반영 VS 빼는 쪽만 먼저** → 빼는 쪽만. 되돌릴 수 있는 쪽을 먼저 한다.

### 세 번째 안: 이벤트 소싱

분산 트랜잭션으로 "지금 맞는 숫자"는 만들 수 있다. 그런데 요구사항에 재현성이 있었다. 지금 설계에서는 잔액 테이블이 덮어써지니까 아래 질문에 답할 수 없다.

1. 아무 과거 시점의 잔액을 알 수 있나?
2. 과거와 현재 잔액이 맞다는 걸 어떻게 아나?
3. 코드를 바꾼 뒤에도 시스템 로직이 맞다는 걸 어떻게 증명하나?

그래서 잔액(결과)을 저장하는 대신, 잔액을 바꾼 **사건**을 전부 저장하고 잔액은 거기서 계산한다.

용어 4개

- 명령(command): 외부에서 들어온 의도. "A에서 C로 1달러 보내줘". 거절될 수도 있다.
- 이벤트(event): 검증을 통과해서 실제로 일어난 사실. "A -1달러", "C +1달러". 과거형이고 거절될 수 없다.
- 상태(state): 이벤트를 적용한 결과. 계좌별 잔액.
- 상태 기계(state machine): 두 가지를 한다.
  1. 명령을 읽고 현재 상태로 검증한 뒤 이벤트를 만든다. (A 잔액이 1달러 이상인가?)
  2. 이벤트를 읽고 상태에 적용한다.

```
명령 큐 ──→ [상태 기계: 검증] ──→ 이벤트 목록 ──→ [상태 기계: 적용] ──→ 상태(잔액)
                    ↑                                                       │
                    └───────────────── 현재 상태 조회 ────────────────────────┘
```

여기서 중요한 성질은 **이벤트 적용은 결정적이어야 한다**는 것이다. 같은 이벤트 목록을 같은 순서로 적용하면 몇 번을 하든 같은 잔액이 나와야 한다. 그러면

1. 과거 잔액 → 처음부터 그 시점까지 이벤트를 재생하면 된다.
2. 잔액이 맞는지 → 이벤트로 다시 계산해서 비교하면 된다.
3. 코드 변경 검증 → 새 버전 코드로 같은 이벤트를 재생해서 결과를 비교하면 된다.

### CQRS

잔액 조회, 과거 잔액 조회, 감사용 리포트 등 읽는 방식이 여러 가지다. 이걸 쓰기용 상태 하나로 다 처리하면 무거워진다.

그래서 쓰기(명령 → 이벤트)는 상태 기계 하나가 담당하고, 이벤트를 외부에 발행한다. 읽기는 그 이벤트를 구독하는 **읽기 전용 상태 기계** 여러 개가 각자 필요한 형태로 뷰를 만든다. 쓰기 쪽은 하나, 읽기 쪽은 여럿.

대신 읽기 뷰는 이벤트를 늦게 받으니 결과적 일관성이다. 5주차에서 "캐시는 조회용, DB는 최종 판정"으로 틀려도 되는 곳과 안 되는 곳을 나눴던 것과 같은 구조다. 잔액 검증(이체 가능한지)은 쓰기 쪽 상태로, 화면에 보여주는 잔액은 읽기 쪽으로.

선택의 기로 (2단계)

- **잔액 저장 VS 이벤트 저장 후 잔액 계산** → 이벤트. 재현성이 요구사항이라 과거 시점을 다시 만들 수 있어야 한다. 대신 저장량이 계속 늘고, 재생 비용이 생긴다(→ 3단계에서 스냅샷으로 해결).
- **읽기/쓰기 같은 모델 VS CQRS** → CQRS. 읽기 패턴이 다양하고 쓰기 경로를 가볍게 유지해야 한다. 대신 읽기는 약간 늦다.

## 3단계 상세 설계

2단계 설계는 명령 큐로 Kafka, 상태 저장소로 원격 관계형 DB를 쓴다. 이체 한 번에 네트워크 왕복이 여러 번이다. 1M TPS를 내기엔 느리다.

### 고성능 이벤트 소싱

**1. 명령과 이벤트를 로컬 파일에**

Kafka 대신 상태 기계가 있는 노드의 로컬 디스크에 append-only 파일로 쓴다.

- 추가만 하니까 순차 쓰기다. HDD에서도 순차 쓰기는 빠르다.
- 최근 명령·이벤트는 mmap으로 메모리에 캐시해서 읽는다.

2주차 분산 메시지 큐에서 Kafka가 빠른 이유가 "디스크에 순차적으로 append만 한다"였는데, 그걸 Kafka 없이 직접 하는 셈이다. 네트워크 한 단계를 없앤다.

**2. 상태를 로컬 RocksDB에**

원격 관계형 DB 대신 로컬 RocksDB. LSM 트리라 쓰기에 최적화돼 있다. 6주차에서는 "한 번 쓰고 여러 번 읽는" 워크로드라 B+트리를 골랐는데, 여기는 잔액이 계속 바뀌는 쓰기 위주라 반대 선택을 한다. 같은 비교에서 워크로드에 따라 답이 바뀌는 게 재밌었다.

**3. 스냅샷**

이벤트가 쌓이면 처음부터 재생하는 데 너무 오래 걸린다. 그래서 주기적으로 상태를 통째로 저장한다(스냅샷). 스냅샷은 HDFS 같은 분산 저장소에 둔다. 6주차 객체 저장소를 써도 될 것 같다. 스냅샷도 한 번 쓰고 안 바뀌니까. 재생은 가장 최근 스냅샷부터 하면 된다.

책에 따르면 재무팀이 매일 00:00 기준 잔액을 검증하는 데에도 스냅샷을 쓴다고 한다. 성능 최적화이면서 동시에 감사 자료다.

### 신뢰할 수 있는 이벤트 소싱

이제 로컬 파일에 다 있으니 노드 하나가 죽으면 끝이다. 뭘 복제해야 할까? 데이터는 네 종류다: 명령, 이벤트, 상태, 스냅샷.

- 상태, 스냅샷 → 이벤트를 재생하면 다시 만들 수 있다.
- 명령 → ?
- 이벤트 → 유일한 진실.

그런데 명령도 재처리하면 같은 이벤트가 나오지 않나? 왜 이벤트만 지켜야 하지?

명령 → 이벤트 생성은 결정적이라는 보장이 없기 때문이다. 이벤트를 만들 때 난수나 현재 시각, 외부 I/O가 끼어들 수 있다. 같은 명령을 다시 처리해도 같은 이벤트가 나온다는 보장이 없다. 반면 이벤트 → 상태 적용은 결정적이어야 한다고 위에서 정했다. 그래서 **이벤트 목록만 높은 신뢰성으로 보존하면** 나머지는 다 복구된다.

-> 결정적인 부분과 아닌 부분의 경계에서 기록을 남긴다. 비결정적인 일이 한 번 일어나면 그 결과를 사실로 박제하고, 그 뒤로는 결정적인 계산만 한다.

이벤트 목록 복제는 Raft로 한다.

- 노드 3개 이상을 Raft 그룹으로 묶는다. 리더만 명령을 받는다.
- 리더가 명령을 검증해 이벤트를 만들고 자기 이벤트 목록에 추가하면, Raft가 팔로워에 복제한다. 과반이 받으면 확정.
- 모든 노드가 같은 이벤트 목록을 같은 순서로 적용하니 상태도 같아진다.
- 리더가 죽으면 새 리더를 뽑는다. 처리 중이던 요청은 클라이언트가 타임아웃 후 재시도한다. 멱등키(transaction_id)가 있으니 중복 처리되지 않는다.
- 팔로워가 죽으면 살아날 때까지 재시도하거나 새 노드로 교체한다.

6주차 배치 서비스를 Paxos/Raft로 묶었을 때는 "메타데이터 하나를 안 잃기 위해"였는데, 여기서는 핵심 데이터 자체를 Raft로 복제한다.

### 분산 이벤트 소싱

남은 문제 두 가지.

**1. CQRS는 비동기인데, 이체 요청한 사용자는 결과를 언제 아나?**

- 풀 모델: 클라이언트가 주기적으로 상태를 물어본다. 폴링이라 비효율적이고 느리다.
- 역방향 프록시를 둔다. 클라이언트는 프록시에 요청하고, 프록시가 명령을 보낸 뒤 결과를 기다려서 응답한다.
- 여기서 더 나아가 푸시 모델: 읽기 전용 상태 기계가 이벤트를 받자마자 결과를 프록시에 밀어준다. 사용자 입장에서는 동기 응답처럼 느껴진다.

**2. Raft 그룹 하나로는 1M TPS가 안 된다.**

그래서 다시 샤딩한다. 계좌 해시로 파티션을 나누고, 파티션마다 Raft 그룹 하나. 그러면 A와 C가 다른 파티션에 있을 때... 처음 문제로 돌아온다. 그래서 파티션 사이는 다시 TC/C나 Saga로 묶는다. 책의 최종 설계는 Saga(오케스트레이션)다.

A → C 1달러 이체 (A는 파티션 1, C는 파티션 2)

1. 사용자가 Saga 조정자에 이체 요청. 연산은 "A -1", "C +1" 두 개.
2. 조정자가 단계 상태 테이블에 레코드 생성.
3. 조정자가 순서를 확인하고 "A -1" 명령을 파티션 1에 보냄.
4. 파티션 1의 Raft 리더가 명령을 저장하고 검증 → 이벤트로 변환 → Raft로 복제 → 이벤트 적용 → 상태(잔액) 갱신.
5. 파티션 1의 이벤트가 CQRS로 읽기 경로에 동기화되고, 읽기 경로가 상태와 처리 결과를 만든다.
6. 읽기 경로가 결과를 조정자에 푸시.
7. 조정자가 성공을 단계 상태 테이블에 기록.
8. 조정자가 "C +1" 명령을 파티션 2에 보냄. 이후 4~7과 같은 과정.
9. 둘 다 성공하면 사용자에게 응답.

처음에 Redis 안에서 버린 "두 노드에 따로 쓰는 문제"가, 결국 마지막에도 파티션 간 Saga로 다시 나온다. 피할 수 없는 문제였고, 각 파티션 안을 이벤트 소싱 + Raft로 튼튼하게 만든 뒤 그 위에서 푼 것이다.

> 궁금했던 점. 그럼 Saga 조정자는 누가 지켜주나? 조정자가 죽으면 단계 상태 테이블로 복구한다는 건 알겠는데, 그 테이블은 어디에 있고 얼마나 안전한가?
> 
> -> 책에서 명확히 다루지 않는다. 내 생각에는 조정자도 결국 "이체 진행 상황"이라는 상태를 가진 상태 기계니까, 같은 방식(이벤트 소싱 + Raft)으로 만들 수 있을 것 같다. 세션에서 물어보고 싶다.

선택의 기로 (3단계)

- **Kafka + 원격 DB VS 로컬 파일 + 로컬 RocksDB** → 로컬. 네트워크 왕복을 없애야 1M TPS가 나온다. 대신 노드가 죽으면 데이터가 같이 죽으니 복제가 필요해진다.
- **명령 복제 VS 이벤트 복제** → 이벤트. 이벤트 적용만 결정적이라 이벤트만 있으면 나머지가 다 복구된다.
- **풀 VS 푸시** → 푸시. CQRS가 비동기여도 요청한 사용자는 빨리 결과를 받아야 한다.
- **단일 Raft 그룹 VS 파티션별 Raft 그룹 + Saga** → 파티션. 한 그룹으로는 처리량이 안 나온다. 대신 파티션 간 이체는 다시 분산 트랜잭션이 된다.

## Appendix. TC/C를 직접 짠다면

실제로 구현하면 어떤 모양일지 정리해봤다. (책 내용은 아님)

**단계 상태 테이블**

```sql
CREATE TABLE tcc_transaction (
    tx_id        VARCHAR(64) PRIMARY KEY,  -- 클라이언트의 transaction_id
    from_account BIGINT,
    to_account   BIGINT,
    amount       DECIMAL(19, 4),
    try_status   VARCHAR(16),  -- NOT_SENT / SENT / DONE / FAILED
    phase2       VARCHAR(16),  -- CONFIRM / CANCEL / NULL
    phase2_status VARCHAR(16),
    cancel_first BOOLEAN DEFAULT FALSE  -- out-of-order 플래그
);
```

**Try (A 계좌 DB에서)**

```sql
-- 1. Cancel이 먼저 왔었는지 확인. 왔으면 바로 실패
SELECT cancel_first FROM tcc_transaction WHERE tx_id = ?;

-- 2. 조건부 update로 잔액 차감 (5주차와 같은 방식)
UPDATE wallet SET balance = balance - :amount
WHERE account_id = :from AND balance >= :amount;
-- 영향받은 행이 0이면 잔액 부족 → 실패
```

1, 2와 tcc_transaction 갱신을 하나의 로컬 트랜잭션으로 묶는다. 하나의 DB 안이니 가능하다.

**Cancel**

```sql
-- Try 기록이 없으면 (빈 롤백) 되돌리지 않고 플래그만 남김
INSERT INTO tcc_transaction (tx_id, cancel_first) VALUES (?, TRUE)
ON CONFLICT (tx_id) DO NOTHING;

-- Try가 실행됐고 아직 Cancel 안 했으면 되돌림
UPDATE tcc_transaction SET phase2 = 'CANCEL', phase2_status = 'DONE'
WHERE tx_id = ? AND try_status = 'DONE' AND phase2 IS NULL;
-- 위 update가 1행이면 그때만 잔액 +amount
```

`phase2 IS NULL` 조건이 멱등성을 지킨다. Cancel이 두 번 와도 두 번째는 0행이라 잔액을 다시 돌려주지 않는다.

분산 트랜잭션 전체는 DB 하나가 못 지켜주지만, 쪼개진 각 단계는 로컬 트랜잭션이라 DB가 지켜준다.

## 정리

1. 계좌가 수천 개 노드에 흩어지면 이체 한 건은 항상 두 노드에 걸친다. 
2. 2PC는 락을 들고 기다리니 느리다. TC/C와 Saga는 각 단계를 바로 커밋하고, 실패하면 보상한다. 중간에 장부가 안 맞는 순간을 허용하는 대신 그 순간을 기록해서 추적한다.
3. 돈은 빼는 쪽을 먼저, 주는 쪽을 나중에. 되돌릴 수 있는 쪽을 먼저 한다.
   1. 보상과 재시도가 들어가는 순간 모든 단계는 멱등해야 한다. 순서가 뒤바뀐 요청까지 고려해야 한다.
4. 재현성은 결과가 아니라 사건을 저장해서 얻는다. 비결정적인 일은 이벤트로 박제하고, 그 뒤로는 결정적인 계산만 한다. 그래서 이벤트만 지키면 된다.
5. 빠르게 하려고 로컬로 내리면 복제(Raft)가 필요해지고, 크게 하려고 쪼개면 분산 트랜잭션(Saga)이 다시 필요해진다. 문제가 사라지는 게 아니라 층마다 다시 나타나서 그 층에서 푼다.
