### 주요 요구사항
- **내 친구들 중, 주변에 있는 친구의 위치를 알려주는 기능을 개발해주세요**
- **동접자 = 천만**
- **30초마다 나의 주변 친구 정보가 갱신돼야한다**
- **주변 친구 데이터는 그리 중요하지 않을수잇음. 그래서 어느정도의 유실은 허용한다**

-> 이 외에 보면 상당히 구체적으로 요구사항을 개략적으로 정하고 요구자로부터 동의받는걸 볼수있다. 내 관점에서 꽤나 요약햇지만 저것들 모두가 상당히 중요하다. 왜냐하면 실제 세상에선 요구사항을 말한 사람 마저도 자기가 뭘 요구하는지, 뭘 요구하지 않았는지를 잘 모르는 경우가 대부분이기 떄문이다.

그래서 이게 충분히 안되면 유용하지 않은, 문제를 풀지 못하는 보기 좋은 쓰레기를 만드는거뿐이다

### 가려져있는 챌린지
- 동접자수가 천만이고 30초마다 인간들 위치가 갱신돼야하면 초당 갱신수는 약 33만건이다
- 단순히 주변 사용자를 알고싶은게 아니라, 주변 사용자 중 내 친구 (혹은 내 친구 중 주변 사용자)를 얻어야한다
- 내 친구가 1000명이면 내 위치의 변화를 1000명에게 알려한다

### 문제 해결 아이디어의 후보
1. 중앙 서버 없이 p2p로 하자
	- 유저 개개인의 휴대폰 네트워크에 의존하자는 것은 여러모로 위험한 발상이다. 유저가 이 리스크를 책임질 이유가 없기에 이런 특성의 서비스에 넣을만한 아이디어는 아님

2. 중앙에 api 서버를 놓자
	- 1이 안되면 이거밖에 답이 없긴함
	- 하지만 단순한 3tier 아키텍쳐로 이거할려고하면 디비가 못버팀. 느리고, 무거움

3. 그러므로 중앙 api를 두되, 기본적 3tier를 넘어 캐싱서버와 메시지 브로커 등... **디비를 덜들르기 위한 수단**이 필요하다


### 솔루션 핵심 아이디어
1. 사용자별 갱신된 위치 정보를 메모리에 캐싱하자 (=레디스 캐싱)
	1. 단, 위치 변경 이력을 수집하라는 요구사항이 있었어서 동시에 디비에도 쓰긴 함.
	2. 캐싱의 이유는 읽기 빠르게하려고하는거임
2. 레디스 펍섭으로 내 위치 변경을 다른 친구들에게 알려주자
	1. 1인 1채널. 내 친구가 내 채널 구독하는 방식
3. 7계층 프로토콜을 http 말고 웹소켓을 쓰자
	1. http를 쓰면 주기적으로 client to server 폴링해서 데이터를 가져와야함. 내 친구가 1000명이면, 30초 갱신조건이기에 나혼자 초당 30번 http 요청 보내는거임
	2. 웹소켓은 연결 안끊기가 가능함
		1. 근데 오해하면 안되는게 http가 네트워크 연결을 라운드트립 한번돌면 아예 끊는건 아님. 4계층 연결(tcp)은 일정시간을 유지함
		2. 다만 http는 매번 통신 시 '완전한' http request/response를 만들어야함. 7계층 연결이 유지가 안됨
		3. 반면 웹소켓은 한번 연결되면 '대충 만든' 프레임만 주고받기가 가능함
	3. 이런 원리로 요청을 줘야 응답이 오는 http와 달리 웹소켓은 아주 단순한 서버 to client 프레임 전송이 가능함. 이것도 큰 이점


###  그러면 레디스는 무적이라는건가
- 레디스가 빠른 이유는 디스크 안쓰고 메모리만 써서, 그리고 레디스서버에 말걸때 7계층 프로토콜을 http 가 아닌 resp라는 레디스 전용 프로토콜을 쓰게되는데 이게 http에 비해 상당히 빠르다고 하네요

- 서버의 스펙을 이루는건 주~로 cpu/ram 이다. 레디스가 빠른건 알겟는데 얘가 cpu/ram 리소스를 덜쓰냐는 다른 문제임. (알고리즘 수업에서 주로 말하는 시간복잡도/공간복잡도랑 비슷한 얘기....)

- 램은 병목이 아니다
	- 첨엔 램을 저장소로 쓰니깐 램 많이쓸줄 알았는데 레디스가 key-value 스토리지이기도하고, 지금 이 기능에서 레디스 스토리지는 '사용자별 최신 1건'의 데이터만 저장하기에 애초에 규모에 비해 데이터가 많지 않음. 모든 데이터쌓는 rdb와 비교할게 아니엇음.

- cpu+nio가 병목이다
	- 책엔 nio 설명이 없는데, 일단 서버에서 클라이언트로 연결을 하면 nio를 거쳐 간다
	- 이 nio 하드웨어가 책에서 말한 '네트워크 카드'이고 네트워크 카드를 보수적으로 봤을 때 현대 고성능 서버 컴퓨터에 10만개 있다는거임.
	- 예상값인 펍섭서버->구독자 데이터 전송이 초당 1400 만개이고 1400만/10만 해서 레디스 펍섭 서버가 140대라는거임
	
- 결론은 레디스 펍섭 서버가 여러개가 잇어야한단거임


### 펍섭을 위해 140개 레디스 펍섭 서버 분산이 필요하다
- (레디스 캐싱서버도 분산 시에도 얘랑 개념적으론 비슷할듯)
- 핵심 아이디어
	- 웹소켓마다 자기 메모리에 해시링을 둔다
	- 그 해시링은 해시 리스트 자료구조라고 생각하면 된다. 여기서쓰는 해싱함수는 이거임:
		- input = 내가 찾고자하는 채널 (사람 이름이겠죠)
		- output = 그 채널이 속한 펍섭 서버
	- 당연하게 펍섭서버는 stateful 서버다. 상태 관리가 필요함.
	- 이걸 위해 서비스 디스커버리 컴포넌트를 만든다
		- 쓰는 기능이 두개임
			1. 현재 레디스펍섭 서버 뭐가 있나 (읽는 기능)
			2. 펍섭 서버 현황이 바뀌엇나(서버 x가 죽엇나, 추가됏나를 watch하는 기능임. 또다른 펍섭 개념)
		 - 그니깐 이 두번째의 와치 기능이 핵심인데, 레디스 서버는 계속 죽고 새로 살아날거임. 이걸 감지하는게 필요해서 서비스 디스커버리를 쓰는거임. ** 그 툴이 주로 etcd, zookeper
	- 물론 이건 방법에 대한 것이지, 안정적인 장치는 아님. 해시링 갱신 해야할떄 엄청난 수의 리딩, 재구독이 발생해서 저자는 고의적으로 변경할거면 새벽에 하라네요



### 친구가 많은 유저에 대해서 펍섭 서버가 핫스팟 이슈를 겪진 않을까요?
- 책에선 소켓서버, 펍섭서버 모두 분산되어있어서 안전하다고 하는데..
- 이런 문제가 있을거같다고 생각햇어요. 
	- **내 정보를 1000명의 친구들에게 전달해주는 경우**
		- 펍섭 서버가 1000개의 데이터를 적절히 분산된 웹소켓 서버들에 전송한다
		- 내 채널은 하나의 펍섭 서버에만 있었을테니(하나의 유저 채널을 분산하진 않으니깐) 펍섭 서버가 부하를 겪는다
	- 1000명의 친구들의 정보가 동시에 내 휴대폰에 전달되는 경우
		- 여러개의 적절히 분산된 펍섭 서버가 1000개의 데이터를 하나의 웹소켓 서버로 전송한다
		- 위 사례와 비슷하게 내 폰이랑 연결된 웹소켓서버는 하나일테니깐. 웹소켓 서버가 부하를 겪는다
	- 이 내용이 책엔 없는거같은데 저자님은 그냥... 최대 5000명 까지만 친구할수잇으니깐 아무튼 괜찮다 하신듯
