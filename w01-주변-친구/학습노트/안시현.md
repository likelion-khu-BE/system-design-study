
# 앱 사용자 가운데 본인 위치 정보 접근 권한을 허락한 사용자에 한해 인근의 친구 목록을 보여주는 시스템

### 기능 요구 사항

- 사용자는 모바일 앱에서 주변 친구를 확인할 수 있어야 한다. 주변 친구 목록에 보이는 각 항목에는 해당 친구까지의 거리, 그리고 해당 정보가 마지막으로 갱신된 시각이 함께 표시되어야 한다.
- 이 친구 목록은 몇 초마다 한 번씩 갱신되어야 한다.

### 비기능 요구 사항

- 낮은 지연 시간 : 주변 친구의 위치 변화가 반영되는데 너무 오랜 시간이 걸리지 않아야 한다.
- 안정성 : 시스템은 전반적으로 안정적이어야 하지만, 때로 몇 개 데이터가 유실되는 것 정도는 용인할 수 있다.
- 결과적 일관성 : 위치 데이터를 저장하기 위해 강한 일관성을 지원하는 데이터 저장소를 사용할 필요는 없다.

### 개략적 규모 추정

- ‘주변 친구’는 5마일 반경 이내 친구로 정의한다.
- 친구 위치 정보는 30초 주기로 갱신한다.
    - 사람이 거든 속도가 시간당 4~6km/h 정도로 느리기 때문이다.
- 평균적으로 매일 주변 친구 검색 기능을 활용하는 사용자는 1억명으로 가정한다.
- 동시 접속 사용자의 수는 DAU 수의 10%로 가정 → 천만명이 동시에 시스템 이용한다고 가정
- 평균적으로 400명의 친구를 갖는다는 가정

### 소규모 백엔드 설계안

- 로드 밸런서
    - RESTful API 서버 및 양방향 유상태 웹소켓 서버 앞단에 위치 → 부하 고르게 분산하기 위해 트래픽 서버에 배분
- RESTful API 서버
    - 무상태 API 서버의 클러스터로서, 통상적인 요청/응답 트래픽 처리
- 웹소켓 서버
    - 실시간에 가깝게 처리하는 유상태 서버 클러스터
    - 각 클라이언트는 그 가운데 한 대와 웹소켓 연결을 지속적으로 유지
- 레디스 위치 정보 캐시
    - 레디스는 활성 상태 사용자의 가장 최근 위치 정보를 캐시하는데 사용
    - TTL 필드를 통해 기간이 지나면 비활성 상태로 바뀌고 캐시에서 삭제
- 사용자 DB / 위치 이동 이력 DB
    - 생략
- 레디스 펍/섭 서버
    - 초경량 메시지 버스
    - 웹 소켓 서버를 통해 수신한 특정 사용자의 위치 정보 변경 이벤트는 해당 사용자에게 배정된 펍/섭 채널에 발행
    - 사용자의 친구 각각과 연결된 웹소켓 연결 핸들러는 해당 채널의 구독자로 설정되어있다

---

### 주기적 위치 갱신

모바일 클라이언트가 위치 변경된 사실을 로드 밸런서에 전송 → 그 위치 변경 내역을 클라이언트와 웹소켓 서버 사이에 설정된 연결을 통해 웹소켓 서버로

웹소켓 서버는 해당 이벤트를 위치 이동 이력 DB에 저장

웹소켓 서버는 새 위치를 위치 정보 캐시에 보관 (TTL 갱신), 웹소켓 연결 핸들러 안의 변수에 해당 위치 반영

웹소켓 서버는 레디스 펍/섭 서버의 해당 사용자 채널에 새 위치를 발행

레디스 펍/섭 채널에 발행된 새로운 위치 변경 이벤트는 모든 구독자에게 브로드 캐스트된다. 

메시지를 받은 웹소켓 서버는 새 위치를 보낸 사용자와 메시지를 받은 사용자 사이의 거리를 새로 계산한다.

---

### 위치 정보 저장에 데이터베이스를 사용하지 않는 이유는?

‘주변 친구’ 기능은 사용자의 현재 위치만을 이용한다. → 사용자 위치는 하나만 보관하면 충분, 영속성 보장할 필요 x

레디스 : 읽기 및 쓰기 연산 속도가 엄청나게 빠름 / TTL 지원 <<< 이란 특성이 맞아서 레디스 사용

---

### 클라이어트 초기화

모바일 클라이언트는 기동되면 웹소켓 클러스터 내의 서버 가운데 하나와 지속성 웹소켓 연결을 맺는다. ‘지속성 연결’이라 한 이유는 연결이 오랜 시간 유지되기 떄문

웹 소켓 연결이 초기화되면 클라이언트는 해당 모바일 단말의 위치, 즉 해당 단말을 이용 중인 사용자의 위치 정보를 전송한다.

# 내가 몰랐던 개념들

## 1. 항구적(지속적) 통신 상태

연결을 매번 새로 맺지 않고 계속 유지하는 방식.

- 연결 유지(Keep-Alive) + 주기적 하트비트
- 세션 정보(주소, 키 등) 보존 → 재핸드셰이크 불필요
- NAT/방화벽 통과 상태(포트 매핑) 유지 필요
- 장점: 지연시간 감소 → 실시간 서비스에 유리
- 단점: 연결 상태 유지로 인한 자원 소모, 확장성 이슈

---

## 2. Cassandra & 샤딩(Sharding)

### Cassandra

- Masterless P2P 구조 (모든 노드 동등)
- CAP 이론상 **AP** 지향 (최종적 일관성)
- Wide Column Store 모델
- 선형 확장성, 대용량 쓰기에 강점

### 샤딩(Sharding)

큰 데이터베이스를 여러 서버에 분산 저장하는 기법.

| 방식 | 설명 |
| --- | --- |
| 범위 기반 | 값의 범위로 분할 |
| 해시 기반 | 해시 함수로 균등 분산 |
| 디렉토리 기반 | 별도 매핑 테이블로 관리 |

Cassandra는 **Consistent Hashing** + **Virtual Node(vnode)**로 파티셔닝 구현.

## 3. etcd vs ZooKeeper

| 구분 | etcd | ZooKeeper |
| --- | --- | --- |
| 언어 | Go | Java |
| 합의 알고리즘 | Raft | ZAB |
| 데이터 모델 | 단순 Key-Value | 트리 구조(znode) |
| 주요 사용처 | Kubernetes | Kafka(구버전), Hadoop |
| CAP | CP | CP |
- 공통점: 강한 일관성, 리더 선출, 분산 락, Watch 메커니즘 지원
- etcd의 Lease(TTL), ZooKeeper의 Ephemeral znode → 둘 다 장애 감지에 활용

---

## 4. 해시 링 (Consistent Hashing)

노드 추가/제거 시 재배치 비용을 최소화하기 위한 분산 알고리즘.

- 해시 공간을 원형(Ring)으로 배치
- 노드와 키를 동일한 해시 함수로 매핑
- 각 키는 **시계방향으로 가장 가까운 노드**가 담당
- 노드 증감 시 **일부 키만** 재배치됨 (전체 재해싱 불필요)
- **Virtual Node**로 데이터 분산을 균등화
- 활용: Cassandra, DynamoDB, Memcached 클라이언트 등

---

## 5. 서비스 탐색 (Service Discovery)

마이크로서비스 환경에서 인스턴스의 네트워크 위치를 동적으로 찾는 메커니즘.

### 두 가지 방식

| 구분 | 클라이언트 사이드 | 서버 사이드 |
| --- | --- | --- |
| 동작 | 클라이언트가 직접 레지스트리 조회+로드밸런싱 | 로드밸런서가 레지스트리 조회 대행 |
| 예시 | Eureka + Ribbon | AWS ELB, Kubernetes Service |

### 등록 방식

- 자가 등록(Self-Registration): 인스턴스가 스스로 등록/하트비트
- 3rd Party 등록: 별도 에이전트가 감시 후 등록/해제

### 대표 구현체

- Consul (Raft 기반, KV+헬스체크 통합)
- Eureka (AP 모델, Netflix)
- etcd + CoreDNS (Kubernetes 기반)
- Kubernetes Service (kube-proxy가 iptables/IPVS로 라우팅)
- ZooKeeper (Kafka 구버전 등)
