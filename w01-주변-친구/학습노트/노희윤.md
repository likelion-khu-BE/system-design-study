## 주변 친구 시스템

앱 사용자 가운데 본인 위치 정보 접근 권한을 허락한 사용자에 한해 인근의 친구 목록을 보여주는 시스템

### 요구사항

#### 기능

1. 주변 친구를 확인할 수 있어야 함
2. 해당 친구까지의 거리, 해당 정보가 마지막으로 갱신된 시각도 함께 표시되어야 함
3. 이것은 몇 초마다 한 번씩 갱신되어야 함

#### 비기능

1. 낮은 지연 시간
2. 안정성
3. 결과적 일관성

## 설계 구조

### RESTful API 서버

- API 서버란? HTTP 요청-응답 처리가 중심인 서버이다. HTTP는 먼저 클라이언트의 요청이 있어야 서버의 응답이 오는 구조기 때문에 사용자의 위치가 계속 바뀌고 이를 polling 해야 하는 위치 공유 서비스에서는 적절하지 않다.
- RESTful API 서버란? 무상태 API 서버로 서버가 이전 요청의 상태를 꼭 기억하고 있어야 하는 방식이 아니라, 각 요청에 필요한 정보를 담아서 보내는 구조이다. 통상적인 요청/응답 트래픽을 처리한다.
- 주변 친구 시스템에서 이 서버는 사용자 관리/친구 관리/인증 및 기타 기능을 처리하는 부가적인 작업을 하도록 설계한다.

### WebSocket 서버

- WebSocket이란? 클라이언트와 서버가 연결을 계속 유지하면서 양방향으로 실시간 통신하는 방식으로 클라이언트와 서버 둘 다 원할 때 먼저 메시지를 보낼 수 있다. 따라서 위치 정보를 실시간으로 계속 공유해야 하는 본 시스템에서 사용하기에 적절하다.
- WebSocket 서버란? 연결을 계속 유지하는 유상태 서버 클러스터이다.
- 주변 친구 시스템에서 이 서버는 클라이언트의 초기화, 거리 계산 등 메인 기능을 처리하도록 설계한다.

### 로드밸런서

- 들어오는 요청을 여러 서버에 나눠주는 장치로 서버의 부하를 낮출 뿐만 아니라 요청 종류에 따라 다른 서버군으로 라우팅하는 역할을 한다.
- 본 시스템에서는 RESTful API 서버와 WebSocket 서버 앞단에 위치하여 트래픽을 서버들에 배분하는 역할을 하도록 설계한다.

### Redis 위치 정보 캐시

- Redis란? 인메모리 key-value 저장소로 속도가 매우 빠르고 TTL을 이용하여 “n분 뒤 자동 삭제” 같은 걸 쉽게 걸 수 있다.
- TTL은 Time To Live, 데이터가 살아 있는 시간을 의미한다.
- 본 시스템에서는 지속적으로 갱신되어야 하는 사용자의 위치 정보를 저장할 캐시로 활용한다. ‘주변 친구’ 기능은 사용자의 현재 위치만을 저장하므로 데이터베이스보다 Redis가 적합하다.
- 해당 캐시에는 `(사용자 ID, {위도, 경도, 시각})`의 키/값 쌍이 저장된다.

### Redis Pub/Sub 서버

- 메시지를 발행하고 구독하는 통신 방식(Publish-Subscribe)이며 새로운 채널을 생성하는 것이 아주 값싼 연산이다.
- 본 시스템에서는 Redis Pub/Sub 서버를 모든 온라인 친구에게 보내는 위치 변경 내역 메시지의 라우팅 계층으로 활용한다.
- 예를 들어 사용자(A)의 친구(B)와 연결된 웹소켓 연결 핸들러가 사용자(A)의 채널 구독자로 설정되어, 특정 사용자의 위치가 바뀌면 B를 포함한 해당 사용자의 모든 친구의 웹소켓 연결 핸들러가 호출된다.

```text
B의 폰  <======== WebSocket 연결 ========>  WS 서버 3
                                             │
                                             └─ B 연결을 처리하는 handler
                                                (Redis의 A 전용 채널 구독)
```

- 이때, 친구의 활성화 여부와 관계없이 모든 친구의 채널을 구독한다. 비활성 친구의 재활성화를 즉시 반영하기 어렵고, 채널 및 구독 관계 생성 비용이 매우 작기 때문이다.

### 위치 이동 이력 데이터베이스

- 사용자의 위치 변동 이력을 `(user_id, latitude, longitude, timestamp)` 형식으로 보관한다.
- 막대한 쓰기 연산 부하를 감당할 수 있어야 하기 때문에 Cassandra나 관계형 데이터베이스 + 샤딩 조합을 이용한다.
  - Cassandra(카산드라)란? 대규모 분산 환경에서 쓰는 NoSQL 데이터베이스로 여러 서버에 데이터를 나눠서 저장한다. 또한, 일부 서버가 죽어도 계속 서비스를 할 수 있다는 게 장점이다.
  - Sharding(샤딩)이란? 데이터가 너무 많아서 DB 한 대에 다 넣기 힘들 때, 데이터를 여러 DB 서버로 나눠 저장하는 방식이다. 각각의 데이터 묶음/서버 단위는 shard(샤드)라고 한다.

### 사용자 데이터베이스

- 사용자 데이터 및 사용자의 친구 관계를 저장한다.
- 관계형 데이터베이스나 NoSQL 중 어느 쪽이든 사용 가능하다.

## 시스템 작동 플로우 - 주기적 위치 갱신

1. 모바일 클라이언트가 위치가 변경된 사실을 로드밸런서에 전송
2. 로드밸런서는 위치 변경 내역을 WebSocket 서버로 전송
3. WebSocket 서버는
   - 해당 이벤트를 위치 이동 이력 데이터베이스에 저장
   - 새 위치를 위치 정보 캐시에 보관, TTL 갱신
   - Redis Pub/Sub 서버의 해당 사용자 채널에 새 위치 발행
4. Redis Pub/Sub 채널에 발행된 새로운 위치 변경 이벤트는 모든 구독된 웹소켓 이벤트 핸들러에게 브로드캐스트됨
5. 메시지를 받은 WebSocket 서버는 새 위치를 보낸 사용자와 메시지를 받은 사용자 사이의 거리를 새로 계산

## 분산 Redis Pub/Sub 서버 클러스터

Redis Pub/Sub 서버 한 대로 모든 채널과 구독자를 감당할 수는 없으니, 여러 Redis 서버에 채널을 나눠서 샤딩한다.

```text
Redis Pub/Sub 클러스터

Redis 1
├─ user:1
├─ user:4
└─ user:7

Redis 2
├─ user:2
├─ user:5
└─ user:8

Redis 3
├─ user:3
├─ user:6
└─ user:9
```

본 설계에서는 서비스 탐색 컴포넌트를 도입하여 분산 Redis Pub/Sub 서버 클러스터에서 특정 채널을 담당하는 Redis 서버를 탐색하는 문제를 해결했다.

### 서비스 탐색 컴포넌트

- 서비스 탐색 컴포넌트란? 분산 시스템에서 서비스들의 현재 위치(IP/포트)와 생존 상태를 관리하고 찾아주는 기능이다.
- 해당 설계에서 서비스 탐색 컴포넌트는 가용한 Redis 서버 목록 관리 + 서버 목록 변경 알림을 담당한다.

서비스 탐색 컴포넌트는 안정 해시 기반의 해시 링 정보를 관리하며, WebSocket 서버는 이를 참조해 각 사용자 채널을 담당할 Redis Pub/Sub 서버를 결정한다.

### 안정 해시에 대해

#### 일반 해시

- 일반적으로 modulo 기반 해시를 의미한다.
- 각 key에 대해 해시값을 구한 뒤 `hash(key) % n`으로 n개 서버 중 하나를 고르는 구조이다.
- 서버가 n → n+1대로 바뀌면 공식이 `hash(key) % (n+1)`로 바뀌면서 대부분의 key가 다른 서버로 재배치되어 많은 채널의 담당 서버와 구독 관계를 다시 설정해야 할 수 있다.

#### 안정 해시

- 서버가 추가되거나 빠질 때 데이터의 재배치를 최소화하는 해싱 방식을 의미한다.
- 서버와 key를 해시 링 위에 배치하고, key는 보통 시계 방향으로 가장 가까운 서버에 할당한다.
- 서버가 추가되어도 추가된 서버 근처에 있던 일부 key만 신규 서버로 이동하고, 나머지는 그대로 유지되어 안정적이다.

#### 본 시스템에서의 적용

- 예를 들어 A의 위치가 갱신돼서 그 위치 변경 메시지를 A 전용 Redis Pub/Sub 채널에 publish하려고 할 때, 그 채널이 어느 Redis 서버에 있는지 찾아야 한다.
- 매번 서비스 탐색 컴포넌트에 가서 최신 해시 링 정보를 조회하면 느릴 수 있기 때문에 WS 서버 내부에 해시 링의 로컬 사본을 캐시할 수 있다.

```text
            서비스 탐색 컴포넌트
            [해시 링 원본]
                  │
          변경사항 subscribe/watch
            ┌─────┴─────┐
            ↓           ↓
       WS 서버 1     WS 서버 2
      [링 사본]      [링 사본]
```
