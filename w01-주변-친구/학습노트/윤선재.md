# 2장 주변 친구

이번 장은 주변에 있는 친구 위치를 실시간에 가깝게 보여주는 기능을 어떻게 대규모로 설계할지 다룸. 처음에는 그냥 친구 위치를 DB에 저장하고 조회하면 되는 문제처럼 보이는데, 사용자가 많아지면 핵심은 저장보다 **위치 변경을 얼마나 빠르게 많은 사람에게 전달할 수 있느냐**가 됨.

책에서는 DAU 1억 명, 동시 접속자는 1,000만 명 정도로 가정함. 사용자가 30초마다 위치를 보내면 초당 약 33만 건의 위치 갱신이 발생함.

```text
10,000,000 / 30 ≒ 334,000 QPS
```

근데 실제 문제는 여기서 끝이 아님. 한 사용자의 위치가 바뀌면 그 사용자의 온라인 친구들에게 다시 위치 변경을 전달해야 함. 평균 친구 수를 400명, 그중 10%가 온라인이라고 보면 한 번의 위치 변경이 약 40명에게 전파될 수 있음. 그래서 내부적으로는 초당 1,400만 건 정도의 메시지가 발생할 수 있음. 이걸 보면서 단순히 외부 QPS만 계산하는 게 아니라 **한 요청이 내부에서 얼마나 증폭되는지도 봐야 한다는 점**이 중요하다고 느낌.

전체 구조는 일반적인 요청은 REST API 서버가 처리하고, 위치 변경처럼 실시간으로 전달해야 하는 부분은 WebSocket 서버가 담당하는 식임.

```text
클라이언트
 ├─ HTTP → API 서버 → 사용자/친구 DB
 └─ WebSocket → WebSocket 서버
                  ├─ 위치 캐시
                  ├─ 위치 이력 DB
                  └─ Redis Pub/Sub
```

WebSocket을 쓰는 이유는 서버가 클라이언트에게 먼저 위치 변경을 전달해야 하기 때문임. HTTP polling으로 하면 클라이언트가 계속 "친구 위치 바뀌었음?" 하고 요청해야 해서 사용자 수가 많을수록 낭비가 커짐. WebSocket은 연결을 계속 유지하고 있으니까 친구 위치가 바뀌는 순간 서버가 바로 전달할 수 있음.

위치 데이터도 한 군데에 다 저장하지 않음. **현재 위치**는 최신 값 하나만 빠르게 읽으면 되고, 조금 유실돼도 30초 뒤에 다시 들어오므로 Redis 같은 캐시에 저장함. 반대로 **위치 이력**은 과거 값이 계속 쌓이므로 별도 DB에 저장함. 같은 위치 데이터라도 사용 방식이 달라서 저장소가 나뉘는 게 인상적이었음.

위치 갱신 흐름은 대충 다음과 같음.

```text
사용자 위치 변경
→ WebSocket 서버가 받음
→ Redis에 최신 위치 저장
→ 위치 이력 DB에도 저장
→ 해당 사용자 Pub/Sub 채널에 publish
→ 친구들이 연결된 WebSocket 서버가 이벤트 수신
→ 거리 계산
→ 반경 안에 있으면 친구 화면에 전달
```

여기서 Redis 캐시와 Pub/Sub 역할이 다름. 캐시는 **현재 위치 값 자체를 저장**하고, Pub/Sub는 **위치가 바뀌었다는 사실을 전달**함. 그래서 사용자가 앱을 처음 켰을 때는 먼저 캐시에서 친구들의 현재 위치를 읽고, 그 이후부터 Pub/Sub로 변경 내용을 받는 구조가 됨. Pub/Sub만 쓰면 앱을 켠 순간 친구가 움직이지 않는 경우 아무 위치도 못 받을 수 있기 때문임.

규모가 커지면 Redis Pub/Sub 서버도 여러 대가 필요함. 그러면 특정 사용자 채널이 어느 Pub/Sub 서버에 있는지 정해야 함. 여기서 안정 해시(consistent hashing)를 사용함. 단순히 `hash % 서버 수`로 나누면 서버가 추가되거나 빠질 때 대부분의 매핑이 바뀌는데, 안정 해시는 일부 구간만 바뀌도록 해서 재배치를 줄여줌.

그리고 현재 어떤 Pub/Sub 서버들이 살아 있는지 알아야 하니까 서비스 디스커버리가 필요함. etcd나 ZooKeeper 같은 시스템이 서버 목록을 관리하고, WebSocket 서버는 그 정보를 이용해 해시 링을 갱신함.

WebSocket 서버는 유상태 서버라는 점도 중요했음. 사용자와 연결이 계속 유지되고 어떤 채널을 구독 중인지 상태를 가지고 있기 때문임. 그래서 서버를 바로 꺼버리면 연결된 사용자들이 전부 끊김. 실제 운영에서는 신규 연결을 막고 기존 연결이 끝날 때까지 기다리는 draining 과정이 필요함.

친구 추가/삭제도 DB만 바꾸면 끝이 아님. 이미 열려 있는 WebSocket 연결에서도 새 친구 채널을 구독하거나 기존 채널 구독을 해제해야 함. 실시간 시스템에서는 저장된 데이터와 현재 연결 상태를 같이 생각해야 한다는 점이 보였음.

또 요구사항이 "내 친구 중 주변 사람"이 아니라 "내 주변의 모든 사람"으로 바뀌면 설계 방식도 달라짐. 이때는 친구 관계를 이용할 수 없으니 geohash로 지도를 격자로 나누고, 주변 격자의 Pub/Sub 채널을 구독하는 방식으로 바꿀 수 있음.

이번 장에서 제일 기억에 남은 건 기술 이름보다 **왜 그 기술이 필요해졌는지 흐름을 따라가는 게 중요하다는 점**이었음.

```text
실시간 위치 전달 필요
→ WebSocket

최신 위치 빠르게 조회
→ Redis 캐시

위치 변경을 여러 친구에게 전달
→ Pub/Sub

Pub/Sub 서버가 많아짐
→ 안정 해시

서버 목록이 계속 바뀜
→ 서비스 디스커버리
```

그리고 시스템 설계할 때는 모든 데이터에 같은 수준의 일관성과 내구성을 요구할 필요가 없고, 데이터 성격에 따라 다르게 설계해야 한다는 것도 이해됐음.

## 궁금한 점

Pub/Sub 서버가 죽거나 증설돼서 해시 링이 바뀌면 많은 채널을 다시 구독해야 하는데, 실제 서비스에서는 이 재구독 과정에서 메시지 유실을 얼마나 허용하는지 궁금함.

또 친구 수가 평균 400명이라고 해도 친구가 수천 명인 사용자는 특정 Pub/Sub 서버에 순간적으로 큰 부하를 줄 수 있을 것 같은데, 이런 핫스팟을 실제로는 어떤 식으로 완화하는지도 궁금함.
