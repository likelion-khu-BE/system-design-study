# 2장 주변 친구

이번 장은 주변에 있는 친구 위치를 실시간에 가깝게 보여주는 기능을 어떻게 대규모로 설계할지 다룸. 처음에는 그냥 친구 위치를 DB에 저장하고 조회하면 되는 문제처럼 보이는데, 사용자가 많아지면 핵심은 저장보다 **위치 변경을 얼마나 빠르게 많은 사람에게 전달할 수 있느냐**가 됨.

책에서는 DAU 1억 명, 동시 접속자는 1,000만 명 정도로 가정함. 사용자가 30초마다 위치를 보내면 초당 약 33만 건의 위치 갱신이 발생함.

개많은듯, 이렇게 요청?, 갱신이 많아지면 일반적인 api 서버라 했을 때 감당이 가능할까? 아닌듯

책에서의 전체 구조는 일반적인 요청은 REST API 서버가 처리하고, 위치 변경처럼 실시간으로 전달해야 하는 부분은 WebSocket 서버가 담당하는 식으로 구성되어 있당


WebSocket을 쓰는 이유는 서버가 클라이언트에게 먼저 위치 변경을 전달해야 하기 때문임. 일반적인 http restful stateless방식으로 하면 클라이언트 요청 -> 서버 응답 -> 연결 해제 - 이런 식으로 가야해서 엄청 많은 갱신이 일어나는 이 상황에선 적합하지 않음. 
또 만약 polling으로 하면 클라이언트가 계속 "친구 위치 바뀌었음?" 하고 요청해야 해서 사용자 수가 많을수록 낭비가 커짐. 
WebSocket은 연결을 계속 유지하고 있으니까(stateful) 친구 위치가 바뀌는 순간 서버가 바로 전달할 수 있음.

여기선 위치 데이터도 한 군데에 다 저장하지 않는다. 
**현재 위치**는 최신 값 하나만 빠르게 읽으면 되고, 조금 유실되어도 ㄱㅊ은 데이터라 보고 Redis 같은 캐시에 저장함. 
반대로 **위치 이력**은 과거 값이 계속 쌓이므로 별도 DB에 저장함. 얘는 유실 되면 안되는 데이터라 보고 db에 저장하는 것 같다. 같은 위치 데이터라도 사용 방식이 달라서 저장소가 나뉘는 게 인상적이었음.

위치 갱신 흐름은 대충 다음과 같다.

```text
사용자 위치 변경
→ WebSocket 서버가 받음
→ Redis에 최신 위치 저장
→ 위치 이력 DB에도 저장
→ 해당 사용자 Pub/Sub 채널에 publish
→ 친구들이 연결된 WebSocket 서버가 이벤트 수신
→ 거리 계산
→ 반경 안에 있으면 친구 화면에 전달
```

여기서 Redis 캐시와 Pub/Sub 역할이 다르다. 캐시는 **현재 위치 값 자체를 저장**하고, Pub/Sub는 **위치가 바뀌었다는 사실을 전달**한다. 그래서 사용자가 앱을 처음 켰을 때는 먼저 캐시에서 친구들의 현재 위치를 읽고, 그 이후부터 Pub/Sub로 변경 내용을 받는 구조가 됨. Pub/Sub만 쓰면 앱을 켠 순간 친구가 움직이지 않는 경우 아무 위치도 못 받을 수 있기 때문임.

규모가 커지면 Redis Pub/Sub 서버도 여러 대가 필요하다. 그러면 특정 사용자 채널이 어느 Pub/Sub 서버에 있는지 정해야 함. 여기서 안정 해시를 사용하게 됨. 이 부분은 다 이해를 못 했는데 그냥 해시 써서 이름 잘 붙여준다? 정도로 이해하고 넘어감

WebSocket 서버는 stateful 서버라는 점도 중요하다. 사용자와 연결이 계속 유지되고 어떤 채널을 구독 중인지 상태를 가지고 있다=stateful. 그래서 서버를 바로 꺼버리면 연결된 사용자들이 전부 끊긴다. 실제 운영에서는 신규 연결을 막고 기존 연결이 끝날 때까지 기다리는 draining 과정이 필요하다고 하네요.

친구 추가/삭제도 DB만 바꾸면 끝이 아니다. websocket 서버 연결도 되어 있기 때문에 웹소켓 연결을 확인하고 펍섭 연결을 어케 잘 바꿔줘야 함. 실시간 시스템에서는 저장된 데이터와 현재 연결 상태를 같이 생각해야 한다는 점이 인상깊엇음.

또 요구사항이 "내 친구 중 주변 사람"이 아니라 "내 주변의 모든 사람"으로 바뀌면 설계 방식도 달라진다고 나옴. 이때는 친구 관계를 이용할 수 없으니 geohash로 지도를 격자로 나누고, 주변 격자의 Pub/Sub 채널을 구독하는 방식으로 바꿀 수 있다는데 어려워서 이해가 잘 안간다.. 그냥 그렇다네요

이 책을 처음 읽으면서 제일 좋았던 점, 도움 되는 점은 기술 이름을 스킬 쓰듯이 레디스 썼다, 카프가 썼다 와--하는 것 보다 왜 그 기술이 필요해졌는지 질문 하면서 답해가는 흐름이 좋았던 것 같다. 백엔드 개발자란 이렇게 사고하는구나라고 생각이 들어 재밌었다

```text
실시간 위치 전달 필요
→ WebSocket

최신 위치 빠르게 조회
→ Redis 캐시

위치 변경을 여러 친구에게 전달
→ Pub/Sub

Pub/Sub 서버가 많아짐
→ 안정 해시

서버 목록이 계속 바뀜
→ 서비스 디스커버리
```

그리고 시스템 설계할 때는 모든 데이터에 같은 수준의 일관성과 내구성을 요구할 필요가 없고, 데이터 성격에 따라(얘는 유실 되어도 ㄱㅊ은지 아닌지 등등) 다르게 설계해야 한다는 것도 사고를 확장시켜준 느낌이라 좋앗음.

## 질문거리 추가

1. WebSocket이 무조건 polling보다 좋은 건가?
 여기서는 실시간성이 중요해서 WebSocket을 썼는데, 만약 한 1분정도 간격으로 친구의 위치를 알아야 하는 서비스라면? polling이 더 비용이 싸지 않을까? 라는 생각이 들었다. 이럴 때 어떤 걸 기준으로 선택해야 할까?
 -> 웹소켓은 보통 채팅같이 실시간성이 굉장히 중요한 서비스에서 사용함, 근데 연결, 구독, 발행 해줘야 하고 상태도 보존해야 하고 클라이언트가 많아지면(많아지는게 클라이언트가 맞나?) 웹소켓 서버도 많아져야 하고 쨋든 비용이 풀링보다 많아질거라서 이렇게 실시간성이 중요한 채팅, 친구 위치 받아서 계속 확인하는 걸 해주고 싶은 페이스북 같은 서비스 말고는 http polling 쓰는 게 더 좋을 듯하다.

2. 웹소켓 서버가 죽으면 연결된 사용자들은 어떻게 되는가?
 웹소켓 서버는 stateful이라서 서버 하나가 죽으면 그 서버에 붙어 있던 사람들의 연결도 같이 끊길 텐데, 이 때 어떻게 되는 걸까? 
 로드밸런서가 웹소켓 서버를 하나 새로 찾음 -> db에서 친구 관계 조회 -> 레디스 캐시에서 최신 친구 위치 조회 -> 필요한 pub/sub 다시함 이렇게 하는건가? 

3. 친구 추가/삭제가 DB에는 반영됐는데 WebSocket 쪽에는 반영이 안 되는 상황은 어떻게 막을까?
DB를 쓰다가 일관성이 안 맞는 거랑 비슷하게, 친구 관계 DB와 현재 WebSocket 구독 상태가 서로 다른 시스템에 있으니까 순간적으로 둘의 상태가 안 맞는 상황이 나올 수도 있지 않을까? 예를 들어 db에서 친구 삭제는 됐는데 웹소켓 구독이 안 풀려서 몇 초 동안 위치를 계속 받는 문제가 생길 수도 있는데, 이 때 어떻게 할까..? 
-> db 친구 삭제 -> 친구 삭제 이벤트 발행 -> 웹소켓에 전송 -> 웹소켓 구독 해제 -- 이런 흐름일텐데 만약 이벤트 발행 -> 웹소켓에 전송되는 과정에서 지연되거나 에러가 떠서 웹소켓 구독 해제가 잘 안 되면 ? 어카죠
