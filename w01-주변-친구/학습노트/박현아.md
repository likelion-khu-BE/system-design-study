# 2장 주변 친구

다른 좋은.. 전문성이 넘치는 글들은 친구들이 정리해주엇으니
저는..배경지식이 조금 부족하다고 판단되어 제가 예시로 이해를 따라간 흐름을 올려보려고 합니다..

## 1. 내 위치를 저장했는데 왜 Pub/Sub이 필요할까?

나와 보검은 친구이고, 각각 서버에 연결돼 있다.

```text
현아 휴대폰 ── 서버 A
보검 휴대폰 ── 서버 B
```

보검이 위치를 보낸다.

> 보검 → 서버 B: 나 지금 정건에 있어.

서버 B는 공용 위치 캐시에 기록한다. 이제 서버 A에서 캐시를 조회하면 현아도 보검의 위치를 알 수 있게 된다.

그런데 **정보를 저장만 한다면 서버 A가 위치가 바뀐 사실을 바로 알 수 없다.**

두 가지 방법이 있다.

| 방법 | 동작 |
| --- | --- |
| 캐시에 계속 물어보기 | 위치가 바뀌었는지 반복해서 확인한다. |
| 위치가 바뀌면 소식 받기 | 새 위치가 들어오면 전달받는다. |

두 번째 방법으로 **Redis Pub/Sub**을 사용한다.

```text
서버 A가 보검 채널을 구독
    ↓
서버 B가 보검의 새 위치를 발행
    ↓
Pub/Sub이 서버 A에 전달
    ↓
서버 A가 나와 보검의 거리를 확인
    ↓
가까우면 내 휴대폰에 전달
```

## 2. 만약 캐시가 없다면?

**앱을 켜자마자 보검의 위치를 알기 어렵다.**

| 시간 | 상황 |
| --- | --- |
| 2:00 | 보검이 “나 정건에 있어!”라고 보낸다. Pub/Sub을 통해 구독 중인 서버들에게 전달된다. |
| 2:10 | 현아의 담당 서버가 보검 채널을 구독한다. |

Redis Pub/Sub은 뒤늦게 구독한 쪽에 이전 소식을 다시 전달해 주지는 않는다. 그래서 2시에 보검이 보낸 위치를 알 수 없다.

> 그래서 최근 위치를 확인할 수 있는 캐시가 필요하다.

## 3. 친구가 앱을 꺼서 위치 소식을 더 이상 알 수 없다면?

보검이 2시에 정건에서 위치를 보내고 앱을 종료했다.

```text
캐시 상태
보검 위치: 정건
마지막 갱신: 2:00
```

그런데 6시에도 이걸 현재 위치처럼 보여주면 안 되겠지.

그래서 **TTL(Time To Live)**이라는 유효기간이 필요하다.

- 새 정보가 들어올 때마다 유효기간이 갱신된다.
- 오래 지난 정보는 사라진다.

## 4. 가까운 친구인지는 어떻게 판단하지?

나는 영통에 있고 보검은 부산에 있다고 해보자. 내 담당 서버는 보검의 위치 채널을 구독하고 있다.

보검이 새 위치를 보내면 다음과 같이 처리한다.

1. Pub/Sub이 내 담당 서버에 보검의 위치를 전달한다.
2. 내 담당 서버가 나와 보검의 거리를 계산한다.
3. 설정한 거리 안에 있을 때만 내 휴대폰에 전달한다.

> **서버가 소식을 받는 것과 내 휴대폰에 표시하는 것은 다르다.**

## 5. 사용자가 많아지면 왜 문제가 될까?

| 계산 | 의미 |
| --- | --- |
| 동시 사용자 수 ÷ 위치 전송 간격 | 초당 위치가 얼마나 들어오는가 |
| 초당 위치 변경 수 × 전달받을 친구 수 | 초당 얼마나 많이 전달해야 하는가 |

300명이 30초마다 자기 위치를 한 번씩 보내고, 각 사람의 소식을 받을 친구가 4명씩 있다고 해보자.

```text
서버가 받는 일
300명 ÷ 30초 = 초당 10건

서버가 전달하는 일
초당 위치 변경 10건 × 친구 4명 = 초당 전달 40건
```

서버는 처리 속도에 한계가 있어서, 일이 너무 많아지면 전달이 늦어질 수 있다.

## 6. 서버 여러 대가 일을 어떻게 나누어 맡지?

사용자가 300명이고 서버가 3대라면 다음처럼 나눌 수 있다.

```text
사용자 100명 ── 서버 A
사용자 100명 ── 서버 B
사용자 100명 ── 서버 C
```

새 사용자가 앱을 켜면 어느 서버에 연결해 줄지 정해 주는 담당자가 **로드 밸런서**다.

웹소켓은 한 번 연결되면 그 연결을 유지한다. 그런데 서버가 갑자기 꺼지면, 해당 서버에 연결돼 있던 사용자들의 연결이 끊긴다.

> 기존 연결이 자동으로 다른 서버로 넘어가지는 않는다.

## 7. Pub/Sub 서버가 여러 대라면 보검 채널은 어디에 둬?

| Pub/Sub 서버 | 담당 채널 |
| --- | --- |
| 서버 1 | 보검 채널, 종석 채널 |
| 서버 2 | 현아 채널, 소원 채널 |

보검의 웹소켓 서버가 서버 1에 소식을 올렸는데, 내 웹소켓 서버가 서버 2에서 보검 소식을 기다리면 안 된다.

```text
보검 담당 서버: 보검 채널은 1번이니 여기에 발행
현아 담당 서버: 보검 채널은 1번이니 여기서 구독
```

채널을 여러 서버에 이렇게 나누어 맡기는 것을 **샤딩**이라고 한다.

## 8. 채널 담당 서버가 바뀌면 다른 서버들은 어떻게 알지?

서버를 추가하거나 고장 난 서버를 빼면 채널 담당 서버가 바뀔 수 있다.

```text
변경 전: 보검 채널 → Pub/Sub 서버 1
변경 후: 보검 채널 → Pub/Sub 서버 3
```

이때 **서비스 탐색(Service Discovery)**은 어떤 Pub/Sub 서버들이 존재하는지 알려 주고, 그 목록이 바뀌면 알려 준다.

1. 현재 서버 목록을 보관한다.
2. 서버 구성이 바뀌면 변경을 알려 준다.
3. 담당이 바뀐 채널은 새 서버에서 다시 구독한다.

> 그래서 Pub/Sub 서버를 아무 때나 늘리고 줄이기는 쉽지 않다.

## 9. Pub/Sub 서버가 갑자기 고장 나면?

보검 채널을 담당하는 서버가 고장 났다.

```text
보검 담당 서버 → [Pub/Sub 서버 1 고장] → 현아 담당 서버
```

보검의 새 위치를 전달받을 수 없다. 다른 서버가 역할을 넘겨받아도 누가 보검 채널을 구독했었는지 알아야 한다.

**복구하는 동안 놓친 위치 소식은 어떻게 하지?**

| 시간 | 보검의 위치 | 전달 여부 |
| --- | --- | --- |
| 2:00 | 정건 | 전달됨 |
| 2:10 | 사색의 광장 | 고장 나서 전달 못 함 |
| 2:20 | 전정대 | 복구 후 전달됨 |

나는 사색의 광장이라는 소식은 못 받았지만, 전정대라는 소식은 받았다.

현재 위치를 보여주는 게 중요해서 **위치 변경 소식을 가끔 놓치는 것은 허용한다**고 가정한다고 한다.

## 10. 앱을 쓰다가 친구를 추가하거나 삭제하면?

### 종석과 새로 친구가 됐다

친구 관계만 저장하면 되는 게 아니다. 내 담당 서버는 아직 종석 채널을 구독하지 않아서 종석의 위치 소식을 받지 못한다.

1. 친구 관계를 저장한다.
2. 내 담당 서버가 종석 채널을 구독한다.
3. 종석의 최근 위치를 확인해서 가까우면 내 앱에 보여 준다.

### 보검과 절교했다

그럼 내 담당 서버가 보검 채널의 구독을 해지해야 한다.

| 상황 | 구독 처리 |
| --- | --- |
| 보검과의 친구 관계를 삭제함 | 구독을 해지한다. |
| 보검이 잠깐 오프라인이 됨 | 구독은 유지한다. |

## 11. 친구가 엄청 많으면?

내 친구가 1,000명이라고 해보자.

1. **내가 움직이면:** 여러 친구에게 알려야 한다.
2. **친구들이 움직이면:** 내 담당 서버가 소식을 많이 받게 된다.

**팬아웃(Fan-out)**은 한 소식을 여러 수신자에게 퍼뜨리는 것이다.

| 서버 | 해야 하는 일 |
| --- | --- |
| 내 채널을 맡은 Pub/Sub 서버 | 내 소식을 여러 구독자에게 전달한다. |
| 내 연결을 맡은 웹소켓 서버 | 여러 친구의 소식을 받아서 처리한다. |

> **한 사람의 친구 수도 서버의 일감을 좌우한다.**

## 12. 친구가 아니어도 위치 공유에 동의한 주변 사람을 보여주려면?

아는 친구 말고 모르는 사람의 위치 소식을 받으려고 한다. 이때는 **지역별로 채널을 만든다.**

```text
내가 E 구역에 있음 → E 구역 채널을 구독
```

**지오해시(Geohash)**는 위치를 구역 코드로 나타낸다.

## 13. 이 기능을 만들려면 Redis Pub/Sub을 꼭 써야 하나?

대안으로 **얼랭(Erlang)**이 있다.

많은 작업이 동시에 실행되고 서로 메시지를 주고받는 시스템을 만드는 데 적합한 프로그래밍 언어와 실행 환경이다.
