## 이번 주의 질문

> 한정된 재고를 여러 사람이 동시에 잡으려 할 때, 어떻게 더 팔지 않으면서 빠르게 응답할까?

호텔 예약은 트래픽 자체가 크지 않다. 객실 100만 개를 가정해도 최종 예약은 초당 3건 정도다. 그런데도 어려운 이유는 **틀리면 안 되기 때문**이다. 이 장은 API 한 줄에서 시작해, 문제가 생길 때마다 설계가 어떻게 바뀌는지를 보여 준다.

## 1. 출발점: 숫자와 제약

- 호텔 5,000개, 객실 100만 개. 10% 초과 예약을 허용하고, 검색은 범위에서 제외한다.
- 예약 수 추정: 100만 × 점유율 70% ÷ 평균 3박 ≈ 하루 24만 건. 24만 ÷ 10⁵초 ≈ **3 TPS**.
- 단계별 부하: 객실 상세 300 QPS → 예약 확인 30 QPS → 최종 예약 3 TPS.

이 숫자에서 시스템의 성격이 정해진다. **읽기 중심이지만, 쓰기는 틀리면 안 되는 시스템**이다.

## 2. API와 데이터 모델

**API는 사용자의 행동에서 도출한다.** 고객과 호텔 직원의 행동을 나열하고 그 대상을 모으면 호텔, 객실, 예약이라는 자원이 나온다. 동사는 HTTP 메서드로, 대상은 URL로 옮긴다.

가장 중요한 API는 `POST /v1/reservations`다. 본문의 두 필드가 뒤에서 다시 등장한다.

- `roomID`: 고객이 정말 특정 방 하나를 고를까? → 개선된 데이터 모델
- `reservationID`: 이 ID는 언제, 누가 만들까? → 동시성

**DB는 이름이 아니라 요구사항으로 고른다.** 읽기 비중이 높고, ACID가 필요하고, 호텔과 객실과 유형의 관계가 뚜렷하므로 관계형 DB를 선택한다.

**예약에는 상태가 있다.** `pending`에서 `paid`, `canceled`, `rejected`로, `paid`에서 `refunded`로 이동한다. 상태가 있어야 예약과 결제가 서로 다른 시점에 끝나도 추적할 수 있다.

## 3. 설계안과 개선된 데이터 모델

서비스는 호텔, 요금, 예약, 결제로 나누고 공개 API 게이트웨이를 진입점으로 둔다. 직원 기능은 내부 API로 분리한다. 다른 서비스의 DB를 직접 읽지 않고 그 데이터를 소유한 서비스를 호출한다.

이 장의 첫 번째 전환점은 **무엇을 세어야 하는가**다. 호텔 예약 사이트에서는 방 번호가 아니라 스탠다드, 킹 같은 유형을 고르고, 방 번호는 체크인 때 정해진다. 그래서 `roomID`를 `roomTypeID`로 바꾸고 재고 테이블을 추가한다.

```text
room_type_inventory
PK: (hotel_id, room_type_id, date)
total_inventory, total_reserved
```

날짜당 한 행이므로 3박 예약은 3행만 확인하면 된다. 행 수는 5,000 × 20개 유형 × 2년 × 365일 = 약 7,300만이다.

예약 가능 조건은 범위 안의 **모든 행**이 통과해야 한다.

```text
total_reserved + 예약할 객실 수 <= 110% × total_inventory
```

스키마 덕분에 초과 예약 정책이 숫자 하나로 표현된다. 하지만 동시에 요청이 오면 이 검사는 깨진다.

## 4. 동시성: 이 장의 핵심

문제는 두 가지이고, **원인과 해법이 다르다.**

### 시나리오 1: 같은 사용자가 버튼을 두 번 누른다

서버는 새 요청과 재전송을 구분하지 못한다. 버튼 비활성화는 우회할 수 있으므로 서버에서 막아야 한다.

해법은 **확인 화면을 보여 줄 때 `reservation_id`를 미리 발급**하고 이를 기본 키로 쓰는 것이다. 다시 눌러도 같은 ID가 전달되므로 두 번째 INSERT는 기본 키 위반으로 거절된다.

### 시나리오 2: 마지막 방을 두 사람이 동시에 잡는다

두 트랜잭션 모두 "1개 남음"을 확인하고 둘 다 예약에 성공한다. 확인과 갱신 사이에 틈이 있고, 커밋 전의 변경은 서로 보이지 않기 때문이다. 멱등 키는 서로 다른 사용자의 요청을 막지 못한다.

| | 비관적 락 | 낙관적 락 | DB 제약 조건 |
|---|---|---|---|
| 아이디어 | 먼저 잠그고 작업 | 작업 후 버전 검사 | 규칙을 어기면 거절 |
| 충돌 처리 시점 | 읽을 때 대기 | 쓸 때 실패, 재시도 | 쓸 때 실패 |
| 구현 위치 | DB 락 + 쿼리 | 애플리케이션 + `version` 열 | DB 스키마 |
| 경합이 낮을 때 | 불필요한 비용 발생 | 빠름 | 빠름 |
| 경합이 높을 때 | 대기열 발생 | 재시도 급증 | 실패 급증 |
| 주요 위험 | 교착 상태 | 재시도 로직과 사용자 경험 | DB 의존, 코드 밖 규칙 |

**선택 기준은 경합 정도다.** 충돌은 같은 호텔, 같은 유형, 같은 날짜에서만 일어나고 예약 QPS도 높지 않다. 그래서 책은 낙관적 락 또는 DB 제약 조건이 적합하다고 본다.

## 5. 확장성

트래픽이 천 배가 되면 서버는 늘리면 되지만 상태를 가진 DB가 병목이 된다.

- **샤딩**: 대부분의 질의에 `hotel_id`가 있으므로 `hotel_id % 16`으로 나눈다. QPS 30,000 ÷ 16 = 샤드당 1,875 QPS로, MySQL 한 대로 감당할 수 있는 수준이다.
- **캐시**: 재고 조회는 Redis가 맡고, 쓰기와 최종 판단은 DB가 맡는다. 키는 `hotelID_roomTypeID_{date}`, 값은 남은 객실 수다.

캐시와 DB가 잠깐 달라지면 어떻게 될까? 캐시에 재고가 있어도 DB 검증에서 거절되므로 **이중 예약은 생기지 않는다.** 재고를 보고도 실패 메시지를 받는 사용자 경험 문제만 남는다. 캐시는 빠른 안내판이고, 예약 확정은 DB가 한다.

## 6. 서비스 간 데이터 일관성

마이크로서비스 원칙대로 DB를 나누면 재고 갱신과 예약 저장을 한 트랜잭션으로 묶을 수 없다. 재고만 줄고 예약이 실패하면 데이터가 어긋난다.

- **2PC**: 전부 성공 또는 전부 실패를 보장하지만, 성능이 좋지 않고 한 노드가 멈추면 진행이 막힐 수 있다.
- **사가**: 각 서비스가 자기 트랜잭션을 차례로 실행하고, 실패하면 보상 트랜잭션을 역순으로 실행한다. 막힘은 줄지만 설계가 복잡해지고 중간 상태가 사용자에게 보일 수 있다.

**책의 선택은 둘 다 아니다.** 예약 서비스가 예약과 재고를 함께 맡아 같은 관계형 DB에 두고, 하나의 트랜잭션으로 ACID를 그대로 쓴다. 원칙을 지키는 비용이 얻는 가치보다 크다면 단순한 설계를 고를 수 있다. 이 장에서 가장 기억할 만한 판단이다.

## 함께 생각해 볼 점 `[보충]`

- RESTful API는 `메서드 /v1/복수명사/:id` 공식으로 정리할 수 있다. 대상은 명사로 URL에, 동작은 HTTP 메서드로, 소속 관계는 경로로, 버전은 맨 앞에 둔다.
- 관계형 DB가 읽기에 유리한 이유는 저장 구조에 있다. B+ 트리는 노드 하나에 키를 수백 개 담아 높이가 낮아서, 수천만 건도 보통 3~4단계면 리프에 닿는다. 단계마다 페이지 하나만 읽고 위쪽 노드는 대개 메모리에 있어 디스크 읽기가 적다. 리프는 정렬된 채 옆으로 연결돼 있어 범위도 이어서 읽는다. 일반적인 경향이고 제품마다 다르다.
- `BETWEEN`은 양 끝을 포함한다. 종료일이 체크아웃일이면 그날 재고는 범위에서 빼야 한다.
- 시나리오 2의 결과는 구현에 따라 다르다. 읽은 값으로 덮어쓰면 `total_reserved`가 100, `reserved + 1`로 갱신하면 101이 될 수 있다. 둘 다 이중 예약이다.
- 낙관적 락은 읽기와 쓰기 사이에 락을 유지하지 않을 뿐, UPDATE 순간에는 행 락이 걸린다.
- 10% 초과 예약을 허용하려면 CHECK 제약 조건의 식도 함께 바꿔야 한다.
- `hotel_id`로 샤딩하면 `guest_id` 기준의 내 예약 조회는 여러 샤드를 찾아야 할 수 있다. `% 16` 방식은 샤드 수를 바꾸기도 어렵다.
