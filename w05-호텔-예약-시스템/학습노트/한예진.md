# 1. 데이터 모델

#### 1-1. 왜 관계형 데이터 베이스인가?

조건

- 읽기가 압도적인 작업 흐름을 잘 지원해야 한다.
- ACID 속성 보장
- 쉽게 모델링 (비지니스 데이터 구조 명확하게 표현, 엔티티 간의 관계 안정적 지원)

**다른 데이터베이스 대안들은 무엇이 있을까?**

| 데이터베이스 | 특징 | 호텔 예약 시스템에서의 활용 및 한계 |
|---|---|---|
| 관계형 DB (MySQL, PostgreSQL) | 정형 데이터, SQL, ACID 트랜잭션 지원 | 예약 및 결제처럼 데이터 정합성이 중요한 작업에 적합 |
| 와이드 컬럼 DB (Cassandra, HBase) | 대규모 데이터 분산 및 높은 쓰기 처리량 | 쓰기 작업이 적은 이 시스템에서는 장점을 충분히 활용하기 어려움 |
| 키-값 DB (Redis, DynamoDB) | 키를 이용한 빠른 데이터 조회 | 단순 조회는 빠르지만 복잡한 범위 검색이나 JOIN에 적합하지 않음 |
| 문서형 DB (MongoDB) | 유연한 데이터 구조와 스키마 | 데이터 구조가 명확한 호텔 예약 시스템에서는 유연성이 크게 필요하지 않음 |
| NewSQL (Spanner, CockroachDB) | SQL과 ACID를 지원하면서 수평 확장 가능 | 장점은 있지만 운영 복잡도와 비용이 증가할 수 있음 |

읽기 작업이 많고 예약 과정에서 데이터 정합성이 중요한 호텔 예약 시스템에서는 ACID 트랜잭션을 지원하고 데이터 간 관계를 명확하게 관리할 수 있는 **관계형 데이터베이스**가 적합

#### 1-2. 관계형 데이터베이스 왜 읽기가 쓰기에 비해 높은 작업 흐름을 잘 지원할까?

데이터베이스의 읽기 작업 효율적으로 처리할 수 있는 다양한 방법

- 인덱스
- 읽기 복제본(Read Replica): 조회 요청 분산 가능
- 캐싱
- 쿼리 최적화: 효율적인 데이터 조회

개별 조회 성능 높이는 것 뿐 아니라 여러 서버로 읽기 요청 분산할 수 있어 읽기 작업 많은 시스템에 적합

# 2. 개략적 설계안

#### 2-1. 왜 마이크로서비스 아키텍쳐인가?

호텔 검색, 객실 조회, 예약, 결제 등 여러 기능 **하나의 애플리케이션으로 관리** or **기능별로 독립적인 서비스로 분리**

모노리스 아키텍쳐 VS 마이크로서비스 아키텍쳐

| 구분 | 모노리스 아키텍처 | 마이크로서비스 아키텍처 |
|---|---|---|
| 구조 | 하나의 애플리케이션으로 구성 | 기능별로 독립적인 서비스 구성 |
| 개발 및 배포 | 전체 애플리케이션을 함께 배포 | 서비스별 독립적인 배포 가능 |
| 확장 | 전체 시스템을 확장해야 함 | 필요한 서비스만 개별적으로 확장 가능 |
| 장애 대응 | 한 부분의 장애가 전체에 영향을 줄 수 있음 | 서비스별 장애 격리가 가능 |
| 복잡도 | 상대적으로 단순 | 서비스 간 통신 및 데이터 관리가 복잡 |

**마이크로서비스 아키텍쳐를 선택하는 이유**

- 호텔 검색과 예약은 요청량과 처리 특성이 다르므로 필요한 서비스만 별도로 확장 가능
- 각 서비스 독립적으로 개발, 배포 가능
- 특정 서비스에 장애 발생해도 다른 서비스에 미치는 영향 줄일 수 O

but 서비스 간 통신 필요, 각각의 데이터베이스 사용하는 경우 서비스 간 트랜잭션과 데이터 일관성 관리하기 어려움

**그 외에 다른 아키텍쳐?**

| 아키텍처 | 특징 |
|---|---|
| 모듈러 모노리스 | 하나의 애플리케이션이지만 내부 기능을 모듈별로 분리하여 관리 |
| 계층형 아키텍처 | 화면, 비즈니스 로직, 데이터 접근 등 역할에 따라 계층을 분리 |
| SOA | 비즈니스 기능을 서비스 단위로 구성하고 서비스 간 재사용을 강조 |
| 이벤트 기반 아키텍처 | 이벤트를 발생시키고 이를 구독하는 서비스가 비동기적으로 처리 |

# 3. 개선된 데이터 모델

#### 3-1. 데이터베이스 서버를 하나만 두면 왜 SPOF(Single-Point-Of-Failure) 문제가 생기나?

SPOF(단일 장애 지점): 시스템에서 특정 구성 요소 하나에 장애가 발생했을 때 전체 서비스가 정상적으로 작동하지 못하는 상황

- 모든 서비스가 하나의 데이터베이스 서버에 의존하는 경우 해당 서버에 장애가 발생하면 모든 서비스가 데이터에 접근할 수 없게 된다.
- 하드웨어 고장, 디스크 손상, 네트워크 장애 등으로 데이터베이스가 중단될 수 있다.
- 데이터베이스 장애는 단순한 서비스 중단뿐 아니라 데이터 손실로 이어질 수도 있다.

해결 방법

- 데이터베이스 여러 서버에 복제
- 다른 가용 영역(AZ)에 대기 서버를 구성하고 장애 발생 시 자동으로 전환(Failover)
- 읽기 복제본 추가해 조회 부하 분산

읽기 복제본과 대기 복제본의 차이

- 대기 복제본(Standby): 주 데이터베이스에 장애가 발생했을 때 서비스를 이어받아 가용성을 높이는 목적
- 읽기 복제본(Read Replica): 조회 요청을 분산해 데이터베이스의 읽기 부하를 줄이는 목적

# 4. 시스템 규모 확장

#### 4-1. 무상태 서비스와 상태 저장 시스템

무상태 서비스 - 서버를 추가하는 것으로 성능 문제 해결

모든 상태 정보가 보관되는 데이터베이스 - 단순 서버 늘리는 것만으로는 성능 문제 해결 X

**무상태 서비스:** 서버가 사용자 요청과 관련된 상태 정보 자체적으로 유지하지 않는 서비스

- 각 요청 독립적으로 처리 됨 → 어떤 서버가 요청을 처리해도 상관 X
- 로드 밸런서를 통해 여러 서버에 요청 분산 가능
- 서버를 추가하는 것 만으로 쉽게 수평 확장 가능

**상태 저장 시스템:** 사용자 정보, 예약 정보, 객실 재고 등 상태 정보 저장하고 관리하는 시스템

- 데이터베이스는 데이터 저장, 유지하기 때문에 대표적인 상태 저장 시스템
- 단순히 서버 추가한다고 기존 데이터가 자동으로 공유되는 것은 X
- 데이터 복제, 동기화, 일관성 등을 고려해야 함 → 확장이 상대적으로 복잡

| 구분 | 무상태 서비스 | 상태 저장 시스템 |
|---|---|---|
| 상태 정보 | 자체적으로 유지하지 않음 | 상태 정보를 저장하고 유지 |
| 예시 | 애플리케이션 서버 | 데이터베이스 |
| 확장 방법 | 서버 추가 및 요청 분산 | 복제, 샤딩 등 별도 전략 필요 |
| 확장 시 고려 사항 | 로드 밸런싱 | 데이터 동기화 및 일관성 |

#### 4-2. 샤딩 외에 데이터베이스 규모 늘리는 방법에는 무엇이 있을까?

1. 수직 확장
2. 읽기 복제본 (수평 확장)
3. 캐싱 (별도 최적화)
4. 인덱스 및 쿼리 최적화 (별도 최적화)
5. 파티셔닝 (데이터 분할)
6. 샤딩 (수평 확장)

| 방법 | 핵심 목적 | 한계 |
|---|---|---|
| 수직 확장 | 서버 자체 성능 향상 | 하드웨어 한계 |
| 읽기 복제본 | 읽기 부하 분산 | 쓰기 부하 해결 불가 |
| 캐싱 | DB 접근 횟수 감소 | 데이터 불일치 가능성 |
| 인덱스 및 쿼리 최적화 | 조회 성능 향상 | 전체 처리 용량의 한계 |
| 파티셔닝 | 데이터 관리 및 조회 효율 향상 | 파티셔닝만으로 여러 DB 서버에 부하가 분산되는 것은 아님 |
| 샤딩 | 여러 서버에 데이터 분산 | 구조 및 관리 복잡도 증가 |

**샤딩을 사용하는 이유는?**

트래픽 크게 증가하면 하나의 데이터베이스 서버로는 읽기 쓰기 부하 감당하기 어려워짐

→ 읽기 복제본은 읽기 요청만 분산 가능, 캐싱도 모든 데이터베이스 접근 대체할 수 없다.

→ 데이터를 여러 데이터베이스 서버에 분산하여 읽기 쓰기 부하 함께 줄일 수 있는 **샤딩 사용**

읽기 요청만 많다면 캐싱과 읽기 복제본으로 대응할 수 O

데이터와 쓰기 요청까지 크게 증가한다면 샤딩을 통해 데이터베이스 자체를 수평 확장해야 함

단순히 조회 속도를 높이려는 것이 X 데이터베이스의 처리 용량 자체를 확장하기 위해
