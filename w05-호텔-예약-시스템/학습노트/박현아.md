# 7장 호텔 예약 시스템


## 1. 이 시스템은 무엇을 할 수 있어야 해?

- 호텔과 방 정보를 보여 준다
- 방을 예약하고, 예약을 취소할 수 있다
- 호텔 관리자는 호텔·방 정보를 추가하고 고칠 수 있다
- 가격은 날짜마다 다를 수 있다
- 방은 실제 개수보다 10% 더 예약을 받을 수 있다 (이거신기한듯..)


## 2. 요청이 얼마나 들어와?

- 호텔, 방 보기 : 300
- 예약 화면: 30
- 예약: 3

구경만 하는 사람이 많고 각 단계마다 1/10으로 줄어듦


## 3. 재고는 왜 방 번호가 아니라 방 종류로 세?

예약을 할 때 방 번호를 예약하는 게 아니라 방 크기로 예약을 한다 (딴 말인데 생각해보니까 이거 왜일까...? 높고 뷰 좋은 방을 미리 선점하면 좋잖아)

예약 가능한지 확인하려면: 예약된 수 + 1 ≤ 전체 방 × 1.1


## 4. 예약 하나는 어떤 상태를 거쳐?

```
대기 -> 결제 완료 -> 환불
    -> 취소 (손님이 취소)
    ->  거절 (결제 실패)
```


## 5. 전체 구조

- API 게이트웨이: 요청이 들어오면 
- 잘 바뀌지 않는 정보나 가격은 캐시해둔다
- 디비는 관계형 디비를 쓴다


## 6. 버튼을 두 번 누르면?

로딩시간이 길어져서 예약하기 버튼을 두 번 누르면 요청이 서버에 두 번 가게 되고 결제 2번으로 이어진다

멱등성 키 -> 요청 1번에 1나의 숫자를 부여해서, 요청이 올 때 이 숫자를 확인한다.
같은 숫자가 오면 같은 요청으로 인식하고 거절함.


## 7. 방 하나를 두 사람이 동시에 잡으면?

방이 100개가 있고 99개가 예약 완료인 상태.
현아와 보검이 100번째 방을 동시에 예약하려고 하고 있다.

1. 현아가 먼저 앱에서 남은 방의 갯수를 확인했다. (99개)
2. 보검도 방의 갯수를 확인했다. (99개)
3. 현아가 먼저 결제를 했다. (100개)
4. 보검도 결제를 했다. (101개)

방은 100개인데 101 개가 결제되는 일이 발생.
현아의 동작 사이의 보검의 동작이 끼어들었기 때문이다.


**어떻게 막을까?**

1. 비관적 락
- 무조건 잠그고 시작한다. 한 동작이 진행 중에 다른 동작이 끼어들 수 없다.
- 장점: 가장 확실하게 막음
- 단점: 기다림이 발생한다.
데드락이 발생할 수 있다.

2. 낙관적 락
- 버전 번호 등을 이용한다.
- 장점: 빠르다
- 단점: 요청이 많을 때는 헛시도가 많아진다.

3. DB 제약조건
- 디비에 규칙을 건다
- 장점: 간단함
- 디비마다 다름


호텔 예약에서 책이 고른 방법: 낙관적 락이나 디비 제약조건이 좋을 것이라고 함. 
호텔 예약은 티켓팅처럼 동시에 예약하는 일이 많지 않아서.

## 8. 호텔이 아주 많아지면?

- 남은 재고를 빠르게 보여주기 위해서 redis 를 이용한다.
- 그래서 redis 의 복사본과 디비가 다를 수 있다
- 실제 예약 시 디비에서 다시 확인하는 과정을 거쳐야 함


## 9. 예약 DB와 결제 DB가 따로면 뭐가 문제가 될까?

서로 다른 디비는 트랜잭션으로 묶을 수 없다. 
결제를 하지 않았는데 예약은 되는 상태가 발생할 수 있음

- 2단계 커밋: 확실해질 때까지 아무것도 정하지 말자
- 사가: 일단 하나씩 확정하고 실패했을 때 되돌리자

**2단계 커밋**
- 1단계: 조정자가 두 디비에 저장할 준비가 되었는지 물음
각각은 락을 걸음
- 2단계: 커밋이나 롤백, 두 디비 모두 준비되면 커밋, 둘 중 하나라도 아니면 롤백
- 비관적 락과 같이 락이 걸려있기 때문에 기다림이 생김
- 조정자가 죽으면 멈추게 된다


**사가**
- 큰 작업을 작은 단위로 나누고 각 단계를 바로 확정한다.
단계마다 보상 트랜잭션을 만들어 둔다.
- 각 단계마다 보상 트랜직션을 짜야 함. 
- 결과적 일관성: 


책에서는 예약과 재고를 같은 디비에 두기로 함. 
그러면 트랜잭션 하나로 묶을 수 있기 때문에.

- [예약 서비스] : 예약 + 재고 를 한 디비에 < 트랜잭션으로 묶음
- [결제 서비스] : 결제 디비
