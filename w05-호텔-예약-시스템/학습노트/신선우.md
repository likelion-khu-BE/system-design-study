# 호텔 예약 시스템

## 이번 문제는?
 
- 호텔 5000개, 객실 100만 개
- 예약 시 비용 전액 지불
- 예약 취소 가능
- **10% 초과 예약 가능**
- 객실 가격 매일 달라짐
### 개략적 규모
 
- 5000개 호텔, 100만 개 객실
- 평균 70% 사용중
- 평균 투숙 기간: 3일
- 일일 예상 예약 건수: **240,000**
> **예약**: 초당 3건
> 
> **예약 페이지**: 초당 30
> 
> **객실 정보 페이지**: 초당 300

## 개략적 설계안
 
### RDB를 사용. 이유는?
 
- 읽기 > 쓰기 연산의 구조
- **ACID** 속성 보장 (원자성, 일관성, 격리성, 영속성)
- 엔티티 간 관계 명확
### MSA 구조를 사용. 이유는?
 
*책에는 안나오지만 이런 이유로 좋지 않을까*
 
- 서비스마다 트래픽의 특성이 다름
- 사용자와 변경 주기가 다름
- 장애 격리
- 서비스별 팀 분리
> 하지만 모놀리식으로 해도 예약 초당 3건 정도면 해결 할 수 있을 것 같은데..
> 
> 그리고 마이크로서비스로 하면 트랜잭션이나 서비스 간 통신 같은 운영 부담도 다 고려해야함
 
> “실제 상업적으로 이용되는 시스템의 서비스 간 통신에는 **gRPC**와 같은 고성능 원격 프로세저 호출 프레임 워크를 사용하곤 한다.” *(여기서 보니 반갑네요)*

## 상세 설계
 
### 스키마 설계
 
`room_id` 대신 `room_type_id`를 넣어줍니다. 우리가 호텔 예약할 때 방 호수로 예약하지 않고 객실 타입으로 예약하니까.
 
> **저장 용량**: 5000개 호텔 * 20개 타입 * 2년치 데이터 * 365일 = **7300만 개**
 
**고가용성**을 달성하고 싶다면 여러 region, AZ에 DB를 복제해두면 됨
 
**예약 데이터가 너무 많으면 어쩌죠?**
 
- 전에 배운 **샤딩** 쓰거나
- 오래된 데이터를 아카이브나 cold storage로 유배 보내기 - 예약 이력은 자주 접근 하지 않으니까
### 재미있는 동시성 문제
 
#### 시나리오 1: 같은 사용자가 예약 버튼을 두 번 누름
 
- 프론트에서 버튼 한 번 누르면 비활성화 처리하기 - *솔직히 이건 화면 상으로만 막는거라 완벽하지 않음*
- **`reservation_id`를 멱등키로 사용하기**: 쉽게 말해서 `reservation_id`를 담은 예약 주문서를 미리 만들어서 고객에서 확인 시키고, 예약을 제출 했을 때 `reservation_id`를 pk로 저장해서 pk의 유일성 조건을 이용하는 것
#### 시나리오 2: 마지막 하나 남은 객실을 여러 명이 동시에 예약 시도 - 락을 걸자
 
> 각각의 트랜잭션은 독립적으로 일어나기 때문에 동시에 잔여 객실이 1인걸 확인 했다면 **이중 예약 가능**
 
- **비관적 락(Pessimistic)**: 비관적으로 “충돌이 발생하고 말거야ㅠㅠ”라고 가정하고 사용
    1. **데이터 조회**: 수정할 의도가 있다면 해당 데이터에 락을 걸고 다른 트랜잭션이 접근 못하게 막아버림
    2. **락 유지**: 락이 걸린 동안 다른 트랜잭션은 해당 데이터에 접근 불가. 락을 획득한 트랜잭션이 끝날때까지 기다리거나 실패함
    3. **데이터 수정**: 나 혼자만 이 데이터에 접근 가능하므로 충돌 없이 안전하게 수정
    4. **락 해제**: 트랜잭션이 완료 되면 락 해제되고 다른 트랜잭션 접근 가능
    과정으로 볼 수 있듯이 충돌 예방이나 데이터 무결성 보장 측면에서는 좋음
    그런데 락을 걸었을 때 다른 트랜잭션은 계속 대기 해야하니까 성능이 좀 떨어지는 문제, 두 트랜잭션이 서로 다른 리소스를 락을 걸고 상호 대기하면 **데드락** 발생해버림
    > 그래서 **충돌이 많이 발생할 것으로 예상되는 환경**에서 사용하면 좋음
- **낙관적 락(Optimistic)**: 낙관적으로 “에이 설마 충돌이 일어나겠어~”라고 가정하고 사용
    *버전과 타임스탬프를 주로 활용*
    1. **데이터 조회**: 사용자가 데이터 조회 시에 해당 레코드의 버전 정보를 함께 가져옴. 버전은 레코드 수정 시 마다 변경됨
    2. **데이터 수정**: 사용자가 데이터를 수정하려고 할 때, 처음 조회 때 가져온 버전 정보를 같이 비교함(아래 쿼리 보면 좀 더 이해 잘 됨)
    3. **검증**: 사용자의 조회 이후 다른 사용자에 의한 수정으로 버전이 변경되었다면 충돌로 판단하고 예외 발생, 수정이 실패하고 트랜잭션은 롤백됨
    4. **수정 성공**: 버전 정보가 동일하면 수정 성공, 버전 번호 증가
```sql
    -- 1. 읽을 때 version도 같이 읽음 (예: version = 5)
    SELECT total_inventory, total_reserved, version
    FROM room_type_inventory
    WHERE hotel_id = ? AND room_type_id = ? AND date = ?;
 
    -- 2. 수정할 때 읽었던 version과 같을 때만 반영하고 version을 올림
    UPDATE room_type_inventory
    SET total_reserved = total_reserved + 1, version = version + 1
    WHERE hotel_id = ? AND room_type_id = ? AND date = ? AND version = 5;
```
 
    JPA에서는 `@Version` 어노테이션 붙이면 위 쿼리를 Hibernate가 자동으로 만들어줌.
 
    예외는 `OptimisticLockException`(Spring에서는 `ObjectOptimisticLockingFailureException`)
 
    낙관적 락 같은 경우는 DB에 락을 걸지 않기 때문에 비관적 락보다 빠름
 
    > 그런데 **경쟁이 치열하다면** 충돌이 계속 발생할테니 한명씩 순서대로 들어가는 비관적 락보다도 성능이 매우 떨어질 것이다
 
- **데이터베이스 제약 조건**
    - `room_type_inventory` 테이블에 제약 조건 추가하면 됨
```sql
    CONSTRAINT 'check_room_count' CHECK(('total_inventory - total_reserved ' >= 0))
```
 
    - 낙관적 락이랑 비슷하게 수정하려고 할 때 제약 조건 실패하면 롤백
 
### 시스템 규모 확장
 
- 데이터베이스 규모 늘리기 - **샤딩**
- **캐시** - 레디스로 잔여 객실 캐싱, TTL, LRU 캐시 교체 정책 사용으로 최적화
    - 잔여 객실 정보를 캐시에 미리 저장
    - 잔여 객실을 캐시에서 확인하고 예약 하면 DB 갱신하고 캐시 비동기로 갱신함
    - 변경 데이터 감지(**CDC**) 매커니즘을 사용할 수도 있음
> **캐시에는 잔여 객실이 있다고 되어있는데 실제 DB에는 잔여 객실이 없는 문제**
> 
> 어짜피 진실은 DB에 있기 때문에 DB를 확인하면 해결 된다.
 
> **DB가서 최종 확인 할거면 캐시를 뭐하러 두나?**
> 
> - 단순 조회 말고 예약을 시도하는 요청에만 DB에 갔다오니까 단순 조회시의 300QPS보다 예약 시도 요청의 3QPS만 감당하면 되니 캐시가 있는게 훨씬 낫다
> - 그리고 캐시가 틀려도 **초과 예약이 절대 일어나지 않는 구조**니까 감수할 만하다
 
### 서비스 간 데이터 일관성
 
- 모노리식 쓰면 DB 하나니까 상관 없는데 MSA면 서비스마다 DB가 다 따로 있음
- 그러면 전체 트랜잭션이 하나의 DB에서 처리되는게 아니라 여러 마이크로서비스의 개별적인 로컬 트랜잭션들이 조합한 형태가 됨
- 그러면 하나의 서비스라도 실패하면? **데이터의 일관성이 깨지는 매우 큰 문제 발생**
**데이터 일관성을 위한 두가지 패턴**
 
#### 2단계 커밋 패턴(2-phase commit, 2PC)
 
- 분산되어있는 트랜잭션들을 **원자적(다같이 성공 또는 다같이 실패)**으로 처리하기 위한 프로토콜
- **prepare 단계**: 코디네이터가 모든 참여자에게 커밋 가능한지 물어보고, 각 참여자는 변경 준비하고 락을 잡은 채로 대기
- **commit 단계**: 참여자 전원이 “가능”으로 답한 경우 실제로 모두 커밋, 하나라도 “불가”면 모두 롤백
- 락을 오래잡아서 느림
- blocking protocol이라 한 노드에 장애 발생 시 해당 노드가 복구될때까지 진행 중단
- 코디네이터가 고장나면? 진행 못하고 영원히 락 잡고 멈춤
#### Saga 패턴
 
- **코레오그래피(Choreography) 방식**: 이벤트 주고받기
    - 중앙 관리자가 없고 각 서비스가 이벤트를 발행하고 구독하면서 알아서 다음 단계 진행
    - 예시
        - 예약 서비스: 잔여 객실 수 차감하고 예약 생성한 뒤 “예약 생성됨” 이벤트를 발행
        - 결제 서비스: 이 이벤트를 구독해서 결제과정 진행
        - 결제 성공 시 “결제 성공” 이벤트 발행하고 예약 서비스가 받아서 상태를 paid로 바꿈
        - 결제 실패 시 “결제 실패” 이벤트 발행하고 예약 서비스가 받아서 보상 트랜잭션 진행(잔여 객실 복구, canceled 처리)
    - 이벤트로 과정이 진행되니 서비스간 결합도가 낮아서 구조가 단순
    - 그렇지만 서비스가 많아지면 트랜잭션 흐름이 복잡해지는데, 이 흐름이 어디에도 명시되어 있지 않아서 파악이 어려움
    - 이벤트를 주고 받는 과정에서 서비스간 순환 의존 발생 위험
- **오케스트레이션(Orchestration) 방식**: 중앙 조정자가 지휘
    - 오케스트레이터가 전체 흐름을 알고, 각 서비스에 명령 보내고 응답 받음
    - 예시
        - 오케스트레이터가 예약 서비스에 “잔여 객실 수 차감해” 명령하고 성공 응답 받음
        - 결제 서비스에 “결제 해~” 명령함
        - 실패하면, 오케스트레이터가 예약 서비스에 “잔여 객실 수 복구해” 보상 트랜잭션 명령
    - 트랜잭션 흐름이 오케스트레이터에 모여 있으니 흐름 이해 쉬움
    - 그런데 이 말은 오케스트레이터에 로직이 집중되고 오케스트레이터 자체를 관리해야한다는 말
    - 즉, 오케스트레이터가 고장나면 아무것도 못한다는 뜻이기도 함
> 그래서 두 패턴의 차이는 2PC는 모아 놓고 실패하면 “**롤백**” 시킨다는거고 Saga는 롤백이 아니라 “**보상 트랜잭션**”을 시킨다는 것
 
- **보상 트랜잭션**은 이미 커밋된 작업을 의미적으로 되돌리는 별도의 트랜잭션
- 롤백과의 차이는? 롤백은 커밋 되기 전이니까 그냥 없던 일이 되는거임. 흔적이 없음
- 그런데 보상 트랜잭션은 이미 커밋된 내용을 그것의 반대되는 동작을 커밋해서 취소하는 것임
- 새로운 작업이 추가되는 것
- 그러면 보상 트랜잭션이 실패하면? 재시도 가능하게 하고 재시도해도 안전하도록 **멱등**하게 만들어놔야지
- 이미 메일을 보내버렸으면? 이미 발송된 메일은 취소할 수 없는 작업이니까 취소 안내 메일을 다시 보내는 식으로 처리해야함

## 분산락
 
- 서버가 여러대, 트래픽이 한꺼번에 몰리는 티켓팅 같은 서비스에서 사용함
- 호텔 예약 서비스라면 “오전 10시 특가 선착순 예약!!” 같은 상황
- 서버를 여러 대 띄우면 각자 자기의 락만 알고 다른 서버의 락은 모름
- 그래서 모든 서버가 함께 보는 **공통 지점**이 필요
- 만일 트래픽이 적다면 DB를 공통지점으로 두고 그 안에서 낙관락, 비관락 쓰면 됨
- 그런데 트래픽이 엄청 많아져서 엄청 많은 사람들이 동시에 같은 자리를 예매하고 싶어함
- 동시에 같은 자리를 누른 사람들 중 **딱 한 사람만 락을 획득**해야함
- 이때 실패하면 “이미 선점된 좌석입니다”가 뜨고 락 획득에 실패한 것임
> 그런데 이 흐름대로 라면 그냥 같은 자리 누른 사람들끼리 낙관락, 비관락으로 막으면 되지 않나?
> 
> **문제는 정합성이 아니라 부하임**
 
- 수만 명이 같은 좌석에 몰리면 UPDATE 쿼리가 같은 행을 두고 싸우는건데 낙관락, 비관락을 사용하면 전부 다 DB에서 경쟁함. 이러면 락 대기, 커넥션 점유, DB CPU 부하로 무조건 터지게 됨
- 그래서 **Redis 락**을 앞에 두어 메모리에서 경쟁이 끝나게 만들고, 열쇠(락)을 획득하지 못한 사람들은 DB까지 가지 않게 하는 것임
> 즉 이번에 나온 호텔 예약 시스템처럼 초당 3건 정도의 예약이 발생하는 상황에서는 DB 락으로 충분하지만, 티켓팅 같은 동시에 극단적으로 부하가 들어오는 서비스에서 DB에서 그 모든 부하가 경쟁하면 무조건 터지게 될테니, **DB로 들어가는 열쇠를 한 명에게만 주는 것임**
 
---
 
그리고 캐시 파트에서 우리가 CDC를 사용하지 않고 cache-aside 방식을 사용했다면 발생할 수 있는 문제가 있음
 
> **cache-aside**: 요청이 올 때 캐시를 채우는 방식. 즉, 캐시에 있으면(**Hit**이면) 캐시에서 읽고, 없으면(**Miss**이면) DB가서 읽고 캐시에 채워 넣는 방식
 
## 캐시 스탬피드(cache stampede)
 
- 만약에 호텔 예약 시스템에서 10시에 특가 객실을 오픈하는데 cache-aside 방식으로 캐시를 사용하고 있었다고 가정
1. 10시에 수천, 수만건의 요청이 동시에 캐시 miss
2. 캐시 miss니까 모든 요청들이 DB에 가서 캐시를 채우려고 함
3. 똑같은 쿼리 수천, 수만개가 DB로 들어오고, DB 느려짐
4. DB 느려져서 캐시 채우기도 느려지고 miss 계속 쌓임
5. **DB 사망 엔딩**
> 즉, 캐시 채우는 데 한번만 조회하면 될 것을 수천, 수만 명이 같은 일을 동시에 함
 
**해결 방법**
 
- 락으로 한 명만 DB 갔다오게 하기(mutex)
- 만료 전 미리 갱신
#### 비슷하지만 다른 친구들로는
 
- **캐시 애벌랜치**: 많은 키가 같은 시각에 한꺼번에 만료되거나 캐시 서버가 죽어서 전체 트래픽이 DB로 가는 현상
    - TTL에 랜덤 시간 더해서 만료 시간을 다 다르게 해서 막음
- **캐시 관통(penetration)**: DB에도 없는 데이터를 계속 요청해서 매번 miss나서 캐시를 통과해 DB로 감
    - “없음”도 짧게 캐싱하거나 블룸 필터로 막음
