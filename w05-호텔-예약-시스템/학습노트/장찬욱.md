## 배경
- 호텔 5000개, 객실 총 100만개
- 객실 평균 점유율 70%, 평균 숙박 3일
- 일일 예약 = 100만 × 0.7 / 3 ≈ 24만건, 초당 약 3건
- 호텔/객실 상세 조회 : 예약 화면 : 예약 = 300 : 30 : 3 (qps). 단계마다 10%만 다음 단계로 넘어간다고 가정
- 10% 초과 예약(오버부킹)을 허용한다
- 객실 가격은 날짜마다 다르다

-> 트래픽 자체는 크지 않다. 초당 3건은 디비 한대로 충분하다.
이 시스템에서 어려운 부분은 트래픽이 아니라 정확성이다. 방이 100개인데 101건이 예약되면 안 된다.

그래서 이번 챕터의 핵심 질문은
> 한정된 자원을 여러 명이 동시에 예약하려 할 때, 있는 만큼만 팔려면 어떻게 해야 하는가


## 방 번호가 아니라 방 유형을 예약한다
처음 설계안은 예약 테이블에 room_id를 넣는다.

호텔은 방 번호가 아니라 방 유형(스탠다드, 디럭스, 킹 등)을 판다. 방 번호는 체크인할 때 정해진다.

> 궁금했던 점. 왜 방 번호를 미리 정하지 않을까?
>
> -> 책에 이유가 나오진 않는다. 찾아본 바로는 방 번호를 늦게 정할수록 운영이 유연해진다. 청소가 늦게 끝난 방을 피하거나 업그레이드를 해줄 수 있고, 오버부킹도 가능해진다. 101호를 두 명에게 팔 수는 없지만, "스탠다드 n개"는 노쇼를 감안해 1.1n개까지 팔 수 있다.

설계에 주는 영향
- 방마다 레코드를 두고 점유하는 모델이 아니다
- (호텔, 방 유형, 날짜)별 남은 개수라는 정수를 줄여나가는 모델이다
- 좌석 예매보다는 재고 관리에 가깝다

그래서 책은 이런 테이블을 둔다

```text
room_type_inventory
───────────────────────────────
hotel_id         (PK)
room_type_id     (PK)
date             (PK)
total_inventory   -- 이 날 팔 수 있는 총 방 수
total_reserved    -- 이 날 이미 예약된 방 수
```

- 날짜마다 행이 하나다. 3박 예약이면 3개 행을 갱신한다
- 매일 도는 스케줄러가 앞으로 2년치 행을 미리 만들어둔다
- 행 개수는 5000 호텔 × 20 유형 × 2년 × 365일 ≈ 7300만. 디비 한대에 들어가는 양이다. 다만 단일 장애 지점이 되므로 복제는 해둔다

예약 가능 여부는 이 조건으로 판단한다
```text
total_reserved + 예약할 방 수 <= total_inventory × 1.1
```


## 저장소
- 읽기가 쓰기보다 훨씬 많다
- 예약은 돈과 관련되어 acid가 필요하다
- 호텔, 방 유형, 재고, 예약 사이 관계가 명확하다

-> rdb를 쓴다.


## 예약 상태
예약은 상태를 가진다

```text
pending ──→ paid ──→ refunded
   │
   ├──→ canceled  (사용자가 취소)
   └──→ rejected  (결제 실패)
```

결제 서비스와 상태가 엮이기 때문에 뒤에서 분산 트랜잭션 문제가 나온다.


## 동시성 문제
책은 동시성 문제를 두 상황으로 나눈다. 둘은 원인과 해결책이 다르다.

**1. 같은 사용자가 예약 버튼을 여러 번 누름** (멱등성 문제)
- 경쟁하는 상대가 없다. 이미 처리한 요청을 다시 처리하지 않으면 된다

**2. 여러 사용자가 같은 방 유형의 마지막 재고를 동시에 예약함** (경쟁 조건)
- 실제 경쟁이 있다. 누군가는 실패해야 한다


### 1. 멱등키
- 클라이언트에서 버튼을 비활성화하는 방법이 있지만, api를 직접 호출하면 우회된다
- 그래서 api를 멱등하게 만든다. 예약 화면을 띄울 때 전역 고유 id 생성기로 reservation_id를 발급하고, 예약 요청에 같이 보낸다
- reservation 테이블의 pk가 reservation_id다. 같은 요청이 두 번 오면 두 번째 insert는 unique 제약 위반으로 실패한다

멱등성 검사를 애플리케이션이 "처리한 적 있나?" 조회하는 대신 디비 unique 제약에 맡긴 점이 좋았다.
조회 후 insert하면 그 사이에 같은 요청이 끼어들 수 있다. 1번 문제를 풀다가 2번 문제가 생기는 셈이다.


### 2. 마지막 재고
남은 방이 1개일 때

```text
     A                    B
read: reserved=99
                      read: reserved=99
99+1 <= 100 ok
                      99+1 <= 100 ok
write: reserved=100
                      write: reserved=100   ← A의 쓰기를 덮어씀
```

둘 다 성공했지만 reserved는 100이다. 방은 하나 줄었는데 예약은 두 건이다.
read와 write 사이에 다른 트랜잭션이 끼어들 수 있어서 생기는 문제다.

책이 제시하는 해결책 세 가지
1. 비관적 락 (`SELECT ... FOR UPDATE`)
	- 읽을 때 행을 잠근다. 트랜잭션이 끝날 때까지 다른 트랜잭션은 그 행을 갱신하지 못한다
	- 충돌을 확실히 막지만, 여러 행을 잠그면 데드락이 생길 수 있고 트랜잭션이 길어지면 다른 요청이 오래 기다린다
	- 책은 확장성 문제 때문에 이 방식을 권하지 않는다
	- 데드락은 잠그는 순서를 날짜 오름차순으로 통일하면 피할 수 있다 (책 내용은 아니고 따로 정리한 것)
2. 낙관적 락 (version 컬럼)
	- 락 없이 읽고, 쓸 때 읽었던 version이 그대로인지 확인한다
	- 그 사이 누가 바꿨으면 실패시키고 사용자가 재시도한다
	- 타임스탬프로도 할 수 있지만 서버 시계가 어긋날 수 있어서 버전 번호가 더 낫다고 한다
	- 충돌이 드물면 빠르지만, 경쟁이 심하면 실패와 재시도가 많아져 성능이 떨어진다
3. 디비 제약조건 (`CHECK (total_inventory - total_reserved >= 0)`)
	- 조건을 디비에 걸어서 위반하는 쓰기를 디비가 거절한다
	- 구현이 쉽고 경쟁이 적을 때 잘 동작한다
	- 경쟁이 심하면 낙관적 락처럼 실패가 많아진다. 제약조건은 코드와 달리 버전 관리가 어렵고, 지원하지 않는 디비도 있다

**책의 선택: 낙관적 락 또는 디비 제약조건**
- 호텔 예약은 qps가 높지 않아서, 같은 호텔·유형·날짜의 마지막 재고를 동시에 노리는 경우가 드물다
- 충돌이 드문데 매번 락을 잡을 필요는 없다
- 콘서트 티켓팅처럼 같은 자원에 요청이 몰리는 경우라면 판단이 달라진다

-> 선택 기준은 충돌이 얼마나 자주 일어나는가이다.

> 궁금했던 점. 책의 CHECK 제약은 `total_inventory - total_reserved >= 0`인데, 요구사항의 10% 오버부킹과 맞지 않는 것 같다.
>
> -> 제약을 `total_reserved <= total_inventory * 1.1`로 걸거나, total_inventory를 오버부킹 포함 값으로 저장해야 할 것 같다. 책에서는 이 부분을 따로 다루지 않는다.

> 책에는 없지만, 조건부 update 한 문장으로도 같은 효과를 낼 수 있다.
> ```sql
> UPDATE room_type_inventory
> SET total_reserved = total_reserved + 1
> WHERE hotel_id = ? AND room_type_id = ? AND date BETWEEN ? AND ?
>   AND total_reserved + 1 <= total_inventory * 1.1;
> ```
> 검사와 갱신이 한 문장 안에서 처리되므로 끼어들 틈이 없다. 영향받은 행 수가 숙박일수와 다르면(어느 하루라도 재고가 없으면) 롤백한다.
> 검사를 애플리케이션이 아니라 디비에 맡긴다는 점에서 제약조건 방식과 같은 발상이다.


## 규모가 1000배가 되면
책은 booking.com, expedia 규모로 커지는 경우를 가정한다.

**1. 샤딩**
- hotel_id로 샤딩한다 (`hash(hotel_id) % 서버 수`). 거의 모든 쿼리가 hotel_id로 필터링하기 때문이다
- 30,000 qps를 16개 샤드로 나누면 샤드당 1875 qps

**2. 캐싱**
- 현재와 미래 날짜의 재고만 의미가 있으므로 ttl을 둔다
- 재고를 redis에 둔다. 키는 `hotelID_roomTypeID_{date}`, 값은 남은 방 수
- 재고 조회는 캐시에서 하고, 재고 갱신은 디비에 먼저 한다
- 디비 → 캐시 동기화는 cdc(Debezium 등)로 비동기 처리한다

캐시와 디비의 역할

```text
캐시 : 예약 가능 여부 조회 (화면 표시용)
디비 : 최종 판정 (예약 확정)
```

- 캐시는 비동기로 갱신되므로 잠깐 실제 값과 다를 수 있다. 남은 방 1개로 보이지만 실제로는 0개일 수 있다
- 최종 판정은 디비의 제약조건이 하기 때문에 초과 예약은 생기지 않는다
- 사용자는 가끔 "방금 마감됐다"는 응답을 받게 된다

-> 틀려도 되는 곳(조회)과 틀리면 안 되는 곳(예약 확정)을 나눈 구조다.


## 서비스 간 데이터 일관성
책의 서비스는 호텔 / 요금 / 예약 / 결제 / 호텔 관리 서비스로 나뉜 msa다.
순수한 msa라면 서비스마다 디비를 따로 가지므로, 재고 차감과 예약 생성이 다른 디비에서 일어난다.

```text
[예약 서비스] ── 예약 디비   : 예약 insert   성공
[재고 서비스] ── 재고 디비   : 재고 차감     실패
                              → 재고는 그대로인데 예약은 생김
```

하나의 디비 트랜잭션으로 묶을 수 없으니 방법은 두 가지다
1. **2pc**: 조정자가 모든 참여자에게 준비 여부를 묻고, 전원이 준비되면 커밋, 하나라도 아니면 롤백한다
	- 강한 일관성을 보장하지만 블로킹 프로토콜이다. 한 노드가 장애를 일으키면 나머지가 진행하지 못한다
2. **saga**: 각 단계를 로컬 트랜잭션으로 바로 커밋하고, 뒤 단계가 실패하면 앞 단계를 보상 트랜잭션으로 되돌린다
	- 결과적 일관성이다. 중간 상태가 잠깐 보일 수 있고, 단계마다 보상 로직을 따로 작성해야 한다

**책의 선택**
- 예약과 재고를 같은 예약 서비스, 같은 rdb에 둔다
- 로컬 트랜잭션 하나로 묶이므로 2pc나 saga가 필요 없다
- 순수한 msa는 아니고, 복잡도를 줄이기 위한 절충이다

이번 챕터에서 가장 기억에 남는 부분이다.
분산 트랜잭션을 기술로 해결하는 대신, 함께 바뀌어야 하는 데이터를 같은 곳에 두어서 문제 자체를 피했다.

-> 서비스 경계를 정하는 일은 트랜잭션 경계를 정하는 일과 같다.

> 결제는 외부 pg사와 연결되어 있어서 같은 디비에 둘 수 없다. 예약(pending) → 결제 → 예약(paid/rejected) 흐름은 보상 처리가 필요할 것 같고, 7·8주차에서 다룰 것 같다.

## Appendix. 스프링/JPA에서는

책의 세 가지 동시성 제어를 코드로 옮기면 다음과 같다. (책 내용은 아님)

**비관적 락**
```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select i from RoomTypeInventory i " +
       "where i.hotelId = :hotelId and i.roomTypeId = :roomTypeId " +
       "and i.date between :start and :end order by i.date")
List<RoomTypeInventory> findForUpdate(...);
```
- 실제 쿼리는 `SELECT ... FOR UPDATE`
- `order by i.date`로 잠그는 순서를 고정하면 데드락을 피할 수 있다

**낙관적 락**
```java
@Entity
class RoomTypeInventory {
    @Version
    private Long version;
    ...
}
```
- `@Version`을 붙이면 jpa가 update에 `WHERE version = ?`를 추가한다
- 충돌하면 `ObjectOptimisticLockingFailureException`이 발생한다
- 재시도 로직은 애플리케이션이 직접 작성해야 한다

**조건부 update**
```java
@Modifying
@Query("update RoomTypeInventory i set i.totalReserved = i.totalReserved + :n " +
       "where i.hotelId = :hotelId and i.roomTypeId = :roomTypeId " +
       "and i.date between :start and :end " +
       "and i.totalReserved + :n <= i.totalInventory * 1.1")
int reserve(...);
```
- 반환값(영향받은 행 수)이 숙박일수와 다르면 예외를 던져 롤백한다
- 엔티티를 읽지 않아서 가장 단순하다

**멱등키**
- reservation 테이블의 pk로 클라이언트가 보낸 reservation_id를 쓴다
- 중복 insert 시 발생하는 `DataIntegrityViolationException`을 잡아, 에러 대신 기존 예약을 그대로 응답한다
- 첫 요청과 같은 응답을 돌려줘야 클라이언트가 재시도 결과를 따로 구분할 필요가 없다

정리하면:

> 이 챕터의 해법들은 모두 "검사와 변경 사이의 틈을 어떻게 막을 것인가"에 대한 답이다.<br>
> 비관적 락은 다른 트랜잭션을 기다리게 하고, 낙관적 락은 충돌을 감지해 다시 시도하게 하고, 제약조건과 조건부 update는 디비가 검사와 변경을 한 번에 처리한다.
