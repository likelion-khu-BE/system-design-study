# W4 광고 클릭 이벤트 집계

---

# 1. 요약

### 온라인 광고

* 실시간 데이터 통해 광고 효과 정량적 측정 가능
* RTB(실시간 경매): 디지털 광고의 핵심 프로세스, 속도 중요 - 1초 내에 모든 프로세스 마무리
* 데이터의 정확성 중요
* 핵심 지표: 클릭률, 전환률

### 기능 요구사항

* 지난 M분간 각 ad_id에 발생한 클릭 수 집계
* 지난 M분간 가장 많은 클릭이 발생한 상위 N개의 ad_id 목록 반환
* 집계 결과 필터링 기능 지원

### 데이터 모델

두 종류 - 1. 원시 데이터 2. 집계 결과 데이터

어떤 형태로 저장? 둘 다 저장 추천

원시 데이터: 디버깅 활용•백업 데이터 활용

집계 결과 데이터: 질의•활성 데이터

원시 데이터가 쓰기 중심 시스템이므로 카산드라나 influxDB를 사용하는 것이 바람직

---

## 개략적 설계안

실시간 빅데이터 처리 - 보통 데이터 무제한

입력은 원시 데이터(무제한 데이터 스트림), 출력은 집계 결과

### 비동기 처리

동기식 - 생산자 소비자 용량이 같을 수 없으므로 좋지않음, 소비자 메모리 부족 오류 등 문제 겪을 수 있음, 특정 컴포넌트 장애 전체 시스템 장애로 이어짐

→ 카프카 같은 메시지 큐 도입하여 생산자 소비자 결합 끊음 (비동기 동작), 생산자 소비자 규모 독립적 확장 가능

구조: 로그 감시자 - 메시지 큐 - 데이터 집계 서비스 - 메시지 큐

### 집계 서비스

**맵리듀스** 프레임 워크 사용

**유향 비순환 그래프(DAG) 모델**: 맵/집계/리듀스 노드 등의 작은 컴퓨팅 단위로 세분화. 각 노드는 한 가지 작업만 처리, 처리 결과 다음 노드에 인계, 맵리듀스 패러다임 표현하기 위한 모델,
빅데이터 입력으로 받아 병렬 분산 컴퓨팅 자원 활용하여 빅데이터를 작은 또는 일반적 크기 데이터로 변환할 수 있도록 설계된 모델

맵 노드 - 데이터 출처에서 읽은 데이터 필터링하고 변환

리듀스 노드 - 모든 집계 노드가 산출한 결과 최종 결과로 축약

## 상세 설계

### 스트리밍 vs 일괄 처리

스트림 처리와 일괄 처리 방식 모두 사용

스트림 처리 - 데이터 오는 대로 처리, 실시간으로 집계된 결과 생성

일괄 처리 - 이력 데이터 백업

**람다** - 두 가지 처리 경로를 동시에 지원하는 시스템 아키텍쳐, 유지 관리해야 할 코드 두벌

**카파 아키텍쳐** - 두 가지 처리 경로 하나로 결합하여 문제 해결, **단일 스트림 처리 엔진**(→ 실시간 데이터 처리, 끊임 없는 데이터 재처리 문제 모두 해결)

설계안 카파 아키텍처 따른다!

이력 데이터 재처리: 이미 집계한 데이터 다시 계산 (버그 발생 시점부터 원시 데이터 다시 읽어 집계 데이터 재계산하고 고쳐야 함)

### 시간

타임스태프 위치

* 이벤트 시각: 지연된 이벤트 처리 문제
* 처리 시각: 집계 결과가 부정확

데이터 정확도 아주 중요 → **이벤트 발생 시각** 사용 추천

이 경우 늦게 도착한 이벤트 처리 어떻게? **워터마크** 사용

워터마크: 여분의 사각형, 집계 윈도의 확장, 집계 결과 정확도 ↑ but 대기 시간, 지연 시간 증가

### 집계 윈도

텀블링 윈도: 시간을 같은 크기의 겹치지 않는 구간으로 분할 → 매 분 발생한 클릭 이벤트 집계 적합

슬라이딩 윈도: 데이터 스트림 미끄러져 나아가면서 같은 시간 구간 안에 있는 이벤트 집계 → M분간 많이 클릭된 상위 광고 알아내기 적합

### 전달 보장

‘정확히 한 번’ 방식 권장

### 시스템 규모 확장

메시지 큐, 집계 서버, 데이터베이스 - 독립 구성 요소, 상호 결합도 낮으므로 각기 독립적으로 규모 확장 가능

**집계 서비스 규모 확장**

노드 추가/삭제 통해 수평적 조정

집계 서비스 처리 대역폭 방안 두가지

1. ad_id마다 별도 처리 스레드 두는 방안
2. 자원 공급자에 배포하는 방식, 다중 프로세싱 활용 방안

구현하기 쉬운 건 1번 이지만 실제로 2번이 더 많이 쓰임, 더 많은 컴퓨팅 자원 추가하여 시스템 규모 확장 가능하기 때문

**데이터베이스 규모 확장**

카산드라는 안정해시와 유사한 방식의 수평적인 규모 확장 기본적 지원

### 핫스팟 문제

핫스팟: 다른 서비스나 샤드보다 더 많은 데이터 수신하는 서비스나 샤드

서버 과부하 문제 발생 가능 → 더 많은 집계 서비스 노드 할당하여 완화

### 결함 내성

집계는 메모리에서 이루어짐 → 집계 노드에 장애 생기면 집계 결과도 손실

업스트림 오프셋 같은 **시스템 상태**를 **스냅숏**으로 저장하고 마지막으로 저장된 상태부터 복구

스냅숏 - 복구 절차 단순해짐

# 2. 의문

## 1. ‘칼럼형 데이터 형식 가운데 하나를 사용하여 아마존 S3에 데이터를 저장하는 방법’이 뭔가?

칼럼형 데이터 형식은 데이터를 행(row) 단위가 아니라 **열(column) 단위로 저장하는 데이터 형식**이다.

대표적으로 **Parquet, ORC** 등이 있다.

아마존 S3 같은 객체 저장소에 데이터를 저장할 때 이러한 칼럼형 형식을 사용하면 필요한 열만 읽을 수 있어 대용량 데이터 분석에 효율적이다.

예를 들어 광고 클릭 데이터에서 `ad_id`와 `timestamp`만 필요하다면 전체 데이터를 읽지 않고 해당 열만 읽을 수 있다.

---

## 2. ‘동일한 ad_id를 갖는 이벤트가 서로 다른 카프카 파티션에 입력될 수도 있다’가 뭘 의미?

카프카에서는 메시지를 어떤 파티션에 넣을지 결정하는 **파티셔닝 방식**에 따라 메시지가 여러 파티션으로 나뉠 수 있다.

즉, 동일한 `ad_id`를 가진 클릭 이벤트라도 파티션 키를 `ad_id`로 지정하지 않았다면 서로 다른 파티션에 저장될 수 있다는 의미이다.

예를 들어 다음과 같은 이벤트가 있다고 하면,

```text
ad_id = A
ad_id = A
ad_id = A
```

`ad_id`를 파티션 키로 사용하지 않는 경우 각각의 이벤트가

```text
Partition 0 → ad_id = A
Partition 1 → ad_id = A
Partition 2 → ad_id = A
```

처럼 서로 다른 파티션에 들어갈 수 있다.

따라서 `ad_id`별로 정확하게 집계하려면 **여러 파티션에 흩어진 동일한 ad_id의 이벤트를 모아서 집계하는 과정**이 필요하다.

## 3. ‘노드 간 통신 TCP로 처리(노드들 서로 다른 프로세스에서 실행되는 경우), 공유 메모리로 처리(서로 다른 스레드에서 실행되는 경우)’ 차이가 뭐지?

**프로세스와 스레드의 실행 환경 차이** 때문이다.

* **서로 다른 프로세스**

  * 각각 독립적인 메모리 공간을 가짐
  * 직접 메모리를 공유할 수 없음
  * 따라서 TCP 같은 네트워크 통신을 이용해 데이터를 주고받음

* **서로 다른 스레드**

  * 같은 프로세스 안에서 실행
  * 같은 메모리 공간을 공유할 수 있음
  * 따라서 공유 메모리를 통해 데이터를 주고받을 수 있음

즉, **프로세스는 메모리가 분리되어 있기 때문에 통신이 필요하고, 스레드는 메모리를 공유할 수 있기 때문에 공유 메모리를 사용할 수 있다.**

---

## 4. ‘비동기적 처리 환경 (데이터는 메시지 큐를 거쳐야 한다)’ 비동기적 처리 환경과 데이터가 메시지 큐 거치는거랑 뭔 상관?

메시지 큐가 **생산자와 소비자를 분리해 주기 때문**이다.

동기식으로 직접 연결되어 있다면 생산자는 소비자가 처리할 때까지 기다려야 한다.

반면 메시지 큐를 사용하면 생산자는 데이터를 메시지 큐에 넣은 뒤 바로 다음 작업을 수행할 수 있고, 소비자는 자신의 처리 속도에 맞춰 메시지를 가져갈 수 있다.

즉,

```text
동기식

생산자 → 소비자
          ↑
       처리될 때까지 기다림
```

에서

```text
비동기식

생산자 → 메시지 큐 → 소비자
             ↑
        중간에 저장
```

와 같이 바뀐다.

따라서 **메시지 큐를 통해 생산자와 소비자가 서로 기다리지 않고 독립적으로 동작할 수 있기 때문에 비동기적 처리가 가능해진다.**

## 5. 클러스트에 새 노드 추가하면 가상 노드 간의 균형 자동으로 다시 조정(수동으로 샤딩 조정 과정 필요하지 않음)되는 원리?

카산드라에서는 데이터를 특정 노드에 직접 지정하는 것이 아니라 **토큰 링과 일관된 해싱을 이용해 데이터의 담당 노드를 결정**한다.

각 노드는 여러 개의 **가상 노드(vnode)**&#xB97C; 가지고 있으며, 새로운 노드가 추가되면 새로운 노드에도 토큰 범위가 할당된다.

그 결과 기존 노드들이 담당하던 데이터 중 일부가 새로운 노드의 담당 범위로 이동하게 되어 데이터가 여러 노드에 다시 분산된다.

즉, 관리자가 데이터를 하나씩 직접 옮기는 것이 아니라 **토큰과 가상 노드 기반으로 데이터가 자동으로 재분배되기 때문에 수동으로 샤딩을 조정할 필요가 줄어든다.**

## 6. ‘배치 작업 결과가 실시간 집계 결과와 정확히 일치하지 않을 수 있다’의 의미?

실시간 집계와 배치 작업이 **데이터를 처리하는 시점이나 방식이 다를 수 있기 때문**이다.

예를 들어 실시간 집계에서는 이벤트가 도착한 순서나 늦게 도착한 이벤트 때문에 일부 이벤트가 아직 집계되지 않을 수 있다.

반면 배치 작업은 나중에 원시 데이터를 다시 읽어 전체 데이터를 기준으로 집계할 수 있다.

따라서 같은 시간 구간을 집계하더라도

```text
실시간 집계 결과 → 980건
배치 작업 결과   → 1,000건
```

처럼 차이가 발생할 수 있다.

특히 **지연된 이벤트, 데이터 누락, 처리 시점의 차이** 등이 원인이 될 수 있다.

# 3. 새롭게 알게 된 개념

### 무제한 데이터 스트림

끝이 정해지지 않고 계속 들어오는 데이터 흐름

### 비동기 처리

생산자와 소비자가 서로 기다리지 않고 독립적으로 작업을 수행하는 처리 방식

### 원자적 커밋

여러 작업을 하나의 단위로 묶어 모두 성공하거나 모두 실패하도록 처리하는 방식으로, 정확하게 한 번 처리하는 데 활용될 수 있음

### 병렬 분산 컴퓨팅 자원

하나의 큰 작업을 여러 컴퓨터나 처리 장치에 나누어 동시에 처리할 수 있는 컴퓨팅 자원

### 데이터 웨어 하우스

여러 곳에서 수집한 데이터를 저장하고 분석 및 의사결정에 활용하기 위한 데이터 저장 시스템

### 분산 트랜잭션

여러 서버나 데이터베이스에 걸쳐 실행되는 작업을 하나의 트랜잭션처럼 일관성 있게 처리하는 방식

### 자원 공급자

컴퓨팅, 네트워크, 저장 공간 등의 자원을 제공하고 관리하는 시스템 또는 서비스

### 다중 프로세싱

여러 프로세스를 동시에 실행하여 작업을 병렬로 처리하는 방식

### 안정 해시, 수평적 규모 확장

안정 해시는 데이터와 서버를 해시 공간에 배치하여 서버가 추가·삭제되어도 데이터 이동을 최소화하는 방식이며, 수평적 규모 확장은 서버를 추가하여 시스템의 처리 능력을 높이는 방식

### 전역-지역 집계, 분할 고유 집계

전역-지역 집계는 전체 데이터를 대상으로 최종 집계를 수행하는 방식이고, 분할 고유 집계는 데이터를 여러 부분으로 나누어 각각 독립적으로 집계하는 방식

### 결함 내성

시스템의 일부 구성 요소에 장애가 발생해도 전체 시스템이 중단되지 않고 계속 동작할 수 있는 능력

### 스냅숏

특정 시점의 시스템 상태나 데이터를 저장해 장애 발생 시 해당 시점의 상태로 복구할 수 있도록 하는 것

### 분산 커밋 로그

여러 서버에 분산되어 저장되면서 데이터의 변경 내역을 순서대로 기록하고 복제하는 로그

### 하이브

대규모 데이터를 SQL과 유사한 방식으로 조회하고 분석할 수 있도록 지원하는 데이터 웨어하우스 시스템

### 일래스틱서치

대규모 데이터를 빠르게 검색하고 분석할 수 있도록 설계된 분산 검색 및 분석 엔진

### 클릭하우스, 드루이드 OLAP 데이터베이스

대규모 데이터를 빠르게 집계하고 분석하는 OLAP(온라인 분석 처리) 용도의 데이터베이스 시스템

### 업스트림, 다운스트림 (카프카)

업스트림은 현재 시스템으로 데이터를 전달하는 이전 단계의 시스템이고, 다운스트림은 현재 시스템에서 처리된 데이터를 전달받는 다음 단계의 시스템

### 빅데이터 처리 시스템

대규모 데이터를 여러 컴퓨터에 분산하여 저장하고 병렬로 처리할 수 있도록 구성한 시스템
