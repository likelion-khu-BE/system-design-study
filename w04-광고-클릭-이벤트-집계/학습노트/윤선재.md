# 6장. 광고 클릭 이벤트 집계

## 1. 요구사항과 설계 범위

- 지난 M분 동안의 ad_id별 클릭 수
- 매분 가장 많이 클릭된 상위 100개 광고
- 속성별 필터링 지원
- 규모는 하루 10억 클릭, 최대 50K QPS, 일 저장량 약 100GB
- 광고 과금과 효과 측정에 쓰이는 숫자라서 지표 모니터링(5장)과 구조는 비슷해도 **정확성** 요구가 훨씬 높다.

## 2. 데이터 저장

원시 데이터와 집계 결과를 둘 다 저장한다.

| 구분 | 용도 |
|---|---|
| 원시 데이터 | 버그 수정, 재계산 |
| 집계 데이터 | 빠른 조회, 용량 절감 |

## 3. 카프카와 메시지 큐 두 개

카프카는 이전 장에서도 계속 나왔다. 쓰는 이유는 생산자와 소비자의 결합을 끊기 위해서다.

- 장애 격리
- 유량 제어: 소비자보다 생산자가 빨라도 브로커가 잠깐 받아 준다.
- 독립적인 확장
- 새 소비자나 새 토픽을 추가하기 쉽다. 기존 생산자와 소비자는 바꿀 필요가 없다.
- 디스크 저장과 복제본 덕에 프로세스가 죽어도 데이터가 남을 확률이 높다.

큐는 두 개로 나눈다.

- 업스트림: 광고 클릭 원본 이벤트
- 다운스트림: 분 단위 집계 결과, 분 단위 상위 N개

## 4. 집계 서비스

- 맵리듀스 구조로 맵 / 집계 / 리듀스 노드를 따로 둔다.
    - 맵: 필터링과 변환
    - 집계: ad_id별 클릭 수 집계
    - 리듀스: 집계 노드들의 결과를 최종 결과로 합침
- 핵심은 한 주체가 다 하지 않고 쪼개서 병렬로 처리하는 것이다. 리소스는 더 쓰지만 더 빨리 끝난다.

## 5. 스트리밍 vs 일괄 처리

- 람다 아키텍처는 배치 계층과 스트리밍 계층을 둘 다 관리해야 한다.
- 카파 아키텍처는 둘을 하나의 스트리밍 경로로 합쳐서 이 부담을 없앤다.
- 재계산이 필요할 때는 **재계산 전용 서비스**를 따로 둔다.
    - 집계 서비스가 큐를 되감으면 지금 흐르는 데이터 처리에 지장이 생겨 전체 장애로 번질 수 있다.
    - 그래서 재계산 서비스는 큐가 아니라 원시 데이터 DB에서 읽고, 결과는 같은 다운스트림 큐로 보낸다.
    - 이 시점에 해당 윈도우의 처리는 이미 늦었다. 시스템에 영향 없이 안전하게 복구하는 게 우선이다.

## 6. 시간 처리

### 타임스탬프

- 이벤트 시각(클릭한 시각)과 처리 시각(서버가 처리한 시각) 중 이벤트 시각을 쓴다.
    - 이벤트 시각: 더 정확하지만 클라이언트 시계 오류나 조작에 취약하다.
    - 처리 시각: 더 안정적이지만 늦게 도착한 이벤트가 있으면 부정확해진다.
- 이벤트 시각을 쓰면 늦게 도착한 이벤트가 문제가 되므로 **워터마크**로 대응한다.
    - 윈도우 끝에 t초를 더 붙여서, 늦게 처리된 이벤트도 받는다.
    - t가 길면 정확도는 오르지만 지연이 늘고, 짧으면 지연은 줄지만 정확도가 떨어진다.
    - 워터마크를 넘겨서 오는 이벤트는 어차피 있다. 드문 경우까지 처리하려고 설계를 복잡하게 하면 ROI가 낮다. 이런 오차는 나중에 조정으로 맞춘다.

### 윈도우

| 종류 | 특징 | 쓰는 곳 |
|---|---|---|
| 텀블링 | 안 겹치는 고정 구간 | 매분 클릭 수 (요구사항 1) |
| 슬라이딩 | 겹치면서 이동 | 지난 M분 상위 N개 (요구사항 2) |

## 7. 전달 보장

- 카프카의 전달 방식은 at-most-once, at-least-once, exactly-once 세 가지다.
- 약간의 중복이 괜찮으면 at-least-once면 된다. 하지만 이 시스템은 몇 % 차이가 수백만 달러로 이어질 수 있어서 **exactly-once**를 쓴다.
- 중복 원인은 클라이언트가 같은 이벤트를 여러 번 보내는 경우와 서버 장애다. 앞의 것은 광고 사기 방지 쪽 영역으로 보고, 여기서는 서버 장애를 본다.

### 오프셋을 언제 저장하나

1. 집계하고 결과를 보낸 뒤 장애가 나서 업스트림에 완료 응답을 못 하면, 같은 구간을 다시 소비해서 중복이 생긴다.
2. 오프셋을 HDFS/S3에 먼저 저장하면, 결과를 보내기 전에 죽었을 때 그 구간이 유실된다.
3. 수신 확인 후에 오프셋을 저장해도, 오프셋 저장 전에 죽으면 같은 이벤트가 다시 전달될 수 있다.
4. 그래서 **"결과 전송 → 오프셋 저장 → 수신 확인"을 하나의 분산 트랜잭션으로 묶는다.**

여기서 원하는 건 "클릭 이벤트 하나가 집계 결과에 정확히 한 번만 반영된다"는 것이다. 업스트림에서 가져오는 것부터 다운스트림에 발행하는 것까지를 논리적으로 하나의 원자적 행위로 만드는 셈이다. 실제로 원자적으로 동작하는 건 그림 속 트랜잭션 영역이고, 이것만 지키면 전체가 논리적으로 원자적이라고 볼 수 있다.

## 8. 규모 확장

### 메시지 큐

- 생산자는 제한이 없어서 확장이 쉽다.
- 소비자는 그룹 재조정으로 늘리고 줄인다. 재조정은 오래 걸릴 수 있어서 트래픽이 적은 시간대에 한다.
- 같은 ad_id의 이벤트를 같은 파티션에 넣으려고 ad_id를 해시 키로 쓴다.
- 파티션 수가 바뀌면 같은 ad_id가 다른 파티션으로 가므로, 처음부터 넉넉히 잡는다.
- 토픽은 지역별, 광고 유형별로 나눌 수 있다. 처리량은 늘지만 복잡도와 유지보수 비용도 늘어난다.

### 집계 서비스

- 방안 1: ad_id마다 처리 스레드를 둔다. 구현이 쉽고 자원 공급자에 의존하지 않는다.
- 방안 2: YARN 같은 자원 공급자에 배포해 멀티 프로세싱을 쓴다. 자원을 더 붙여 확장할 수 있어서 실무에서는 이쪽을 더 쓴다.

### DB

- 카산드라는 안정 해시와 비슷한 방식으로 수평 확장을 기본 지원한다.
- 새 노드를 추가하면 가상 노드 간 균형이 자동으로 조정된다.

### 핫스팟 문제

- 큰 광고주의 광고는 클릭이 몰린다. ad_id로 파티션을 나누기 때문에 특정 집계 노드에 부하가 집중된다.
- 리소스 매니저에 추가 노드를 요청해서 이벤트를 나눠 처리하고, 축약 결과를 원래 노드에 기록한다.

## 9. 결함 내성

- 집계는 메모리에서 하므로 노드가 죽으면 결과가 사라진다. 카프카를 처음부터 재생하면 너무 오래 걸린다.
- 그래서 **스냅숏**을 저장한다. 업스트림 오프셋뿐 아니라 "지난 M분 상위 N개" 같은 시스템 상태도 함께 저장한다.
- 노드가 죽으면 새 노드로 교체하고 마지막 스냅숏에서 복구한다. 스냅숏 이후의 이벤트는 카프카에서 다시 읽는다.

## 10. 모니터링과 조정

### 지속적 모니터링

- 지연 시간: 단계마다 타임스탬프를 남겨서 차이를 지표로 본다.
- 메시지 큐 크기: 갑자기 늘면 집계 노드를 추가한다. 카프카는 records-lag으로 본다.
- 집계 노드의 CPU, 디스크, JVM 같은 자원

### 조정(reconciliation)

- 집계 결과는 비교할 제3자가 없다. 그래서 원시 데이터를 이벤트 시각 순으로 정렬해 배치로 다시 집계하고, 실시간 결과와 비교한다.
- 정확도가 더 필요하면 윈도우를 더 작게(예: 1시간) 잡는다.
- 늦게 도착한 이벤트 때문에 배치와 실시간이 완전히 일치하지는 않는다.
- 무겁고 오래 걸리지만 실시간성이 필요 없는 작업이라, 주기적으로 돌리는 것으로 충분하다.
- 워터마크를 넘긴 이벤트를 버려도 된다는 뜻이 아니다. 지금 처리하기엔 ROI가 낮으니 나중에 조정에서 잡겠다는 뜻이다.

## 11. 대안 설계

기존안은 집계 로직을 직접 만드는 방식이었다. 대안은 역할을 전문 시스템에 나눠 맡긴다.

- 원본 보관: **Hive**
- 원본 탐색(특정 사용자, IP, 광고 조건 검색): **Elasticsearch**
- 실시간 집계 조회(최근 M분 클릭 수, Top N, 국가별 클릭 수): **ClickHouse** (Druid 같은 OLAP DB도 가능)


## 정리

- 이 장의 한 줄은 "이미 계산한 것을 기억해서 다시 계산하지 않는다"이다.
- 정확성이 돈과 직결되므로 exactly-once, 재계산 서비스, 조정으로 세 겹의 안전장치를 둔다.
- 시간(워터마크), 전달 보장(분산 트랜잭션), 확장(핫스팟), 복구(스냅숏)는 모두 **정확도, 지연, 복잡도 사이의 트레이드오프**로 결정한다.
