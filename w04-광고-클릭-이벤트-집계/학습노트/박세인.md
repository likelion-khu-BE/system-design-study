# 6장 광고 클릭 이벤트 집계

디지털 광고 프로세스: RTB(real-time bidding)
→ 여러 수요자가 하나의 지면에 실시간 경매를 진행해서 가장 높은 가격을 제시한 수요자가 입찰돼 해당 지면에 실시간으로 광고가 뜨는거. 온라인 겜 하다가 중간에 잠깐 뜨는 광고 그런거 

입찰가 지정에 영향 주는거

- CTR: 클릭수/노출수*100
- CVR: 전환수/클릭수*100

# 면접 요구사항

데이터

- 여러 서버에 분산된 로그파일. id, time, userid, ip, country 정보

기능적 요구사항

- 특정 광고에 대한 M분간의 클릭 수 집계
- 1분간 가장 많이 클릭된 광고 100개 집계
    - 기간, 광고 수 변경 가능해야 함
- 질의 결과 필터링 - ip, userid, country 기준

비기능적 요구사항

- 매일 10억개 광고 클릭
- 광고 200만회
- 광고 클릭 매년 30% 증가
- 늦게 도착, 중복 이벤트, 시스템 복구 고려
- 모든 처리 수 분 내
    - 집계 결과 중요. 몇 분 지연 가능

#### 집계 서비스

- 맵리듀스 프레임워크 사용: 큰 데이터를 여러 컴퓨터에 나눠 처리하고 결과를 합치는 프레임워크. Map(나누기)+Reduce(합치기)
    - DAG 모델 사용 : 방향있고 순환 안되는 그래프 → 전으로 돌아가지 않도록
    - Map 노드 : 집계하기 좋은 형태로 데이터 정리+올바른 노드로 분배 후 보내기
        - Map노드 대신 그냥 카프카 파티션을 구독하면 안되는 걸까?
        ⇒파티션 기준이 ad_id가 아닌 경우 여러파티션에 같은 ad_id 이벤트가 나눠져있을 수가 있음→ 재파티셔닝 필요→보통 flink와 kafka stream으로 구현
    - 집계 노드 : 매분 집계
    - 리듀스 노드 : 집계 노드가 산출한 결과를 축약.
- 노드 간 통신 - TCP(다른 프로세스)/공유 메모리(다른 스레드)
- 면접에 적용
    - 클릭 이벤트 수 : ad_id%(집계 노드 수)를 기준으로 분배
        - 한 노드 안에 광고 몇 종류가 들어가는지는 상관 없고 같은 종류의 광고가 같은 집계 노드 안에 들어가기만 하면 됨 그 후 집계 노드 내부에서 ad_id 별로 나뉘어 다시 count
    - 가장 많이 클릭된 상위 N개 : ad_id기준으로 나눠서 분배된 맵 별로 상위 3개 집계→다 합쳐서 최종 상위 3개
    - 데이터 필터링: 필터링 기준 사전에 정의하고 집계
        - 스타 스키마 방- 데이터 웨어하우스에서 자주 사용(걍 다 모아놓은 회사 전체 데이터 저장소)
            - 이해 쉬움+구축 간단
            - 기존 집계 서비스 재사용 가능
            - 데이터에 빠르게 접근 가능
            - 레코드 많이 생성

메시지 큐의 전달 방식→ 최대 한 번, 최소 한 번, 정확히 한 번

해당 서비스 → 정확히 한 번(경매 가격이 달라져서)

1. 데이터 중복 제거
    1. 클라이언트가 의도적으로 여러번 → 위험제어
    2. 서버 장애 :이벤트받아서 오프셋 100부터 소비→100~110했다고 보냈는데 그걸 못 받음→ 100부터 다시 보냄→데이터 중복 
        1. 외부 파일 저장소에 오프셋을 기록하면 됨.
            1. 근데 만약에 오프셋을 먼저 기록했는데 110까지 사실 처리를 못했다면???→110까지 했다는 응답을 받고 나서 오프셋을 저장하면 됨(확인은 첨에 110까지 할거다 그때 확인. 확정을 나중에)

### 6. 시스템 규모 확장

일단 메시지 큐 방식이므로 독립적. 

1. 메시지 큐 확장 → 걍 생산자 늘리고 소비자는 시스템에 맞춰서 늘렸다 줄였다
2. 집계 서비스 확장 → 규모는 맵 리듀스 방식이니까 그냥 노드 추가/삭제 통해서 조정. 처리 대역폭은 별도의 처리 스페어 두거나 집계 서비스 노드를 자동으로 늘리고 줄일 수 있게 서버 자원을 알아서 배정해주는 관리 시스템 위에 올림. 클라우드가 노는 서버 위에 사용자들 데이터를 저장해주는 시스템인 것 처럼 놀고있는 서버에 처리 노드를 자동으로 올리는거

### 7. 데이터 베이스 규모 확장

데이터를 여러 서버에 골고루 나눠 담고, 서버 추가하면 알아서 다시 나눠 담는 서비스를 이미 기본으로 카산드라가 쓰고 있음

- 해시 링에 데이터를 해시해서 원형 링 위의 한 지점에 놓고, 링을 여러 구간으로 잘라 각 구간마다 담당 서버 지정. 데이터는 거기에 저장
- 다른 서버에도 복사본 둠
- 가상 노드: 서버 하나가 큰 구간 하나만 맡으면 구간 크기가 들쭉날쭉한 경우 어떤 서버에 데이터가 몰림. 서버 하나 추가하면 바로 옆 서버 하나만 데이터를 떼줘야해서 부담이 쏠림 → 링을 작게 많이 쪼개고 각 서버가 여러 조각을 맡게 함

### 8. 핫스팟 문제

특정 노드 하나에만 일이 몰려서 그 노드가 과부하 걸리는 문제 

- 같은 ad_id는 무조건 같은 집계 노드로 보내는데 이때 광고마다 클릭수가 많이 차이나면 과부하가 옴

해결 방법

1. 더 많은 집계 서비스 노드 할당해서 완화 : 한 노드가 감당할 수 있는 양을 초과하면 자원 관리자에게 추가 자원 신청하고 할당. 원래 집계 서비스 노드는 각 서비스 노드가 수용 가능한 크기의 이벤트를 처리할 수 있도록 (새로 추가된 노드+기존 집계서비스 노드-1-)개의 그룹으로 분할→ 집계 끝나 축약되면 다시 원래 집계 서비스 노드로 
2. 전역-지역 집계
3. 분할-고유 집계

### 9. 결함 내성

: 시스템 일부가 고장나도 전체가 멈추거나 결과가 틀어지지 않고 계속 돌아가는 성질. 원점부터 다시 시작하지 않도록 시스템 상태를 스냅숏으로 저장해 마지막으로 저장된 상태부터 복구해 나가는 것

- 서비스 노드 하나에 장애→해당 노드 새 것으로 대체→마지막 스냅숏에서 데이터 복구

### 10. 데이터 모니터링 및 정확성

: 돈 문제(경매 가격, 지불 가격)가 걸려있어서 정확성은 매우 중요

- 지속적으로 모니터링 해야하는 경우
    - 지연 시간 : 시스템의 중요 부분마다 시각 추적 가능하도록
    - 메시지 큐 크기: 카프카의 경우에는 레코드 처리 지연 지표
    - 집계 노드의 시스템 자원
- 조정: 다양한 데이터를 비교하여 데이터 무결성을 보증
    - 매일 각 파티션에 기록된 클릭 이벤트를 이벤트 발생 시각에 따라 정렬한 결과 만들어 실시간 집계와 비교

---

- DAU : 일간 능동 사용자
- QPS : 초당 쿼리 수. 1초동안 처리하는 요청의 수
    - QPS 구할 때 하루는 대략 10^5로 처리한다
