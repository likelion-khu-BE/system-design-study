# 광고 클릭 이벤트 집계

## RTB(Real-Time Bidding) | 실시간 입찰

- 디지털 광고의 핵심 프로세스
- 온라인 광고에서 사용자가 어떤 페이지를 열었을 때, 해당 사용자에게 보여줄 광고 자리를 누가 차지할 것인지를 광고주들이 실시간으로 입찰해서 결정하는 방식
  1. 사용자가 웹페이지/앱을 엶
  2. 광고를 보여줄 자리가 생김
  3. 여러 광고주가 거의 실시간으로 입찰
  4. 가장 적절한 광고가 선택됨
  5. 사용자에게 광고가 노출됨
- 속도와 데이터의 정확성이 중요

### 기능/비기능 요구사항

- 기능
  - 지난 M분 동안의 ad_id 클릭 수 집계
  - 매분 가장 많이 클릭된 상위 100개 광고 아이디를 반환
  - 다양한 속성에 따른 집계 필터링 지원
- 비기능
  - 집계 결과 정확성은 데이터가 RTB 및 광고 과금에 사용되므로 중요
  - 지연되거나 중복된 이벤트를 적절히 처리할 수 있어야 함
  - 전체 처리 시간은 최대 수 분을 넘지 않아야 함
  - 부분적인 장애는 감내할 수 있어야 함

### 개략적 설계안

#### 1. 질의 API

두 개의 api만 필요하고 집계 결과 필터링은 호출 인자를 이용하여 한다.

- 지난 M분간 각 ad_id에 발생한 클릭 수 집계
  - GET
  - ad_id와 해당 광고에 대한 count 반환
- 지난 M분간 가장 많은 클릭이 발생한 상위 N개 ad_id 목록
  - GET
  - 광고 식별자 목록인 ad_ids 반환

#### 2. 데이터 모델

원시 데이터와 집계 결과 데이터 둘 다를 저장하는 것을 추천. 원시 데이터를 디버깅에 활용할 수 있게 백업 데이터로 저장

- 원시 데이터 = 로그
- 집계 결과 데이터
  - 같은 광고 아이디와 클릭 시간을 갖는 레코드에 동일한 filter_id를 붙이고 이에 따라 count 집계

작업 흐름이 ‘쓰기 중심’이기 때문에 관계형 DB보다 카산드라나 InfluxDB가 적합

#### 3. 비동기 처리

데이터를 동기적으로 처리하면, 트래픽이 갑자기 증가하여 이벤트 수가 소비자의 처리 용량을 넘어서게 될 때 문제가 발생할 수 있다.

- 메시지 큐(ex. 카프카)를 도입하여 생산자와 소비자의 결합을 끊기
- 첫번째 메시지 큐: 원시 데이터 저장
- 두번째 메시지 큐: 위에서 언급한 두개의 api에 대한 반환값(집계 결과 데이터) 저장

#### 4. 집계 서비스

- 맵리듀스(MapReduce) 프레임워크
  - 아주 많은 데이터를 여러 서버에 나눠서 병렬 처리하기 위한 방식
  - DAG(유향 비순환 그래프)와 같이 활용됨
  - 단계
    1. Map(맵 노드): 데이터를 중간 형태로 변환

       ```text
       ad1 → (ad1, 1)
       ad2 → (ad2, 1)
       ad1 → (ad1, 1)
       ad3 → (ad3, 1)
       ...
       ```

    2. Shuffle / Group(집계 노드): 같은 key끼리 모으기

       ```text
       ad1 → [1, 1, 1]
       ad2 → [1, 1]
       ad3 → [1]
       ```

    3. Reduce(리듀스 노드): 모인 값을 최종 집계

       ```text
       ad1 → 3
       ad2 → 2
       ad3 → 1
       ```

  - 유향 비순환 그래프(DAG): 각 노드는 한가지 작업만 처리하며 처리 결과를 다음 노드에 인계

## 상세 설계

### 1. 데이터 처리 방식

- 일괄 처리 | Batch Processing
  - 데이터를 일정량 모아뒀다가(로그를 수집했다가) 한번에 처리
  - 집계 결과 데이터를 생성하는데 사용
- 스트림 처리 | Stream Processing
  - 데이터가 들어오는 즉시 처리
  - 이력 데이터를 백업하는데 사용
- 설계 방식
  - 람다 아키텍처 | Lamda Architecture
    - 일괄 처리와 스트림 처리를 동시에 돌리고 나중에 합침
    - 유지 관리해야 할 코드가 두 벌

      ```text
                  ┌─ Batch Layer ─→ 정확한 최종 집계
      이벤트 ─────┤
                  └─ Speed Layer ─→ 빠른 실시간 집계
      ```

  - 카파 아키텍처 | Kappa Architecture
    - 스트림 처리 하나로 일괄 처리까지 대체
    - 일괄 처리는 저장된 이벤트 로그를 다시 스트림으로 재생해서 처리

      ```text
      이벤트 로그 → Stream Processing → 결과
      ```

→ 운영 복잡도, 실시간성의 관점에서 람다보다 카파 아키텍처가 적합

### 2. 시간

- 생성되는 타임스탬프
  - 이벤트 시각
  - 처리 시각

→ 처리 시각이 지연된다면 집계 결과가 부정확할 수 있음

- 해결책: 워터마크(watermark)
  - 늦게 도착하는 이벤트를 얼마나 기다릴지 정하는 기준선
  - 집계 윈도우 뒤에 붙는 여유 시간 블럭
- 집계 윈도우의 종류
  - 스트림 데이터를 시간 구간으로 묶는 방법

| 종류 | 윈도우 크기 | 이동 간격 | 겹침 여부 | 예시 |
| --- | --- | --- | --- | --- |
| 고정 윈도우 | 고정 | 윈도우 크기만큼 | X | 1분 단위 집계 |
| 텀블링 윈도우 | 고정 | 윈도우 크기만큼 | X | 10:00~10:01, 10:01~10:02 |
| 호핑 윈도우 | 고정 | 정해진 간격, 윈도우보다 짧을 수 있음 | O 가능 | 5분 데이터를 1분마다 집계 |
| 슬라이딩 윈도우 | 고정 또는 조건 기반 | 현재 시점을 기준으로 이벤트/시간이 흐를 때 계속 이동 | O | 현재 시점 기준 최근 5분 |

→ 지난 M분간 가장 많이 클릭된 상위 N개 광고를 알아내야 하므로 슬라이딩 윈도우가 적합

### 3. 전달 보증 | Delivery Guarantee

- 메시지 큐는 보통 3가지 유형의 전달 방식 지원
  1. 최대 한 번 | at-most once
     - 중복은 없음
     - 유실되면 광고주 과금이나 통계가 틀어질 수 있어 위험
  2. 최소 한 번 | at-leat once
     - 유실은 막지만 중복이 발생할 수 있음
  3. 정확히 한 번 | exactly once
     - 이상적으로는 각 클릭을 정확히 한 번만 반영하는 것
     - 실제로 구현하는 것이 어렵고 비용이 큼
     - 현실적으로 at-leat once 방식으로 데이터를 받고, 집계 결과는 중복 제거/idempotency를 통해 exactly-once처럼 보이게 만든다.

- 데이터 중복 제거
  - 중복 상황
    1. 클라이언트 측이 악의적으로 같은 이벤트를 여러 번 보냄
    2. 서버 장애로 인해 이벤트를 처리했지만 ACK를 못 보내서 같은 이벤트가 다시 옴
       - 업스트림 서비스 | Upstream Service: 현재 서비스 기준으로 데이터를 보내주는 앞단 서비스
  - 2번 상황의 해결책: 오프셋 저장
    - 메시지 처리 및 집계 결과 저장이 완료된 이후, ACK를 보내기 전에 처리한 메시지의 오프셋을 저장
    - 장애 후에는 저장된 오프셋부터 이어서 처리

- idempotency(멱등성)
  - 여러 번 처리해도 최종 결과가 한 번 처리한 것과 같게 유지되는 성질
  - 보통 각 이벤트에 고유한 event_id를 붙여 이미 처리한 ID인지 확인하는 방식으로 구현

### 4. 결함 내성 | Fault Tolerance

- 집계 서버 일부가 죽거나 장애가 나도 전체 집계 시스템이 계속 동작하고, 데이터도 최대한 잃지 않는 능력
- 해결책: 스냅숏(snapshot)
  - 집계 노드에 장애가 생겨 집계 결과가 손실되었을 때, 업스트림 카프카 브로커에서 이벤트 로그를 다시 받아와 집계할 수 있음
  - 하지만 이벤트 로그를 처음부터 재생하여 집계하면 오래 걸리기 때문에 업스트림 오프셋과 집계 결과 데이터를 스냅숏으로 저장하고
  - 마지막으로 저장된 상태부터 복구해 나가면 됨

### 5. 데이터 모니터링 및 정확성

- 데이터 무결성과 집계 정확성을 검증하기 위해 조정(reconciliation) 단계가 필요
- 광고 클릭 집계 결과는 비교할 수 있는 독립적인 제3의 기준 데이터가 없음
- 따라서, 원본 클릭 이벤트 로그와 실시간 집계 결과를 비교하는 방식으로 조정을 할 수 있음
