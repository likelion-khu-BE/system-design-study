# 광고 클릭 이벤트 집계

> **real time bidding(RTB)**, 광고주와 공급자 사이에 광고 거래소가 있고 경매를 한다

---

## 1. 요구사항

- 지난 M분 동안의 ad_id 클릭 수
- 매분 가장 많이 클릭된 상위 100개 광고 아이디 반환
- 다양한 속성에 따른 집계 필터링 지원
- 데이터 양은 페이스북이나 구글 규모

---

## 2. 데이터 저장 방안

**원시 데이터 저장, 집계 결과 데이터 보관 둘다 한다**

| 구분 | 용도 |
|---|---|
| 원시 데이터 | 버그 수정 용 |
| 집계 데이터 | 빠른 쿼리 성능, 데이터 용량 절감 |

---

## 3. 비동기 처리

**비동기로 또 카프카 쓰자**

로그 감시자, 집계 서비스, 데이터베이스 두개의 메시지큐로 분리

| 메시지큐 | 내용 |
|---|---|
| 첫번째 메시지큐 | 광고 클릭 이벤트 데이터 |
| 두번째 메시지큐 | 분 단위로 집계된 광고 클릭 수, 분 단위로 집계한 가장 많이 클릭 N개 광고 |

---

## 4. 집계 서비스

- 맵리듀스 프레임워크 사용하기
- 맵, 집계 , 리듀스 노드 다 따로 놓고 사용

| 노드 | 역할 |
|---|---|
| 맵 노드 | 데이터 필터링하고 변환 |
| 집계 노드 | id별 클릭 이벤트 수 집계 |
| 리듀스 노드 | 모든 집계 노드가 산출한 결과를 최종 결과로 축약 |

---

## 5. 스트리밍 vs 일괄 처리

- 람다 아키텍처는 일괄 처리 계층과 스트리밍 계층 두 개 다 관리해야함
- 카파 아키텍처는 일괄처리와 스트리밍 처리 경로를 하나로 결합하여 이 문제 해결
- 데이터 재계산은 재계산 전용 서비스에서 진행 그래야 원래 서비스와 간섭 없음

---

## 6. 타임 스탬프

### 이벤트 시각 vs 처리 시각

- 이벤트 발생 시각을 사용할건데 늦게 도착한 이벤트 처리하려면 워터마크 사용
- 워터마크는 허용 지연이라고 보면 될 듯

### 윈도우

| 윈도우 | 설명 |
|---|---|
| 텀블링 윈도우 | 같은 크기를 겹치지 않게, 매 분 발생한 이벤트 집계 적합 |
| 슬라이딩 윈도우 | 같은 시간 구간 안에 있는 이벤트 집계, 지난 M분간 가장 많이 클릭된 광고 |

---

## 7. 전달 보장

- 약간 중복 괜찮으면 최소 한번이 적절
- 하지만 돈 문제가 걸려있으니 **'정확히 한 번'** 을 사용

---

## 8. 시스템 규모 확장

- 메시지 큐 확장
- 집계 서비스 확장 - ad_id마다 별도 처리 스레드, 다중 프로세싱 활용
- db 확장
