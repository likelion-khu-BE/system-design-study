

# 6장 광고 클릭 이벤트 집계 학습노트 - 장찬욱

> 광고 클릭 이벤트 집계는 **돈이 걸린 집계**다. 5장 지표 모니터링과 구조는 거의 같은데 정확성 요구가 다르다. 약간 틀려도 되는 대시보드가 아니라 과금과 광고 효과 측정에 쓰이는 숫자다.

## 1단계 문제 이해 및 설계 범위 확정

Q&A

1. 입력 데이터는 어떤 형태인가?

> 여러 서버에 쌓이는 로그 파일에 클릭 이벤트가 append됨. 이벤트는 ad_id, click_timestamp, user_id, ip, country 등으로 구성.

2. 데이터 양은? <- 기능적 요구사항

> 일간 능동 클릭 이벤트 10억 건, 광고 게재 2백만회, 매년 클릭 이벤트 수가 30%씩 증가.

3. 어떤 질의를 지원해야 하는가? <- 기능적 요구사항

> 1. 지난 M분간 특정 ad_id의 클릭 수 
> 2. 지난 M분간 가장 많이 클릭된 상위 N개 광고
> 3.  ip, user_id, country 등 속성으로 필터링.

4. 고려해야 할 엣지 케이스는? <- 비기능 요구사항

> 늦게 도착하는 이벤트, 중복 이벤트, 시스템 일부 장애시 복구 가능해야. + 부분적 장애는 감내할 수 있어야. 

5. 지연 시간 요건은? <- 비기능 요구사항

> 모든 처리가 수 분 내에 이루어져야. RTB와 클릭 집계의 지연 시간 요건은 매우 다름. RTB는 1초 미만, 집계는 과금 및 보고에 사용되기에 몇 분 정도 지연은 허용.



**정확성(중복, 유실, 지연 이벤트 처리)을 지키면서 정해준 지연 시간을 충족해야 한다.**

## 2단계 개략적 설계안 제시

### 질의 API

- `GET /v1/ads/{:ad_id}/aggregated_count` : 기간(from, to)과 필터를 받아 클릭 수 반환
- `GET /v1/ads/popular_ads` : 윈도 크기, 개수, 필터를 받아 상위 N개 광고 반환

### 데이터 모델

원시 데이터와 집계 데이터 둘 다 저장하는 것이 권장된다.

| 구분  | 원시 데이터                             | 집계 데이터            |
| --- | ---------------------------------- | ----------------- |
| 장점  | 원본 보존, 버그 시 재계산 가능, 데이터 필터링·재집계 가능 | 질의가 빠름, 저장 용량이 작음 |
| 단점  | 용량이 크고 질의가 느림                      | 원본이 없어서 재계산 불가    |
| 용도  | 백업, 재계산용 (오래된 건 cold storage)      | 활성 질의용            |

5장에서 "수집 에이전트 집계 vs 파이프라인 집계 vs 질의 시 집계"를 비교하며 **앞단에서 집계하면 해상도가 낮아져 원인 추적이 어렵다**고 나의 생각을 정리했었다. 같은 상황이 다시 논의되었다. 5장에서 내린 결론(단서를 최대한 남기자)이 여기서도 똑같이 나와어 이전의 내 생각이 일리가 있었다는 것을 확인할 수 있었다. 다만 여기서 원시 데이터는 질의용이 아니라 **재계산용 안전장치**라는 목적이붙었다.

### 데이터베이스 선택

쓰기 부하가 막대하고, 읽기는 집계 데이터 위주이며, 시간 범위 질의가 중심이다.

5장의 DB 비교 논리가 그대로 반복된다. RDBMS는 쓰기 부하에서 막히고, 쓰기에 최적화된 LSM 계열 저장소(카산드라)나 시계열 DB가 맞다. 원시 데이터는 쓰기 위주라 카산드라류, 집계 데이터는 시간 범위 질의가 중심이라 시계열 DB도 가능해 보인다.

### 개략적 설계: 비동기 처리

```
로그 감시기 → 메시지 큐1 → 데이터 집계 서비스 → 메시지 큐2 → DB 기록
                  ↓
              원시 데이터 저장
```

**4장, 5장에서 이미 나온 구조다.** 5장에서 "수집기와 TSDB 사이에 카프카를 두면 결합도가 낮아지고 TSDB 장애에도 데이터가 소실되지 않는다"고 했는데, 여기서도 로그 감시기와 집계 서비스 사이에 큐1을 둔다. 근거도 같다. 4장에서 정리한 메시지 큐의 이득(결합도 완화, 가용성 개선, 규모 확장성)이 그대로 쓰인다.

다만 정확히 한 번 처리를 위해서 추가된 부분이 있는데 **메시지 큐2**다. 집계 결과를 DB에 바로 쓰지 않고 한 번 더 큐에 넣는다. 이유는 **정확히 한 번 처리** 때문이다. 집계 결과를 DB에 쓰는 것과 오프셋을 갱신하는 것이 어긋나면 **중복 집계되거나 유실**된다. 큐를 하나 더 두면 "집계 서비스 노드가 집계 결과를 카프카에 전송 + 오프셋을 HDFS/S3에 저장 + 수신확인 응답을 집계 서비스 노드에 전송"을 묶기 쉬워진다. 이게 분산 트랜잭션으로 안 묶이면 오프셋 저장 후 집계 결과 전송 전에 장애 시에는 이벤트가 유실된다. 그래서 집계 결과 전송 후에 오프셋 저장을 해야하고, 이 구조에서도 결과 전송 후 오프셋 저장을 못한 채 장애가 일어나면 처리한 클릭 이벤트를 다시 보내는 중복 이벤트가 발생할 수 있다. 즉 분산 트랙잭션으로 "집계 서비스 노드가 집계 결과를 카프카에 전송 + 오프셋을 HDFS/S3에 저장 + 수신확인 응답을 집계 서비스 노드에 전송"을 묶어야 한다. **결과 전송 -> 오프셋 저장 -> 확인 응답** 구조다.

### 집계 서비스: MapReduce

5장에서 "질의가 너무 크면 여러 TSDB에 분할 질의하고 응답을 조립한다, MapReduce와 유사하다"고 적었는데, 이 챕터에서 **MapReduce가 등장**한다. DAG 형태로 구성된다.

- **Map 노드:** 입력을 읽고 ad_id 기준으로 어느 Aggregate 노드로 보낼지 분배 (예: `ad_id % N`)
- **Aggregate 노드:** ad_id별로 분 단위 클릭 수를 메모리에서 계산
- **Reduce 노드:** 각 Aggregate 노드의 상위 N개를 모아 최종 상위 N개 계산

**사용 사례 3가지**

1. 클릭 수 집계: ad_id별 분 단위 카운트
2. 상위 N개 광고: Aggregate 노드마다 상위 N개를 뽑고 Reduce에서 합침
3. 데이터 필터링: `filter_id`를 미리 정의해 두고(스타 스키마) 필터 조합별로 미리 집계

데이터 필터링은 5장의 **레이블 카디널리티** 문제와 같은 고민이다. 필터 조합이 많아질수록 미리 계산해야 할 집계가 늘어난다. 5장에서는 "레이블 조합의 가짓수가 곧 시계열 개수라서 메모리를 많이 먹는다"고 정리했는데, 여기서는 필터 조합의 가짓수가 곧 집계 개수가 된다.

## 3단계 상세 설계

### 스트리밍 vs 배치

두 가지 아키텍처가 등장한다.

- **람다 아키텍처:** 스트리밍 경로(빠르지만 근사)와 배치 경로(느리지만 정확)를 둘 다 운영. 코드 두 벌을 유지해야 한다.
- **카파 아키텍처:** 스트리밍 하나로 통일하고, 재처리가 필요하면 같은 코드로 과거 데이터를 다시 흘려보낸다.

이 챕터는 카파를 택한다. 람다 아키텍처가 두 가지 경로를 가지기에 유지 관리해야 할 코드가 두 벌이 된다는 것을 단점으로 지적한다. 

### 데이터 재계산

집계 서비스에 버그가 있었다면 이미 DB에 들어간 결과가 잘못 되었을 것이다. 이때 **원시 데이터 저장소에서 다시 읽어 재계산**한다. 재계산 전용 집계 서비스를 따로 두고, 결과는 큐2로 보내 같은 경로로 DB에 반영한다.

### 시간: 이벤트 시각 vs 처리 시각

**이벤트 시각**은 클릭이 실제 일어난 시각이고, **처리 시각**은 집계 서비스가 이벤트를 처리한 시각이다.

|     | 이벤트 시각           | 처리 시각                        |
| --- | ---------------- | ---------------------------- |
| 정확도 | 높음               | 늦게 도착한 이벤트가 엉뚱한 윈도에 들어가 낮음   |
| 구현  | 늦게 온 이벤트 처리가 어려움 | 서버 타임스탬프가 클라이언트의 타임스탬프보다 안정적 |

광고 클릭은 정확성이 중요하니 이벤트 시각을 기준으로 한다. 이렇게 되면 늦게 도착한 이벤트가 엉뚱한 윈도우에 들어갈 가능성을 받아들이겠다는 선택을 한 것이므로 이를 대응할 방안도 생각해봐야 한다. 책에서는 워터마크를 도입한다.

#### 워터마크

워터마크란 **늦게 오는 이벤트를 윈도가 닫히기 전까지 얼마나 더 기다릴지 정하는 여유 시간**이다. 윈도 경계에 걸친 이벤트가 몇 초 늦게 도착해도 윈도를 열어두어 포함시킨다.

> 워터마크 길이도 트레이드오프다.
> 
> **길게 잡으면 정확도는 오르지만 결과가 늦게 나온다 VS 짧게 잡으면 빠르지만 늦은 이벤트를 놓친다**

정확도를 얻으려면 지연을 내줘야 하는 구조다. 

### 집계 윈도

- **텀블링(고정) 윈도:** 겹치지 않는 고정 구간. 분 단위 클릭 수 집계에 사용.
- **슬라이딩 윈도:** 구간이 계속 이동하며 겹침. "지난 M분간 상위 N개 광고"에 사용.

### 전달 보장

**4장의 메시지 전달 방식(최대 한 번 / 최소 한 번 / 정확히 한 번)이 여기서 다시 나온다.** 이전에 정확히 한 번은 "금융 관련 서비스"에 쓴다고 적었는데, 광고 과금이 바로 그 경우다. 최소 한 번은 중복을 소비자가 제거할 수 있을 때 쓴다고 정리했는데, 여기서는 중복 제거 자체가 문제의 핵심이 된다.

**데이터 중복이 생기는 경우**

- 클라이언트 측: 악의적이거나 실수로 같은 클릭이 여러 번 전송됨
- 서버 장애: 집계 서비스 노드가 죽은 뒤 재처리하면서 같은 이벤트를 다시 처리함

서버 장애로 "오프셋 갱신을 못하면 재발송으로 중복 처리된다".

**해결 방향**

1. 업스트림 오프셋을 노드 로컬이 아니라 **외부 저장소(HDFS, S3 등)** 에 기록해 둔다.
2. 집계 결과를 다운스트림으로 보내고 **ACK를 받은 뒤에 오프셋을 갱신**한다.
3. 결과 전송과 오프셋 갱신을 하나로 묶기 위해 **분산 트랜잭션**을 쓴다.

이미 큐2를 둔 이유로 위에서 설명한 내용이다.

### 시스템 규모 확장

**이 부분은 4장의 복습이다.**

**메시지 큐**

- 생산자는 쉽게 늘릴 수 있다. 소비자는 그룹에 합류하거나 이탈할 때마다 **리밸런싱**이 일어나는데, 4장의 코디네이터 동작 그대로다. 리밸런싱이 길어지면 처리가 멈출 수 있으니 소비자 추가는 트래픽이 한가한 시간에 하는 것이 좋다.
- 파티션: `ad_id`를 해시 키로 써서 같은 광고가 같은 파티션으로 가게 한다. 4장에서 "객체 ID를 키로 쓰면 같은 객체의 순서가 보장된다"고 했던 것과 같다.
- 파티션을 나중에 늘리면 키-파티션 매핑이 바뀌므로 미리 충분히 잡아두는 것이 좋다. 4장에서 "파티션이 너무 많아지면 브로커 장애 시 혼란이 크다"고 한 것과 균형을 맞춰야 한다.

**집계 서비스**

- Map/Aggregate/Reduce 노드를 늘려 수평 확장한다.
- 자원 관리자(YARN 등)가 노드를 할당하는 방식으로 확장하는 것이 일반적이다.

**데이터베이스**

- 카산드라는 안정 해시 기반이라 노드를 추가하면 자동으로 재분배된다. 주변 친구 챕터에서부터 여러번 반복된 서버를 안정 해시 링으로 분배하는 방식이다. 다만 가상 노드에 대해 이번 챕터에서 좀 더 이해하게 되었는데, 안정 해시링 위에서 서버 하나를 한 지점에 두는 게 아니라 여러 지점에 뿌려둬서 부하 분산이 고르게 되도록 할 수 있다는 것을 알게 되었다. 다만 이 뿌리는 게 한 서버를 너무 많은 지점에 뿌려두면 관리가 복잡해질 수 있어서 실제로 쓸 때는 가상 노드를 적당히만 둔다고 한다.

**핫스팟 문제**

인기 광고 하나에 클릭이 몰리면 해당 `ad_id`를 담당하는 노드만 과부하가 된다. 해시로 균등하게 나눠도 키 자체의 쏠림은 해시로 해결되지 않는다. 쏠리는 광고에는 **추가 노드를 할당**해서 처리한다. 

### 결함 내성

집계 서비스는 윈도별 상태를 **메모리에** 들고 있다. 노드가 죽으면 그 상태가 사라진다.

- 집계 상태(윈도 카운트, 상위 N개, 오프셋)를 주기적으로 **스냅숏**으로 저장한다.
- 노드가 죽어서 메모리가 날아갔다면 새 노드는 스냅숏을 읽고 그 오프셋부터 이어서 처리한다.

상태를 노드 밖에 두어서 노드를 교체 가능하게 만드는 구조다. 우진이가 발표했던 것이 생각 났었는데, 주제가 수평 확장시 서버가 stateless해야 하는데 인증정보가 stateful하게 만드는 요소여서 이에 대한 해결방식을 다뤘던 것으로 기억한다. 세션 인증 정보를 레디스에 둬서 수평확장이 이루어지고도 어느 서버로 요청을 보내도 해당 세션을 가지고 인증이 가능하도록 했던 것으로, 특정 서버에서만 세션 인증이 가능한 현상을 해결했던 것으로 기억한다. 이 결함 내성 단락에서도 유사하게 대응한 것 같다. 스냅숏으로 stateful한 부분을 격리해둬서 노드가 stateless로 시작해도 현재 상태를 따라잡을 수 있도록 한 것이다.

### 데이터 모니터링과 정확성

**지속적 모니터링**

- 지연 시간: 이벤트 타임스탬프를 단계별로 추적
- 메시지 큐 크기: 쌓이기 시작하면 소비자가 못 따라가는 것
- 집계 노드 시스템 자원: CPU, 디스크, JVM 등

**조정(reconciliation)**

조정이란 **다양한 데이터를 비교해서 틀린 곳을 찾고 데이터 무결성을 보증하는 기법**이다. 매일 파티션에 기록된 클릭 이벤트를 이벤트 시각 기준으로 정렬해 배치로 다시 집계하고, 실시간 집계 결과와 비교한다. 워터마크로 못 잡은 늦은 이벤트 때문에 완벽히 일치하지는 않지만, 차이를 보정하고 허용 범위를 넘는지 확인할 수 있다. 

### 대안 설계

원시 데이터를 하이브에 저장하고 엘라스틱서치로 인덱싱해 질의하는 방식도 있다. 다만 집계 질의와 필터링이 느릴 수 있어서, 이런 분석성 질의에는 OLAP 계열(ClickHouse, Druid 등)이 더 적합하다고 책은 언급한다.
