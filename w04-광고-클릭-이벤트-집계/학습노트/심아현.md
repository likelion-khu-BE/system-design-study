# 광고 클릭 이벤트 집계

## 데이터 모델

광고 클릭 이벤트는 **원시 데이터와 집계 결과 데이터** 두 가지 형태로 저장할 수 있음.

### 원시 데이터

사용자가 광고를 클릭할 때 발생한 이벤트를 그대로 저장한 데이터.

데이터 양은 많지만 나중에 집계 결과에 문제가 생겼을 때 다시 계산하거나 분석할 수 있다는 장점이 있음.

### 집계 결과 데이터

원시 데이터를 광고 ID, 시간 등을 기준으로 미리 집계해둔 데이터.

매번 원시 데이터를 읽어서 계산할 필요가 없기 때문에 조회 속도가 빠름.

---

## 비동기 처리

광고 클릭 이벤트가 대량으로 들어오는 상황에서 이벤트가 발생할 때마다 바로 집계 서비스가 처리하도록 하면 부하가 커질 수 있음.

→ 중간에 메시지 큐를 두고 비동기적으로 처리

생산자 → 메시지 큐 → 소비자(집계 서비스)

메시지 큐가 버퍼 역할을 하기 때문에 갑자기 많은 이벤트가 발생해도 안정적으로 처리 가능.

---

## 집계 서비스

많은 클릭 이벤트를 하나의 서버에서 전부 처리하기 어려움.  
→ 여러 노드가 데이터를 나누어 처리

### 맵리듀스

맵 노드 → 집계 노드 → 리듀스 노드

**맵 노드**

들어온 데이터를 어떤 집계 노드가 처리할지 분배하는 역할.

**집계 노드**

전달받은 클릭 이벤트를 실제로 집계하는 역할.

**리듀스 노드**

여러 집계 노드에서 만들어진 결과를 모아서 최종 결과를 만드는 역할.

---

## 스트리밍 vs 일괄 처리

**스트리밍 처리**

이벤트가 들어오는 대로 계속 처리하는 방식.  
→ 실시간에 가까운 결과를 빠르게 제공할 수 있음.

**일괄 처리**

일정량의 데이터를 모은 뒤 한꺼번에 처리하는 방식.  
→ 실시간성은 떨어지지만 많은 데이터를 다시 계산하거나 분석하기 좋음.

---

## 데이터 재계산

실시간으로 계산한 집계 결과에 문제가 생길 수도 있음.

→ 저장해둔 **원시 데이터를 다시 처리해서 집계 결과를 계산**

따라서 원시 데이터를 보관해두면 집계 과정에 오류가 발생하더라도 결과를 다시 만들 수 있음.

---

## 이벤트 시각과 처리 시각

**이벤트 시각(Event Time)**  
실제로 광고 클릭이 발생한 시간.

**처리 시각(Processing Time)**  
집계 시스템이 해당 이벤트를 처리한 시간.

네트워크 지연 등의 이유로 이벤트가 발생한 시간과 실제 처리되는 시간이 달라질 수 있음.

10:00:50 광고 클릭 -> 네트워크 지연 -> 10:01:05 이벤트 처리

---

## 집계 윈도

스트리밍 데이터는 계속 들어오기 때문에 끝나는 시점이 없음.  
→ 일정한 **시간 구간(Window)**으로 나누어서 집계

**텀블링 윈도**

서로 겹치지 않는 일정한 크기의 시간 구간.

10:00 ~ 10:01
10:01 ~ 10:02
10:02 ~ 10:03

**슬라이딩 윈도**

서로 겹칠 수 있는 시간 구간.  
최근 일정 시간 동안의 데이터를 계속 집계할 때 사용할 수 있음.

늦게 도착하는 이벤트의 경우 **워터마크**를 이용해서 어느 시점까지 이벤트를 기다릴지 결정할 수 있음.

---

## 전달 보장

메시지를 처리하는 과정에서 데이터가 유실되거나 중복 처리될 수 있음.

**At-most-once**  
최대 한 번 처리. 중복은 없지만 데이터가 유실될 수 있음.

**At-least-once**  
최소 한 번 처리. 데이터 유실 가능성은 낮지만 중복 처리될 수 있음.

**Exactly-once**  
이벤트가 최종 결과에 정확히 한 번 반영되도록 처리.

광고 클릭 이벤트가 중복으로 집계되면 실제 클릭 수와 결과가 달라질 수 있기 때문에 정확한 처리가 중요함.

---

## 시스템 규모 확장

클릭 이벤트가 많아지면 하나의 집계 서버로 처리하기 어려움.

→ 메시지 큐를 여러 **파티션**으로 나누고 여러 소비자(집계 서버)가 병렬로 처리

Partition 0 → 집계 서버 A
Partition 1 → 집계 서버 B
Partition 2 → 집계 서버 C


트래픽이 증가하면 파티션과 집계 서버를 추가하는 방식으로 처리량을 늘릴 수 있음.

---

## 핫스팟 문제

광고 ID를 기준으로 데이터를 나눴는데 특정 광고에 클릭이 몰릴 수 있음.

광고 A → 100회
광고 B → 120회
광고 C → 100,000회


이 경우 광고 C를 담당하는 파티션에 대부분의 트래픽이 몰리게 됨.

→ 데이터를 여러 파티션으로 나눴다고 해도 **특정 키에 요청이 집중되면 부하가 한쪽으로 몰릴 수 있음.**

---

## 결함 내성

집계 서버에 장애가 발생하면 현재까지 계산하던 집계 상태를 잃어버릴 수 있음.

→ **체크포인트(Checkpoint)**를 이용해서 현재 처리 상태를 주기적으로 저장

이벤트 처리 -> 체크포인트 저장 -> 이벤트 처리 -> 서버 장애 -> 최근 체크포인트 복구 ->이후 이벤트 재처리


메시지 큐 등에 이벤트가 남아 있다면 체크포인트 이후의 데이터를 다시 읽어서 처리할 수 있음.

→ 서버 일부에 장애가 발생하더라도 **저장된 상태를 복구하고 이벤트를 재처리해서 집계를 계속할 수 있음.** :chatgpt-content-reference{index="0"}
