지표 데이터는 시계열 데이터이고 
저장소는 그냥 일정한 시간마다 정해진 지표를 쓰는 연산이므로
데이터 수정이 적고 쓰기가 많으므로
쓰기 연산에 최적화된 OPendTSDB를 사용해준다.

풀 모델 vs 푸쉬 모델

cpu사용률,요청 수, 메모리 사용량, 메시지 규 내의 메세지 수 등 다양한 지표 출처로 부터
지표 수집기가 데이터를 가져와 저장소에 저장한다.

pull 모델인 경우 지표 수집기가 출처로부터 요청을 보내서 가져와야 한다.
따라서 본인이 담당할 지표들의 엔드포인트 DNS/IP 정보를 갖고 있어야 한다.
하지만 대규모 시스템에서 collector은 서로 대체, 삭제 되므로 메타데이터를 관리할 프로세스가 필요하다
collector들의 현황을 서비스 디스커버리가 관리하고, 이 메타 데이터를 collector들이 주기적으로 확인해
본인의 담당 지표를 확인 한다.
또 담당 지표가 바뀔 때 발생하는 오버헤드를 줄이기 위해, 단순 해시 계산 보단, 일부 collector만 조정될 수 있게 해시링으로 
수집기와 지표 출처의 대응관계를 관리해준다.

push 모델인 경우 source에서 직접 데이터를 보내주므로 수집 에이전트를 설치해서 collector에게 보낸다.
collector의 부하가 생길 수 있으므로, 로드 벨런서가 collector들의 트래픽을 분배해준다.
수집기 입장에서는 로드벨런서에게 지표 데이터를 보내고, 로드벨런가 collector들에게 균등하게 전달해준다고 보면 된다.

(Service Discovery = 갈 수 있는 서버가 누구냐? / Load Balaner = 그 서버들 중 누구에게 이 요청을 전달할까)

Pull = 중앙 수집기가 통제하기 쉬움
Push = 지표 발생 측이 전송하기 쉬움

서버 인프라 모니터링처럼 중앙에서 관리된다면 Pull이 자연스럽고, source에 직접 접근하기 어렵거나 동적이고 수명이 짧다면
Push가 자연스럽다고 생각하면 된다.

지표 수집기와 데이터 베이스 사이 카프카?

높은 안정성과 유연한 파이프라인이라는 요구사항 달성을 위해
비용을들여 수집기와 DB사이 카프카를 둘 수 있다.

예를 들어 순간적으로 metric이 몰려 DB에 장애가 발생했을때, 
회복 된 후 kafka의 디스크에서 데이터를 가져올 수 있기 때문이다.
시계열 데이터의 특성상 순차처리에 능하고 appned-only인 kafka가 좋은 선택지가 될 것 이다.
대역폭 요구 사항에 따라 파티션 수를 조절 할 수 있으므로 서버 scaling과도 잘 맞다.

(kafka 구축이 쉽지 않을 수 있으므로, 높은 수준의 쓰기 가용성을 유지해 비싸지만
안정적인 고릴라 데이터베이스시스템을 사용하기도 한다고 함)
