## 5장 지표 모니터링 및 경보 시스템

 이번 장에서는 대규모 서비스에서 서버의 상태를 수집하고 저장한 뒤, 필요한 지표를 조회하거나 문제가 생겼을 때 경보를 보내는 시스템을 설계한다. 
 처음에는 단순히 CPU나 메모리 사용량을 모으면 되는 문제처럼 보였지만, 서버가 수천 대 이상으로 늘어나면 지표를 어떻게 수집하고 저장할지, 데이터가 몰렸을 때 어떻게 확장할지까지 같이 생각해야 한다.

## 지표 수집과 서비스 탐색

지표 수집기는 우선 어떤 서버에서 지표를 가져와야 하는지 알아야 한다. 서버의 DNS/IP 목록을 파일에 직접 저장할 수도 있지만 서버가 계속 추가되고 삭제되는 환경에서는 관리하기 어렵다.

그래서 etcd나 ZooKeeper 같은 Service Discovery 시스템을 사용한다. 각 서비스가 자신의 상태와 주소를 서비스 탐색 시스템에 등록하고, 지표 수집기는 여기서 현재 살아 있는 서버 목록을 가져온다. 
서버 목록이 변경되면 이를 통지받거나 일정 주기로 다시 조회할 수도 있다.

서비스 탐색 시스템에는 단순히 서버 주소뿐만 아니라 지표 수집 주기, timeout, retry 같은 설정도 같이 저장할 수 있다.

## Pull 모델 
### 수집기 -> 각 서버에 Pull 요청

Pull 모델은 지표 수집기가 각 서버에 직접 요청해서 지표를 가져오는 방식이다.

각 서버는 /metrics 같은 HTTP 엔드포인트를 제공하고, 지표 수집기는 서비스 탐색 시스템에서 서버 목록을 얻은 뒤 일정 주기로 이 엔드포인트에 요청한다. Prometheus가 대표적인 Pull 방식의 시스템이다.

Pull 방식은 수집기가 직접 서버에 접근하기 때문에 디버깅이 비교적 쉽고, 서버가 응답하지 않는 것을 보고 장애 여부를 판단하기도 쉽다. 반대로 매우 짧게 실행되고 사라지는 프로세스는 수집기가 요청하기 전에 없어질 수 있다는 문제가 있다.

수집기가 여러 대가 되면 같은 서버의 지표를 여러 수집기가 중복해서 가져오지 않도록 해야 한다. 전장에서도 나왔던 안정 해시를 사용해 특정 서버의 지표를 담당할 수집기를 정하는 방식을 사용한다.

## Push 모델
### 각 서버 -> 수집기에게 Push

Push 모델은 반대로 각 서버가 지표 수집기에게 자신의 지표를 직접 보내는 방식이다.

서버에 collection agent를 설치하고, 이 agent가 CPU나 메모리 같은 지표를 모은 뒤 일정 주기로 지표 수집기에 전달한다. 간단한 카운터 값은 agent가 미리 집계해서 보낼 수도 있다. 이렇게 하면 전송해야 하는 데이터의 양을 줄일 수 있다.

다만 지표 수집기가 순간적으로 데이터를 처리하지 못하는 경우에는 agent가 데이터를 잠시 버퍼링해야 한다. 서버가 자동으로 추가되거나 삭제되는 환경에서는 로컬에 저장한 데이터가 서버와 함께 사라질 수도 있다는 문제가 있다.

Push 방식에서는 수집기 앞에 로드밸런서를 두고, 수집기의 CPU 사용량 등에 따라 수집기 서버 수를 자동으로 늘리거나 줄이는 방식으로 확장할 수 있다.

## Pull과 Push 중 어떤 것을 선택할까

두 방식 중 하나가 무조건 좋은 것은 아니다. Pull 방식은 수집 대상에 직접 접근할 수 있어서 디버깅이나 
health check가 편하지만(pull 안되면 서버가 죽엇구나) 모든 서버가 /metrics 엔드포인트를 수집기에 노출해야 한다.

Push 방식은 서버가 수집기로 데이터를 보내기 때문에 네트워크 구성이 상대적으로 단순하고 짧게 실행되는 작업의 지표도 전달하기 쉽다. 
반대로 서버에서 지표가 오지 않는 상황이 발생했을 때 서버 장애인지 네트워크 문제인지 바로 판단하기 어렵다.

결국 서비스의 네트워크 구조와 지표의 특성에 따라 선택하는 문제인 것 같다.

## 지표 전송 파이프라인 확장

서비스 규모가 커지면 지표 수집기에서 발생하는 데이터도 엄청나게 많아진다. 
지표 수집기에서 바로 시계열 데이터베이스로 데이터를 넣는 구조에서는 데이터베이스가 순간적으로 느려지거나 장애가 발생했을 때 데이터가 유실될 가능성이 있다.

그래서 책에서는 수집기와 데이터베이스 사이에 Kafka를 둔다.

전체적으로는 지표 출처에서 지표 수집기로 데이터를 보내고, 수집기가 Kafka에 전달한 뒤 consumer가 데이터를 가져가 시계열 데이터베이스에 저장하는 구조가 된다.

Kafka를 중간에 두면 데이터 수집 부분과 저장/처리 부분을 분리할 수 있고, 
데이터베이스에 장애가 생겨도 Kafka에 데이터가 남아 있기 때문에 바로 유실되지 않는다는 장점이 있다.

Kafka 자체도 파티션을 이용해 규모를 확장할 수 있다. 
지표 이름 등을 기준으로 같은 종류의 지표를 같은 파티션에 넣을 수도 있고, 태그나 레이블을 이용해 더 세분화할 수도 있다. 중요한 지표를 우선적으로 처리하도록 구성하는 것도 가능하다.

## 데이터를 언제 집계할 것인가

지표 데이터는 그대로 저장하면 양이 매우 많기 때문에 어느 시점에서 집계할지도 생각해야 한다.

수집 agent에서 미리 집계하면 전송량을 줄일 수 있지만 복잡한 집계는 하기 어렵다. 
데이터 저장 전에 Flink 같은 스트림 처리 시스템에서 집계할 수도 있는데, 이 경우 데이터 양은 줄어들지만 원본 데이터가 사라질 수 있고 처리 과정에서 지연이 생긴다.

반대로 원본 데이터를 그대로 저장한 뒤 질의할 때 집계하면 데이터 손실은 없지만 매번 많은 데이터를 계산해야 하므로 조회 속도가 느려질 수 있다.

결국 저장 비용, 조회 성능, 원본 데이터 보존 중 무엇이 중요한지에 따라 선택해야 한다.

## Query Service

시각화 시스템이나 경보 시스템이 시계열 DB에 직접 접근하게 만들 수도 있지만, 책에서는 중간에 질의 서비스(Query Service) 를 둔다.

질의 서비스가 시계열 DB에 접근하는 부분을 대신 처리하면 시각화나 경보 시스템이 특정 데이터베이스에 직접 의존하지 않아도 된다. 
나중에 데이터베이스 제품을 변경해도 클라이언트 쪽의 변경을 줄일 수 있다는 장점이 있다.

질의 결과를 캐싱하면 반복적인 요청의 부하를 줄일 수도 있다. 
다만 실제 시계열 DB 제품들이 자체적으로 여러 최적화 기능을 제공하기 때문에 별도 캐시가 항상 필요한 것은 아니다.

Prometheus나 InfluxDB 같은 시계열 데이터베이스는 SQL이 아닌 별도의 질의 언어를 제공하기도 한다. 
시간에 따라 데이터를 집계하거나 이동 평균을 계산하는 작업은 일반 SQL로 표현하면 복잡해질 수 있기 때문이다.

## 시계열 데이터베이스와 저장 공간 최적화

지표 데이터는 시간에 따라 계속 쌓이므로 일반 DB보다 시계열 데이터베이스가 적합하다. 
특히 최근 데이터에 대한 조회가 많기 때문에 이런 데이터 패턴에 맞춰진 데이터베이스를 선택하면 성능상 이점이 있다.

문제는 저장되는 데이터의 양이 매우 크다는 점이다. 
이를 줄이기 위해 데이터 인코딩과 압축을 사용할 수 있다. 예를 들어 timestamp 전체를 매번 저장하기보다는 이전 값과의 차이를(ex. +5 +3 ..) 저장하면 훨씬 적은 공간만 사용할 수 있다.

또 하나의 방법은 다운샘플링(Downsampling) 이다. 오래된 데이터일수록 세밀한 값이 덜 중요하다고 보고 해상도를 낮추는 방식이다.

책의 예시에서는 최근 7일 데이터는 그대로 저장하고, 30일 이내 데이터는 1분 단위로, 1년 이내 데이터는 1시간 단위로 낮춰 저장한다. 
예를 들어 10초마다 저장하던 CPU 값 여러 개를 30초 단위 평균값 하나로 만들어 보관할 수 있다.

거의 조회하지 않는 오래된 데이터는 Cold Storage(싸고 느림) 로 이동시켜 비용을 절약할 수도 있다.

## 경보 시스템

경보 시스템은 특정 지표가 기준을 넘었을 때 운영자에게 알림을 보내는 역할을 한다.

경보 규칙은 YAML 같은 설정 파일로 정의할 수 있고, 경보 관리자가 일정 주기로 질의 서비스를 통해 지표를 확인한다. 설정된 threshold를 넘으면 경보 이벤트를 만든다.

같은 문제가 여러 서버에서 동시에 발생하면 경보가 너무 많이 생성될 수 있으므로 경보를 필터링하거나 병합하고 중복을 제거하는 과정도 필요하다.
또한 경보 전달 실패에 대비해 retry가 필요하고, 중요한 경보 설정은 특정 사용자만 변경할 수 있도록 접근 제어도 필요하다.

경보 상태는 Cassandra 같은 저장소에 보관할 수 있고, 생성된 경보 이벤트는 Kafka로 전달한 뒤 allert comsumer가 처리한다.
이후 이메일, 단문 메시지, PagerDuty, HTTPS 엔드포인트 등의 여러 채널로 실제 알림을 보낸다.

경보 시스템은 직접 개발할 수도 있지만 이미 다양한 상용 제품이 있고 시계열 데이터베이스와의 연동도 잘 되어 있기 때문에 
실제 환경에서는 구매하거나 기존 서비스를 사용하는 것도 충분히 고려할 수 있다.

## 시각화 시스템

모아둔 지표는 사람이 직접 확인할 수 있어야 한다. 이를 위해 대시보드를 제공하는 시각화 시스템이 필요하다.

지표 대시보드에서는 CPU, 메모리, 요청 수, 응답 시간, 네트워크 트래픽 같은 값을 시간 흐름에 따라 확인할 수 있고, 
경보 대시보드에서는 현재 발생한 장애나 경보 상태를 볼 수 있다.

책에서는 Grafana 같은 기존 시각화 도구를 활용하는 것을 권장한다. 
시각화 기능 자체를 처음부터 구현하기보다는 이미 시계열 데이터베이스와 연동이 잘 되는 제품을 사용하는 편이 현실적이다.

## 최종 구조

최종적인 흐름은 지표 출처 → 지표 수집기 → Kafka → Consumer → 시계열 데이터베이스 → 질의 서비스 순서로 이어진다.

질의 서비스의 데이터를 이용해 시각화 시스템이 대시보드를 만들고, 
경보 시스템은 이상 상태를 감지해 이메일, 문자, PagerDuty, HTTPS 엔드포인트 등으로 알림을 전달한다. 반복적으로 사용하는 질의 결과는 캐시를 통해 부하를 줄일 수도 있다.

이번 장에서 제일 중요하다고 느낀 부분은 단순히 지표를 모으는 것이 끝이 아니라는 점이다. 
서버가 많아지면 수집 대상 자체를 관리하기 위해 서비스 탐색이 필요하고, 지표가 많아지면 Kafka와 시계열 DB가 필요하며, 
저장량이 너무 커지면 압축과 다운샘플링까지 고려해야 한다.

결국 수집 → 전달 → 저장 → 조회 → 시각화/경보가 하나의 파이프라인으로 이어지고, 
각각의 단계가 대규모 환경에서 병목이나 장애가 나지 않도록 따로 확장 가능하게 설계하는 것이 이번 장의 핵심이라고 이해했다.
