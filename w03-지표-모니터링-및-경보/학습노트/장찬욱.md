### 개략적 요구사항 및 가정

대규모 인프라 모니터링이다.

- 일간 능동 사용자 수 1억명.
  
- 서버 풀 1000개에 풀 당 서버 수 100개, 서버당 100개 운영 지표 수집한다 하면 모니터링하는 지표 수는 천만개 수준.
  
- 데이터 보관 기간 1년
  
- 일주일 간 그대로 보관, 그 뒤에는 1분 단위로 30일 보관, 그 뒤에는 1시간 단위로 1년간 보관.
  

모니터링할 지표는 예로 cpu 사용률, 요청 수, 메모리 사용량, 메시지 큐 내의 메시지 수가 있음.

## 2단계 개략적 설계안 제시

- 데이터 수집: 여러 출처로부터 지표 데이터를 수집해야 한다.
  
- 데이터 전송: 지표 데이터를 지표 모니터링 시스템으로 전송해야 한다.
  
- 데이터 저장소: 전송받은 데이터를 정리하고 저장한다.
  
- 경보: 받은 데이터를 분석하고 이상 징후 감지, 경보를 발생시킨다. 다양한 채널로 경보를 발송할 수 있어야 한다.
  
- 시각화: 엔지니어의 이해를 돕기 위해 데이터를 차트나 그래프 등으로 제공한다.
  

#### 데이터 모델

지표 데이터는 시계열로 기록된다. 값 집합에 타임스탬프가 붙는 형태다. 시계열 각각에 고유 이름이 있고 레이블을 붙이기도 한다.

1. 메트릭 이름
  
2. 레이블(optional)
  
3. 타임스탬프
  
4. 메트릭 값
  

지난 10분간 특정 리전의 모든 웹 서버의 cpu 부하 평균값이 궁금하다면 지표 이름은 cpu 부하로 하고, 지역 이름 레이블로 조회해서 데이터를 저장소에서 가져와 평균값을 구하면 된다.

(e.g. CPU.load host=webserver01,region=us-west 1613707265 50)

특정 리전에서 문제가 발생하는 경우이므로 아무래도 지역적으로 특수한 이벤트가 있어서 서버에 장애가 발생했을 경우에 위와 같은 쿼리를 날려볼 것 같다.

#### Line protocol

시장의 많은 모니터링 sw가 행 프로토콜(e.g.와 같음)의 형식을 준수한다. 프로메테우스나 openTSDB가 그러하다. **모든 시계열 데이터는 다음과 같이 구성된다.**

| 이름  | 자료형 |
| --- | --- |
| 지표 이름 | 문자열 |
| 태그/레이블 집합 | key - value 쌍의 리스트 |
| 지표 값-타임스탬프 배열 | metric value - timestamp 쌍의 배열 |

#### 데이터 접근 패턴

**쓰기 부하가 언제나 막대하다.**

많은 시계열 데이터가 기록되며, 매일 천만개 운영 지표가 기록된다. 상당 수의 지표는 발생 빈도도 높다고 보자. 시스템 운영지표이기 때문이다.

**읽기 부하는 일시적으로 치솟았다 사라지는 편**이다.

시각화나 경보 서비스가 db를 읽을 때 발생할텐데 이 조회하는 패턴에 따라 읽기 연산이 잠잠하다가 일시적으로 증가할 것이다.

### 데이터 저장소 시스템

무엇을 기준으로 결정해야 할까? 본문을 읽어보고 뽑아보니 다음과 같은 것들이 등장했다.

1. 시계열 데이터의 지수이동평균 지속적으로 갱신하는 등 시계열 데이터 모델 기반의 계산에 최적화된 쿼리 인터페이스 지원
  
2. 태그/레이블에 대한 쿼리, 집계 및 분석 기능 지원
  
3. 레이블별 인덱스 구축 가능해야
  
4. 레이블별 카디널리티 낮아야
  
5. 많은 양의 쓰기 연산 지원
  
6. 많은 시계열 데이터 저장 위해 확장이 용이한 스키마 설계
  
7. 보관기간 설정 가능하면 좋음
  

### 시계열 데이터 처리를 위한 DB 유형별 비교(by AI)

| **구분** | **RDBMS (SQL)** | **일반 NoSQL** | **시계열 DB (TSDB - Prometheus 등)** |
| --- | --- | --- | --- |
| **쓰기 구조** | B-Tree (Random IO 병목) | LSM-Tree / Document (상대적 우수) | **LSM-Tree + WAL + In-Memory Head Block** (극도의 쓰기 최적화) |
| **압축률** | 낮음 (일반 행 단위) | 보통 (JSON/Document) | **매우 높음** (Gorilla XOR, Delta-of-Delta 전용 압축) |
| **레이블 쿼리** | Join 및 B-Tree 인덱스 폭증 | Partitioning이 장점인데 시계열이라 오히려 full scan으로 병목 위험 | **역인덱스(Inverted Index)**로 다차원 고속 검색 |
| **시계열 연산** | 복잡한 SQL 작성 필요 (느림) | 애플리케이션 단에서 직접 구현 | **PromQL, Flux 등 내장 시계열 함수 (EMA, P99 등)** |
| **데이터 보관** | 대량 `DELETE` 시 DB 마비 | TTL 지원하나 다운샘플링은 직접 구현 | **시간 단위 Block 분할 삭제 & 자동 다운샘플링** |

전반적으로 보면 RDBMS와 NoSQL은 애초에 시계열 데이터를 다루기 위해 만들었던 것이 아닌 게 보인다. 관계형 모델, 키값 관계를 효율적으로, 안정적으로 저장, 관리, 질의하기 위한 용도로는 적합하지만 막대한 양의 시계열 데이터를 다루려는 우리 입장에서는 일반적인 데이터베이스는 적합하지 않았다. 자기 전공이 있는데 갑자기 다른 학과에 편입되어버린 학생 같은 느낌이다.

B tree는 데이터 변경 시 디스크의 특정 물리적 위치를 찾아가 덮어쓰느라 느리다. 그 물리적 위치도 랜덤이다. 디스크 헤더 이동이 시간이 걸리는 것이다. LSM tree는 메모리에서 Red-Black Tree 등을 사용해 정렬을 유지한다. 메모리가 차면 플러시 하는 방식. 백그라운드 스레드가 하드에 순차적으로 저장한 시계열 데이터들을 합병정렬해준다고 한다. 디스크 쪽 문제는 위임해버리는게 비동기 처리 같다. db용 디스크를 따로 두고 다른 프로세스가 못 건드린다면 시분할로 인한 다른 프로세스의 간섭없이 완전 순차쓰기만 가능하게 만들수도 있을 것 같다.

좋은 시계열 데이터베이스에서는 레이블/태그 기준으로 집계, 분석하는 기능을 제공한다. 레이블 별로 인덱스를 구축한다.

레이블의 카디널리티가 낮아야 한다고 책에서 언급되는데 이 이유는 레이블 조합의 가짓수가 곧 생성되는 시계열 데이터의 개수가 되기 때문. 메모리를 많이 먹을 수 있다.

## 3단계 상세 설계

### 풀 모델

지표 수집기가 각 서버에 http 요청해서 가져온다면 서비스 디스커버리 기술이 필요하다. 요청할 서버가 많아서 수집기 서버가 여러 대인 경우에는 안정 해시 링을 사용해 각 수집기 서버가 담당할 서버들을 분배하면 될 것이다. 다만 오토 스케일링 아웃 사용 시 서비스 디스커버리 서비스가 꼭 필요해진다. 요청을 보낼 IP들은 계속 관리되어야 하기 때문이다.

### 푸시 모델

모니터링 대상 서버에 수집 에이전트를 설치하고 에이전트가 주기적으로 지표 데이터를 수집기에 전달한다. 데이터 집계를 해서 보내면 데이터 양도 줄일 수 있을 것이다. 만약 수집기가 죽으면 내부 버퍼에 저장했다가 보내는 것으로 대응한다. 지표 수집기가 전송량을 감당 못하면 클러스터로 스케일아웃하는 방식도 가능하다. 앞에 로드밸런서를 두면 고르게 트래픽이 분배될 것이다.

> 두 방식 모두 갑작스러운 트래픽 증가로 지표 출처가 많아지는 것에 대비해서 수집기 서버의 스케일아웃을 요구하는 것을 알 수 있다. 어느 모델이든 안정해시링이나 로드밸런서를 써서 일이 터지기 전에 먼저 준비해두는 게 좋아보인다.

### 지표 수집기에서 TSDB로 전송 시

TSDB에 장애가 생기면 지표 수집기가 데이터를 바로 보낼시 데이터 손실이 발생할 수도 있다.

저번 챕터에서처럼 큐를 두는 것을 책에서 제안한다. 카프카는 안정적이고 규모확장성이 좋은 분산 메시지 플랫폼이다. 수집기들과 TSDB 사이의 결합도를 낮출 수 있다. TSDB 장애에도 데이터가 소설되지 않고 브로커에 저장되어 있을 것이다. 만약 TSDB 장애시 복구까지 데이터가 계속 쌓일테니 브로커들의 디스크를 늘려서 대응할 수 있을 것 같다. 제발 TSDB 자체 문제이길 바란다. 만약 트래픽이 폭증해서 TSDB가 장애가 난 것이라면 디스크를 얼마나 늘려야할지 두렵다...

카프카의 파티션을 사용해 규모 확장이 가능하다. 대역폭 요구에 맞게 파티션 수를 정하고 지표별로 어느 파티션에 배치할지 결정하면 소비자가 원하는 지표에 따라 파티션에 접근하면 될테니 원하는 데이터를 집계할 수 있다. TSDB의 역인덱스 방식이 여기서도 비슷하게 나오는 듯한데 책에서는 태그/레이블에 따라 지표데이터를 더 세분화된 파티션으로 나누는 걸 제안한다. 딱 역인덱스적(?)인 사고방식 같다. 다만 이에 대해 AI가 이러한 부분을 지적했다.

`카프카 파티션은 적절한 개수(예: 32개, 64개)로 제한하고, 역인덱싱 및 데이터 처리는 카프카 소비 후 TSDB 메모리(Head Block)에 들어가는 시점에 처리합니다. 카디널리티가 매우 높은 레이블을 카프카 Key로 써서 파티셔닝을 하면, 카프카 파티션 수가 수천~수만 개로 폭증하여 카프카 클러스터 자체가 마비될 수 있습니다.- Gemini`

### 데이터 집계 시점

수집 에이전트가 집계, 데이터 수집 파이프라인이 집계, 쿼리하면 집계하는 3가지 방식에 대해 간략히 다루는데, 일단 실제로 많이들 치는 쿼리를 알아두고 그 쿼리들에 맞게 설계하는 것도 좋을 것 같다. 수집 에이전트는 책에서 나오는 대로 간단한 집계 정도만 하는 게 좋을 거 같고 복잡한 걸 시도하는 건 그 역할에 부합하지 않아 보인다. 비용도 더 들지도 모른다. 데이터 수집 파이프라인에서 집계하는 건 집계 결과만 TSDB에 저장할 수 있다는 것을 장점으로 든다. 다만 우려스러운 부분은 예를 들어 특정 에러들이 났던 요청들을 추적해보고 싶다고 하자. 앞단에서 집계가 되어버려서 그만큼 해상도가 낮아진 데이터만 가지고 추적해야한다는 큰 단점이 있다. 질의 시에 집계하는 것이 가장 문제 발생시 원인 추적에 좋을 것 같다. 단순히 알람만 울리는 게 목적이라면 먼저 집계해도 문제는 없을테지만 **문제 해결에 쓸 시스템이라면 질의 시에 집계하는 게 최고일 것 같다.** 단서를 최대한 남겨두자는 마인드. 물론 그만큼 돈이 나갈 것이다.

### 질의 서비스

질의 결과를 저장할 캐시 서버는 상당히 중요해보인다. TSDB에 읽기 부하가 너무 걸리면 부하분산 측면에서 이 캐시 계층이 큰 도움이 될 것이다. 다만 상용 시각화 및 경보 시스템에 이러한 캐시 기능이 내장되어 있다면 필요가 없어질 것 같다.

질의처리 전담 서비스를 두어 클라이언트와 TSDB 간의 결합도를 낮출 수 있다는데 TSDB를 읽는 요청이 갑자기 몰리는 경우에 대비도 될 것이고 OOM 나는 것을 방지해줄 것 같다. 보다 근본적인 해결책은 TSDB도 여러 대로 샤딩하고 데이터 사본을 가지도록 설계하는 것이라고 생각한다. 질의가 너무 연산량이 크면 여러 TSDB로 분할 질의하는 방식으로 하고 응답을 조립해서 결과가 나오는 방식이다. 분할된 각 질의는 병렬처리되는 셈이니 속도도 빠를 것이다. MapReduce와 유사한 것 같다. 책에서 TSDB를 여러 대 두는 말이 언급되지 않는데 다른 영역에서 안정성을 위해 카프카, 로드밸런서를 고려하니까 여기서도 안정성을 고려한다면 이게 나을 것 같다.

#### 시계열 데이터베이스 질의어

지수이동평균 계산식이 sql로는 복잡한데 flux로는 아주 간략하게 나온다. 시계열 데이터베이스의 쿼리 언어는 따로 공부해봐도 재밌을 것 같다.

#### 저장용량 최적화

요구사항에서 언급되었던 보관 정책의 구현이다. 데이터를 인코딩 및 압축하여 저장한다. 책에서는 **타임스탬프를 압축**하는 예시를 든다. 데이터 해상도를 특정 주기에 맞게 점차 낮추는 **다운샘플링**도 설명한다. 해상도 단위가 n배 커지는 만큼 저장해야할 데이터 크기는 1/n배가 된다.

### 경보 시스템

경보 매니저가 지정된 시간마다 쿼리를 날혀서 그 결과가 임계값을 위반하면 경보 이벤트를 생성한다. 경보를 필터링, 병합, 중복 제거하는 등의 작업을 처리한다. 재시도 로직으로 최소 한번 전달을 보장하는 것이 경보 특성상 중요해 보인다. 카산드라 같은 키값 저장소를 경보 저장소로 쓰는 것과 카프카로 경보 전달하는 것은 안정성을 보장하려는 것으로 이해했다. 다만 왜 이렇게 여러 장치를 두어서 뭔가에 대비하듯이 하나 싶었는데, 찾아보니 장애가 터지면 그와 연계된 서비스들도 줄줄이 터지면서 경보가 짧은 시간에 아주 많이 발생할 수 있다는 것을 알게 됐다. 서버 대수가 지금 1000*100로 십만대인데 동시에 여러대가 죽거나 한대가 죽어도 그 안에 여러 서비스가 돌고 있었다면 경보 수는 그만큼 늘어날 것이다. 갑작스러운 경보 폭주는 경보 유실로 이어질 수 있다. 그리고 알람 매니저가 죽으면 누가 경보를 전달할 수 있을까? 카프카나 카산드라에 전달만 되었다면 알람 매니저가 죽어도 이후 해당 경보를 필요로하는 시스템들에 전달이 가능한데 만약 전달하지 못한 경보들이 있다면? 결국 알람매니저도 여러 노드에 두는 것이 좋을 것 같다.
