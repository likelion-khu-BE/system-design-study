# 지표 모니터링 및 경보 시스템

## 시계열 데이터

시간의 흐름에 따라 지속적으로 기록되는 데이터.  
cpu 사용률, 메모리 사용량, 요청 수와 같은 시스템 지표가 대표적인 시계열 데이터이다.

> **지표 데이터 = Metric name + Label + Timestamp + Value**

→ Timestamp를 통해 언제 측정된 값인지 알 수 있고, Label을 이용하면 서버나 데이터의 출처 들을 구분할 수 있음.

---

## TSDB

시계열 데이터를 저장하고 조회하는데 특화된 데이터베이스.

모니터링 데이터는 새로운 값이 계속 추가돼서 쓰기 작업이 많고, 특정 시간 범위의 데이터를 조회하는 경우가 많음.  
→ 시계열 DB 사용하는 것이 좋음. ex) influxDB, OpenTSDB

---

## 대량의 시계열 데이터 관리하는 방법

지표가 지속적으로 생성되다보면 저장해야하는 데이터의 양이 매우 커짐  
→ aggregation, Downsampling 방법을 활용해 데이터를 효율적으로 보관

### 집계

여러 지표 값을 하나의 통계값을 집계하는 방법

```text
10:00:00 → 50%
10:00:10 → 60%
10:00:20 → 70%
        ↓
평균 CPU 사용률 → 60%
```

여러 지표값의 평균, 최댓값, 최솟값, 합계 등 필요한 방식으로 집계 가능

### 다운 샘플링

시간이 오래된 데이터의 시간 해상도를 낮추어 저장하는 방법

```text
10초 단위 데이터
      │
      │ 시간이 지나면
      ↓
1분 단위 데이터
      │
      │ 더 오랜시간이 지나면
      ↓
1시간 단위 데이터
```

최근 데이터는 자세한 분석이 필요할 가능성이 높으니까 세밀하게 보관하고, 오래될 수록 낮은 해상도로 저장하여 데이터 양을 줄임.

## pull vs push

지표 데이터 수집 방법에는 pull과 push 두가지 방식이 있다.

### pull

지표 수집기가 주기적으로 서버에 접근하여 지표를 가져오는 방식

```text
수집기 → 서버
       ← 지표
```

서버가 동적으로 추가,제거 되는 환경에서는 서비스 탐색 기술을 활용하여 현재 어떤 서버들이 존재하는지 알아낼 수 있다.

### push

서버가 직접 지표를 수집기에 전송하는 방식

```text
서버 → 수집기
```

수집 에이전트를 통해 지표 데이터를 모은 다음 주기적으로 수집기에 전달한다.  
데이터 집계(aggregation)을 통해 수집기에 보내는 데이터의 양을 효과적으로 줄일 수 있다.

## Kafka

시계열 데이터베이스에 장애가 생기면 데이터 손실이 발생할 가능성이 있음.  
→ Kafka와 같은 메세지 큐를 둠으로써 해결

- 데이터 수집 컴포넌트와 처리 컴포넌트 사이의 결합도를 낮춤
- 데이터베이스에 장애가 생겨도 데이터는 소실되지 않음. → 카프카에 보관해두면 되기 때문

```text
데이터 수집
    ↓
  Kafka
    ↓
데이터 처리
    ↓
  TSDB
```

## 질의 서비스

시각화 또는 경보 시스템에서 접수된 요청을 시계열 데이터 베이스를 통해 처리하는 역할 담당  
→ 클라이언트와 시계열 데이터베이스 사이의 결합도 낮출 수 있음.

반복적으로 요청되는 데이터의 경우 Cache를 사용하여 TSDB에 대한 반복적인 조회를 줄일 수 있다.

```text
클라이언트
    ↓
질의 서비스
    ↓
   TSDB
```

## 경보 시스템

수집된 지표가 미리 설정한 조건을 만족하는지 확인하고, 문제가 발생하면 알림을 보내는 시스템.

```text
경보 규칙
    ↓
지표 확인
    ↓
조건 만족 여부 판단
    ↓
경보 이벤트 생성
    ↓
메시지 큐
    ↓
경보 소비자
    ↓
알림
```

경보 시스템은 중복 제거가 중요.  
동일한 장애에 대하 계속 같은 경보를 보내면 사용자가 많은 중복 알림을 받게 되므로 중복된 경보를 제거하거나 억제할 필요가 있음.
