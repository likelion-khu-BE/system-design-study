# 메세지 큐 학습 정리

## 대규모 분산 메세지 큐를 직접 설계한다면 어떠한 구조로 만들어야하는가?

생산자 → 메세지 큐 → 소비자


## 메세지 큐가 필요한 이유

생산자와 소비자의 결합도 감소를 위해 메세지 큐를 사용함.
메세지 큐 덕분에 생산자는 메세지를 누가 가져가는지 신경쓰지않아도 됨.


## 우리가 만드는 것

엄청나게 많은 메세지를 여러 서버가 나눠 처리하면서도 데이터가 사라지지 않아야 하는 분산 시스템임.


## 메세지 큐 구성 요소

생산자, 소비자, 브로커, 저장소, 소비 상태 데이터베이스

브로커: 메세지를 저장하고 전달하는 서버
  → 대규모 트래픽 감당하기 위해 여러개를 둠.


## 토픽

같은 종류의 메세지를 모아 놓는 카테고리 → 토픽으로 메세지 구분


## 파티션

병렬 처리를 위해 토픽 하나를 여러 조각으로 나눔
-> 데이터를 분산해서 저장하고 처리 가능


## offset

메세지의 위치를 나타내는 번호
-> 소비자가 어디까지 읽었는지를 알 수 있음.
-> 과거 메세지를 다시 읽는 것이 가능해짐.


## 소비자 그룹

같은 소비자 그룹의 소비자들이 파티션을 나눠서 처리하면 병렬성 높일 수 있음.


## 메세지는 실제로 어디에 저장할까?

메모리에만 저장하면 서버 죽는 순간 메세지 다 날라감
-> 디스크에 데이터를 순차적으로 쓰는 방식을 활용해 저장 (계속 뒤에 붙이는 방식)
-> 높은 성능 확보

## 서버가 죽을 때를 대비해서

동일한 파티션 데이터를 여러 브로커에 복제함.


## 메세지를 정확히 몇 번 전달할 것인가

- at-most-once: 최대 한번 -> 메세지가 가끔 유실되도 되는 상황에 좋음
- at-least-once: 최소 한번 ->  알림 발송처럼 유실은 절대 안 되지만, 중복 정도는 애플리케이션에서 걸러낼 수 있는 상황에 쓰기 좋음.

- exactly-once: 정확히 한번 -> 결제 처리와 같은 유실과 중복이 절대 허용되지 않는 상황에 쓰기 좋음.
