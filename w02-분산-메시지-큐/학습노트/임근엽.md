# 분산 메시지 큐 설계 정리 — 전통적 Queue에서 Kafka까지

> 목표: 단순히 Kafka 용어를 외우는 것이 아니라,  
> **왜 Topic / Partition / Broker / Consumer Group / Offset / Replication / KRaft 같은 구조가 필요한지**를 요구사항에서부터 자연스럽게 이해한다.

---

## 1. 출발점: 메시지 큐가 왜 필요한가

애플리케이션 A가 어떤 일을 애플리케이션 B에게 시키거나, 어떤 사건이 발생했다는 사실을 여러 시스템에 전달한다고 하자.

가장 단순하게는 직접 호출할 수 있다.

```text
Producer → Consumer
```

하지만 시스템이 커지면 문제가 생긴다.

- Consumer가 죽으면 Producer도 영향을 받음
- Consumer가 느리면 Producer가 기다려야 함
- Consumer가 많아지면 Producer가 모든 Consumer를 알아야 함
- 순간적으로 요청이 몰리면 Consumer가 감당하지 못함

그래서 둘 사이에 **Message Broker**를 둔다.

```text
Producer → Broker → Consumer
```

Broker는 메시지를 잠시 보관하고 Producer와 Consumer를 분리한다.

이렇게 하면 Producer는 Consumer의 상태를 몰라도 되고, Consumer도 자기 속도대로 메시지를 처리할 수 있다.

---

# 2. Producer와 Consumer

## Producer

메시지를 만들어 Broker에 전달하는 역할이다.

중요한 점:

**Producer = 최종 사용자(client browser)가 아니다.**

예를 들어 쇼핑몰이라면:

```text
사용자 Browser
      ↓ HTTP
Order Backend Process
      ↓
KafkaProducer 객체
      ↓
Kafka Broker
```

Kafka Producer는 보통 별도의 서버 프로세스가 아니라 **백엔드 애플리케이션 내부에 포함된 Kafka client library 객체**다.

Producer의 주요 역할:

1. 메시지 직렬화
2. Topic 결정
3. Key를 이용한 Partition 선택
4. Metadata cache 관리
5. Partition Leader Broker 선택
6. 메시지 batching
7. 압축
8. TCP를 통한 Broker 전송
9. ACK 처리
10. 실패 시 retry

---

## Consumer

Broker에서 메시지를 가져와 실제 비즈니스 로직을 수행한다.

예:

```text
Kafka
  ↓
Payment Consumer
  ↓
결제 처리
```

Consumer도 일반적으로 애플리케이션 프로세스다.

---

# 3. 메시지 모델: Point-to-Point vs Publish-Subscribe

## 3.1 Point-to-Point

하나의 메시지를 여러 Consumer 중 **하나만 처리**한다.

```text
Queue

m1 → Worker A
m2 → Worker B
m3 → Worker C
```

대표적인 사용 사례:

- 이메일 보내기
- 이미지 리사이즈
- PDF 생성
- 백그라운드 Job
- 비동기 작업 처리

핵심은:

> "이 일을 누군가 한 명이 처리하면 된다."

전통적인 RabbitMQ Queue 모델이 여기에 잘 맞는다.

---

## 3.2 Publish-Subscribe

하나의 이벤트를 여러 독립적인 시스템이 각각 처리한다.

```text
             OrderCreated
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
     Payment   Inventory  Analytics
```

핵심은:

> "이 사건이 발생했다. 관심 있는 시스템은 각자 처리해라."

---

# 4. Topic

Topic은 메시지를 종류별로 구분하는 **논리적인 메시지 스트림**이다.

```text
order-events
payment-events
user-events
server-logs
```

예:

```text
Topic = order-events
Key   = orderId=123
Value = OrderCreated
```

Topic은 "어떤 종류의 이벤트인가?"를 표현한다.

---

# 5. 왜 Partition이 필요한가

Topic 하나에 초당 수십만~수백만 개의 메시지가 들어오면 한 서버/한 Consumer로 처리하기 어렵다.

그래서 Topic을 여러 개의 Partition으로 나눈다.

```text
Topic: order-events

P0
P1
P2
P3
```

각 Partition은 **독립적인 순서 있는 로그**다.

```text
P0:
offset 0 → m1
offset 1 → m4
offset 2 → m7

P1:
offset 0 → m2
offset 1 → m5
offset 2 → m8
```

Partition의 핵심 역할:

- 병렬 처리 단위
- 순서 보장 단위
- 저장 단위
- 복제 단위
- Consumer 할당 단위

---

# 6. Partition과 Ordering

Partition 내부에서는 순서를 보장할 수 있다.

```text
P0:
m1 → m2 → m3 → m4
```

하지만 Partition이 여러 개라면 Topic 전체의 전역 순서는 일반적으로 보장하지 않는다.

```text
P0: m1 → m3 → m5
P1: m2 → m4 → m6
```

실제 처리 완료 순서는:

```text
m1 → m2 → m4 → m3 → ...
```

처럼 될 수 있다.

즉:

> Kafka는 **Topic 전체 순서가 아니라 Partition 내부 순서**를 보장한다.

---

# 7. Message Key

Key는 "어느 Topic으로 갈지"를 고르는 값이 아니라, **이미 정해진 Topic 안에서 어느 Partition으로 갈지 결정하는 데 사용하는 값**이다.

예:

```text
topic = order-events
key   = orderId=123
value = PaymentCompleted
```

Producer는 개념적으로:

```text
hash(key) → Partition
```

을 수행한다.

동일한 `orderId=123` 이벤트를 모두 같은 Key로 보내면:

```text
OrderCreated(123)
PaymentCompleted(123)
ShippingStarted(123)
```

가 같은 Partition에 들어간다.

```text
P2:
OrderCreated
→ PaymentCompleted
→ ShippingStarted
```

따라서 중요한 설계 원칙은:

> **순서를 함께 보장해야 하는 이벤트들이 같은 Key를 갖도록 애플리케이션 개발자가 설계한다.**

Producer가 메시지 의미를 읽고 자동으로 "얘들은 순서가 중요하네"라고 판단하는 것은 아니다.

---

# 8. Broker란 무엇인가

Broker는 Kafka의 **서버 프로세스**다.

하드웨어적으로는 보통 다음과 같다.

```text
Physical Server / VM
────────────────────
CPU 여러 코어
RAM
SSD/HDD
NIC
────────────────────
Kafka Broker Process
```

Broker는 여러 Partition을 동시에 가지고 있다.

```text
Broker 1
 ├─ Topic A / P0
 ├─ Topic B / P3
 ├─ Topic C / P7
 └─ Replica ...
```

즉:

- Partition = 논리적인 로그/데이터 단위
- Broker = Partition을 실제로 보관하는 서버 프로세스

Broker 하나가 Partition 하나만 갖는 것이 아니다.

---

# 9. Broker와 Partition의 관계

예:

```text
Topic A

P0 → Broker 1
P1 → Broker 2
P2 → Broker 3
```

Broker 입장에서는 Topic이 무엇인지와 관계없이 여러 Partition을 관리한다.

```text
Broker 1
 ├─ Topic A / P0
 ├─ Topic B / P2
 └─ Topic C / P1
```

Scaling 관점에서는 Partition이 **배치와 부하 분산의 기본 단위**가 된다.

Broker가 과부하되면 Broker를 추가하고 Partition을 재배치할 수 있다.

```text
Before

Broker1: P0 P1 P2 P3 P4 P5

After

Broker1: P0 P1 P2
Broker2: P3 P4 P5
```

---

# 10. Consumer Group

같은 역할을 하는 Consumer들을 하나의 Consumer Group으로 묶는다.

```text
Payment Group
 ├─ Payment Consumer 1
 ├─ Payment Consumer 2
 └─ Payment Consumer 3
```

같은 Group 안에서 하나의 Partition은 동시에 최대 한 Consumer에게 할당된다.

```text
P0 → C1
P1 → C2
P2 → C3
```

따라서 같은 메시지가 동일한 업무에서 여러 번 처리되는 것을 방지하면서 병렬 처리할 수 있다.

---

# 11. Consumer Group과 Pub/Sub

Group 내부:

```text
P0 → Consumer 1
```

즉 Point-to-Point 성질.

Group 사이:

```text
                    Topic
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
    Payment Group Inventory Group Analytics Group
```

같은 메시지를 각 Group이 독립적으로 읽는다.

즉:

> 같은 Group 내부 = 작업 분배  
> 다른 Group 사이 = Publish-Subscribe

---

# 12. Partition 수와 Consumer 수

Consumer Group이 구독하는 전체 Partition 개수가 최대 병렬 처리량을 제한한다.

예:

```text
Topic A = 4 partitions
Topic B = 3 partitions

총 7 partitions
```

Group에 Consumer가 7개면 최대한 병렬로 처리 가능하다.

```text
C1 → A-P0
C2 → A-P1
C3 → A-P2
C4 → A-P3
C5 → B-P0
C6 → B-P1
C7 → B-P2
```

Consumer가 3개여도 가능하다.

```text
C1 → 여러 Partition
C2 → 여러 Partition
C3 → 여러 Partition
```

하지만 Consumer가 Partition보다 많으면 남는 Consumer는 할당받을 Partition이 없다.

---

# 13. Offset과 Consumer 상태

Kafka는 메시지를 읽었다고 바로 삭제하지 않는다.

```text
P0:
offset 100 → m100
offset 101 → m101
offset 102 → m102
...
```

각 Consumer Group은 자신이 어디까지 처리했는지 Offset을 기억한다.

```text
Payment Group   P0 offset = 500
Inventory Group P0 offset = 420
Analytics Group P0 offset = 300
```

즉 **메시지의 생명주기와 Consumer의 처리 위치가 분리**되어 있다.

이것이 Kafka의 매우 중요한 특징이다.

---

# 14. 왜 상태 저장소가 필요한가

전통적인 Queue라면 메시지를 처리한 뒤 삭제할 수 있다.

```text
[m1][m2][m3]

m1 처리
↓
m1 제거

[m2][m3]
```

이 경우 Queue의 맨 앞이 곧 현재 처리 위치다.

하지만 Kafka처럼 메시지를 계속 보관하면:

```text
[m1][m2][m3][m4][m5]
```

Group마다 처리 위치가 다를 수 있기 때문에:

```text
Group A offset = 5
Group B offset = 3
Group C offset = 1
```

를 따로 저장해야 한다.

즉 상태 저장소가 필요한 본질적 이유는:

> **메시지를 읽었다고 삭제하지 않고, Consumer별 진행 상태를 따로 관리하기 때문**

2주 retention은 이 필요성을 더욱 강하게 만들 뿐, 근본 원인은 아니다.

---

# 15. Metadata

Metadata는 실제 메시지가 아니라 **Kafka 클러스터 구조에 대한 정보**다.

예:

```text
Topic A
 ├─ P0 leader = Broker1
 ├─ P1 leader = Broker2
 └─ P2 leader = Broker3

P0 replicas = Broker1, Broker2, Broker3
Broker1 alive
Broker2 alive
Broker3 alive
```

즉:

- Broker 목록
- Topic 목록
- Partition 개수
- Partition Leader
- Replica 위치
- ISR
- 클러스터 구성

등이 Metadata다.

---

# 16. Controller

Controller는 Kafka 클러스터 전체 구조를 관리하는 **Control Plane 서버 역할**이다.

Broker가 실제 메시지 데이터를 다룬다면 Controller는:

- Broker 생존 상태
- Topic/Partition 구성
- Partition Leader
- Replica 배치
- Leader 변경
- 클러스터 Metadata 변경

등을 관리한다.

하드웨어적 실체:

```text
Controller Machine
────────────────────
CPU
RAM
SSD
NIC
────────────────────
Kafka Process
role = controller
```

현대 Kafka의 KRaft에서는 여러 Controller가 quorum을 구성한다.

```text
Controller C1
Controller C2
Controller C3
```

Metadata는 RAM에 현재 상태를 유지하고, SSD/HDD에는 replicated metadata log 형태로 영속 저장한다.

---

# 17. KRaft

KRaft는 Kafka가 ZooKeeper 없이 자체적으로 Metadata를 관리하도록 만든 **Raft 기반 Controller quorum 시스템**이다.

```text
Controller C1
    ↕
Controller C2
    ↕
Controller C3
```

Controller들은 Metadata log를 복제한다.

하나가 장애 나도 과반수가 살아 있으면 클러스터 Metadata를 유지할 수 있다.

즉:

```text
Message Data
→ Broker replica들에 복제

Cluster Metadata
→ Controller quorum에 복제
```

---

# 18. Control Plane vs Data Plane

## Control Plane

"클러스터가 어떻게 구성되어 있는가?"

```text
P0 Leader = Broker1
Broker2 alive
Broker3 dead
```

를 관리한다.

주체:

```text
Controller ↔ Broker
```

대표 통신:

- Broker registration
- Broker heartbeat
- Metadata log replication/fetch
- Leader/replica 상태 변경

---

## Data Plane

실제 메시지가 이동하는 경로.

```text
Producer → Broker
Consumer ← Broker
Broker ↔ Broker replication
```

즉:

```text
Control Plane
= 길을 관리

Data Plane
= 실제 데이터가 이동
```

---

# 19. Broker ↔ Controller 통신

Broker가 시작하면 Controller에게 자신을 등록한다.

```text
Broker
  │ BrokerRegistrationRequest
  ▼
Controller
```

그리고 계속 Heartbeat를 보낸다.

```text
Broker
  │ BrokerHeartbeat
  ▼
Controller
```

개념적으로:

```text
"나 Broker7 살아 있음"
"metadata offset 500까지 따라왔음"
```

Controller는 이를 보고 Broker의 생존 여부와 Metadata 동기화 상태를 판단한다.

Broker들은 KRaft metadata log를 따라가며 최신 클러스터 상태를 얻는다.

---

# 20. Producer는 Metadata에 어떻게 접근하는가

Producer는 Controller SSD를 직접 읽지 않는다.

Producer는 Broker에게 Metadata를 요청한다.

Producer 설정:

```text
bootstrap.servers =
  broker1:9092,
  broker2:9092,
  broker3:9092
```

이 주소들은 "항상 이 Broker에게 보내라"는 의미가 아니라 **클러스터에 처음 진입하기 위한 주소**다.

Producer:

```text
Producer
  │ MetadataRequest
  ▼
Broker1
```

Broker 응답:

```text
order-events

P0 leader → B1
P1 leader → B3
P2 leader → B2
```

Producer는 이것을 자기 애플리케이션 서버 RAM에 캐시한다.

```text
KafkaProducer RAM

metadata cache
P0 → B1
P1 → B3
P2 → B2
```

---

# 21. 왜 Producer가 Metadata를 캐시하는가

메시지는 초당 수십만 번 발생할 수 있지만:

```text
P2 Leader → Broker2
```

같은 정보는 비교적 자주 바뀌지 않는다.

매 메시지마다:

```text
"Leader 누구?"
→ 응답
→ 메시지 전송
```

하면 네트워크 왕복과 CPU 오버헤드가 엄청 커진다.

그래서:

```text
Metadata 한번 조회
↓
RAM cache

m1 → cache 사용
m2 → cache 사용
m3 → cache 사용
...
```

한다.

Metadata가 틀리면 Broker 요청이 실패한다.

```text
Producer cache:
P2 → B2

실제:
P2 → B3
```

Producer:

```text
B2로 Produce
↓
실패 / Not Leader 계열 오류
↓
Metadata refresh
↓
P2 → B3
↓
B3으로 retry
```

즉 Producer들의 Metadata cache끼리 서로 동기화하지 않는다.

각자 필요할 때 Broker에서 최신 Metadata를 다시 받아오면 된다.

---

# 22. Metadata와 Router의 차이

Router 방식:

```text
Producer
  ↓
Router
  ↓
Broker
```

모든 실제 메시지가 Router를 통과한다.

그러면 Router가 중앙 병목이 될 수 있다.

Kafka 방식:

```text
Producer
  ↓ Metadata 조회
"P2 → Broker3"
  ↓

Producer ─────────────→ Broker3
       실제 메시지
```

즉:

> Router = 실제 데이터를 중계  
> Metadata = 어디로 갈지만 알려주는 정보

Kafka는 **작은 routing 정보는 캐시하고, 큰 메시지는 Broker로 직접 보내는 구조**다.

---

# 23. Producer가 Partition을 선택하는 과정

Producer record:

```text
topic
partition (optional)
key       (optional)
value
```

일반적으로 개발자는:

```text
topic = order-events
key   = orderId=123
value = OrderCreated
```

를 지정한다.

Producer는:

```text
Key
 ↓
Partitioner / Hash
 ↓
P2
 ↓
Metadata Cache
 ↓
P2 Leader = B3
 ↓
B3으로 ProduceRequest
```

한다.

즉 정확한 구조는:

```text
KEY
 ↓
PARTITION
 ↓
METADATA
 ↓
LEADER BROKER
```

---

# 24. Broker 간 복제

Partition 하나를 여러 Broker가 복제한다.

```text
P0

Broker1 = Leader
Broker2 = Follower
Broker3 = Follower
```

Producer는 Leader에게 쓴다.

```text
Producer → Broker1 Leader
```

Follower는 Leader의 로그를 따라간다.

```text
Broker2 ──Fetch──→ Broker1
Broker3 ──Fetch──→ Broker1
```

복제 후:

```text
Broker1 [m1][m2][m3]
Broker2 [m1][m2][m3]
Broker3 [m1][m2][m3]
```

---

# 25. Leader와 Follower가 필요한 이유

Partition 순서를 하나의 서버가 결정해야 한다.

여러 Broker에 동시에 쓰면:

```text
B1: m1
B2: m2
```

에서 `m1 → m2`인지 `m2 → m1`인지 결정하기 어렵다.

그래서:

```text
Partition 하나
→ Leader 하나
→ 모든 쓰기 순서 결정
```

한다.

Follower는 Leader 장애 시 대체할 수 있는 Replica다.

---

# 26. ISR

Follower가 너무 뒤처져 있을 수도 있다.

```text
Leader:
m1 m2 m3 m4 m5

Follower A:
m1 m2 m3 m4 m5

Follower B:
m1 m2
```

Follower B를 바로 Leader로 올리면 m3~m5가 유실될 수 있다.

그래서 Leader와 충분히 동기화된 Replica 집합을 **ISR(In-Sync Replicas)**라고 한다.

```text
ISR = [Broker1, Broker2]
```

Leader 장애 시 가능한 한 ISR 안에서 새 Leader를 뽑는다.

---

# 27. Replication과 ACK

Replication은 latency를 조금 희생하고 안정성을 높이는 구조다.

Producer가 얼마나 기다릴지에 따라 내구성이 달라진다.

```text
acks=0
→ 응답 기다리지 않음

acks=1
→ Leader 저장 성공만 확인

acks=all
→ ISR의 필요한 Replica 복제까지 확인
```

더 강한 안정성을 원할수록 latency가 증가할 수 있다.

모든 Replica가 동시에 영구적으로 사라지면 데이터는 유실된다.

그래서:

- 여러 Broker에 분산
- 장애 도메인 분리
- Leader 장애 후 새 Replica 확보
- replication factor 유지

등으로 확률을 낮춘다.

---

# 28. Consumer와 Broker 통신

Consumer는 **Pull 방식**으로 Broker에서 메시지를 가져온다.

```text
Consumer
  │
  │ Fetch(offset=1500)
  ▼
Broker
```

Broker:

```text
offset 1500 → m1
offset 1501 → m2
...
```

를 반환한다.

---

# 29. Poll vs Long Poll

## 일반 Poll

```text
Consumer: 메시지 있어?
Broker: 없음

Consumer: 메시지 있어?
Broker: 없음
```

빈 요청이 많이 발생할 수 있다.

---

## Long Poll

```text
Consumer:
"메시지 없으면 최대 500ms 기다려"

Broker
  ↓
대기
  ↓
메시지 생기면 즉시 반환
```

장점:

- 빈 요청 감소
- 낮은 latency
- batching 가능

단점:

- 연결/timeout 관리 필요
- 서버 구현이 조금 더 복잡

Kafka Fetch는 이런 Long Polling 성격을 가진다.

---

# 30. Push vs Pull

## Push

```text
Broker → Consumer
```

Broker가 속도를 주도한다.

문제:

Consumer가 느리면 과부하될 수 있다.

---

## Pull

```text
Consumer → Broker
```

Consumer가 자기 처리 속도에 맞춰 가져온다.

장점:

- 자연스러운 backpressure
- batching 용이
- 느린 Consumer 대응 쉬움

Kafka는 Pull 모델이 잘 맞는다.

---

# 31. Consumer Group Coordinator

Consumer Group마다 관리 역할을 맡는 Broker가 있다.

```text
Group G
Coordinator = Broker2
```

Coordinator는:

- Consumer 가입/탈퇴
- Heartbeat
- 장애 감지
- Rebalance 관리
- Group 상태
- Offset commit

등을 관리한다.

중요:

Coordinator Broker도 일반 Broker다.

```text
Broker2
 ├─ 실제 Partition 보유
 ├─ Produce/Fetch 처리
 └─ 여러 Consumer Group Coordinator 역할
```

Coordinator 전용 머신이라는 뜻이 아니다.

---

# 32. Rebalance

Consumer Group의 멤버가 바뀌면 Partition 담당자를 다시 정한다.

기존:

```text
C1 → P0, P1
C2 → P2, P3
```

C3 추가:

```text
C1 → P0, P1
C2 → P2
C3 → P3
```

C2 장애:

```text
C1 → P0, P1
C3 → P2, P3
```

이 과정이 Rebalance다.

Coordinator가 Group 변화를 감지하고 재조정을 관리한다.

---

# 33. 데이터 저장: 왜 DB 대신 로그인가

메시지 큐의 주요 workload는 매우 단순하다.

```text
Producer:
뒤에 계속 append

Consumer:
앞에서부터 sequential read
```

반면 관계형 DB는:

- WAL
- Table page
- Index
- Transaction
- MVCC / Lock
- Query optimizer
- random query

등 범용 기능을 제공한다.

메시지 하나 INSERT에도:

```text
WAL 기록
Table page 수정
Index 수정
Dirty page flush
```

같은 작업이 생길 수 있다.

Kafka에서는 복잡한 검색 기능이 필요하지 않으므로 더 단순한 로그 구조를 사용한다.

---

# 34. Append-Only Log

Partition은 본질적으로 순차 로그다.

```text
[m1][m2][m3][m4][m5]
                    ↑
                  append
```

장점:

- Sequential write
- 단순한 저장 구조
- 높은 처리량
- 순차 replay 용이
- Segment 삭제 쉬움

---

# 35. Segment

Partition 로그 하나를 엄청 큰 파일 하나로 만들면 관리가 어렵다.

그래서 여러 Segment 파일로 나눈다.

```text
Partition P0

000000.log
001000.log
002000.log
003000.log
```

논리적으로는 하나의 Partition이지만 물리적으로 여러 파일이다.

장점:

- 오래된 Segment 단위 삭제
- Retention 관리
- Index 크기 감소
- Offset 탐색 용이
- 장애 복구/파일 관리 쉬움

---

# 36. HDD / SSD / RAM

## HDD

회전 원판 + 헤드.

Random access:

```text
block 100
→ block 900000
→ block 50
```

마다 헤드 이동과 회전 대기가 필요하다.

따라서 매우 느리다.

Sequential access:

```text
100 → 101 → 102 → 103
```

은 헤드가 거의 계속 같은 방향으로 이동하므로 상대적으로 빠르다.

---

## SSD

NAND Flash 기반.

기계적 움직임이 없어서 Random access가 HDD보다 훨씬 빠르다.

하지만 RAM보다는 느리다.

---

## RAM

CPU가 Memory Controller를 통해 매우 빠르게 접근한다.

Random access도 매우 빠르지만:

- 비쌈
- 휘발성

이라는 단점이 있다.

---

# 37. 왜 Kafka 설계에서 HDD가 자주 언급되는가

SSD가 당연히 더 빠르다.

하지만 Kafka workload는:

```text
append
+
sequential read
```

이기 때문에 HDD가 잘하는 패턴이다.

그리고 HDD는 용량 대비 매우 저렴하다.

따라서:

> **더 싸고, 요구 성능을 만족하므로 HDD도 충분히 실용적**

이라는 설계가 가능했다.

현대 시스템에서는 SSD/NVMe도 많이 사용한다.

핵심은 HDD 자체가 아니라 **Sequential I/O를 극대화하는 로그 구조**다.

---

# 38. OS Page Cache

Kafka는 디스크만 직접 믿는 것이 아니라 OS가 RAM을 디스크 캐시로 적극 활용하도록 한다.

```text
Broker
  ↓
OS Page Cache (RAM)
  ↓
SSD/HDD
```

읽기:

```text
Consumer가 offset 100부터 읽음
↓
OS가 101,102,...도 미리 읽음
↓
다음 요청은 RAM에서 처리
```

이를 Read-Ahead라고 한다.

쓰기:

```text
m1 m2 m3 ...
↓
RAM Page Cache
↓
나중에 묶어서 Disk flush
```

이를 Write Buffering / Write-back이라고 볼 수 있다.

---

# 39. WAL

WAL = Write-Ahead Log.

DB에서 실제 Data Page를 변경하기 전에 변경 내용을 로그에 먼저 기록한다.

```text
UPDATE balance 100 → 50

↓
WAL에 먼저 기록
↓
COMMIT
↓
Data Page는 나중에 flush 가능
```

장애 발생:

```text
Data Page = 100
WAL = 100 → 50 committed
```

이면 재시작 후 WAL을 이용해 복구한다.

중요:

- DB 본체 = Table / Index
- WAL = 장애 복구용 변경 기록
- RAM Buffer Pool = 빠른 작업 공간

Kafka는 DB의 WAL을 그대로 가져온 것이 아니라, **WAL과 비슷한 append-only log 아이디어를 메시지의 본 저장 구조로 사용**한다.

---

# 40. Database vs Kafka Log

DB:

```text
Table / Index가 본 데이터
WAL은 복구용
```

Kafka:

```text
Append-only Log 자체가 본 데이터
```

Kafka Consumer가 원하는 건 대체로:

```text
"offset 1000부터 순서대로 줘"
```

이지:

```text
"userId=123이고 price > 10000인 메시지 검색"
```

이 아니다.

복잡한 랜덤 질의는 DB/Search Engine이 담당하는 편이 자연스럽다.

---

# 41. Retention과 Replay

Kafka가 메시지를 2주 보관한다고 하자.

```text
14일 전 ---------------- 오늘
[Segment][Segment]...[Segment]
```

Kafka의 강점은:

```text
"10일 전 위치부터 다시 쭉 읽어"
```

다.

```text
offset 2,000,000
→ 2,000,001
→ 2,000,002
→ ...
```

처음 한 번 과거 위치로 seek하고, 이후에는 Sequential Read가 된다.

반대로:

```text
3일 전
→ 10일 전
→ 오늘
→ 7일 전
→ 1일 전
```

처럼 랜덤하게 왔다 갔다 하는 검색에는 적합하지 않다.

그런 질의는 DB, Elasticsearch, Data Warehouse, Data Lake 등에 맡긴다.

---

# 42. Kafka에서 Replay가 중요한 이유

Kafka의 중요한 특성은 단순한 "디스크 영속성"보다:

> **Retained Ordered Log + Independent Offset + Replay**

에 가깝다.

예:

실시간 분석 코드에 어제 오후 2시부터 버그가 있었다.

```text
offset 8,000,000 ← 버그 시작
...
offset 10,000,000 ← 현재
```

코드 수정 후:

```text
offset 8,000,000부터
→ 오늘까지 다시 순차 처리
```

하면 된다.

---

# 43. 새로운 Consumer Group으로 과거 처리

Consumer Group마다 독립적인 offset을 가진다.

```text
Realtime Group     offset = 10,000,000
Analytics Group    offset = 9,800,000
Fraud Group        offset = 9,900,000
```

새 알고리즘을 만들었다면:

```text
Fraud-V2 Group 생성
offset = 5,000,000
```

로 시작해 과거부터 현재까지 replay할 수 있다.

즉:

> **새로운 처리 목적이 생기면 새 Consumer Group을 만들고 원하는 offset부터 읽을 수 있다.**

---

# 44. Kafka가 잘 맞는 서비스

Kafka의 핵심 선택 기준은 단순히 "서비스를 오래 운영하느냐"가 아니다.

더 정확한 기준:

> **서비스에서 발생한 사건의 순서 있는 기록이 미래의 새로운 처리·분석·재계산에 계속 가치가 있는가?**

대표 예:

### 추천 시스템

```text
click
watch
like
search
```

이벤트를 Kafka에 저장.

새 추천 알고리즘 등장:

```text
새 Consumer Group
→ 7일 전부터 replay
→ feature 재계산
```

### Fraud Detection

결제 이벤트를 Kafka에 저장.

새 사기 패턴 규칙 등장:

```text
3일 전부터 replay
→ 새로운 탐지 규칙 검증
```

### 검색 서비스

검색/클릭 로그를 Kafka에 저장.

새 autocomplete 알고리즘:

```text
과거 로그 replay
→ 새로운 index 구축
```

### 게임

```text
아이템 획득
거래
강화
경매
로그인
```

새 작업장 탐지 알고리즘 등장:

```text
최근 2주 replay
```

### Observability / Security

```text
Server logs
API events
Network events
```

새 탐지기:

```text
어제부터 replay
```

---

# 45. Kafka vs RabbitMQ

## RabbitMQ 전통 Queue

핵심 질문:

> "이 작업을 누군가 처리하면 되는가?"

```text
SendEmail
ResizeImage
GeneratePDF
```

처리:

```text
Queue
↓
Worker
↓
ACK
↓
끝
```

과거 메시지 자체의 재사용 가치가 낮다.

---

## Kafka

핵심 질문:

> "이 사건 기록을 여러 시스템이 서로 다른 시점에서 계속 읽을 가치가 있는가?"

```text
UserClicked
OrderCreated
PaymentOccurred
ServerLogGenerated
SensorMeasured
```

Consumer가 읽어도 로그가 retention 동안 남는다.

---

## 가장 중요한 구분

```text
RabbitMQ
= Queue abstraction
= 처리해야 할 일

Kafka
= Retained Log abstraction
= 발생한 사건의 기록
```

기능적으로 서로 흉내 낼 수 있는 부분은 많다.

중요한 것은 어떤 abstraction이 workload의 정상적인 운영 패턴과 맞는가다.

---

# 46. 장기 보관

Kafka retention보다 더 오래 보관하려면 별도 Sink Consumer를 둘 수 있다.

```text
Kafka
  ├→ 실시간 Consumer
  ├→ Analytics Consumer
  └→ Archive Consumer
          ↓
      S3 / Data Lake / DB
```

장기 Storage에 적재할 Consumer Group을 따로 둔다.

```text
S3 Sink Group
Warehouse Group
Search Index Group
```

각각 독립된 목적이면 서로 다른 Consumer Group이다.

Broker가 직접 외부 DB/S3에 저장하지 않는 이유:

- 외부 Storage 장애가 Broker에 영향을 줄 수 있음
- Broker를 단순하게 유지
- 느슨한 결합
- Sink 확장/재시도 독립 가능

---

# 47. Tiered Storage

Kafka 자체에서도 최근 데이터와 오래된 데이터를 서로 다른 저장 계층에 둘 수 있다.

```text
HOT
최근 Segment
→ Broker local SSD/HDD

COLD
오래된 Segment
→ Remote Storage
```

즉 장기 데이터는 S3 같은 Remote Storage에 두고, 논리적으로는 같은 Kafka Log처럼 다룰 수 있다.

---

# 48. Throughput / Bandwidth와 Latency

## Throughput

단위 시간당 얼마나 많은 실제 데이터를 처리하는가.

```text
100,000 msg/s
1 GB/s
```

## Latency

메시지 하나가 들어와 Consumer에게 도달하기까지 걸리는 시간.

```text
Producer send
→ 5ms
→ Consumer receive
```

---

# 49. Batching

메시지 하나씩 전송하면:

```text
[data][overhead]
[data][overhead]
[data][overhead]
```

매번:

- system call
- network packet
- request parsing
- ACK
- disk I/O request

비용이 발생한다.

Batching:

```text
[data data data data data][overhead]
```

하면 메시지당 고정 비용이 줄어든다.

결과:

```text
Throughput ↑
CPU 효율 ↑
```

하지만 첫 메시지는 Batch가 모일 때까지 기다려야 하므로:

```text
Latency ↑ 가능
```

즉:

> 큰 Batch = 높은 Throughput  
> 작은 Batch = 낮은 Latency

라는 trade-off가 존재한다.

---

# 50. Zero-Copy

Broker가 디스크 메시지를 Consumer에게 전달한다고 하자.

일반 방식:

```text
Disk
 ↓
Kernel Buffer
 ↓ copy
Broker User Buffer
 ↓ copy
Socket Buffer
 ↓
NIC
```

Broker는 메시지 내용 자체를 수정하지 않는 경우가 많다.

그래서 불필요한 메모리 복사를 제거한다.

```text
Disk / Page Cache
       ↓
      NIC
```

Linux `sendfile()` 같은 방식이 대표적인 예다.

효과:

- CPU 사용 감소
- Memory bandwidth 낭비 감소
- Throughput 증가

---

# 51. Kafka 고성능 설계의 공통 철학

지금까지 나온 최적화는 전부 같은 방향이다.

```text
Append-only log
→ random I/O 감소

Sequential I/O
→ HDD/SSD 효율 증가

Page Cache
→ RAM 적극 활용

Batching
→ 메시지당 고정비용 감소

Zero-copy
→ 메모리 복사 감소

Client-side metadata cache
→ routing lookup 감소

Direct Broker communication
→ 중앙 Router 제거
```

즉:

> **메시지 하나를 처리할 때 쓸데없는 일을 최대한 줄여 같은 하드웨어에서 더 많은 메시지를 처리한다.**

```text
                          KRaft Controllers
                      ┌────────┬────────┐

                      └────────┴────────┘
                              │
                         Control Plane
```

# 54. 최종 핵심 요약

## Kafka를 왜 쓰는가

단순히 "메시지를 디스크에 저장해서"가 아니다.

Kafka가 강한 경우:

```text
1. 사건(event)의 기록이 중요하다.
2. 여러 독립 Consumer가 같은 이벤트를 읽는다.
3. Consumer마다 처리 속도/시점이 다르다.
4. 새로운 Consumer가 나중에 추가될 수 있다.
5. 과거 특정 offset부터 replay/backfill/rebuild가 자주 필요하다.
6. 높은 처리량을 위해 Partition 병렬화가 필요하다.
```

---

## RabbitMQ와 가장 본질적인 차이

```text
RabbitMQ:
"이 일을 누군가 처리해라."

Kafka:
"이 사건이 발생했다.
이 기록은 여러 시스템이 다시 읽을 수 있다."
```

---

## Kafka를 한 문장으로

> **Kafka는 Topic을 여러 Partition으로 나눈 뒤 각 Partition을 여러 Broker에 복제하여 저장하고, 여러 Consumer Group이 각자의 offset을 가지고 동일한 순서 있는 이벤트 로그를 독립적으로 읽고 replay할 수 있게 만든 분산 로그 기반 메시징 시스템이다.**
