## 1. 사전 지식

### 1.1 메시지 큐란?
> 프로그램 간에 데이터를 보낼 때 중간에서 대기열(Queue) 역할을 해주는 우체통

### 1.2 분산 메시지 큐란?
> 서로 다른 서버나 시스템끼리 데이터를 주고받을 때 buffer 역할을 해주는 중간 저장소

| 구분 | 일반 메시지 큐 (Single-node) | 분산 메시지 큐 (Distributed) |
|---|---|---|
| 설치 및 구조 | 단일 서버(1대)에서 동작 | 여러 대의 서버(클러스터)로 묶여서 동작 |
| 처리량 | 단일 서버의 CPU/메모리 한계까지만 처리 | 브로커를 늘리는 대로 처리량 확장 가능 |
| 안정성(고가용성) | 서버가 죽으면 서비스 중단 및 데이터 손실 위험 | 일부 서버가 죽어도 다른 서버에 복제본이 있어 안전 |
| 대표 예시 | Redis (Pub/Sub, Stream), RabbitMQ(단일 노드) | Apache Kafka, Apache Pulsar |

- **일반 메시지 큐**: 손님이 주문서를 주문 접수함(큐)에 넣어두는 방식. 요리사는 자기 속도에 맞춰 접수함에서 주문서를 하나씩 꺼내 요리하지만, 카운터 컴퓨터가 고장 나면 주문이 멈춘다.
- **분산 메시지 큐**: 주문 접수함과 카운터 컴퓨터가 여러 대 백업되어 연동되어 있어, 한 대가 고장 나도 다른 카운터가 계속 주문을 받고 저장한다.

### 1.3 메시지 큐로 얻는 이득

| 이득 | 설명 |
|---|---|
| 결합도 완화 | A가 B를 직접 호출하면 B 장애 시 A도 영향을 받지만, 중간에 큐를 두면 B 장애 중에도 데이터 손실 없이 큐에 쌓인다 |
| 규모 확장성 개선 | 트래픽 부하에 맞게 시스템 규모를 독립적으로 조절 가능 (트래픽 몰릴 때 소비자 추가 → 처리 용량↑) |
| 가용성 개선 | 특정 컴포넌트 장애가 발생해도 다른 컴포넌트는 큐와 계속 상호작용 가능 |
| 성능 개선 | 비동기 통신으로 생산자는 응답을 기다리지 않고 메시지 발행, 소비자는 읽을 메시지가 있을 때만 소비 |

**예시: 회원가입 시 웰컴 이메일 발송 / 포인트 지급**

```
[동기 방식 - 메시지 큐 없음]
1. 회원가입 버튼 클릭
2. DB에 사용자 정보 저장 (0.1초)
3. 이메일 전송 API 호출 (2초 대기)
4. 포인트 지급 로직 실행 (0.5초)
→ 총 2.6초 후 "회원가입 완료" 응답
```

```
[비동기 방식 - 메시지 큐 사용]
1. 회원가입 버튼 클릭
2. DB에 사용자 정보 저장 (0.1초)
3. 큐에 "이메일 발송해라", "포인트 지급해라" 메시지 적재 (0.01초)
4. 즉시 "회원가입 완료" 응답
→ 총 0.11초 소요
```

> 응답이 빠른 이유: 서버가 이메일 전송·포인트 지급이 실제로 끝날 때까지 기다리지 않고, "큐에 잘 넣어뒀으니 나중에 처리되겠지" 하고 곧바로 응답하기 때문.

### 1.4 이벤트 스트리밍 플랫폼

시스템 내부에서 발생하는 이벤트(예: *"결제 완료"*, *"택시 GPS 위치 변경"*, *"센서 온도 상승"* 등 상태 변경 데이터)를 실시간으로 수집·저장·전달·처리하는 데이터 파이프라인의 핵심 인프라.

**활용 사례**

- **배달/모빌리티** (배민, 우버): 라이더 GPS 위치 변경 이벤트를 실시간 추적해 지도에 반영
- **금융** (이상 거래 탐지, FDS): 결제 이벤트를 즉시 분석해 이상 패턴(예: 서울 결제 직후 해외 결제) 탐지 및 차단
- **커머스** (쿠팡, 아마존): 상품 클릭 이벤트를 실시간 수집해 연관 상품을 즉시 추천

## 2. 문제 이해 및 요구사항 확정

### 기능 요구사항
1. 텍스트 형태 메시지, 수 KB 정도의 크기
2. 메시지 반복 소비 가능 (하나의 메시지를 여러 소비자가 수신) — *부가 기능. 전통적 메시지 큐는 소비 즉시 폐기되어 반복 소비 불가*
3. 생산 순서대로 소비 — *부가 기능. 전통적 분산 메시지 큐는 순서를 보증하지 않음*
4. 데이터는 약 2주간 지속성 보장 — *부가 기능. 전통적 분산 메시지 큐는 지속성 보관을 보증하지 않음*
5. 생산자/소비자는 많을수록 좋음 (높은 확장성)
6. 메시지 전달 방식은 3가지(최소 한 번 / 최대 한 번 / 정확히 한 번)를 모두 지원하되, **최소 한 번(at-least-once)은 필수**이며 사용자가 설정 가능해야 함

### 비기능 요구사항
- 높은 수준의 대역폭 제공 / 낮은 전송 지연

### 요구사항 → 분산 시스템 도출 근거

| 요구사항 조합 | 왜 분산이 필요한가 |
|---|---|
| 데이터 2주 보관(지속성) + 높은 대역폭(대용량 트래픽) | 단일 서버 디스크 용량 초과 → 여러 대 서버로 구성된 분산 저장소 필수 |
| 생산자/소비자가 많을수록 좋음(높은 확장성) | 생산자/소비자 증가 시 SPOF 발생, CPU/메모리/연결 수 부족 → 여러 서버로 분산해야 감당 가능 |
| 데이터 보장(최소 한 번 전달 + 지속성) | 특정 서버 장애 시에도 데이터가 남아있어야 함(At-least-once) → 여러 서버에 분산 저장 + 복제본 필요 |

## 3. 메시지 전달 방식 (Delivery Semantics)

생산자가 보낸 메시지를 소비자가 얼마나 신뢰성 있게 전달받는가에 대한 약속 수준. 네트워크 장애, 서버 다운, 재전송 등의 변수 발생 시 유실/중복을 어떻게 처리하느냐에 따라 3가지로 나뉜다.

### 3.0 생산자 측 ACK 설정: acks=0 / acks=1 / acks=all

전달 방식(Delivery Semantics)을 이해하려면 먼저 **생산자가 브로커에게 메시지를 보낸 뒤 "잘 저장됐다"는 응답(ACK)을 얼마나 엄격하게 기다릴지**를 정하는 `acks` 설정을 알아야 한다. 이는 카프카 등 분산 메시지 큐에서 생산자가 조절할 수 있는 값으로, 안정성과 성능(대역폭/지연) 사이의 트레이드오프를 결정한다.

파티션은 보통 **리더(Leader) 브로커 1대 + 팔로워(Follower) 브로커 여러 대**로 복제되어 있는데, `acks` 값에 따라 "누구의 저장 완료를 확인해야 ACK로 인정할지"가 달라진다.

| 설정 | 동작 방식 | 속도 | 안정성 |
|---|---|---|---|
| **acks=0** | 생산자가 메시지를 보내고 브로커의 응답을 아예 기다리지 않음. "보냈으니 됐다"고 바로 다음 메시지로 넘어감 | 가장 빠름(지연 최소) | 가장 낮음 — 전송 중 유실돼도 생산자는 알 수 없음 |
| **acks=1** | 파티션의 **리더 브로커**가 메시지를 저장한 시점에만 ACK를 받음. 팔로워로의 복제 완료는 기다리지 않음 | 중간 | 중간 — 리더가 ACK 직후, 복제되기 전에 다운되면 메시지 유실 가능 |
| **acks=all(-1)** | 리더 + **모든(또는 min.insync.replicas 만큼의) 팔로워**가 메시지를 복제·저장 완료할 때까지 기다린 후 ACK | 가장 느림(지연 최대) | 가장 높음 — 리더가 죽어도 팔로워에 복제본이 남아있어 유실되지 않음 |

> 즉, `acks`는 **"생산자 → 브로커" 구간**의 신뢰도를 결정하는 설정이고, 이 값을 무엇으로 두느냐가 아래 3가지 전달 방식(At-Most-Once / At-Least-Once / Exactly-Once) 중 어디에 가까워지는지를 좌우하는 핵심 변수 중 하나다. (참고: 전달 방식은 생산자 ACK뿐 아니라 소비자의 오프셋 커밋 방식과도 함께 맞물려 결정된다.)

### 3.1 최대 한 번 (At-Most-Once)

**메시지가 최대 1번만 전달된다(0번 또는 1번). 중복은 없지만 유실될 수 있다.**

생산자가 ACK를 확인하지 않거나(`acks=0`), 소비자가 메시지를 받자마자 곧바로 "처리 완료"로 기록해버리는 방식이다. 실제 처리 도중 소비자가 다운되면 그 메시지는 재전송 없이 그대로 사라진다. 대신 확인 절차가 없어 가장 빠르다.

- **관련 설정**: `acks=0` (또는 재시도 없는 `acks=1`)
- **사용 사례**: IoT 센서 데이터, 실시간 화면 프레임, 클릭 스트림 분석 등 약간의 유실이 허용되는 영역

### 3.2 최소 한 번 (At-Least-Once)

**메시지가 최소 1번 이상 전달된다. 유실은 없지만 중복 처리될 수 있다.**

소비자는 DB 저장 같은 실제 로직을 완수한 뒤에야 큐에 ACK를 보낸다. 로직 처리 직후, ACK 전에 소비자가 죽거나 네트워크가 끊기면 큐는 이를 실패로 간주하고 동일 메시지를 다른 소비자에게 재전송한다. 생산자 쪽도 `acks=all`로 브로커 저장을 확인하고 실패 시 재전송하므로, "확인되기 전까지는 안 끝난 것으로 보고 다시 보낸다"는 철학을 생산자·소비자 양쪽이 공유한다.

- **관련 설정**: `acks=all`(또는 재시도가 붙은 `acks=1`) + 처리 완료 후 오프셋 커밋
- **사용 사례**: 결제 내역, 주문 내역, 알림 발송 등 대부분의 대규모 시스템 기본값

> 💡 실무에서는 이 방식을 채택한 뒤, 애플리케이션 단에서 **멱등성(Idempotency)**을 확보(예: 동일 주문 번호 중복 결제 방지)해 중복을 해결하는 것이 가장 안전하고 보편적이다.

### 3.3 정확히 한 번 (Exactly-Once)

**유실도 중복도 없이 정확히 1번만 처리된다. 가장 이상적이지만 구현이 어렵고 성능(대역폭·지연) 손실이 크다.**

`acks=all`이 기본 전제지만 그것만으로는 부족하다. `acks=all`은 "생산자→브로커" 구간의 유실만 막을 뿐, 네트워크 재시도로 인한 중복 저장까지는 막지 못하기 때문이다. 그래서 여기에 **멱등성 프로듀서**(중복 제거 키 기반)와 **트랜잭션**(생산·소비 오프셋 커밋을 하나의 원자적 단위로 묶는 처리)을 추가로 결합해야 하며, 필요하면 분산 트랜잭션(2-Phase Commit)까지 동원해 메시지 큐와 소비자가 상태를 긴밀히 협동 관리한다.

- **관련 설정**: `acks=all` + 멱등성 프로듀서 + 트랜잭션(오프셋 커밋 원자화)
- **사용 사례**: 송금·계좌 이체, 중복 시 과금 오차가 심각한 금융 결제 엔진

## 4. 대역폭과 지연 시간

### 4.1 대역폭 (Bandwidth)
- 단위 시간(보통 1초) 동안 처리(전송) 가능한 데이터량 = 처리량(Throughput)
- 비유: 고속도로 차선 수 — 차선이 늘어날수록 한 번에 지나갈 수 있는 차량이 많아짐
- **분산 메시지 큐에서의 의미**: 초당 수십만~수백만 건(수 GB)의 메시지도 병목 없이 저장·소비하는 능력. 디스크 순차 쓰기(Sequential I/O), 배치(Batching) 처리, 파티션 분산 기술로 달성

### 4.2 지연 시간 (Latency)
- 하나의 메시지가 생산자에서 발생해 소비자에게 전달되기까지 걸리는 시간
- 비유: 차량의 이동 속도 — 도로가 넓어도(대역폭↑) 차가 느리면(지연↑) 도착이 늦음
- **분산 메시지 큐에서의 의미**: 발행부터 소비까지 수 밀리초(ms) 이내여야 함. 실시간 결제 승인, 라이더 위치 추적 등 반응 속도가 중요한 서비스에 필수

## 5. 메시지 모델

### 5.1 일대일 모델
생산자가 큐에 메시지를 보내고, 어떤 소비자가 메시지를 가져갔음을 큐에 알리면 해당 메시지는 큐에서 삭제됨 → **데이터 보관 미지원**

### 5.2 발행-구독 모델
생산자로부터 토픽에 전달된 메시지는 해당 토픽을 구독하는 모든 소비자에게 전달됨

### 5.3 분산 메시지 큐는 두 모델을 모두 지원
- 발행-구독 모델 → **토픽**을 통해 구현
- 일대일 모델 → **소비자 그룹**을 통해 지원

## 6. 핵심 구성 요소: 토픽 · 파티션 · 브로커

| 구성 요소 | 설명 |
|---|---|
| **토픽(Topic)** | 메시지를 주제별로 정리하는 단위. 각 토픽은 서비스 전체에서 고유한 이름을 가짐 |
| **파티션(Partition)** | 토픽 데이터량이 커져 서버 한 대로 감당 안 될 때, 샤딩으로 토픽을 여러 파티션으로 분할하고 메시지를 균등 분배(토픽의 부분집합). 같은 파티션 내 메시지는 FIFO처럼 순서가 유지됨(메시지 위치 = **오프셋**) |
| **브로커(Broker)** | 파티션을 유지하는 서버. 파티션을 여러 브로커에 분산하는 것이 높은 확장성 달성의 핵심. 토픽 용량을 늘리려면 파티션 개수를 늘리면 됨 |

---

## 7. 소비자 그룹 (Consumer Group)

### 7.1 목적: 병렬 처리와 수평 확장
어떤 토픽에 초당 1만 건의 메시지가 쏟아진다고 가정:
- 소비자가 1명 → 혼자 처리 불가, 병목 발생
- 소비자 4명을 하나의 그룹으로 묶음 → 파티션 단위로 일감을 4명에게 분배 → 초당 2,500건씩 병렬 처리

### 7.2 핵심 규칙: 1 파티션 : 1 소비자
> 하나의 파티션은 그룹 내에서 오직 하나의 소비자만 연결되어 메시지를 읽는다.

| 파티션 수 : 소비자 수 | 결과 |
|---|---|
| 4 : 4 | 소비자 1명당 파티션 1개 — 가장 이상적 |
| 4 : 2 | 소비자 1명당 파티션 2개씩 담당 |
| 4 : 5 | 4명이 파티션 1개씩 담당, 1명은 유휴 상태 (소비자 수를 무작정 늘려도 속도가 빨라지지 않는 이유) |

**왜 이 규칙이 필요한가?**

1. **메시지 순서 보장 (핵심 이유)**
   같은 파티션의 메시지는 순서대로 처리되어야 한다는 보증이 있다. 만약 소비자 A, B가 파티션 1개를 동시에 읽으면, 처리 속도 차이로 인해 뒤 메시지(예: "결제 완료")가 앞 메시지(예: "주문 생성")보다 먼저 처리되는 순서 꼬임이 발생할 수 있다. 파티션당 소비자를 1명으로 제한해야 순서대로 안전하게 처리할 수 있다.

2. **오프셋 관리의 단순화**
   소비자는 어디까지 읽었는지를 오프셋으로 주기적으로 커밋한다. 여러 소비자가 하나의 파티션을 공유하면 어느 메시지까지 정상 처리됐는지 추적이 꼬인다. 1 파티션 : 1 소비자 구조여야 오프셋을 단일 선상에서 깔끔하게 추적할 수 있다.

3. **중복 처리 및 Lock 비용 방지**
   여러 소비자가 파티션을 공유하면 중복 소비를 막기 위한 동기화(Locking)가 필요해지고, 이는 분산 메시지 큐의 핵심 장점인 고속 대역폭을 크게 저하시킨다. 파티션-소비자를 1:1로 매핑하면 Lock이 아예 필요 없어져 성능이 극대화된다.

### 7.3 멀티캐스팅: 서로 다른 소비자 그룹
동일한 메시지를 서로 다른 목적으로 각각 독립적으로 소비할 수 있다.

예) `결제 완료` 이벤트 1건 발행 시:
- **그룹 A (결제 처리 팀)**: 메시지를 읽어 결제 DB 업데이트
- **그룹 B (알림 팀)**: 동일 메시지를 읽어 카카오톡 알림 발송
- **그룹 C (빅데이터 분석 팀)**: 동일 메시지를 읽어 분석 DB에 저장

→ 그룹이 다르면 동일 메시지를 각자 독립적으로 반복 소비할 수 있다.

## 8. 상세 설계: 저장소 및 성능 최적화

카프카 같은 분산 메시지 큐가 디스크 기반이면서도 빠른 성능을 내는 이유는 디스크 본연의 특성과 OS의 저수준 기능을 최대한 활용하기 때문이다.

### 8.1 Append-only Log
디스크는 임의 위치를 찾아 수정할 때는 느리지만, 끝에 순차적으로 덧붙여 쓸 때는 메모리 수준으로 빠르다. 메시지 큐는 데이터를 절대 중간에 수정하지 않고 로그 끝에 순차적으로만 기록하는 **Append-only Log** 구조를 사용해 이 디스크 한계를 극복한다.

### 8.2 페이지 캐시 (Page Cache)
OS 커널이 기본 제공하는 페이지 캐시에 데이터를 얹어 사실상 메모리 속도로 읽고 쓴다.

### 8.3 Zero-Copy
생산자가 보낸 메시지 포맷을 저장 시에도, 소비자에게 전달 시에도 가공하지 않고 원본 그대로 유지한다. CPU가 데이터를 가공할 필요가 없고, OS 수준의 **Zero-Copy** 기술로 디스크 캐시의 데이터를 CPU를 거치지 않고 곧바로 네트워크 카드로 전송한다.

> 결국 애플리케이션 단에서 무리하게 처리하지 않고 디스크 순차 쓰기와 OS 저수준 기능에 위임함으로써, 디스크 기반이면서도 높은 대역폭과 성능을 낼 수 있다.

### 8.4 배치 우선 시스템 (Batching)
소규모 I/O가 많으면 높은 대역폭 지원이 어렵다. 그래서:
- 생산자는 메시지를 일괄 전송
- 메시지 큐는 메시지를 더 큰 단위로 묶어 보관
- 소비자도 가능하면 메시지를 일괄 수신

## 9. 메시지 키와 파티셔닝

### 9.1 메시지 키의 역할
메시지 키는 해당 메시지가 어느 파티션으로 갈지 결정하는 데 사용된다. 키가 없는 메시지의 파티션은 무작위로 결정된다.

### 9.2 안정 해싱 (Consistent Hashing)
단순히 `Hash(Key) % 파티션_수` 연산을 사용하면 파티션 개수가 바뀔 때 거의 모든 키의 파티션 위치가 재배치되는 문제가 발생한다. **안정 해싱**은 파티션 수가 변경돼도 메시지를 균등하게 분산시키면서 기존 키들의 파티션 재배치(Remapping)를 최소화한다.

**동작 원리**
1. **링 위에 배치**: 해시 공간의 양 끝을 이어 붙인 원형 링(Hash Ring)을 만들고, 파티션과 메시지 키를 동일한 해시 함수로 이 링 위에 배치
2. **파티션 찾기**: 메시지 키 위치에서 시계 방향으로 가장 가까운 파티션에 메시지를 저장
3. **파티션 수 변경 시**: 파티션이 추가/삭제돼도 전체 키를 재배치할 필요 없이, 해당 파티션과 인접한 구간의 키들만 이동 → 균등한 분산(Rebalancing) 유지

### 9.3 현실적인 한계와 가상 노드 (Virtual Node)
- **데이터 쏠림(Hotspot)**: 파티션 수가 적으면 안정 해싱만으로는 데이터가 한쪽에 몰릴 수 있다.
- **가상 노드**: 하나의 물리적 파티션을 링 위의 여러 '가상 위치'로 흩뿌려 배치함으로써 데이터 균등 분산을 극대화한다.

### 9.4 카프카(Kafka)의 실제 전략: MurmurHash2
카프카는 기본적으로 `MurmurHash2(Key) % 파티션_수` 방식을 사용한다. 따라서 파티션 수 변경 시 키-파티션 매핑이 깨지는 것을 감수해야 한다.

> **실무 규칙**: 키 순서 보장이 필요한 시스템이라면 운영 중 파티션 개수를 함부로 늘리지 않거나, 안정 해싱 기반의 커스텀 파티셔너(Custom Partitioner)를 구현해 사용한다.
