# 4장 분산 메시지 큐

이번 부분에서는 분산 메시지 큐를 여러 브로커로 운영할 때 메시지를 어떻게 안전하게 저장하고, 장애가 나도 계속 서비스를 유지할 수 있게 하는지를 다룸.

## 주키퍼

브로커가 여러 대가 되면 현재 어떤 브로커가 살아 있는지, 어떤 파티션이 어느 브로커에 있는지 같은 정보를 따로 관리할 필요가 있음. 여기서 주키퍼(ZooKeeper)를 사용함.

주키퍼는 대충 분산 시스템에서 브로커나 파티션 같은 메타데이터를 관리하는 역할이라고 이해함. 브로커가 여러 대일수록 서로의 상태를 알아야 하기 때문에 이런 관리 시스템이 필요한 것 같음.

## 파티션 복제

파티션 하나를 브로커 한 곳에만 저장하면 해당 브로커가 죽었을 때 그 파티션의 메시지를 사용할 수 없게 됨. 그래서 같은 파티션을 여러 브로커에 복제해둠.

각 파티션에는 리더가 하나 있고 나머지는 복제본 역할을 함. 생산자와 소비자는 기본적으로 리더를 통해 메시지를 주고받고, 다른 복제본들은 리더의 메시지를 계속 따라가면서 복제함.

만약 리더가 있는 브로커가 죽으면 복제본 중 하나가 새로운 리더가 되어 서비스를 이어감. 결국 복제의 목적은 브로커 하나가 장애가 나도 해당 파티션 자체가 사라지지 않게 하기 위함임.

## ISR

복제본이라고 해서 항상 리더와 데이터가 완전히 똑같은 것은 아님. 네트워크가 느리거나 특정 브로커가 문제가 생기면 복제가 늦어질 수도 있음.

그래서 리더를 정상적으로 잘 따라가고 있는 복제본들을 ISR(In-Sync Replicas)이라는 그룹으로 관리함. 리더에 장애가 발생했을 때 아무 복제본이나 새로운 리더로 만드는 것이 아니라, 비교적 최신 상태를 유지하고 있는 ISR 안에서 새로운 리더를 고르는 방식임.

결국 ISR은 복제본 중에서도 지금 믿을 만한 복제본들을 따로 관리하는 개념이라고 이해함.

## ACK 설정

생산자가 메시지를 보냈을 때 어느 순간에 메시지 전송이 성공했다고 판단할지도 설정할 수 있음.

ACK=all은 리더뿐 아니라 필요한 복제본까지 메시지가 반영된 것을 확인한 뒤 성공으로 판단함. 그만큼 데이터 유실 가능성은 낮지만 여러 복제본을 기다려야 해서 느릴 수 있음.

ACK=1은 리더가 메시지를 받으면 바로 성공으로 판단함. ACK=all보다는 빠르지만 리더가 다른 복제본에 데이터를 넘기기 전에 장애가 나면 메시지가 유실될 가능성이 있음.

ACK=0은 생산자가 메시지를 보낸 뒤 응답을 기다리지 않는 방식임. 가장 빠르지만 실제로 메시지가 제대로 저장됐는지 알 수 없음.

결국 ACK 설정도 무조건 안전한 쪽을 선택하는 게 아니라, 서비스에서 속도와 데이터 안정성 중 무엇을 더 중요하게 보는지에 따라 결정하는 것 같음.

## 내구성

메시지를 얼마나 안전하게 저장할지는 한 가지 설정으로 끝나는 것이 아니었음. 파티션 복제본을 몇 개 만들 것인지, ACK를 어떻게 설정할 것인지, ISR을 어느 정도 유지할 것인지 등이 같이 영향을 줌.

안전성을 높이면 데이터를 여러 곳에 복제하고 더 많은 응답을 기다려야 하므로 당연히 성능이나 비용 측면에서는 손해가 생김. 결국 여기서도 안정성과 성능 사이의 trade-off가 생김.

## 브로커 장애

브로커 한 대가 장애가 나면 그 브로커가 가지고 있던 파티션의 복제본을 다른 브로커에서 이용해서 서비스를 계속함. 리더 파티션이 사라졌다면 다른 복제본이 새로운 리더가 됨.

근데 장애 이후 특정 브로커에 리더 파티션이 너무 많이 몰리면 그 브로커만 부하가 커질 수도 있음. 그래서 리더와 파티션을 여러 브로커에 적절히 분산하는 것도 중요함.

새 브로커가 추가되거나 기존 브로커가 다시 살아났을 때도 파티션을 적절히 재배치해서 부하를 분산해야 함. 그냥 서버를 추가했다고 자동으로 모든 부하가 균등하게 나뉘는 것은 아닌 듯함.

## 규모 확장

생산자는 새로운 생산자를 추가하는 식으로 비교적 쉽게 확장 가능함.

소비자는 소비자 그룹을 이용해서 여러 소비자가 파티션을 나눠 처리함. 소비자가 추가되거나 빠지면 기존에 담당하던 파티션을 다시 나눠주는 과정이 필요함.

브로커를 추가할 때도 기존 파티션을 새 브로커로 옮기거나 이후 데이터를 새로운 브로커에 분산하는 식으로 확장함. 확장 자체보다 데이터를 어떻게 다시 분배할지가 더 중요한 문제인 것 같음.

## 메시지 전달 방식

메시지를 소비자에게 전달하는 방식도 여러 종류가 있음.

최대 한 번(at-most-once)은 메시지가 중복으로 전달되지는 않지만 메시지가 유실될 수 있는 방식임. 말 그대로 메시지를 최대 한 번만 전달함.

최소 한 번(at-least-once)은 메시지가 제대로 처리됐는지 확실하지 않으면 다시 전달함. 그래서 메시지 유실 가능성은 줄지만 같은 메시지가 두 번 이상 전달될 수 있음.

여기서 전에 봤던 멱등성이 중요해짐. 예를 들어 결제 이벤트가 두 번 전달됐다고 해서 실제 결제가 두 번 일어나면 안 되기 때문에 같은 메시지가 여러 번 들어와도 결과가 한 번 처리했을 때와 같도록 만들어야 함.

정확히 한 번(exactly-once)은 메시지를 유실하지도 않고 중복 처리도 하지 않도록 하는 방식인데, 그만큼 구현이 가장 어려움.

결국 메시지를 몇 번 전달할지에 대한 보장도 서비스 특성에 따라 선택해야 하는 것 같음.

## 파티션과 메시지 보관

메시지는 파티션 안에 순서대로 쌓이게 됨. 파티션이나 브로커의 개수가 바뀌면 메시지를 어느 브로커에 저장할지도 다시 고려해야 함.

메시지를 계속 무한정 저장할 수는 없기 때문에 일정 시간이 지나거나 저장 용량이 일정 기준을 넘어가면 오래된 메시지를 삭제하는 정책도 필요함.

## 파티션 장애와 복구

파티션을 여러 브로커에 복제해두면 특정 브로커가 죽어도 다른 복제본을 이용할 수 있음. 다만 복제본이 있다고 해서 무조건 안전한 것은 아니고, 복제본이 얼마나 최신 상태인지도 중요하기 때문에 ISR과 같이 사용됨.

복구할 때도 어느 복제본을 새로운 리더로 선택할지에 따라 데이터 유실 가능성이 달라질 수 있음.

## 메시지 지연 전송

메시지를 바로 소비자에게 전달하지 않고 일정 시간이 지난 뒤 전달해야 하는 경우도 있음.

예를 들어 주문 후 30분 동안 결제가 되지 않으면 주문을 취소하는 기능이 있다면, 주문이 들어온 순간 메시지를 보내는 게 아니라 30분 뒤에 메시지가 처리되도록 해야 함.

이런 기능을 구현하기 위해 timing wheel 같은 방식을 사용할 수 있다고 나옴. 메시지를 특정 시간까지 보관해두고 시간이 되었을 때 소비할 수 있도록 하는 구조라고 이해함.

## 오래된 메시지 보관

메시지를 장기간 보관해야 한다면 모든 데이터를 계속 메시지 브로커에 가지고 있는 것은 비효율적임.

그래서 최근 메시지는 브로커에서 관리하고, 오래된 메시지는 HDFS나 객체 저장소 같은 별도의 저장소로 옮겨서 보관할 수 있음.

결국 메시지 브로커는 실시간 메시지 전달과 최근 데이터 처리에 집중하고, 오래된 데이터는 장기 보관에 더 적합한 저장소로 넘기는 느낌임.

## 메시지 전달 보장과 중복

메시지를 최소 한 번 전달하도록 만들면 장애 상황에서도 메시지를 잃어버릴 가능성은 줄어들지만, 대신 동일한 메시지가 여러 번 전달될 수 있음.

그래서 생산자와 소비자 모두 중복 메시지에 대해 생각해야 함. 특히 결제나 주문처럼 같은 작업이 여러 번 실행되면 문제가 되는 경우에는 메시지 ID 같은 것을 이용해서 이미 처리한 메시지인지 확인하거나, 처리 자체를 멱등하게 설계해야 함.

## 정리

이번 부분은 단순히 메시지 큐 서버를 여러 대 두는 것에서 끝나는 게 아니라, 실제 분산 환경에서는 장애와 데이터 유실, 중복 메시지까지 같이 생각해야 한다는 내용이었음.

브로커 하나가 죽을 수 있으니까 파티션을 복제하고, 복제본이 모두 최신인 것은 아니니까 ISR을 관리함. 또 생산자가 언제 메시지 전송에 성공했다고 볼 것인지 ACK 설정으로 정하고, 장애 때문에 메시지를 다시 전달하면 중복이 생길 수 있으니까 멱등성도 필요해짐.

결국 분산 메시지 큐도 무조건 데이터 안전성을 최대로 높이는 게 좋은 것이 아니라, 메시지가 얼마나 중요한지와 어느 정도의 성능이 필요한지를 보고 복제 수, ACK 설정, 전달 방식 등을 선택해야 한다는 게 핵심인 것 같음.
