# 4장 분산 메시지큐 학습노트 - 장찬욱

가정1. 시스템은 잘 정의된 "인터페이스"를 경계로 나뉜 작고 "독립적인 블록"들로 구성되어 있다.

가정2. 메시지 큐가 이 블록 간 통신과 조율을 담당한다.

예상되는 이득은

1. 결합도 완화 : 각 시스템을 독립적으로 갱신 가능

2. 규모 확장성 개선 : producer, consumer 규모를 부하에 맞게 조정 가능.

3. 가용성 개선 : 특정 블록이 장애가 생겨도 다른 블록은 큐와 계속 상호작용.

4. 성능 개선 : 비동기 통신 가능. producer, consumer 서로가 서로를 기다릴 필요가 없어짐.

우린 데이터 장기 보관, 메시지 반복 소비 등을 갖춘 분산 메시지 큐를 설계할 것. 이 둘은 부가 기능이며, 원래 이벤트 스트리밍 플랫폼에서만 이용 가능하다. 여기서 이벤트 스트리밍 플랫폼이란? 다양한 소스에서 발생하는 실시간 데이터를 끊김 없이 수집, 저장, 처리하고 필요한 곳으로 전달하는 시스템이다.

이벤트 스트리밍 플랫폼과 분산 메시지 큐는 시스템 간 비동기 통신을 담당한다는 공통점이 있지만, 설계 목적과 데이터 처리 방식에서 큰 차이가 있다.

## 이벤트 스트리밍 플랫폼 vs 분산 메시지 큐(by AI)

| 비교 항목            | 이벤트 스트리밍 플랫폼 (예: Kafka, Pulsar) | 분산 메시지 큐 (예: RabbitMQ, ActiveMQ)    |
| ---------------- | ------------------------------- | ----------------------------------- |
| 핵심 개념            | 지속적인 이벤트의 로그 스트림 관리             | 브로커 중심의 메시지 전달 및 교환                 |
| 데이터 보존           | 영구/장기 보관 (소비되어도 데이터가 삭제되지 않음)   | 일시적 보관 (소비자가 수신 확인하면 즉시 삭제)         |
| 소비 방식            | Pull 방식 (소비자가 원하는 시점에 데이터를 가져옴) | Push 방식 (브로커가 소비자에게 메시지를 밀어넣음)      |
| 데이터 재처리 (Replay) | 가능 (포인터를 과거로 돌려 데이터 재소비 가능)     | 불가능 (소비된 메시지는 소멸하므로 재처리 불가)         |
| 처리량 (Throughput) | 대용량 처리에 특화 (초당 수백만 개 로그 처리)     | 복잡한 라우팅에 특화 (트래픽 규모는 상대적으로 제한됨)     |
| 라우팅 유연성          | 단순함 (토픽 및 파티션 기반 구조)            | 매우 유연함 (Exchange, 와일드카드, 헤더 기반 라우팅) |
| 주요 활용처           | 실시간 분석, IoT 데이터 수집, 로그 통합, CDC  | 마이크로서비스 간 연동, 작업 큐, 순서 보장 태스크       |

---

우리는 분산 메시지 큐인데 데이터 보존과 재처리를 구현해야 하므로 좀 더 노력이 필요한 것이다.

우리는 설계를 위해 이 기본적인 모델 외에도 요구되는 성능, 메시지 전달방식, 데이터 보관기간 등을 알아야 한다.

## 2단계 개략적 설계안 제시 (뼈대 세우기)

일대일모델은 소비자가 메시지를 가져가고 큐에 ACK 보내면 해당 메시지가 삭제되므로 데이터 보관을 2주간 해야하는 우리에게는 맞지 않다.

발행구독모델은 메시지가 자신이 속한 고유한 토픽 별로 정리되는데 메시지를 생산자가 보낼 때 토픽으로 보내는 것이고 메시지를 소비자가 받을 때 토픽을 지켜보다가 받는다. 생산자가 토픽에 전달한 메시지는 이 토픽을 구독하는 모든 소비자들에게 전달된다.

본 설계안은 일대일 모델, 발행구독모델 둘 다 지원해야 한다. 일대일 모델로는 소비자 중 하나만 받으면 되는 경우에 대응한다. 발행 구독 모델로는 한 소비자 그룹 내 모든 소비자들 혹은 존재하는 모든 소비자들이 받아야 하는 경우를 대응하는 것이다.

메시지는 토픽에 보관되는데 토픽에 보관되는 데이터 양이 서버 한대로 감당할 수 없으면 파티션(샤딩)을 사용한다. 한 토픽에 여러 파티션을 두는 것이다. 한 토픽으로 들어오면 방대한 메시지들을 여러 파티션에 고르게 분산 저장하도록 하며, 이 파티션을 가지는 서버를 브로커라 부른다. 이것으로 규모확장성을 달성한다. 한 토픽이 가질 수 있는 메시지 용량을 늘리고 싶으면 파티션을 늘리면 된다. 한 토픽의 각 파티션은 큐처럼 동작하고, 한 파티션 안에서는 메시지 순서가 보장된다. 파티션 내에서 오프셋 값을 가진다.

그렇다면 각 파티션이 고유한 순서를 가지는 것인데. 원래 메시지들은 한 토픽에 보내진 거라면 이렇게 여러 파티션으로 나눠졌을 때, 소비자 입장에서 어떻게 순서를 보장하면서 메시지를 받을 수 있을까?

전체 토픽 기준의 절대적 순서 보장은 불가능하다고 한다. 하지만 '전체 순서'가 아니라, '연관된 데이터 간의 순서(예: 동일한 객체의 작업 처리 순서)'라면 보장할 수 있다. 즉, 특정 객체의 ID를 키값으로 사용해서 그 키를 가지는 메시지는 항상 동일한 파티션으로 가도록 하는 것이다. 이 상태에서 특정 소비자가 그 파티션을 항상 담당하도록 하면 해당 소비자를 통해 우리가 관심있는 객체에 대해 순서가 보장된 메시지를 얻을 수 있을 것이다. 다만 이러한 설계는 대역폭 측면에서는 메시지의 소비자를 하나로 제한하므로 좋지 않다. 순서보장이 요구되면 이러한 설계로 가겠으나, 그보다 대역폭이 더 중요한 경우에는 한 소비자 그룹을 형성해서 병렬로 메시지를 받을 수 있을 것이다. 당연히 여러 토픽 구독도 가능하다. 다만 한 소비자 그룹이 여러 토픽을 구독하고 교재에서처럼 그것도 그 토픽의 특정 파티션에서만 메시지를 받아오면 점점 머리 아파질 것 같다. 파티션이 용도로 분명히 나눠진 것이라면 이러한 문제는 해소될 것이다.

> 여기서 우리는 하나의 트레이드오프를 만났다.
> 
> **대역폭을 키울 것인가 VS 한 객체에 대한 메시지 순서를 보장할 것인가**

## 3단계 상세 설계 (살 붙이기)

데이터 장기 보관, 높은 대역폭을 요구했는데 이 2가지는 무엇으로 이룰 수 있을까?

1. **회전 디스크의 순차탐색 성능, 적극적 디스크 캐시를 이용하는 디스크 기반 자료구조**가 필요하다. 빠르게 쓰기 위해.

메시지 저장에 가장 좋은 방법은 뭘까? 트래픽 패턴을 보면 순차 읽기, 쓰기가 빈번하고 대부분이다. 데이터베이스는 읽기/쓰기를 동시에 대규모로 하기에 부적합하므로 패스. 트랜잭션 격리, 락, 인덱스 구조가 무작위 접근 사용, 데이터 삭제가 비싸기 때문.

WAL(append-only 일반 파일) 방식을 사용. 지속성 보장해야 하는 메시지라는 점과 읽기 쓰기가 순차적이라는 점에 적합. 회전식 디스크와도 맞다. 보관 기한이 지나거나 용량 한계를 만났을 때 낡은 세그먼트 파일을 삭제하면 됨. 한 토픽의 한 파티션 내에 특정 수의 새 메시지를 쓰고 이를 한 세그먼트 단위로 봐서 세그먼트 파일 단위로 관리하는 방식.

2. **메시지 전체 전달과정에서 중간에 수정과정이 없도록 하는 자료구조 설계**가 필요하다. 전송량이 많을수록 복사하는 비용(연산능력, 처리 시간)이 크기 때문이다.

메시지 자료구조는 생산자에서 소비자로 가는 과정에서 불필요한 복사를 방지해야 한다. 복사 비용이 비싸서 성능이 심각히 낮아질 수 있음. 메시지의 구성요소를 살펴보자.

메시지 키가 해시를 거쳐 나온 값으로 저장될 파티션이 정해진다. 어떤 알고리즘을 써야 파티션 수가 달라져도 모든 파티션에 메시지가 균등히 분산될 수 있을까 궁금하다.

이외에도 메시지 값, 위치 정보(토픽 이름, 파티션 id, 오프셋), 타임스탬프, 크기, crc 등이 있다. 필드 추가 가능.

3. 생산자, 소비자, 메시지 큐는 메시지를 **일괄 처리**해야 한다. 단건 처리를 하면 CPU, Disk, network 전부 낭비하는 것. 특정 크기(하드웨어의 처리 단위인 블록 사이즈에 맞게), 특정 시간(예: 10ms) 단위로 한 번에 디스크에 쓰고 전송하면 효율적.

대역폭과 응답 지연은 메시지 일괄처리량에 달려있다. 둘이 함께 커지고 작아지므로 고려해서 설계하자. 지연되도 좋으니 대역폭이 중요하면 늘리고, 지연을 최소화해야하면 대역폭을 손해보더라도 일괄처리량을 낮춰야한다.

### 브로커가 소비자에게 보낼 것인가, 소비자가 브로커에게서 가져갈 것이냐

대부분의 메시지 큐는 풀 모델을 지원. 소비자가 토픽을 구독하면 파티션을 할당받고 소비자가 일정시간 기다리며 계속 데이터를 가져가려고 시도한다. 브로커가 받는 즉시 메시지를 전송하는 푸시 모델 대비 일괄처리에 적합. **자원 효율(풀모델) vs 처리속도(푸시모델) 간의 트레이드 오프 같다.**

### 주키퍼

주키퍼는 분산 메시지 큐 설계에 아주 유용. 계층적 키-값 저장소 서비스.

#### 소비자 상태 저장소, 메타데이터 저장소, 조정 서비스

위 3가지를 주키퍼로 구현한다.

#### 소비자 상태 저장소

1. 각 소비자와 파티션의 구체적인 대응 관계

2. 각 소비자 그룹이 각 파티션에서 마지막으로 가져간 메시지의 오프셋

#### 메타데이터 저장소

1. 토픽 식별자, 이름

2. 해당 토픽의 파티션 수

3. 메시지 보관기간

4. 사본 배치할 브로커 id들의 우선순위 등

#### 조정 서비스

이외에 **브로커 컨트롤러**가 브로커 중에 존재한다.

#### 

### 파티션 배치 계획(소비자 레벨)과 코디네이터(브로커 레벨)

##### 소비자 그룹 이름 해싱

##### <-> 그룹 내 각 소비자의 오프셋 값 토픽의 파티션을 소유한 브로커

##### <-> 소비자 그룹 코디네이터 브로커

코디네이터는 새 소비자가 합류하거나 기존 소비자가 떠나거나 어떤 소비자가 장애가 생기거나 파티션이 조정되면 소비자 재조정을 시행한다. 그룹의 소비자들은 박동 메시지를 그룹 코디네이터 브로커에게 보낸다. **기존 소비자가 그룹을 이탈하거나 새 소비자가 합류하려 할 때** 코디네이터가 리더 소비자를 선출해서 **새로운 파티션 배치 계획**을 만들게 한다. 리더 소비자한테 계산된 배치 계획을 받고, 소비자들이 동기화 요청을 보내오면 코디네이터가 각 소비자에게 새로운 파티션 배치 계획을 보내준다. **각 소비자는 그 계획에 맞게 자신의 파티션에 해당하는 브로커로부터 메시지를 가져오기 시작한다.**

### 파티션 사본 분산 계획과 리더 브로커

위에서는 코디네이터가 선출한 리더 소비자가 새로운 파티션 분산 계획을 다뤘는데 **한 파티션의 사본을 여러개 별도 노드에 복제**해두는 경우에는 **조정 서비스(주키퍼)가 선출하는 리더 브로커**가 사본 분산 계획을 만든다.

#### ISR : 동기화된 사본 IN-SYNC Replicas

리더와 동기화된 사본을 말한다. 이는 브로커들 간의 이야기다. 소비자의 이야기 아님. 리더 파티션, 즉 리더 사본을 가진 브로커를 리더 브로커로 한다고 위에서 언급했었다. 이는 조정 서비스가 선출한 것이며, 리더 사본의 합의된 오프셋에서 몇 정도(토픽 설정에서 조작)만 차이 나는, 다른 브로커의 단순 사본들을 ISR이라고 한다. 여기서 성능과 영속성의 트레이드오프가 있다. ACK 설정에 따라 모든 ISR로부터 확실히 사본 동기화를 끝내는 대신 시간을 좀 더 들일지, 시간을 단축하기 위해 ACK를 0이나 0에 가깝게 두어 영속성을 희생할지 결정하게 된다. 리더 브로커가 자신의 사본 브로커들을 추적해서 잘 따라오고 있나 ISR 리스트를 관리한다.

#### 생산자는 리더 브로커에게 메시지를 보낸다.

그리고 리더 브로커가 사본 브로커들에게 메시지를 전달한다. 생산자가 어떤 파티션으로 메시지를 보내야 할 때 어느 브로커에게 보내야 하는 걸까? 파티션마다 사본(원본도 사본에 포함)을 가지며, 리더 파티션이 존재하며, 이 리더 파티션을 가지는 브로커를 리더 브로커라고 한다. 브로커가 여러개일 때 메시지를 받을 적절한 브로커는 리더 브로커이다. 이러한 리더 브로커는 조정 서비스(주키퍼)에 의해 선출된다.

#### 규모 확장성

생산자는 스킵.

소비자는 소비자 그룹 단위로 보자. 그룹에 소비자가 참가하거나 이탈하는 경우 위에서 언급된 코디네이터가 동작하여 파티션 배치 계획에 따라 재조정을 한다. 소비자 그룹으로 규모 확장성, 내결함성이 보장된다.

브로커는 합의 오프셋 설정할 때 얼마나 많은 사본에 메시지가 반영되어야 하는지를 가지고 안정성과 속도 사이의 균형을 잡아야 한다. 소비자의 파티션 배치 계획과 비슷하게 사본 분산 계획을 짤 수도 있고, 브로커 컨트롤러로 일시적으로 사본 수를 늘릴 수 있다. 브로커 추가 -> 새 브로커에 파티션 사본 추가 -> 기존 파티션 삭제. 이런 방식으로 브로커 추가 도중의 데이터 손실을 피할 수 있다. 브로커 제거 시에도 마찬가지.

#### 파티션 추가, 삭제

파티션 추가로 간단히 토픽의 규모를 늘릴 수 있음. 가용성과 대역폭 사이 트레이드 오프 고려해야함. **파티션이** 많을수록 대역폭은 오르지만 **너무 많아지면 브로커 하나 죽었을 때 엄청난 수의 파티션이 동시에 죽으면 그게 리더 사본이었든 아니든 새 파티션을 다른 노드에 추가하거나 새로운 리더 사본을 선출해야 하는 혼란 야기됨. 또 파티션이 많아질수록 관리 오버헤드로 동기화 시차가 벌어질 수 있음.**

파티션 제거 시에는 바로 제거 X. 세 파티션이 있다면 **삭제할 파티션을 일정 시간 유지**하며 사용 중인 소비자가 없어지길 기다린다. 삭제 전까지는 남은 두 파티션이 생산자의 메시지 감당하도록 만들고 생산자들이 더이상 삭제할 파티션으로 보내지 말아야 할 것.

### 메시지 전달 방식

#### 최대 한번 <- 소량의 데이터 손실은 감수할 수 있는 경우

ACK = 0, 메시지 전달 실패해도 다시 시도 안 함. 생산자 -> 메시지 큐, 메시지 큐 -> 소비자 단계에서 메시지 소실 가능. 읽고 처리하기 전에 오프셋부터 갱신.

#### 최소 한번 <- 중복이 큰 문제가 아니거나 중복을 소비자가 직접 제거 가능한 경우

ACK = 1 ~ all, 메시지 전달된 걸 반드시 확인. 전달 실패시 재시도함. 메시지 성공적으로 처리할 때만 오프셋 갱신. 재시도로 인해 손실 없음. 오프셋 갱신을 못한 경우 재발송으로 인한 중복 처리될 수 있음. 생산자 -> 메시지 큐, 메시지 큐 -> 소비자 단계에서 중복 메시지 발생 가능.

#### 정확히 한번 <- 금융 관련 서비스

생산자 -> 메시지 큐, 메시지 큐 -> 소비자 단계에서 정확히 한번 메시지 전송. 중복 허용 x, 멱등성이 구현되지 않는 앱에서 중요한 방식.
