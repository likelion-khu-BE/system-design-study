### 클라이언트
- 생산자
- 소비자 그룹

### 핵심 서비스 및 저장소

## 메시지 큐란?
Queue라는 자료구조를 이용해 메시지를 일시적으로 저장해 두었다가
소비자에게 전달하는 비동기 통신 시스템으로, 
MOM(메시지 지향 미들웨어)을 구현하는 대표적인 방식중 하나임.

MOM은 응용 소프트웨어 간의 비동기적 데이터 통신을 지원하는 미들웨어로
메시지 전달 과정에서 보관/라우팅/변환이 가능함.

## 메세지 브로커와 이벤트 브로커
메세지 브로커: Producer가 생산한 메시지를 큐에 저장하고 Consumer가 가져갈 수 있도록 중개함.
메시지가 정상적으로 처리되면 일반적으로 큐에서 제거됨.

이벤트 브로커: 발생한 이벤트를 토픽이나 로그 형태로 저장하고 여러 Consumer가 같은 이벤트를 각각 읽을 수 있도록 함.
이벤트는 일정 기간 보관되므로 필요한 경우 다시 소비할 수 있으며, 대규모 스트림 처리에 적합함.

## 데이터 저장소의 선정
DB: 분산 메시지 큐가 요구하는 매우 높은 처리량의 
단순 읽기/쓰기 패턴을 처리하기 위한 저장소로는 비효율적임

WAL: 분산 메시지 큐에서는 메시지가 순차적으로 저장되고 수정은 거의 없기 때문에
DB보다 순차 읽기/쓰기 방식의 WAL이 높은 처리량과 지속성 보장 측면에서 더 적합함

## 성능 개선을 위한 일괄 처리
메시지 일괄 처리를 통해 네트워크 요청과 디스크 I/O 횟수를 줄여 처리량을 높이고, 
네트워크 왕복 비용을 줄일 수 있음.
하지만, 높은 대역폭과 낮은 응답 지연을 동시에 달성하기는 어려움.
- 높은 대역폭을 얻으려면 여러 메시지를 모아 일괄 처리를 해야 하는데, 이때 메시지를 모으려면 기다려야 하기 때문에 응답이 지연됨
- 반대로 낮은 지연을 원하면 메시지가 도착하자마자 바로 처리해야 하는데, 매번 네트워크 요청을 해야 하므로 처리 효율이 떨어져 대역폭이 낮아짐
따라서, 둘 사이에서 타협점을 찾아야 함.

## 메시지 소비 방식과 소비자 관리
Push 모델의 경우에는 브로커가 데이터를 소비자에게 바로 전달하므로 지연이 낮음. 
하지만 소비자의 메시지 처리 속도가 느릴 경우 소비자에게 큰 부하가 걸릴 수 있음.
반면 Pull 모델은 소비자가 브로커로부터 직접 데이터를 가져가는 방식이므로 
일괄 처리에도 적합하고 소비자가 자신의 처리 속도에 맞게 메시지를 가져올 수 있어
과도한 부하가 걸릴 가능성이 낮음.
하지만 브로커에 메시지가 없어도 소비자가 계속해서 pull 요청을 보낼 수 있으므로 
이 자원 낭비 문제를 해결하기 위해 Long Polling 모델을 사용하는 것이 적합함.

따라서 Long Polling 기반의 Pull 모델로 메시지를 소비하도록 설계하고, 
각 소비자 그룹에 대해 특정 브로커가 코디네이터 역할을 맡도록 함. 
코디네이터는 소비자의 유입/이탈/장애가 발생했을 때 
어떤 소비자가 어떤 파티션을 담당할지 다시 조정하는 역할을 함.

## 상태 저장소와 메타데이터 저장소
상태 저장소: 소비자와 파티션의 관계, 각 소비자 그룹이 파티션에서 마지막으로 가져간
메시지의 오프셋 등의 정보를 저장함. 
메타데이터 저장소: 파티션 수, 메시지 보관 기간, 사본 배치 정보 등의 
토픽 설정이나 속성 정보를 보관함. 

이러한 데이터는 실제 메시지 데이터에 비해 양이 적지만,
소비자 재조정이나 파티션 관리에 사용되기 때문에 높은 일관성이 요구됨.

과거 Kafka에서는 ZooKeeper가 클러스터 메타데이터와 일부 상태 관리에 사용되었으나,
현재는 클러스터 메타데이터를 KRaft(Kafka Raft)로 관리함.
소비자 그룹의 오프셋과 그룹 상태는 Kafka 내부 토픽(__consumer_offsets)을 통해 관리함.
