# 분산 메시지 큐 학습 노트

## 1. 기능 요구사항
- 생산자 → 메시지 큐 → 소비자 가능
- 반복 or 한번만 수신 설정 가능
- 오래되면 삭제
- 메시지 크기: KB
- 메시지 순서 보장
- 메시지 전달 방식: 최소 한 번, 최대 한 번, 정확히 한 번 中 1

## 2. 비기능 요구사항
- 높은 대역폭, 낮은 전송 지연 택 1
- 규모 확장성
- 지속성, 내구성

## 3. 메시지 큐 기본 기능
1. 생산자가 메시지를 메시지 큐에 발행
2. 소비자는 큐를 구독하고 구독한 메시지 소비
3. 메시지 큐: 생산자와 소비자의 결합을 느슨하게 해줌
4. 생산자, 소비자: 클라이언트 / 메시지 큐: 서버
5. 네트워크로 통신

## 4. 메시지 모델

### 4.1 일대일 (Point to Point)
- 메시지 1개 → 소비자 1명
- 소비자가 메시지를 가져갔다는 사실을 큐에 알리면 해당 메시지 삭제
- 데이터 보관 지원 X

### 4.2 발행 구독 모델
- 토픽: 주제별 정리
- 해당 토픽을 구독중인 모든 소비자에게 메시지가 전달됨

## 5. 토픽, 파티션, 브로커
1. **토픽**: 메시지가 보관됨
2. **파티션**: 토픽을 쪼개요, 토픽에 보낼 메시지의 작은 부분집합
3. **브로커**: 파티션을 유지하는 서버
4. 토픽 용량 늘리고 싶으면 파티션 개수 늘리면 됨
5. 파티션 안에서 FIFO 순서 유지됨
6. **오프셋**: 파티션 내에서의 메시지 위치
7. **key**: 메시지 안에 넣어서 보낼 수 있는데, 같은 key면 같은 파티션

## 6. 소비자 그룹
1. 토픽을 구독하는 소비자가 여럿인 경우, 그들을 묶어 소비자 그룹
2. 하나의 소비자 그룹: 여러 토픽 구독 가능, 오프셋 별도 관리
3. 같은 그룹 내의 소비자는 메시지 병렬 소비 가능
4. 병렬로 읽으면 대역폭 측면에서 좋음, but 같은 파티션 내의 소비 순서 보장 X
5. 해결 방법: 어떤 파티션의 메시지는 한 그룹 안에서 한 소비자만 읽을 수 있게 하기
6. 근데 이러면 일대일
7. 그러면 처음부터 파티션을 더 늘려, key를 더 쪼개기
8. kafka의 경우 특정 파티션의 메시지는 한 그룹 안에서 오직 한 소비자만 읽을 수 있음 (1:1)

## 7. 설계안

### 7.1 클라이언트
- 생산자
- 소비자

### 7.2 저장소
- **브로커**
- **저장소**
  - 데이터 저장소: 메시지 보관
  - 상태 저장소: 소비자 상태 저장
  - 메타데이터 저장소: 토픽 설정, 토픽 속성 등 저장

### 7.3 조정 서비스
- 서비스 탐색: 살아있는 브로커 목록
- 리더 선출: 브로커 가운데 하나가 컨트롤러 역할, 클러스터 내 반드시 활성 상태 컨트롤러 하나 필요, 이 컨트롤러가 파티션 배치 담당
- 예시: ZooKeeper, etcd

## 8. 상세 설계 - 데이터의 장기 보관 요구사항, 높은 대역폭
- 회전 디스크의 높은 순차 탐색 성능, 적극적 디스크 캐시 전략 → 디스크 기반 자료구조
- 메시지가 생성자로부터 소비자에게 전달되는 순간까지 아무 수정 없이도 전송이 가능하도록 하는 메시지 자료구조 설계
- 일괄 처리(batching) 우선 시스템 설계, 소규모 I/O가 많으면 높은 대역폭 지원 어려움

## 9. 데이터 저장소

### 9.1 트래픽 패턴
- 읽기/쓰기 빈번
- 갱신/삭제 없음
- 순차 읽기/쓰기 대부분

### 9.2 선택지 1: 데이터베이스
- 요구사항 맞출 수는 있는데
- 읽기/쓰기 동시에 대규모로 빈번하게 일어나면 별로임

### 9.3 선택지 2: 쓰기 우선 로그 (Write-Ahead Log, WAL)
- 로그만 먼저 쓰고 나중에 데이터 변경하기

## 10. 메시지 자료구조
1. **메시지 키**: 파티션 정하기 용
2. **메시지 값**: 내용, payload
3. 토픽, 파티션, 오프셋, 타임스탬프, 크기, 순환중복검사(CRC) 등등

## 11. 일괄 처리 (Batching)
1. 비싼 네트워크 왕복 비용 제거
2. 한번에 로그 기록 → 더 큰 규모의 순차 쓰기 연산 → 디스크 캐시에서 더 큰 규모의 연속된 공간 점유 → 더 높은 디스크 접근 대역폭 달성!

## 12. 생산자 측 작업 흐름
1. 메시지를 라우팅 계층으로 보냄
2. 라우팅 계층은 메타데이터 저장소에서 사본 분산 계획을 읽어 자기 캐시에 보관
3. 메시지가 도착하면 파티션 1의 리더 사본에 보냄
4. 리더 사본이 우선 메시지를 받고 다른 사본은 리더로부터 데이터 받기
5. 충분한 수의 사본이 동기화 되면 리더가 커밋
6. 이 때가 소비 가능 상태
7. 커밋하고 생산자에 회신

## 13. 소비자 측 작업 흐름
1. 특정 파티션의 오프셋을 주고 해당 위치에서부터 이벤트를 묶어 가져옴

## 14. 푸시 vs 풀

### 14.1 푸시
- **장점**: 낮은 지연, 왜냐면 받자마자 바로 보냄
- **단점**: 소비자의 처리속도가 메시지 생산 속도보다 느리면 소비자 개큰부담

### 14.2 풀
- **장점**: 소비자가 속도 조절 가능, 소비 속도가 더 느려도 소비자 늘리거나 기다리면 됨, 일괄 처리에도 적합
- **단점**: 브로커에 메시지 없을 때 낭비. 롱 폴링으로 극복

## 15. 소비자 재조정
1. 새로운 소비자 합류, 기존 소비자가 그룹을 떠남, 어떤 소비자 장애, 파티션 조정 시에 발생
2. **코디네이터**: 소비자 재조정을 위해 소비자들과 통신하는 브로커 노드, 소비자의 심장박동, 파티션 내 오프셋 정보 관리
3. 코디네이터가 소비자 장애 발생 감지 시 재조정 프로세스 시작

## 16. 상태 저장소
1. 소비자에 대한 파티션의 배치 관계
2. 각 소비자 그룹이 각 파티션에서 마지막으로 가져간 메시지의 오프셋

## 17. 메타데이터 저장소
1. 토픽 설정
2. 속성 정보

## 18. 주키퍼
1. 계층적 키-값 저장소 기능을 제공
2. 분산 메시지 큐를 설계하는 데 아주 유용
3. 분산 설정 서비스, 동기화 서비스, 이름 registry 등으로 이용됨

**주키퍼가 들어오고 달라진 점**
- 메타데이터와 상태 저장소는 주키퍼를 이용해 구현한다
- 브로커는 이제 메시지 데이터 저장소만 유지하면 된다
- 주키퍼가 브로커 클러스터의 리더 선출 과정을 돕는다

## 19. 복제
1. 데이터 손상, 장애 발생 위험 해결
2. 높은 가용성 보장
3. 생산자는 파티션에 메시지를 보낼 때 리더에게만 보내며, 다른 사본은 리더에서 새 메시지를 지속적으로 가져와 동기화

## 20. 사본 동기화
1. **동기화된 사본 (In-Sync Replicas, ISR)**: 리더와 동기화 된 사본
2. `replica.lag.time.max.ms` — 카프카는 시간 기준(기본 30초)

### 20.1 ACK = all
- 모든 ISR이 메시지를 수신한 뒤에 ACK
- 가장 느린 ISR의 응답을 기다려야 함
- 영속성 측면에서 당연히 가장 좋음

### 20.2 ACK = 1
- 리더만 메시지 저장하면 ACK
- 빠르지만 ACK 직후 리더에 장애가 생기면 데이터 소실
- 때로 데이터가 사라져도 괜찮, 낮은 응답 지연을 보장해야하는 시스템

### 20.3 ACK = 0
- 잘 수신 했는지 관심 없음, 생산자 재시도 없음
- metric 수집이나 로깅처럼 메시지 양 많고 손실 발생해도 상관 없는 경우 좋음

## 21. 파티션 삭제
1. 파티션 퇴역 결정 → 새로운 메시지 더이상 안들어옴
2. 바로 제거하지 않고 일정 시간 유지 - 소비자 있을 수 있음
3. 유지 기간 끝나면 데이터 삭제, 저장 공간 반환

## 22. 메시지 전달 방식

### 22.1 최대 한 번 (ACK = 0)
- 메시지가 소실되어도 다시 전달될 일 없음

### 22.2 최소 한 번 (ACK = all or ACK = 1)
- 중복 가능, 메시지 소실 X

### 22.3 정확히 한 번
- 중복 안됨, 딱 한 번만
- 지불, 매매, 회계 등 금융 관련 응용
