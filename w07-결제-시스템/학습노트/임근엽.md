## 결제 시스템 설계

## 요구사항

 하루 100만 건의 트랜잭션
 신용 카드 데이터는 법률에 맞게 직접 저장하지 않고 전문 결제 업체에게 위임한다.
 대금 수신(고객 → 우리 계좌) / 대금 정산(우리 계좌 → 판매자)

하루 100만 건은 데이터베이스로도 충분히 처리 가능하다.
결제는 고객에게 민감한 데이터라 실패했을 때 어떻게 되돌리고 맞출지가 중요하다.
처리량보다 정확하게 한 번 처리에 집중해서 설계한다.

그리고 하나의 결제로 다양한 작업들이 실행된다 (지갑 잔액 갱신, 원장 기록, 판매 대금 지급 등)
이걸 전부 동기적으로 엮으면 하나만 느려지거나 죽어도 결제 전체가 막히므로 비동기적으로 설계한다.

## 대금 수신 흐름

 1. 사용자가 주문하기 클릭 → 결제 이벤트 생성, 결제 서비스로 전송
 2. 결제 서비스는 이벤트를 DB에 저장하고 위험 확인
 3. 결제 이벤트 하나에 결제 주문이 여러 개 있을 수 있음
 4. 결제 실행자가 결제 주문을 하나씩 PSP에 보내 카드 결제 처리
 5. 성공하면 지갑 갱신 → 원장 갱신

결제 서비스 / 결제 실행자 / 지갑 / 원장으로 역할이 나뉜다.
실제 카드사와 통신하는 건 PSP에게 맡긴다.

## 원장과 복식부기

모든 거래를 두 개의 계좌에 같은 금액으로 기록한다. 한쪽은 차감, 한쪽은 증가.

 구매자 : 차감 $1
 판매자 : 증가 $1

모든 항목의 합은 항상 0이어야 한다.

## 외부 결제 페이지

카드 정보를 직접 저장하지 않고, 토큰만 저장하고, 실제 카드 정보는 PSP에게 넘긴다.

 1. 사용자가 결제 클릭 → 결제 서비스가 PSP에 결제 등록 요청
 2. PSP가 토큰 반환 → 결제 서비스가 토큰을 DB에 저장
 3. 클라이언트가 토큰으로 PSP 결제 페이지를 띄우고 사용자가 카드 정보 입력
 4. 결제 끝나면 결제 완료 페이지로 돌아옴
 5. PSP가 웹훅으로 결제 서비스에 결과를 비동기로 알려줌


## 조정

정확한 검증을 위해 PSP의 정산 파일과 우리 원장을 주기적으로 비교한다.

불일치가 나오면 3가지로 분류한다.

 1. 원인과 해결법을 알고 자동화 가능 → 자동 조정 프로그램
 2. 원인과 해결법은 알지만 자동화 비용이 큼 → 작업 큐에 넣고 재무팀이 수동 처리
 3. 원인을 모름 → 별도 큐에 넣고 재무팀이 조사

### 재시도 전략

 즉시 재시도
 고정 간격 : 일정 시간 기다렸다가
 증분 간격 : 기다리는 시간을 조금씩 늘림
 지수적 백오프 : 1초 → 2초 → 4초 두 배씩 늘림
 취소 : 영구적인 실패면 그냥 포기

네트워크 문제는 금방 풀리지 않으므로 지수적 백오프 사용한다.

## 정확히 한 번 전달

고객에게 이중 청구하는 것을 막기 위해 정확히 한 번 전달이 필요하다.

 정확히 한 번 = 최소 한 번  + 최대 한 번

### 멱등성

여러 번 실행해도 결과가 처음 한 번과 같은 성질.
클라이언트가 요청 헤더에 멱등 키를 붙여 보낸다.

결제 시스템은 이 키를 DB 고유 키 제약 조건으로 저장한다.
 새 레코드 추가 성공 → 처음 온 요청이니 처리
 추가 실패 → 이미 처리한 요청이니 처리하지 않고 이전 결과를 반환
