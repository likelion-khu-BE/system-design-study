## PSP?
카드사랑 이어주는 중간 회사임

- 손님: 카드로 만원 결제
- 쇼핑몰(우리): 만원 받아야 하는데 카드사랑 직접 소통할 수 없음
- PSP: 쇼핑몰 대신 카드 결제 처리
- 카드 네트워크: Visa, Mastercard 등 카드사와 PSP를 이어줌

PSP를 쓰지 않으면 카드 번호 등을 다루기 위해 복잡한 보안 규정 등을 지켜야 함. PSP는 이런 것들이 이미 갖추어져 있어서 이걸 이용함 (우리나라의 KG이니시스, 토스페이먼츠 등이 이것이다)

결제는 두 번에 나누어서 일어남

1. 승인 (결제 버튼을 누르면): 카드 입력 -> PSP 가 카드사에 잔액이 충분한지 조회 -> 카드사가 승인 -> PSP가 결제 성공을 전달 (실제 돈은 움직이지 않음)
2. 정산 (며칠 후): 카드사가 돈을 보내면 PSP 가 수수료를 제외한 돈을 쇼핑몰에 전달.

## 대금 수신
1. 결제하기 -> 이벤트가 결제 서비스로 감
2. 결제 서비스가 결제 이벤트를 디비에 저장
3. 결제 이벤트 하나에 주문이 여러개인 경우 결제 실행자를 부름
4. 결제 실행자가 결제 주문을 디비에 저장
5. 결제 실행자가 PSP에 결제 요청
6. 성공하면 결제 서비스가 지갑을 갱신함
7. 지갑 서버가 갱신된 잔액을 디비에 저장
8. 결제 서비스가 원장을 갱신함
9. 원장 서비스가 새 기록을 디비에 저장함

## 결제 이벤트랑 결제 주문이 뭐가 달라?
- 현아가 보검네 가게에서 만원 종석네 가게에서 2만원을 결제했다
- 결제 이벤트: 결제하기 한번을 눌렀으므로 1개의 결제 이벤트 발생
- 결제 주문: 두 가게에서 주문했으므로 두 개의 주문 발생.

## 결제 정보는 어떻게 저장하는가?
결제 이벤트 표
- checkout_id
- buyer_info
- seller_info
- credit_card_info
- is_payment_done

결제 주문 표
- payment_order_id
- buyer_account
- amount, currency
- checkout_id
- payment_order_status
- ledger_updated
- wallet_updated

디비는 안정성이 중요하므로 관계형 DB를 쓴다. (그런데 블프같이 초당 10건이 아니라 이벤트가 많아지면 어떻게 되는가...?)

## 결제 주문은 어떤 상태를 거치는가
1. NOT_STARTED
2. 결제 서비스가 결제 실행자한테 보내면 EXECUTING
3. 성공하면 SUCCESS, 실패하면 FAILED
4. SUCCESS면 wallet_updated=TRUE
5. ledger_update=TRUE
6. payment_order_status=TRUE

## 카드 번호를 왜 받지 않는가?
카드 번호를 받게 되면 PCI DSS 라는 복잡한 보안을 지켜야 함. 우리는 PSP라는 외부 결제 페이지를 이용해서 카드 번호를 직접 보지 않도록 한다

주문 ID 를 멱등키로 이용해서 중복 주문을 막고, 우리는 토큰을 대신 갖는다

## 대사는 뭐임
비동기로 주고 받으면 어긋날 수도 있음. 
- 원인을 알고 자동으로 고칠 수 있음 -> 자동 보정 프로그램
- 원인은 아는데 자동화를 할 수 없음 -> 재무팀이 손으로 고침
- 원인을 모름 -> 사람이 직접 조사함

## 어디는 동기고 어디는 비동기일까
- 동기: 답을 기다렸다가 다음으로 넘어감
- 비동기: 맡겨 두고 다음으로 넘어감

**동기로 할 때**

- 지갑이 느리면 사용자도 기다림
- 흐름이 단순함

**비동기로 할 때**

- 지갑이 느려도 서비스는 상관 없음
- 원장이 죽어도 메시지는 큐에 남음
- 두 번 받는 경우를 대비해서 멱등 처리를 해야 함
- 단일 수신자: 메시지 하나를 소비자 한 명이 처리함
- 다중 수신자: 메시지 하나를 여러 소비자가 처리

## 결제가 실패하면?
- 재시도 큐: 다시 요청할 것들을 쌓아둠
- 실패 메시지 큐: 계속 실패한 요청들을 모아두는 큐
따로 실패한 이유를 조사함

## 결제 버튼을 두 번 누르면
최소 한 번, 최대 한 번
- 즉시 재시도: 바로 다시 보냄
- 고정 간격: 정해진 간격마다 다시 보냄
- 증분 간격: 점점 늘려서 보냄
- 지수 백오프: 두 배씩 늘려서 보냄
- 요청을 취소함

**멱등성**

같은 요청을 여러 번 보내도 아이디를 확인하여 한 번 보낸 걸로 처리함

요청 헤더에 멱등키를 붙여서 보냄

## 보안
- 도청: HTTPS로 대응함
- 변조: 암호화와 무결성 모니터링을 함
- 중간자 공격: SSL+인증서 고정
- 데이터 손실: 디비 복제
- DDOS: 방화벽, 처리율을 제한

---
**세일 때는 어떻게 하나**

손님 -> (앞) -> API 서버 -> 결제 서비스 (뒤:큐) -> 지갑, 원장, 디비

**앞에서 줄이기**
- 디비가 꼭 해야 하는 일만 디비까지 가게 함
- 캐시, CDN: 상품 정보 같이 자주 조회되는 것은 레디스 같은 곳에 저장한다
- 대기열: 대기순번 화면을 보여주고 감당 가능한 만큼만 들여보낸다 (티켓팅 화면)
- 처리율 제한:한 사람당 몇 번까지만 받는 등의 제한을 둠
- 중복 막기

**뒤에서 늦추기**
- 뒷단의 일만 천천히 처리하도록 한다

**미리 키우기**
- API 서버: 평소 서버보다 늘려 둠
- 결제 DB: 더 좋은 디비로 바꿈
- 캐시: 정보 등은 캐시에 넣어 둠
- 부하 테스트: 가짜 트래픽으로 미리 테스트함
- PSP에 미리 알리기
