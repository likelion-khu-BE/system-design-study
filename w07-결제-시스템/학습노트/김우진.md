## 배경

1. 이커머스의 결제 시스템이다.
2. 구매자가 플랫폼에 돈을 내는 흐름(대금 수신, pay-in)이랑, 플랫폼이 수수료 떼고 판매자한테 정산해주는 흐름(대금 정산, pay-out)을 둘 다 다룬다.
3. 읽기 비율이 압도적인 곳은 아니고, 초당 트래픽 처리량을 늘리는 것보다 데이터 정합성이랑 중복결제 방지가 훨씬 중요한 도메인이다.
4. 카드사나 은행이랑 직접 연동하는건 현실적으로 불가능해서(큰 기업은 가능), stripe나 한국으로 따지면 토스페이먼츠 같은 외부 결제대행사(psp)를 끼고 통신한다.
    

### 결제 도메인에서 돈이 실제로 움직이는 방식

기술 설계 들어가기 전에 이 도메인에서 돈이 어떻게 흐르는지부터 알아야한다. 일반 쇼핑몰 crud랑은 결이 다름.

1. 대금 수신(pay-in)과 대금 정산(pay-out)의 주체들
- 결제는 우리 서버랑 유저 둘이서만 하는게 아니다. psp 뒷단에 카드사, 구매자 카드를 발급해준 발급 은행(issuing bank), 판매자 쪽 돈을 받아주는 매입 은행(acquiring bank)이 얽혀있다.
- 그리고 나중에 판매자한테 정산해줄 때도 플랫폼이 직접 은행망 뚫어서 쏘는게 아니라, 타사 정산 서비스를 끼고 정산하는 경우가 많다.

2. 승인 -> 매입 -> 정산의 시차
- 유저가 결제버튼 누르면 바로 판매자 통장에 돈이 꽂히는게 아니다. 3단계로 시차를 두고 돈이 움직인다.
    - 승인(authorization) : 발급 은행한테 "이 사람 한도 되니까 돈 묶어놔" 하는 단계다. 아직 실제 돈이 넘어온건 아니다.
    - 매입(capture) : 상점이 매입 은행한테 "아까 묶어둔 돈 진짜 청구할게" 요청하는 단계다.
    - 정산(settlement) : 카드사나 psp가 수수료 떼고 우리 플랫폼 계좌에 실제 현금을 입금해주는 단계다. (보통 며칠 걸림)
        
- 이 시차 때문에 "결제는 성공했는데 실제 우리 통장 잔고엔 아직 돈이 없는" 애매한 구간이 필연적으로 생긴다. 백엔드 시스템이 제어할 수 없는 영역이다. 그래서, 부분취소나 정산 지연 같은 골치아픈 케이스들이 다 튀어나온다.
    
3. 돈의 성격을 쪼개서 관리해야한다 (미수금과 예수금)
- 구매자가 결제하자마자 판매자한테 바로 정산해주면 안된다. 구매자가 환불할수도 있고, 아직 psp에서 우리한테 돈이 안들어왔기 때문이다.
- 그래서 회계에서는 돈의 상태를 가계정(clearing account)으로 쪼개서 관리한다.
    - 구매자 결제 직후 : 미수금(psp한테 받을 돈) +10000 / 예수금(판매자한테 줄 부채) +10000
    - 며칠 뒤 psp가 실제 돈 꽂아줌 : 플랫폼 현금 +10000 / 미수금 -10000
        
- 같은 이유로 판매자 지갑 잔액도 하나로 두지 않는다. 정산 대기 잔액이랑 출금 가능 잔액을 분리해둬야 구매확정도 안됐는데 판매자가 돈 빼가는 사고를 막을 수 있다.

4. 1원 오차도 허용 안되는 계산 정책
- 금액 데이터에 float이나 double 쓰면 부동소수점 오차 때문에 나중에 원장 합이 안맞는다. 그래서 책에선 문자열로 다루길 권장한다. 
- 수수료를 계산할 때 소수점 이하를 버릴지 반올림할지 정책을 코드에 못박아둬야 한다. 이게 어긋나면, 나중에 psp 정산 파일이랑 조정할때 1원씩 어긋나는 사고가 발생한다.
    
      
5. 타임아웃 났을때의 방어 (망취소)
- psp로 결제 요청 보냈는데 네트워크 지연으로 타임아웃이 났다고 치자. 우리 서버는 실패로 아는데, 실제 카드사 쪽에선 승인이 떨어졌을수도 있다.
- 이대로 두면 유저는 결제 실패 화면을 봤는데 카드 문자는 찍히는 사고가 발생한다
- 그래서 pg나 금융망 연동할땐 타임아웃 발생 시 직전 거래를 강제로 롤백시키는 망취소(net cancel) api를 무조건 같이 구현해서 방어해야만한다
    

### 어떤 저장소를 써야할까 (=데이터 특징과 보안)

- 금융 데이터라 acid 보장이 필수다. 데이터 유실이나 롤백 실패가 곧 돈 문제라 엔진레벨에서 트랜잭션을 잡아주는 rdb를 쓰는게 맞다.
- 근데 디비에 사용자 카드번호나 cvc 같은걸 직접 저장하면? 그때부터 pci dss라는 보안 규정을 다 맞춰야하고 리스크가 너무 크다.
- 그래서 대개는, 아예 내 서버랑 디비에 카드정보를 다루지 않게끔 회피한다.
    - psp가 제공하는 외부 결제 페이지를 띄우거나, 프론트에서 psp로 카드정보를 바로 쏴서 토큰만 받아오는 토큰화 방식을 쓴다.
    - 우리 서버는 그 토큰만 들고 결제 요청을 날리면 되니까 보안 부담이 줄어든다.
- 그리고 결제 주문 상태가 바뀔 때 기존 row를 계속 덮어쓰는 것보다, 상태 변경 이력을 쌓아두는 어펜드온리 테이블로 설계하면 나중에 추적하거나 감사할 때 훨씬 유리하다.

### 데이터를 어떻게 저장해두는게 좋을까

- 구매자는 장바구니에 여러개 물건을 담아서 한번에 결제한다.(하나의 구매에 여러 판매자가 섞이는 경우) 정산은 판매자별로 따로 해줘야한다.
- 그래서 데이터 모델을 1:N으로 쪼갠다
    - payment event : 체크아웃 한번에 생기는 전체 결제 건 (1)
    - payment order : 판매자별로 쪼개진 개별 결제 주문 (N)
        
원장은 왜 복식부기로 쌓아야할까
- 단순하게 생각하면 지갑 테이블에 balance -= 10000 이렇게 update 칠 것 같다.
- 근데 돈 오가는 시스템에서 이렇게 덮어쓰기를 하면 나중에 이 돈이 어디서 와서 왜 빠졌는지 추적이 안된다.
- 그래서 회계에서 쓰는 복식부기(double-entry) 방식을 그대로 쓴다
    - 모든 거래를 차변(debit)이랑 대변(credit) 두 줄로 동시에 기록한다.    
    - (debit: 구매자 -10000, credit: 플랫폼 +10000)
    - 이렇게 하면 전체 원장 레코드의 합이 항상 0이 되어야 맞다.  
- 생각해보면, 이게 결국 event sourcing이랑 결이 같다. 잔액이라는 상태를 update 하는게 아니라 돈이 이동한 사실을 불변 레코드로 계속 쌓아두고 필요할때 합산해서 잔액을 계산하는 식이라 감사할 때 유리할것이다.
    
### 동시성과 중복결제

결제 시스템에서 제일 무서운건 사용자가 결제버튼을 두번 눌렀거나 네트워크가 팅겨서 재시도가 날아가 돈이 두번 빠져나가는거다.

어떻게 exactly-once를 보장할 것인가?
- 분산 환경에서 네트워크 통신만으로 exactly-once를 보장하는건 불가능에 가깝다.
- 그래서 at-least-once + at-most-once(idempotency) = exactly-once공식을 쓴다.
    
- idempotency key (멱등 키)
    1. 클라이언트가 결제창 들어갈때 고유한 키(보통 uuid)를 만들어서 http 헤더에 담아 보낸다.
    2. 서버는 결제 로직 돌리기 전에 디비에서 이 멱등키로 처리된 이력이 있는지 먼저 조회한다.
    3. 이미 처리된 키면 psp에 요청 또 안보내고 이전에 저장해둔 결과를 그대로 리턴한다.

- 이떄 중요한건 멱등키의 갱신 혹은 만료 시점이다. 이 경우엔 "장바구니 관련 정보가 변경되거나, 결제가 완료됏을때" 일것같다.
    
    
> 만약 사용자가 광클해서 0.001초 차이로 같은 멱등키 요청 두개가 동시에 들어오면 어떡하지? 둘 다 디비 조회했을때 "아직 없네?" 하고 통과해서 중복결제 터질수 있는거 아닌가?
>
> -> 맞다. 애플리케이션 레벨에서 select 먼저 하고 insert 하는식이면 레이스 컨디션이 무조건 생긴다. 그래서 디비 테이블의 멱등키 컬럼에 unique 제약조건을 걸어서 디비 엔진이 두번째 요청을 튕겨내게 하거나, 앞단에 redis setnx 같은걸로 분산락을 먼저 잡아야한다. 

### 외부 psp 지연과 내부 서비스 통신 문제

카드사 점검이나 은행망 지연, 혹은 3D secure authentication 같은 추가 인증 때문에 결제 요청을 보냈는데 응답이 지연되는 경우가 흔하다.

1. 웹훅과 폴링 기반 비동기 처리
- 결제 요청을 받으면 psp는 일단 펜딩상태를 먼저 내려준다.
- 실제 승인이 떨어지면 psp가 미리 등록된 우리 서버의 webhook url로 최종 결과(성공 혹은 실패)를 비동기로 쏴준다.
- 이때 웹훅 api는 외부에 열려있어서 가짜 요청이 올 수 있으니 psp가 헤더에 담아주는 시그니쳐 검증이 필수다.
- 그리고 psp가 웹훅을 안주거나 네트워크 문제로 유실될 때도 있어서, 우리 서버가 주기적으로 psp api를 찔러서 상태를 확인하는 폴링(polling) 방식도 같이 보완책으로 쓴다.

2. 내부 서비스 간 결합도 낮추기
- 결제가 끝나면 원장도 써야하고, 판매자 지갑 잔액도 올려야하고, 알림도 보내야한다.
    
- 이걸 http같은 동기식으로 묶어두면 알림서버 죽었을때 결제 전체가 롤백될수있다. 그래서 카프카 같은 메시지큐를 두고 결제완료 이벤트를 발행해서 여러 서비스가 알아서 구독해 처리하게 만든다.
    
> 결제 디비에는 성공으로 커밋했는데, 바로 다음줄에서 kafka로 메시지 쏘려는 순간 서버가 죽으면 어떻게 될까?
> 
> 결제는 됐는데 원장 기록이랑 지갑 업데이트 이벤트가 날아간다. 그렇다고 디비 트랜잭션이랑 카프카 발행을 2pc로 묶자니 너무 느리다.
> 
> 그래서 보통은 outbox pattern을 통해 로컬 디비 트랜잭션 안에 outbox 테이블에 이벤트를 같이 insert해두고, 별도 워커나 cdc가 긁어서 메시지를 쏘는게 좋다.
> 
>   

3. 실패 처리
- 일시적인 네트워크 장애는 무작정 바로 재시도하면 상대 서버를 때리는 꼴이라 익스포넨셔널 백오프를 쓴다.
    
- 재시도 큐(retry queue)에 넣어서 재시도를 하고 정해둔 횟수만큼 실패하는 메시지는 실패 메시지 큐(dlq)로 격리해두고 나중에 (보통은)수동으로 재처리한다.
    

### 조정 

- 멱등키 걸고 카프카 쓰고 아웃박스 패턴까지 다 써도, 분산 환경에 외부 시스템까지 엮여있으면 100% 완벽이란게 없다. 패킷 유실이나 psp 내부 버그로 우리 원장 디비랑 실제 카드사 정산 금액이 어긋나는 일이 무조건 생긴다.
    
- 그래서 매일 밤 배치로 psp가 주는 정산 파일을 받아서 우리 내부 원장 데이터랑 1원 단위로 대조하는 조정작업을 돌려야만 한다.
- 안맞는 데이터가 나올 시 책에선 3가지로 분류한다.
    1. 유형을 알고 자동화하기 쉬운건 자동 조정 프로그램(보정 배치)으로 돌리고,
    2. 유형은 알지만 자동화 비용이 너무 큰건 재무팀이 수동으로 수정하고,
    3. 아예 분류조차 안되는 알수없는 불일치는 특별한 작업 대기열에 넣어서 재무팀이나 개발자가 직접 까볼수있게 띄워서 맞춘다.

### 일관성과 보안

- 일관성 : 내부 서비스(결제, 원장, 지갑)끼리 데이터 정합성을 맞추는 건 결국 2pc 아니면 사가이다. 그리고 읽기 성능 때문에 db를 master-slave로 분리하면 복제 지연 때문에 방금 결제했는데 내역 조회에 안뜨는 문제도 같이 신경써야한다.
    
- 보안 : 중간자 공격을 막으려고 https에 인증서 고정까지 걸고, 사기 결제 막으려고 주소 확인이나 카드 확인 번호 검증, 레이트리미팅, 방화벽 같은걸 앞단에 둬서 방어한다.
