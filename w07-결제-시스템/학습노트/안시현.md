# 결제 시스템

> 돈이 오가는 시스템이라 **빠른 것보다 틀리지 않는 것**이 훨씬 중요함.
> 처리량은 초당 10건 정도로 작지만, 한 건이라도 중복되거나 빠지면 그대로 돈 문제가 됨.

---

## 요구사항

* 기능 요구사항
  * 대금 수신 (결제 시스템이 고객으로부터 대금 수령)
  * 대금 정산 (제품 판매 대금을 판매자에게 송금)

* 비기능 요구사항
  * 신뢰성 및 내결함성
  * 내부 서비스와 외부 서비스 간의 조정 프로세스

> 하루 100만 건 → 초당 약 10건. 6장 광고 클릭 집계(초당 최대 5만 건)와 비교하면 규모는 작음.
> 그래서 이 장의 고민은 "많이 처리하기"가 아니라 "정확하게 처리하기"에 몰려 있음.

## 결제 정보의 흐름

### 1. 대금 수신 흐름

<img width="1332" height="893" alt="image" src="https://github.com/user-attachments/assets/cf86530f-1182-4924-ab63-65640b4e82b5" />

- ① 사용자가 주문하기를 누르면 **결제 이벤트**가 결제 서비스로 들어옴
- ② 결제 서비스가 결제 이벤트를 DB에 저장
- ③ 결제 이벤트 안에 들어 있는 **결제 주문**마다 결제 실행자를 호출
- ④ 결제 실행자가 결제 주문을 DB에 저장
- ⑤ 결제 실행자가 외부 PSP를 호출해 실제 카드 결제 진행
- ⑥ ⑦ 결제가 성공하면 결제 서비스가 **지갑**(판매자 잔액)을 갱신하고 DB에 저장
- ⑧ ⑨ 지갑 갱신이 끝나면 **원장**을 갱신하고 DB에 저장

> **결제 이벤트와 결제 주문은 1:N**
> 장바구니에 여러 판매자의 물건을 담고 한 번에 결제하면, 결제 이벤트는 하나지만 판매자별로 결제 주문이 나뉨.

 **구성 요소 한 줄 정리**
> - 결제 서비스: 결제 과정 전체를 조율함. 시작할 때 자금 세탁(AML/CFT) 같은 위험 점검부터 함
> - 결제 실행자: 결제 주문 하나를 PSP를 통해 실제로 실행함
> - PSP: 계좌 A에서 B로 돈을 실제로 옮겨주는 외부 업체 (Stripe, PayPal 등)
> - 카드 유형: 비자, 마스터카드 같은 카드사
> - 지갑: 판매자별 잔액
> - 원장: 모든 돈의 이동 기록. 매출 집계, 사후 검증의 기준

### 2. 대금 정산 흐름

- 구조는 대금 수신과 거의 같음
- 차이는 PSP 대신 **정산 서비스 업체**가 플랫폼 계좌 → 판매자 계좌로 돈을 보낸다는 것

### 3. 결제 주문의 상태

결제 주문은 `NOT_STARTED → EXECUTING → SUCCESS / FAILED` 순서로 상태가 바뀜.

성공 뒤에는 지갑 갱신 여부(`wallet_updated`), 원장 갱신 여부(`ledger_updated`)도 따로 기록함.

> 단계별로 상태를 남겨두는 이유는 **중간에 장애가 났을 때 어디까지 진행됐는지 알기 위해서**임.
> 예를 들어 PSP 결제는 성공했는데 지갑 갱신 전에 서버가 죽었다면, 재시작 후 `SUCCESS`이면서 `wallet_updated = FALSE`인 주문만 골라서 이어서 처리하면 됨.

### 4. 외부 결제 페이지를 쓰는 흐름 (PSP 연동)

카드 정보를 우리 서버가 직접 받으면 PCI DSS 같은 까다로운 보안 규정을 전부 지켜야 함.

그래서 카드 입력 화면 자체를 **PSP가 제공하는 결제 페이지**로 띄우고, 카드 정보는 PSP만 보게 함.

<img width="1308" height="867" alt="image" src="https://github.com/user-attachments/assets/2f5e99b4-f555-4d85-ac95-c6aea23778fb" />

- ① 사용자가 구매 페이지에서 구매를 누름
- ② 결제 서비스가 PSP에 결제 등록을 요청. 이때 **비중복 난수**(nonce)를 같이 보냄
- ③ PSP가 결제 토큰을 돌려줌
- ④ 결제 서비스가 토큰을 DB에 저장
- ⑤ 토큰을 담아 PSP의 결제 페이지를 사용자 브라우저에 띄움
- ⑥ 사용자가 그 페이지에 카드 정보를 입력하고 결제 시작
- ⑦ PSP가 결제 결과를 돌려줌
- ⑧ 브라우저가 우리 쪽 결제 완료 페이지로 리다이렉트됨
- ⑨ 이와 별개로 PSP가 **웹훅**으로 결제 서비스에 최종 결과를 알려줌

> **⑦⑧과 ⑨가 따로 있는 이유**
> 브라우저를 통한 결과(⑦⑧)는 사용자가 창을 닫거나 네트워크가 끊기면 우리 서버까지 안 올 수 있음.
> 그래서 PSP가 서버 대 서버로 직접 알려주는 웹훅(⑨)을 진짜 결과로 믿음.

> **nonce(②)가 중요한 이유**
> 같은 결제 요청을 다시 보내도 nonce가 같으면 PSP가 "이미 받은 요청"으로 알아봄 → 아래 멱등성과 연결됨

## 결제 시스템이 지켜야 할 것들

### 1. 복식부기 원장

- 모든 거래를 **두 계정에 같은 금액으로** 기록함. 한쪽은 빠지고 한쪽은 들어옴

| 계정 | 차변 | 대변 |
| --- | --- | --- |
| 구매자 | $1 | |
| 판매자 | | $1 |

- 그래서 모든 항목을 더하면 **항상 0**이어야 함
- 0이 아니면 어딘가에서 돈이 사라졌거나 생겼다는 뜻 → 오류를 바로 잡아낼 수 있음
- 돈이 어디서 와서 어디로 갔는지 끝까지 추적 가능함

> 잔액만 덮어쓰는 방식(`UPDATE balance`)이면 이력이 남지 않아서, 숫자가 틀렸을 때 왜 틀렸는지 알 수 없음.

### 2. 조정 (reconciliation)

- 내부 서비스끼리, 그리고 PSP와 비동기로 주고받다 보면 메시지 유실이나 상태 불일치가 생길 수 있음
- 그래서 매일 밤 PSP가 보내주는 **정산 파일**과 우리 원장을 비교함
- 불일치가 나오면 원인에 따라 나눠서 처리함
  - 원인이 분류되고 자동화 가능 → 프로그램으로 자동 수정
  - 원인은 알지만 자동화가 어려움 → 재무팀이 수동으로 처리
  - 원인을 모름 → 따로 조사

> 6장 광고 클릭 집계의 "하루 끝 조정"과 같은 생각임.
> 실시간 처리가 완벽할 수 없다는 걸 인정하고, **나중에 한 번 더 맞춰보는 안전망**을 두는 것.

### 3. 결제 지연 처리

- 위험 심사나 3D 보안 인증처럼 추가 확인이 필요하면 결제 결과가 몇 시간~며칠 늦게 나오기도 함
- PSP는 일단 **대기(pending)** 상태를 돌려주고, 사용자에게도 그대로 보여줌
- 결과가 나오면 웹훅으로 받거나, 결제 서비스가 주기적으로 상태를 조회함

### 4. 내부 서비스 간 통신

| | 동기 (HTTP) | 비동기 (메시지 큐) |
| --- | --- | --- |
| 장점 | 단순함 | 서비스끼리 덜 묶임, 한 곳의 장애가 번지지 않음, 트래픽 완충 |
| 단점 | 한 서비스가 느리면 전체가 느려짐, 장애가 번짐, 확장이 어려움 | 구조가 복잡함 |

- 결제 하나에 지갑, 원장, 분석, 알림 등 여러 서비스가 동시에 반응해야 함
- 그래서 같은 메시지를 여러 서비스가 각자 받아 처리할 수 있는 **Kafka 같은 다중 수신 구조**가 잘 맞음

### 5. 실패 처리와 재시도

- 결제의 모든 단계에서 상태를 남겨두고(추가만 하는 테이블), 실패하면 성격에 따라 갈라 보냄
  - 다시 시도하면 될 실패 (일시적인 네트워크 오류 등) → **재시도 큐**
  - 다시 해도 안 될 실패 (잘못된 입력 등) → DB에 기록
  - 여러 번 재시도해도 계속 실패 → **실패 메시지 큐**(DLQ)에 모아두고 따로 조사

- 재시도 전략

| 전략 | 방식 |
| --- | --- |
| 즉시 재시도 | 실패하자마자 다시 보냄 |
| 고정 간격 | 정해진 시간만큼 기다렸다가 다시 |
| 증분 간격 | 기다리는 시간을 조금씩 늘림 |
| 지수적 백오프 | 기다리는 시간을 1초, 2초, 4초... 배로 늘림 |
| 취소 | 영구적인 실패라고 판단되면 그만둠 |

> 상대 서버가 이미 과부하인데 즉시 재시도를 쏟아부으면 상황이 더 나빠짐.
> 그래서 보통은 지수적 백오프처럼 **점점 간격을 늘리는 쪽**이 안전함.

### 6. 멱등성과 정확히 한 번

결제에서 가장 피해야 할 건 **이중 청구**임.

그런데 실패하면 재시도를 해야 하니, 재시도 때문에 같은 결제가 두 번 될 위험이 생김.

**정확히 한 번 = 최소 한 번(재시도) + 최대 한 번(멱등성)**

- 재시도로 "적어도 한 번은 처리된다"를 보장하고
- 멱등성으로 "여러 번 와도 한 번만 처리된다"를 보장함

**멱등성 구현**
- 클라이언트가 요청마다 고유한 **멱등 키**(보통 UUID)를 HTTP 헤더에 담아 보냄
- 서버는 이 키를 DB의 **고유 키 제약 조건**으로 저장함
- 같은 키로 또 들어오면 저장이 실패하니까, 새로 처리하지 않고 이전 결과를 돌려줌

> **멱등성이 필요한 대표 상황**
> - 사용자가 결제 버튼을 빠르게 두 번 누름 → 두 번째 요청은 키가 같아서 걸러짐
> - PSP는 결제에 성공했는데 응답이 네트워크 문제로 안 돌아옴 → 다시 보낼 때 **같은 nonce/토큰**을 쓰니까 PSP가 이미 처리한 결제로 알아봄

### 7. 일관성

데이터가 여러 곳에 나눠 저장되니, 곳곳에서 어긋나지 않게 맞춰야 함.

- **내부 서비스끼리**: 정확히 한 번 처리로 맞춤
- **우리 서비스와 PSP 사이**: 멱등성 + 조정으로 맞춤
- **DB 복제본끼리**: 복제가 늦어서 주 DB와 복제본 값이 잠깐 다를 수 있음
  - 읽기·쓰기를 모두 주 DB에서만 하거나
  - Paxos, Raft 같은 합의 알고리즘으로 복제본을 맞추거나
  - 처음부터 합의 기반으로 만든 분산 DB(YugabyteDB, CockroachDB)를 씀

## 결제 보안

### 1. 요청/응답 도청 → HTTPS
- 클라이언트와 서버 사이 데이터가 평문으로 오가면 중간에서 그대로 읽힘
- HTTPS는 TLS로 통신 내용을 암호화함. 누가 패킷을 가로채도 내용을 알아볼 수 없음
- 결제 정보, 토큰, 개인정보가 오가는 모든 구간에 필수임

### 2. 데이터 변조 → 암호화 및 무결성 모니터링
- 도청이 "엿보기"라면 변조는 "고쳐 치기". 예를 들어 결제 금액 1만 원을 100원으로 바꿔 보내는 식
- 저장된 데이터와 전송 데이터를 암호화하고, 체크섬이나 서명으로 내용이 바뀌지 않았는지 확인함
- 무결성 모니터링은 원장·결제 기록 같은 중요한 데이터가 허가 없이 바뀌면 바로 알아채도록 계속 감시하는 것

### 3. 중간자 공격 → 인증서 고정 + SSL
- 공격자가 클라이언트와 서버 사이에 끼어들어 서버인 척, 클라이언트인 척하며 둘 사이 통신을 중계하는 공격
- HTTPS를 써도, 클라이언트가 공격자의 가짜 인증서를 믿어버리면 뚫림
- **인증서 고정(certificate pinning)**: 앱에 "우리 서버 인증서는 이것"이라고 미리 박아두고, 그 인증서가 아니면 연결을 끊음
  → 가짜 인증서가 그럴듯해도 통과하지 못함

### 4. 데이터 손실 → 여러 지역에 DB 복제 + 스냅숏
- 결제 기록은 잃어버리면 복구할 방법이 없는 데이터임
- **여러 지역에 복제**: 한 데이터센터가 통째로 문제가 생겨도 다른 지역의 복제본으로 버팀
- **스냅숏**: 특정 시점의 데이터를 통째로 떠둠. 실수로 지우거나 잘못 덮어쓴 경우 그 시점으로 되돌릴 수 있음
  → 복제는 장애 대비, 스냅숏은 실수 대비라 둘 다 필요함

### 5. 분산 서비스 거부(DDoS) → 처리율 제한 + 방화벽
- 여러 곳에서 엄청난 양의 요청을 보내 서비스를 마비시키는 공격
- **처리율 제한(rate limiting)**: 한 사용자·IP가 일정 시간 안에 보낼 수 있는 요청 수를 제한함
- **방화벽**: 의심스러운 트래픽이나 알려진 공격 패턴을 앞단에서 걸러냄
  → 정상 사용자의 결제는 계속 처리되도록 하는 게 목적

### 6. 카드 도난 → 토큰화
- 실제 카드 번호를 우리 DB에 저장하면, DB가 털리는 순간 카드 정보가 그대로 유출됨
- **토큰화**: 실제 카드 번호 대신 의미 없는 대체값(토큰)을 저장하고 결제에 사용함
- 실제 카드 번호는 PSP 같은 안전한 금고에만 있고, 토큰은 그 금고 안에서만 카드 번호로 바뀜
  → 토큰이 유출돼도 그 자체로는 쓸모가 없음
- 앞의 "외부 결제 페이지"를 쓰는 이유와 같은 맥락임

### 7. PCI 규정 준수 → PCI DSS
- PCI DSS는 비자, 마스터카드 같은 카드 브랜드들이 만든 **카드 정보를 다루는 조직이 지켜야 하는 보안 표준**
- 네트워크 방화벽, 카드 데이터 암호화, 접근 권한 제한, 정기적인 보안 점검 등 지켜야 할 항목이 많음
- 카드 정보를 직접 다룰수록 지켜야 할 범위가 넓어지고 부담도 커짐
  → 그래서 외부 결제 페이지와 토큰화로 **카드 정보를 아예 우리 서버에 안 들이는 것**이 부담을 줄이는 현실적인 방법

### 8. 사기 → 주소 확인, 카드 확인번호, 사용자 행동 분석
- 훔친 카드로 결제하는 것처럼, 기술적으로는 정상 요청이지만 실제로는 부정한 결제를 막는 것
- **주소 확인(AVS)**: 입력한 청구 주소가 카드사에 등록된 주소와 맞는지 확인
- **카드 확인번호(CVV)**: 카드 뒷면 3자리. 카드 번호만 유출된 경우를 걸러냄
- **사용자 행동 분석**: 평소와 다른 지역·시간·금액, 짧은 시간에 반복된 결제 같은 이상 패턴을 감지함

### 1. 지갑 갱신과 원장 갱신은 서로 다른 단계인데, 그 사이에 장애가 나면 어떻게 될까?

책 그림에서 둘은 각자 DB를 가진 별도 서비스라 한 번에 묶이지 않음. 그래서 세 가지로 버팀.

- `wallet_updated` / `ledger_updated` 상태로 어디까지 했는지 확인하고 이어서 처리
- 이어서 처리할 때 두 번 반영되지 않게 지갑·원장 갱신도 멱등하게 만듦
- 그래도 어긋난 건 조정에서 거름

### 2. 멱등 키는 언제까지 보관해야 할까?

- 너무 짧으면 늦게 온 재시도가 새 요청으로 처리돼 이중 청구가 생기고, 너무 길면 저장 공간이 계속 늘어남
- 그래서 재시도가 일어날 수 있는 기간보다는 길게 잡음
- Stripe 공식 문서 기준, 키는 최소 24시간 지나면 지울 수 있고 지워진 뒤 같은 키로 보내면 새 요청으로 처리함
- 책의 설계에서는 멱등 키인 `payment_order_id`가 결제 주문 테이블의 기본 키라 사실상 영구 보관됨
