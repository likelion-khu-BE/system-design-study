# W7 결제 시스템

# 1. 개략적 설계안

### 1-1. 대금 수신 흐름 / 대금 정산 흐름, 꼭 두 단계로만 세분화 해야 하나? 다른 방법이 있다면? 그 방법이 안되는 이유는?

**두 단계로 나누는 이유:** 돈의 소유권이 바뀌는 시점이 두 번이기 때문

- 수신(pay-in): 구매자 → 플랫폼 계좌 (돈은 플랫폼에 있지만 대부분 판매자 몫)
- 정산(pay-out): 플랫폼 계좌 → 판매자 계좌 (배송 완료 등 조건 충족 후)

**다른 방법은?**

| 방법 | 설명 | 안 쓰는(못 쓰는) 이유 |
| --- | --- | --- |
| 직접 결제 (1단계) | 구매자 → 판매자로 바로 송금 | 수수료 차감, 환불·차지백 대응, 배송 확인 전 대금 보류가 불가능 |
| PSP 분할 결제 (Split payment) | PSP가 결제 시점에 판매자/플랫폼 몫을 나눠서 바로 이체 | 실제로 쓰임. 하지만 정산 시점·조건을 플랫폼이 통제하기 어렵고 PSP 종속 |
| 더 잘게 세분화 | 승인(authorization) → 매입(capture) → 정산(settlement) → 지급(payout) | 실무 카드 결제는 실제로 이렇게 나뉨. 책은 면접용으로 **돈의 방향 기준**으로 크게 묶은 것 |

→ "꼭 두 단계"가 아니라 **돈의 흐름 방향 기준으로 크게 두 덩어리**라는 의미. 마켓플레이스(아마존)처럼 플랫폼이 중간에 돈을 보관해야 하는 구조라 두 흐름 분리가 필요하고, 실무에서는 각 흐름 안이 더 세분화된다.

### **1-2. (복식부기 원장 시스템) 한 계좌에서는 차감, 다른 계좌에서는 입금, 이외의 방법은 없나?**

| 방법 | 설명 | 한계 |
| --- | --- | --- |
| 단식부기 | 잔액 변화만 한 줄로 기록 (가계부 방식) | 돈이 어디서 와서 어디로 갔는지 추적 불가, 오류 검증 불가 |
| 잔액만 갱신 (UPDATE balance) | 지갑처럼 현재 잔액만 덮어씀 | 이력이 사라져 감사·조정 불가 |
| 복합 분개 (multi-leg) | 하나의 거래를 여러 계좌로 나눔 (예: 구매자 -$100 / 판매자 +$90 / 수수료 +$10) | 복식부기의 확장. 합계 0 원칙은 그대로 |
- 복식부기의 핵심은 "두 계좌"가 아니라 **모든 항목의 합 = 0** 이라는 불변식
- 실무에서는 수수료·세금·쿠폰 때문에 **복합 분개가 일반적**
- 원장은 수정(UPDATE)하지 않고, 틀리면 **반대 분개(역분개)를 추가**해서 바로잡음 → 불변(immutable) 원장

# 2. 상세 설계

### **2-1. (조정, 내부 서비스 통신) PSP, 은행 같은 외부 시스템이 비동기 통신을 선호하는 이유, 무조건 대규모 결제 시스템은 비동기 통신이 더 나은 선택인가?**

**외부 시스템이 비동기를 선호하는 이유**

- 처리 시간이 길고 예측 불가 (3D 보안 인증, 위험 심사, 은행 처리 → 몇 시간~며칠)
- 은행 정산은 원래 **배치(하루 1번 정산 파일)** 구조
- 호출하는 쪽과 장애를 분리 (PSP가 느려도 우리 서버 스레드가 묶이지 않음)

**무조건 비동기? → X**

| 구분 | 동기 | 비동기 |
| --- | --- | --- |
| 적합한 곳 | 사용자가 결과를 기다리는 결제 승인 단계 | 지갑·원장 갱신, 알림, 분석, 정산 |
| 장점 | 단순, 즉시 결과, 강한 일관성 | 장애 격리, 확장성, 트래픽 버퍼링 |
| 단점 | 의존 서비스 장애 전파 | 최종적 일관성, 중복·순서 문제, 디버깅 어려움 |
- 실무는 **혼합**: 승인은 동기(사용자에게 바로 성공/실패), 그 이후 후속 처리는 비동기(Kafka 등)
- 이 책 예시는 10 TPS → 동기로도 충분. "의존 서비스 많고 규모가 클수록" 비동기가 유리하다는 의미

### **2-2. (결제 지연 처리) 웹훅 vs 폴링, 뭐가 더 좋은가?**

| 구분 | 웹훅 (Push) | 폴링 (Pull) |
| --- | --- | --- |
| 방식 | 상태 바뀌면 PSP가 우리 URL 호출 | 우리가 주기적으로 PSP에 상태 조회 |
| 실시간성 | 높음 | 폴링 주기만큼 지연 |
| 효율 | 변경 있을 때만 호출 | 변경 없어도 계속 호출 (낭비, rate limit) |
| 단점 | 유실·중복·순서 뒤바뀜 가능, 공개 엔드포인트·서명 검증 필요 | 구현 단순하지만 비용↑ |

**뭐가 더 좋은가? → 웹훅이 기본, 폴링은 보조**

- 웹훅을 메인으로 쓰고, 웹훅이 일정 시간 안 오면 **폴링으로 상태 확인 (백업)**
- 웹훅은 중복으로 올 수 있으므로 **멱등하게 처리** 필요
- 최종적으로는 **조정(reconciliation)** 이 마지막 방어선

### **2-3. (재시도) 재시도 간격이 얼마나 중요한가? 실제로 지수적 백오프를 많이 사용하는 것인가? 상황에 맞게 바뀌는 것인가?**

**간격이 중요한 이유**

- 너무 짧으면: 장애 난 서버에 요청 폭주 → **재시도 폭풍(retry storm)** 으로 장애 악화
- 너무 길면: 결제 완료가 늦어짐 (사용자 경험↓)

**실제로 많이 쓰나? → O, 사실상 업계 표준** (단, 지터와 함께)

- AWS 권장: 지수적 백오프 + **지터(jitter, 무작위 지연)** + **최대 재시도 횟수 제한**
- 지터가 필요한 이유: 모든 클라이언트가 똑같이 1초, 2초, 4초에 재시도하면 또 동시에 몰림
- 상한(cap)도 둠: 지수는 너무 빨리 커지므로 최대 대기 시간 제한
- Stripe SDK도 자동 재시도 시 지수적 백오프 사용

**상황에 맞게 바뀐다**

| 상황 | 전략 |
| --- | --- |
| 일시적 네트워크 오류, 5xx | 지수적 백오프 + 지터 |
| 서버가 `Retry-After` 헤더를 줌 | 그 시간을 따름 |
| 4xx (잘못된 카드, 잔액 부족) | 재시도 X → 바로 실패 처리 |
| 반복 실패 | 실패 메시지 큐(DLQ)로 |

→ 전제: **멱등성이 보장된 요청만 재시도** (아니면 이중 결제)

### **2-4. (멱등성) 데이터베이스의 고유 키 제약 조건이 멱등성 지원 방법 중 가장 좋은 방법인가?**

**"가장 좋다"기보다 "가장 확실한 최후 방어선"**

| 방법 | 설명 | 장점 | 한계 |
| --- | --- | --- | --- |
| DB 고유 키 제약 | 멱등 키를 PK/UNIQUE로, INSERT 실패 = 중복 | DB가 원자적으로 보장, 동시 요청에도 안전 | 이전 결과를 돌려주려면 별도 저장 필요, 샤딩 시 같은 샤드여야 함 |
| 멱등 키 저장소 (Stripe 방식) | 키 + 첫 응답(상태코드·본문) 저장, 재요청 시 그대로 반환 | 재시도에 **같은 결과** 반환 | 저장소 관리, TTL 필요 |
| Redis SETNX / 분산 락 | 키 선점으로 중복 차단 | 빠름 | Redis 장애·만료 시 보장 약함 |
| 상태 기반 조건부 UPDATE | `UPDATE ... WHERE status='NOT_STARTED'` | 상태 머신과 자연스럽게 결합 | 영향받은 행 수 확인 필요 |
- Stripe: 첫 요청의 상태 코드와 응답 본문을 저장해 같은 키로 오면 그대로 돌려줌 (500 에러 포함), 키는 24시간 후 삭제 가능
- 실무는 **조합**: 멱등 키 테이블(UNIQUE 제약) + 처리 상태(IN_PROGRESS/COMPLETED) + 저장된 응답 + TTL
- 처리 중(IN_PROGRESS)에 같은 키가 또 오면 409/429 반환

### **2-5. (일관성) 결제 서비스가 PSP에 비중복 난수를 전송하는 방법 말고 다른 방법도 있나? 있으면 비중복 난수 전송하는 방법보다 왜 안좋은지**

| 방법 | 설명 | 비중복 난수보다 안 좋은 이유 |
| --- | --- | --- |
| 버튼 비활성화 (프론트) | 한 번 누르면 버튼 막음 | 새로고침·네트워크 재시도·다른 기기에서는 못 막음. UX 보조일 뿐 |
| 내용 기반 중복 판단 | (금액, 카드, 판매자, 시간)이 같으면 중복 | 정상적인 같은 금액 재구매도 막힘(오탐), 시간 창 설정이 애매 |
| 재시도 전 PSP 상태 조회 | 결제됐는지 먼저 물어보고 재시도 | 조회와 재시도 사이 경쟁 조건, 호출 추가, 조회 자체도 실패 가능 |
| 멱등 키 헤더 (Idempotency-Key) | 요청마다 고유 키를 헤더로 | 사실상 **같은 개념** (Stripe·PayPal 방식) |

→ 비중복 난수(멱등 키)는 "이 요청이 누구인지"를 **명시적 ID로** 식별 → 오탐 없음, 서버가 결정적으로 판단 가능. 다른 방법들은 보조 수단으로 같이 씀

### **2-6. (일관성) 상태 정보 유지 관리하는 여러 서비스가 있는데(책에는 5개) 이외에도 사용하는 서비스가 더 있는가? 실제로는 어떤 어떤 서비스를 주로 사용하는지, 다 사용하는건지**

5개: 결제 서비스, 원장, 지갑, PSP, 데이터베이스 사본

**실무에서 추가로 많이 보는 서비스**

| 서비스 | 역할 |

- 작은 회사: PSP(Stripe 등)에 대부분 맡김 → 결제 + 주문 + 웹훅 처리 정도
- 대형(우버, 에어비앤비): 위 서비스를 대부분 직접 운영

### **2-7. (일관성) 데이터 불일치 문제 해결 방법 두가지(주 데이터베이스 안에서만 읽기 쓰기 연산 처리, 모든 사본 항상 동기화) 외에 더 있나? 뭐가 가장 효과적인가**

| 방법 | 설명 |
| --- | --- |
| 읽기 라우팅 분리 | 돈과 관련된 중요한 읽기는 주 DB, 조회·분석은 복제본 |
| Read-your-writes | 내가 방금 쓴 데이터는 일정 시간 주 DB에서 읽음 |
| 반동기 복제 (semi-sync) | 최소 1개 복제본이 받았다고 응답해야 커밋 완료 |
| 복제 위치 대기 (LSN/GTID) | 복제본이 특정 쓰기까지 따라잡았는지 확인 후 읽음 |
| 최종적 일관성 + 조정 | 잠깐의 불일치는 허용하고 조정으로 바로잡음 |

**가장 효과적인 것? → 데이터 성격에 따라 섞어 씀**

- 잔액·결제 상태처럼 **틀리면 안 되는 데이터**: 주 DB(또는 합의 기반 분산 DB)
- 거래 내역 조회, 대시보드, 분석: 복제본 (약간 늦어도 OK)
- 그래도 생기는 불일치는 **조정**이 마지막 방어선

# 3. 개념 정리

### **3-1. 비중복 난수 (Nonce, Number used Only Once)**

- 딱 한 번만 쓰이는 값. 같은 요청인지 구별하는 데 사용
- 결제에서는 결제 주문을 유일하게 식별 → PSP가 중복 결제 방지에 사용
- 암호학에서는 재전송 공격(replay attack) 방지용

### **3-2. 분산 시스템**

- 여러 대의 컴퓨터가 네트워크로 연결되어 하나의 시스템처럼 동작하는 것
- 특징: 네트워크 지연·유실, 부분 장애(일부만 고장), 공유 시계 없음
- 그래서 결제 시스템에서 재시도, 멱등성, 조정 같은 장치가 필요한 것

### **3-3. 비중복 난수 == UUID? → X (겹칠 수는 있음)**

| 구분 | 비중복 난수 (Nonce) | UUID |
| --- | --- | --- |
| 정체 | **용도/역할** ("한 번만 쓴다") | **형식** (128비트 고유 식별자) |
| 형태 | 카운터, 랜덤 바이트, UUID 등 아무거나 | 정해진 포맷 (예: `550e8400-e29b-...`) |
| 관계 | UUID를 nonce로 쓸 수 있음 | 모든 UUID가 nonce는 아님 (예: 사용자 ID) |

→ 책에서는 **UUID를 비중복 난수로 사용**한 것. "UUID 형식의 값을 nonce 용도로 쓴다"
