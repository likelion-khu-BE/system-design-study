# 결제 시스템

## Pay-in / Pay-out

- **pay-in**: 결제 시스템이 판매자를 대신해서 고객한테 돈 받기
- **pay-out**: 결제 시스템이 판매자에게 돈 보내기

### pay-in 순서

1. 사용자가 주문하기 누르면 결제 이벤트 생성, 결제 서비스로 전송
2. 결제 서비스가 결제 이벤트를 DB에 저장
3. 이벤트 안의 결제 주문마다 결제 실행자 호출
4. 결제 실행자가 결제 주문 저장
5. 결제 실행자가 PSP를 호출해 카드 결제 처리
6. 성공하면 결제 서비스가 지갑 갱신, 판매자 잔고 기록
7. 지갑 서버가 잔고를 db에 저장
8. 결제 서비스가 원장 호출
9. 원장 서비스가 새 원장 정보 DB에 추가

## PSP 연동 방법

- **API 직접 연동**
- **외부 결제 페이지**
    1. 사용자가 결제 버튼을 누르면 클라이언트가 주문 정보를 담아 결제 서비스 호출
    2. 결제 서비스가 PSP에 결제 등록 요청 보내기, 결제 ID를 `nonce`로 보내 정확히 한번 등록
    3. PSP가 토큰 반환, `nonce`와 1:1
    4. 결제 서비스가 토큰을 DB에 저장
    5. 클라이언트가 토큰과 redirection URL로 PSP SDK를 초기화해 PSP 결제 페이지를 띄우기
    6. 사용자가 카드 정보를 입력하면 PSP가 결제 처리
    7. PSP가 결제 상태 반환
    8. 브라우저가 redirection url로 이동
    9. PSP가 웹훅으로 결제 서비스에 결제 상태를 비동기 전송, 결제 서비스 주문 상태 갱신

## 조정 (Reconciliation)

- 비동기 통신에서 메시지 전달이나 응답 반환이 보장되지 않으니 **마지막 방어선**으로 조정 사용
- 매일 밤 PSP와 은행은 **정산 파일**을 보내고 여기에는 잔액과 모든 거래내역이 들어있음
- 정산 파일을 파싱해 원장과 비교
- 내부 서비스끼리도 확인

## Payment Service Provider와 Payment Gateway

책에서 말하는 **PSP(Payment Service Provider)** 를 한국에서는 보통 **PG사(전자지급결제대행사)** 라고 부름

한국의 PG사들을 글로벌에서 PSP라고 보면 됨

토스페이먼츠, NHN KCP, KG이니시스 같은 회사

| **구분** | **PG (Payment Gateway)** | **PSP (Payment Service Provider)** |
| --- | --- | --- |
| **개념 범위** | 결제 승인 및 정산 **중계 기술·인프라** (좁은 의미) | 결제 중계 + 리스크 관리 + 정산 + 부가 서비스 **통합 플랫폼** (넓은 의미) |
| **주요 사용처** | **한국**에서 결제 대행사를 부를 때 주로 사용 | **글로벌(해외)** 시장에서 결제 기업을 통칭할 때 주로 사용 |
| **핵심 기능** | 카드사/은행 연동, 결제창 제공, 대금 정산 | PG 기능 + 다국어/다통화 처리, 사기 탐지(FDS), 데이터 분석 등 |

## 토스페이먼츠를 우리 서비스에 연동한다면?

1. 우리 서버가 `orderId`(책의 payment_order_id)와 금액을 정한다.
2. 프론트가 토스 **결제위젯**을 띄우고, 사용자는 거기서 카드 정보를 입력한다. 우리 서버는 카드 번호를 볼 일이 없다(호스팅 결제 페이지).
3. 인증이 끝나면 `successUrl`로 리다이렉트되고, `paymentKey`, `orderId`, `amount`가 같이 넘어온다.
4. 우리 서버가 **금액이 우리 DB와 같은지 검증**한 뒤 토스의 **결제 승인 API**를 호출한다. 이때 멱등 키 헤더를 붙이면 재시도해도 이중 승인이 되지 않는다.
5. 가상계좌 입금처럼 늦게 끝나는 결제는 **웹훅**으로 결과를 받는다

---

### 큰 그림: 역할을 세 군데로 나눈다

| 누가 | 하는 일 | 쓰는 키 |
| --- | --- | --- |
| 프론트(결제창) | 사용자가 카드 정보를 입력하고 인증까지 진행 | 클라이언트 키 (공개돼도 됨) |
| 우리 서버 (Spring) | 주문 생성, 금액 검증, **결제 승인 API 호출**, DB 저장 | 시크릿 키 (절대 노출 금지) |
| PG사 | 실제 결제 처리, 늦게 끝나는 결제는 웹훅으로 알림 | — |

> **핵심:** 결제창에서 인증만 끝났다고 결제가 된 게 아니다. **우리 서버가 승인 API를 호출해야** 돈이 빠져나간다. 그래서 서버가 마지막에 금액을 검증할 수 있다.
> 

### 전체 흐름

1. 사용자가 "결제하기" 클릭 → 서버가 `orderId`와 금액을 정해 `READY` 상태로 저장
2. 프론트가 클라이언트 키로 결제위젯을 띄움
3. 사용자 인증 성공 → `successUrl?orderId=...&paymentKey=...&amount=...` 로 리다이렉트
4. 프론트가 이 세 값을 서버로 전달
5. 서버가 금액 검증 후 **결제 승인 API** 호출
6. 승인 결과(`paymentKey`, 상태)를 DB에 저장
7. 가상계좌처럼 늦게 끝나는 결제는 웹훅으로 결과 수신

### 0. 준비: API 키

- 토스페이먼츠 회원가입만 해도 "개발자용 테스트상점" 이름으로 **테스트 키**가 발급된다.
- 테스트 키는 실제 결제가 일어나지 않고, 라이브 키는 실제 서비스 배포용이다.
- 키는 상점관리자 → 개발자센터에서 확인한다.

```yaml
# application.yml — 시크릿 키는 환경변수로
toss:
  secret-key: ${TOSS_SECRET_KEY}
```

### 1. 주문 먼저 만들기 (금액은 서버가 정한다)

```java
@Entity
public class Payment {
    @Id @GeneratedValue
    private Long id;

    @Column(unique = true)          // 책의 payment_order_id 역할
    private String orderId;

    private Long amount;            // 원화는 소수점이 없어서 Long도 OK
    private String paymentKey;      // 승인 후 토스가 준 키

    @Enumerated(EnumType.STRING)
    private PaymentStatus status;   // READY, DONE, FAILED, CANCELED
}
```

금액을 프론트가 정하게 두면 조작될 수 있다. 금액은 반드시 서버가 정하고 저장한다.

### 2. 프론트에서 결제위젯 띄우기

프론트는 클라이언트 키로 결제위젯을 띄우고 `orderId`, `amount`, `successUrl`, `failUrl`을 넘긴다. 인증이 성공하면 브라우저가 아래 형태로 돌아온다.

```
/success?orderId={ORDER_ID}&paymentKey={PAYMENT_KEY}&amount={AMOUNT}
```

이 세 값을 우리 서버로 보낸다.

### 3. 서버에서 승인하기 (제일 중요)

- 엔드포인트: `POST https://api.tosspayments.com/v1/payments/confirm`
- 바디: `paymentKey`, `orderId`, `amount`
- 인증: **Basic 인증**. 시크릿 키를 사용자 ID로 쓰고 비밀번호는 비운다. 그래서 `시크릿키 + ":"` 를 Base64로 인코딩한다.

```java
@Service
@RequiredArgsConstructor
public class PaymentService {

    private final PaymentRepository paymentRepository;
    private final RestClient restClient = RestClient.create("https://api.tosspayments.com");

    @Value("${toss.secret-key}")
    private String secretKey;

    @Transactional
    public void confirm(String paymentKey, String orderId, Long amount) {
        Payment payment = paymentRepository.findByOrderId(orderId)
                .orElseThrow(() -> new IllegalArgumentException("주문 없음"));

        // ① 금액 검증: 프론트에서 넘어온 금액을 믿지 않는다
        if (!payment.getAmount().equals(amount)) {
            throw new IllegalStateException("금액 불일치");
        }
        // ② 이미 처리된 주문이면 다시 승인하지 않는다 (중복 클릭 대비)
        if (payment.getStatus() == PaymentStatus.DONE) return;

        String auth = Base64.getEncoder()
                .encodeToString((secretKey + ":").getBytes(StandardCharsets.UTF_8));

        // ③ 토스 승인 API 호출
        TossConfirmResponse res = restClient.post()
                .uri("/v1/payments/confirm")
                .header(HttpHeaders.AUTHORIZATION, "Basic " + auth)
                .header("Idempotency-Key", orderId)   // 재시도해도 한 번만 승인
                .contentType(MediaType.APPLICATION_JSON)
                .body(Map.of("paymentKey", paymentKey, "orderId", orderId, "amount", amount))
                .retrieve()
                .body(TossConfirmResponse.class);

        // ④ 결과 저장
        payment.approve(paymentKey);   // status = DONE, paymentKey 저장
    }
}
```

- `paymentKey`는 승인·취소·조회 API에 모두 필요하므로 **반드시 DB에 저장**한다.
- `Idempotency-Key` 헤더가 11장의 **멱등성** 그대로다. 결제 취소 요청에도 같은 방식으로 붙인다.

### 4. 실패와 타임아웃 처리

| 상황 | 처리 |
| --- | --- |
| 실패 응답 (4xx) | 에러 코드·메시지를 보고 주문을 `FAILED`로 변경, 사용자에게 안내 |
| 타임아웃 (응답 못 받음) | **실패로 단정하지 않는다.** 토스에서는 결제가 됐을 수 있다(11장 시나리오 2). 결제 조회 API로 실제 상태를 확인하거나 같은 멱등 키로 재시도 |
| 승인 성공 후 우리 DB 저장 실패 | 결제 취소 API를 호출해 돈을 되돌린다 |

### 5. 웹훅 (늦게 끝나는 결제)

가상계좌처럼 사용자가 나중에 입금하는 결제는 승인 시점에 끝나지 않는다. 개발자센터에 웹훅 URL을 등록하면 입금·상태 변경을 토스가 알려준다.

```java
@PostMapping("/webhooks/toss")
public ResponseEntity<Void> webhook(@RequestBody TossWebhook event) {
    paymentService.handleWebhook(event);   // 같은 이벤트가 여러 번 와도 안전하게 (멱등)
    return ResponseEntity.ok().build();    // 200을 빨리 돌려줘야 재전송이 안 온다
}
```

### 참고: 여러 PG사를 쓸 때

PG사를 바꾸거나 여러 곳을 같이 쓸 가능성이 있으면 **포트원** 같은 통합 서비스를 고려할 수 있다. 포트원은 PG사가 아니라, 여러 PG사와의 계약·연동을 하나의 콘솔로 묶어준다. 해커톤이나 팀 프로젝트라면 토스 하나를 직접 붙이는 게 가장 빠르다.
